# Публичная регистрация и защита входа — 28 октября 2026

Статус: реализация bce4f32 проверена локально, затем по отдельному поручению
отправлена в staging и выпущена на daryadarcy.dev.reeskeen.ru. Существующие
данные и админские входы сохранены. Проверка использовала один временный
аккаунт, он удалён. Новых зависимостей, миграций и изменений 2FA нет.

## Подтверждённые причины

`SessionController.register` отвечал409 для существующего аккаунта и202 для
нового/ожидающего регистрации. Вход имел только IP-квоту20/15мин, а общий
helper входа возвращал JSON с `sessionToken` вместе с HttpOnly-cookie.
Текущий браузерный клиент уже использует `credentials: include` и `user`;
удаление токена из JSON не требует изменений его компонентов.

## Изменённый REST-контракт

- `POST /api/auth/register`: одинаковые HTTP202 и `{ok:true,message:string}`
  для внутреннего исхода created/pending/duplicate. Нет user, token, признака
  существования адреса или cookie. Сообщение условное: инструкция придёт, если
  регистрация доступна; существующему пользователю предложен вход/восстановление.
  Валидация/согласие400, IP-квота429 и настоящие инфраструктурные503/500
  сохранены. Активный, заблокированный, staff или чужой checkout-аккаунт
  не изменяется и не получает лишний setup-токен/письмо.
- `POST /api/auth/login`: успешный JSON — только `{user}`. Сессия остаётся
  в штатной HttpOnly host-only cookie; публичный профиль прежний.
  Общий helper также убирает JSON-токен из отключённого SMS-входа, не включая
  эту функцию. Bearer→cookie bridge `/api/auth/session` и logout прежние.
- Дополнительная квота по аккаунту действует вместе с прежней IP-квотой.
  Первые пять допусков без искусственной паузы, затем1/2/4/8/16/30сек,
  дальше максимум30сек между допусками. HTTP429 содержит одинаковое сообщение,
  `retryAfterSec` и `Retry-After`, cookie не выдаётся. Проверка пароля/2FA
  и запись lastSignedIn при отказе не выполняются. Сервер не удерживает
  запрос в sleep. Успешный завершённый вход сбрасывает свой счётчик.

Адрес сначала разрешается обычным SQL-запросом. Ключ берётся из найденной
записи, а не из написания запроса: MySQL может приравнивать варианты с
диакритикой. Существующий SELECT не дублируется. Для ненайденного адреса
используется тот же limiter с нормализованным введённым email.
Перед асинхронной проверкой пароля допуск резервируется синхронно;
параллельный burst не обходит квоту. Запоздалый успешный запрос не сбрасывает
более новые попытки. Отказы не продлевают дедлайн; окно наблюдения15мин.

Хранилище ограничено10000 SHA256-ключами, сырые email/пароли не сохраняются
в счётчике и не логируются. Просроченные ключи удаляются лениво;
живые не вытесняются. При исчерпании ёмкости новый ключ получает429/60сек.

## Границы защиты и совместимость

Счётчик process-local, как прежняя IP-квота: общий для разных IP в одном
API-процессе, сбрасывается при рестарте. Перед запуском нескольких API workers
нужно заменить хранилище на общее атомарное, сохранив семантику. Новая Redis/SQL
инфраструктура для текущего одного API-процесса не добавлялась.

Унифицированы явные статус и тело регистрации; равенство сетевого времени
и времени SQL/почтового outbox не заявляется. Удаление JSON-токена уменьшает
его копирование в JS, но не делает XSS безвредным: вредоносный скрипт всё ещё
может отправлять запросы с cookie. CSP/защита скриптов остаются необходимыми.

Архивный `apps/legacy-expo` ждёт Bearer-токен в JSON и с cookie-only контрактом
несовместим. Он не является текущим web-клиентом; не добавлен небезопасный
переключатель выдачи токена по произвольному заголовку/телу запроса.
Локальный инструмент нагрузки обновлён: проверяет cookie и отсутствие
sessionToken. tRPC105/generated frontend-контракт прежние: менялся REST.

Подход к общему ответу и короткой нарастающей паузе сверён с
[OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages).
