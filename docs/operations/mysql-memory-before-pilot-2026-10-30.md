# Память MySQL перед пилотом: замеры и предложение

30 октября 2026. Статус: исследование завершено, рабочие настройки не применялись.
Действующая БД, учётные данные, контейнеры приложения и строгий режим сохранены.

## Вывод

После локальной проверки для серверной репетиции предлагается лимит MySQL
**1536 МиБ**, явный бюджет
TempTable **64 МиБ**, прежние buffer pool **128 МиБ** и максимум **30 соединений**.
Это стартовый профиль для проверки на копии, не гарантия отсутствия OOM при любой
нагрузке. Увеличивать лимит БД на нынешнем общем 4-ГБ сервере сейчас не следует:
ему самому не хватает резерва памяти и диска.

Уточнение после первоначального исследования: 1024 МиБ дали успешные ответы,
но пик 75,7% не оставил выбранный резерв. В локальном варианте 1536 МиБ
с двумя API-пулами пик составил 68,1%; 1000 запросов на ступени 100 виртуальных
пользователей прошли без ошибок. [Репетиция и её ограничения](mysql-memory-local-rehearsal-2026-10-30.md).
Эта проверка не меняла рабочий сервер и не заменяет SSD/длительную приёмку.

Для пилота до 100 одновременно активных посетителей остаётся рекомендация
отдельного сервера проекта: **4 vCPU / 8 ГиБ RAM / 100 ГБ SSD/NVMe**.
Вариант увеличения RAM общего сервера требует бюджета остальных проектов:
несколько их контейнеров сейчас не имеют собственного ограничения памяти.
Покупка ресурсов не меняет автоматически существующие лимиты контейнеров.

## Что объясняет риск

Предыдущий инцидент подтверждён журналом ядра: исчерпан именно 512-МиБ cgroup
MySQL, завершён mysqld. В записи ядра его anon RSS был 481548 КиБ, около 470 МиБ.
Одновременно внутри этого же контейнера выполнялись два проверочных клиента.
Их память тоже учитывалась в лимите. Точный вклад отдельных буферов в тот момент
не измерялся. [Подробности инцидента и сверки данных](admin-recovery-release-2026-10-30.md).

На действующем сервере дополнительно обнаружен несогласованный предел:
`temptable_max_ram=1073741824` (1 ГиБ), то есть выше лимита всего контейнера.
Это верхняя граница потенциального расхода TempTable, не выделенная при старте
память и не доказанная причина прошлого OOM. Лимит одной временной таблицы уже
16 МиБ, но несколько одновременных запросов используют общий бюджет.
Уменьшение этого бюджета может увеличить дисковую работу, поэтому при нынешних
709 МиБ свободного диска применять изменение без подготовки нельзя.
[Модель временных таблиц MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/internal-temporary-tables.html).

Пул InnoDB не ограничивает весь процесс. Дополнительная память нужна log buffer,
соединениям, сетевым буферам, кешам метаданных и исполнению запросов; часть
буферов может удерживаться после запроса. Поэтому небольшая схема не означает
столь же маленький RSS. [Модель памяти MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/memory-use.html).

## Минимальный профиль для репетиции

Изменения ниже только предлагаются для рабочего сервера. Его Compose, my.cnf
и переменные в рамках исследования не редактировались. Варианты проверялись
только на собственном локальном временном контейнере.

| Параметр | Сейчас | Предложение | Основание |
| --- | ---: | ---: | --- |
| `mysql.mem_limit` | 512 МиБ | 1536 МиБ | Уточнено по локальной репетиции двух пулов: пик 1046,4 МиБ |
| CPU MySQL | 0,4 CPU | 1 CPU на отдельном 4-vCPU хосте | Бюджет пилота; текущий замер не доказывает упор в CPU |
| `innodb_buffer_pool_size` | 128 МиБ | Оставить 128 МиБ | Большая часть пула сейчас свободна; увеличивать вместе с лимитом не требуется |
| `temptable_max_ram` | 1024 МиБ | 64 МиБ | Ограничить общий бюджет временных таблиц относительно контейнера |
| `tmp_table_size` | 16 МиБ | Оставить 16 МиБ | Лимит отдельной внутренней таблицы уже задан |
| `max_heap_table_size` | 16 МиБ | Оставить 16 МиБ | Не расширять отдельные MEMORY-таблицы |
| `max_connections` | 30 | Оставить 30 | Два серверных пула по 10 соединений, остаётся запас для служебных действий |
| `thread_cache_size` | 8 | Оставить 8 | Нет подтверждённой проблемы создания потоков |
| `innodb_log_buffer_size` | 64 МиБ | Оставить 64 МиБ | Снижение ради экономии сейчас не требуется для минимального изменения |
| `performance_schema` | OFF | Оставить OFF на первом сравнении | Не менять одновременно модель наблюдения и памяти |
| `innodb_dedicated_server` | OFF | Оставить OFF | API/web и БД делят ресурсы хоста; автоматический большой пул не нужен |
| `innodb_flush_log_at_trx_commit` / `sync_binlog` | 1 / 1 | Оставить 1 / 1 | Сохранить политику надёжности записи |

Текущие `max_allowed_packet=64 МиБ`, table caches и остальные буферы тоже
не увеличивать. Предложенные 1536/64 МиБ являются инженерным выбором для
репетиции, а не рекомендуемыми Oracle универсальными значениями.
`temptable_max_ram` не ограничивает всю память MySQL, в том числе не учитывает
все локальные блоки потоков. Результат обязательно измерять.

В коде `apps/backend/src/db.ts` один общий пул с `connectionLimit:10` на процесс.
Два действующих потребителя SQL в Compose — API и Prodamus TEST. Сто посетителей
сайта не требуют ста выделенных SQL-соединений. При добавлении реплик API
необходимо заново посчитать сумму всех пулов и служебный резерв.

Существующий `compose.resources-8gb.example.yaml` содержит потолок MySQL 2048 МиБ.
Он не применён и автоматически не меняется этим документом. Для ограниченного
пилота предлагается сначала проверить 1536 МиБ и сохранить лишний запас хосту;
2048 МиБ остаются отдельным вариантом после измерения реального пика.

## Условия применения и приёмки

1. До изменения обеспечить свободную память хоста не менее 2 ГиБ и свободный
   диск не менее 5 ГиБ. На нынешнем сервере оба условия не выполнены.
   Это пороги допуска этой репетиции, не универсальные требования MySQL.
2. Согласовать профиль. Сделать свежий защищённый бэкап и проверить восстановление
   в отдельной БД. Сохранить старые image/config pins и отпечатки админских входов.
3. Сначала проверить профиль на отдельной копии: обычные списки, поиск, админка,
   конкурентные чтения и один последовательный backup/restore. Диагностические
   SQL-клиенты запускать отдельным ограниченным процессом, не внутри MySQL.
4. На тестовом API/БД увеличивать активных посетителей 10 → 25 → 50 → 100,
   с паузами между действиями, без внешних платежей и писем. Новые приложения
   и frontend-изменения для этого не требуются. На рабочем сайте нагрузку не запускать.
5. Во время репетиции наблюдать полный `memory.current`, RSS, рестарты/OOM,
   MemAvailable хоста, задержки API, соединения, SQL-ожидания и диск. Контрольные
   ориентиры: пик MySQL ниже 70% лимита, запас хоста не менее 1 ГиБ, нет OOM/
   рестартов/ошибок БД; предупредить при 75%, остановить разгон при 85% или
   MemAvailable ниже 1 ГиБ. Пороги — эксплуатационный выбор для этого пилота.
6. Отдельно проверить непрерывную работу 24 часа: короткое окно после рестарта
   не показывает рост удержанной памяти. Качество фото и лимиты вложений этой
   репетицией не менять; большие загрузки остаются отдельной приёмкой.
7. Только после успешной репетиции отдельно согласовать замену действующего
   контейнера MySQL с прежним volume. Сверить историю, данные и все админские
   входы. Откат — прежний образ/параметры с тем же volume; старый dump поверх
   более новых пользовательских записей не восстанавливать автоматически.

## Сохранность и границы

Сняты только агрегированные счётчики, параметры, метаданные и отпечатки трёх
администраторов. SQL выполнялся в отдельном 96-МиБ контейнере с read-only сессией;
в контейнер БД дополнительные клиенты не запускались. Временные диагностические
контейнеры и закрытые env-файлы удалены после чтения. SHOW/SELECT не меняли
прикладные строки; естественные серверные счётчики активности могли увеличиться.

До/после совпали хеши 15 действующих config/env-файлов, отпечатки паролей,
ролей и версий сессий всех трёх администраторов, история 50; MySQL сохранил ID,
образ, лимиты и время запуска. На рабочем сервере нагрузочных проб, restart/recreate, SET GLOBAL,
SET PERSIST, миграций, изменений S3/фронта, push и выкладки не было.

Закрытые артефакты: `.local-artifacts/mysql-memory-review-20261030-42641fe9`
родительского workspace, каталог 700 / evidence 600, вне Git. Статистика
содержит исходные значения и шесть снимков cgroup; пользовательские email,
пароли и токены в публичный документ не включены.
