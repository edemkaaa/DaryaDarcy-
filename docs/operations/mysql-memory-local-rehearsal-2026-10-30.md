# Локальная репетиция профиля памяти MySQL — 30 октября

Статус: ограниченная репетиция завершена. Рабочий сервер не использовался,
его настройки, БД и админские входы не менялись. Push и выкладки нет.
Код API: `050e5c5e198c8836468b870f074518075c31f422`; локальные изменения
во время проверки относились только к документации, не к коду приложения.

## Результат и уточнение предложения

Для следующей серверной репетиции предлагается **MySQL 1536 МиБ** с прежним
пулом InnoDB 128 МиБ, максимумом 30 соединений и TempTable 64 МиБ.
Первоначальный вариант 1024 МиБ выполнил запросы без ошибок, но превысил
выбранный ориентир 70% памяти. При двух API-пулах кандидат 1536 МиБ дал
пик 1046,4 МиБ, то есть 68,1% лимита, без OOM/перезапусков.

Эта рекомендация консервативна: тестовая БД находилась в tmpfs, её файлы
тоже учитывались в памяти контейнера. Прямо переносить этот пик на сервер
с SSD или вычитать из него размер tmpfs как точную оценку нельзя.
Работа настоящего серверного стека и длительный рост памяти ещё не приняты.

## Изоляция и конфигурация

Использован существующий MySQL 8.4.11 на Linux ARM64 внутри Docker Desktop.
Mac и SQL-образ нативные ARM64, эмуляции не было. MySQL ограничен одним CPU;
API и генератор работали отдельными локальными Node-процессами на Mac.

Диск Mac имел около 1,4 ГиБ свободного места. Вместо создания дисковой БД
для этой предварительной проверки использован собственный tmpfs 384 МиБ
с ограничением размера и read-only корневой файловой системой контейнера.
Новые образы не скачивались, сборки/дисковые volumes не создавались.
Обычная серверная репетиция по-прежнему требует предусмотренного запаса диска.

Контейнер создавался с уникальными именем/меткой владельца, случайным паролем,
портом только на 127.0.0.1, без bind/дисковых mounts. Перед работой штатная
проверка fixture подтвердила ID, owner, loopback, `backend_test` и tmpfs.
В пустой схеме применены все 50 миграций, затем повторно проверена история.

Настройки SQL: pool128M/max_connections30/performance_schemaOFF,
temptable_max_ram64M; tmp_table_size/max_heap_table_size16M. Политики надёжности
innodb_flush_log_at_trx_commit=1 и sync_binlog=1 проверены, не ослаблялись.
Первый лимит контейнера — 1024 МиБ; затем на этом же прогретом временном
контейнере поднят только лимит до 1536 МиБ. Перезапуска/очистки кешей между
этими вариантами не было. Это не изолированное A/B-сравнение скорости.

## Данные и сценарии

Только синтетические данные: сначала 60 пользователей, затем 110;
1000 постов, 4000 комментариев, 50 статей, 20 тегов, 500 сохранений.
Для расширенного прогона у 100 синтетических участниц был локальный оплаченный
период. Он создан непосредственно в одноразовой БД, без провайдера и писем.

Проверены 11 GET-процедур настоящего API:

- feed.listPaginated и feed.getById;
- club.listByCategory и club.commentsPage;
- articles.getById и feed.savedPostsPage;
- admin.postsPage, articlesPage, membersPage, postCounts, postCalendar.

Использовались настоящие HTTP, JSON/tRPC-сериализация, подписи тестовых сессий,
права и SQL. Перед каждым нагрузочным вариантом 11 smoke-запросов проверяли
HTTP 200 и наличие разбираемого результата. Приложение запускалось через
composition root без фоновых работников. TCP API разрешался только к собственному
SQL-порту; попыток внешнего подключения не было. Медиафайлов в данных нет.

Каждый виртуальный пользователь делал запрос и выдерживал паузу 2 секунды.
Каждая ступень длилась около 20 секунд. Это закрытая модель с паузами,
не неограниченный поток запросов и не 100 реальных браузеров.

Два процесса — два обычных читающих API с собственными пулами по 10 соединений.

с одним пулом — 11, с двумя — 21, включая проверочное соединение.

## Память и надёжность

Полный cgroup peak варианта 1024 МиБ: 774,95 МиБ, 75,7% лимита.
Запросы успешны, но целевой резерв 30% не выполнен. Двухпуловый вариант
при лимите 1024 МиБ намеренно не проверялся; обязательный OOM на SSD из этих
цифр не следует.

При 1536 МиБ пик достиг 1046,38 МиБ, 68,1%. После повторного backup/restore
исторический пик остался тем же. Значения включают tmpfs, прогрев и небольшие
процессы чтения cgroup. Сэмплы, memory.stat и финальный memory.peak сохранены.

Во всех вариантах: OOM=0, рестартов=0, отказов max_connections=0,
Innodb_buffer_pool_wait_free=0, Innodb_log_waits=0. При двух пулах счётчик
дисковых временных таблиц достиг 47; это накопленный показатель за все прогоны,
в данном стенде их файлы тоже расположены в RAM. Измерения дискового IO нет.

## Резервная копия и восстановление

После нагрузки выполнен последовательный mysqldump отдельным 96-МиБ
клиентским контейнером, а не процессом внутри MySQL. Создана закрытая gzip-копия
только синтетических данных. Она восстановлена в отдельную backend_restore
внутри того же собственного контейнера. Для каждой из 42 таблиц сравнивались
количество строк и сортированные SHA-256 всех строк; совпали все таблицы,
история 50 и пользователи. Исходная backend_test сохранялась.

Проверка повторена после расширения до двух пулов/100 пользователей.
Последний gzip — 67712 байт. Обе проверки восстановления прошли.
Сбой питания, fsync/скорость реального SSD и физическая сохранность диска
этим tmpfs-стендом не проверяются.

## Очистка и остаток

После последней проверки сверены точные ID/name/owner и отсутствие mounts,
затем удалён только собственный контейнер с tmpfs. Его тестовые данные
уничтожены и не восстанавливаются из RAM; синтетический dump сохранён отдельно.
Временные пароль/env и собственный dependency symlink удалены. Образы,
volumes, чужие контейнеры, исходники и рабочие данные не удалялись.

Артефакты вне Git: `.local-artifacts/mysql-profile-local-20261030-dbfe5319`
родительского workspace: result/result-100/result-1536-two-pools, schema logs,
backup/restore receipts, финальные cgroup-метрики и cleanup.json.

Перед применением остаются: подходящий сервер с резервом RAM/диска,
согласование профиля 1536/64/128/30, репетиция на обычном SSD и целевом Linux,
24-часовое наблюдение и совместная проверка реального стека. Нагрузку на рабочий
сайт не запускать; больших загрузок и полного пользовательского пилота здесь нет.
