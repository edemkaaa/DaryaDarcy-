# Восстановление заполненных журналов операций и очереди писем

30 октября 2026. Локальная приёмка AG5 после добавления 0048/0049.
Исходники `057e12d0`; runtime относительно `54ea67d8` не менялся.

## Результат

Восемь сценариев и 37 настоящих HTTP-запросов прошли на синтетических данных.
После backup/restore и запуска нового API-процесса сохранены квитанции действий,
результаты отказов, очередь с зашифрованной ссылкой и ненулевая ревизия VK.
Нового дефекта runtime не выявлено; продуктовый код не менялся.

Предыдущая репетиция резервирования проверяла все 42 таблицы, но в её dump
`admin_action_operations`, `access_email_outbox` и `videos` были пустыми.
Нынешний срез проверяет именно восстановление заполненных новых данных,
а не повторяет нагрузку или прежнюю проверку схемы.

## Изоляция

Cached MySQL 8.4.11 native ARM64, свой loopback/tmpfs-контейнер: 1536 МиБ,
пул 128 МиБ/max30/TempTable64, datadir 384 МиБ в RAM. Пять синтетических пользователей,
50 миграций с нуля, неопубликованное VK-видео с тестовым источником.
Рабочие БД, сервер, frontend, S3, админские входы и strict не использовались.

При свободных ~696 МиБ диска не было pull/build/установки пакетов. Для маленького
RAM-стенда установлен guard 512 МиБ свободного диска. Снимок создан отдельным
96-МиБ mysqldump-клиентом из кешированного образа, не процессом внутри MySQL.
API через composition root не запускал таймеры и внешние workers; TCP разрешён
только к собственному SQL-порту. Попыток внешнего TCP — 0.

После остановки исходного API полный gzip-dump размером 8 516 байт восстановлен в отдельную
`backend_restore`. Исходная `backend_test` сохранялась. Для каждой из 42 таблиц
сверены количество и сортированные SHA-256 всех строк, включая историю из 50 миграций.
В источнике: 4 квитанции success/rejected, 1 очередь с tokenCipher,
1 password token, 1 VK-видео с editRevision=1. Они действительно вошли в dump.

## Следствия для восстановления

- Сохранять полную БД с `admin_action_operations`, очередью, password tokens и
  `videos.editRevision`, а не выборку старого состава таблиц.
- Отдельно сохранять исходные `AUTH_LINK_ENCRYPTION_KEY` и `JWT_SECRET` в закрытом
  хранилище. SQL-dump не содержит ключ расшифрования. Генерация нового ключа
  вместо исходного не восстанавливает уже зашифрованные ссылки.
- После restore проверять прежние status/ключи и ревизии до включения workers.
  Не обнулять квитанции и не создавать новые ключи для неизвестного результата.
- `queued:true` остаётся подтверждением очереди, не доставки. Повтор после
  потери ответа SMTP и доставка на реальный ящик этим тестом не принимаются.
- Проверены действия, **попавшие в снимок**. Действия после времени backup и
  согласование старой копии с уже выполненными внешними эффектами требуют
  отдельной сверки. Это не проверка полного point-in-time recovery.
