## Что нужно для следующего шага

1. Согласованный выпуск backend-кода. На стенде пока API `ff2c229`, web
   `ce56ebe`; локальные изменения оператора и inline JPEG/PNG/GIF не выложены.
   Новых DDL нет: все44 локальные миграции совпали с серверным ledger.
   Все четыре нужных private content/media/library флага уже true — менять их
   ради этой подготовки не потребовалось. Origin/staging=`a762b4a`, новых
   удалённых коммитов при fetch не обнаружено.
2. Условия выпуска: на сервере около **863 МиБ** свободного диска и
   **442 МиБ MemAvailable** при предварительной проверке. Сборку/параллельный
   API здесь не запускали. Перед выпуском заново проверить ресурсы и сохранять
   рабочие образы отката/backup; не чистить базы и образы ради освобождения места.
3. Непосредственно перед каждой привязкой повторить expected-old/роль/флаги и
   проверку источника. Снимок отражает время проверки, не замораживает дальнейшую
   работу заказчицы. При расхождении остановить конкретную операцию.
4. Сначала ограниченная проверяемая партия: фото/GIF/документ и небольшое видео,
   SHA/байты, admin/member/guest/revoke и повтор после потерянного ответа.
   Исходные URL остаются открытыми. Девять больших реальных видео этим шагом
   не приняты; нужны отдельные замеры времени/памяти потокового процесса.
5. После успешной партии — оставшиеся согласованные привязки последовательно,
   по одной операции, с durable receipt. Отказ/конфликт не должен запускать
   восстановление всей рабочей БД поверх новых записей.
6. Отзыв прежних публичных URL/производных — отдельная последующая операция,
   после frontend server-only guard перед кешем image optimizer. Сейчас это
   **не включать**, источник не удалять, старые ACL не менять.
