# Переезд Daryadarcy в Россию, проверка прокси в Алматы и CDN

План для владельца проекта и DevOps. Сначала восстанавливаем рабочее приложение и данные в России. Затем независимо проверяем маршрут через Алматы и раздачу публичных изображений через CDN. Основной домен переключаем только после проверки выбранной схемы.

## Что сохранилось

- В Timeweb S3 найдена копия рабочей БД стенда `daryadarcy_candidate_20261019`. Дамп от **31 октября 2026 года** скачан в закрытое локальное хранилище. Архив читается. Внутри 42 таблицы, 50 записей в журнале миграций, 933 поста, 2 статьи, 82 видео, 10 пользователей, включая три админских аккаунта с хешами паролей, записи оплат и привязки закрытых файлов. Восстановление именно этого дампа ещё предстоит.
- Архив от **10 ноября** содержит старую `default_db`. Его можно использовать как дополнительный источник для сверки. Записи и изменения после 31 октября требуют подтверждения по отдельным источникам, включая историю платёжного кабинета. Записи сверяем по идентификаторам и датам, каждое расхождение рассматриваем отдельно.
- Код и инструкции сборки есть локально. Перед выпуском нужно выбрать и зафиксировать исходный коммит, включая согласованные локальные правки. Получить актуальное состояние `staging`, когда удалённый Git доступен. [Пакет сборки](../../infrastructure/deploy/teamassist/README.build.md)

## 2. Восстановление в России

1. **Поднять изолированную БД-кандидат.** Использовать совместимую версию MySQL из принятого пакета, сейчас в Compose указан MySQL 8.4. Принять дамп по закрытому каналу. Проверить `gzip -t` и SHA-256. Для `latest-staging.sql.gz` ожидается `9c674eac9366169c7e0a6339df96519893a8fa11624b2097aab7c1d79df44a32`. Перед импортом проверить, какую схему выбирает дамп и нет ли конфликтующих команд `USE` или `CREATE DATABASE`. Импорт выполнять только в изолированный экземпляр.
2. **Сверить импорт.** Сопоставить количество и состояние пользователей, ролей, постов, статей, медиа, подписок и записей оплат с дампом. Проверить журнал Drizzle. Перед переходом на выбранный коммит запустить `pnpm db:preflight --require-database` с подключением к кандидату. Если есть ожидающие миграции, сделать снимок кандидата и выполнить `pnpm db:push` одним процессом. После применения снова сверить журнал. При расхождении истории остановиться и выяснить причину. [Порядок сборки и миграций](../../infrastructure/deploy/teamassist/README.build.md)
3. **Собрать и поднять web/API.** Использовать образы по digest, зафиксировать публичные параметры сборки Next и серверные настройки. Страницы, `/api/` и `/media/` обслуживаются под одним публичным именем. MySQL доступен только во внутренней сети. Изолировать отправку писем, push, платёжные вызовы и фоновые операции с рабочим S3 на время репетиции. Для сценариев записи использовать отдельные тестовые данные и хранилище.
4. **Сверить доступ и интеграции.** Проверить вход существующего администратора, гостевой отказ и доступ участницы Клуба. Проверить загрузку публичного изображения и чтение защищённого объекта через API. При наличии исходных ключей сверить сессии и ожидающие письма. Если `JWT_SECRET` недоступен, потребуется повторный вход. Если потерян `AUTH_LINK_ENCRYPTION_KEY`, отдельно разобрать зашифрованные операции очереди перед возобновлением отправки. Проверить результат оплаты и доступ в TEST. Включение LIVE требует боевых настроек и отдельной приёмки. Перед запуском сверить реальные оплаты и подписки после даты дампа.

**Контрольная точка.** Российский адрес отвечает по HTTPS. Проходят `/api/health`, `/api/capabilities`, вход, лента и проверка прав Клуба. Состояние данных после даты дампа разобрано. Есть резервная копия принятого кандидата и протокол её восстановления.

## 3. Второй маршрут через Алматы

```text
Тестовый адрес КЗ → VPS Алматы TCP 443 → WireGuard → Nginx РФ TLS → web/API → MySQL и S3 в РФ
Тестовый адрес РФ → отдельный HTTPS-вход Nginx РФ → тот же web/API и та же БД
```

1. Поднять WireGuard между двумя серверами. Разрешить из туннеля доступ к российскому HTTPS-входу только узлу КЗ. Открыть публичный `443/tcp` на Алматы и ограничить административный доступ. Привязать тестовый DNS к IPv4 узла. Для сравнения прямой вход в РФ можно ограничить адресами проверяющих. [WireGuard](https://www.wireguard.com/quickstart/)
2. На VPS в КЗ использовать Nginx с модулем `stream`. Пример ниже размещается в контексте `stream` верхнего уровня. `10.66.0.2` обозначает адрес российского узла в туннеле. Подставить фактическую подсеть и проверить отсутствие пересечений с другими сетями.

   ```nginx
   stream {
       server {
           listen 443;
           proxy_pass 10.66.0.2:443;
           proxy_protocol on;
           proxy_connect_timeout 5s;
           access_log off;
       }
   }
   ```

3. На российском Nginx выделить отдельный listener на адресе туннеля. В нём использовать `listen 10.66.0.2:443 ssl proxy_protocol;`, `set_real_ip_from 10.66.0.1/32;` и `real_ip_header proxy_protocol;`, где `.1` — адрес узла КЗ. Настроить сертификат для тестового имени и те же правила передачи в web/API, что и на прямом входе. Доступ к этому listener ограничить файрволом. На входе приложения передавать `Host`, проверенный IP клиента и HTTPS-схему, заменяя одноимённые заголовки из внешнего запроса. Прямой HTTPS-вход оставлять на другом адресе или сокете, без требования `PROXY protocol`. Проверить `nginx -t` перед перезагрузкой. [TCP-прокси Nginx](https://nginx.org/en/docs/stream/ngx_stream_proxy_module.html), [Доверенные IP в Nginx](https://nginx.org/en/docs/http/ngx_http_realip_module.html)
4. Хранить сертификат и ключ в РФ. Для автоматического выпуска и продления за TCP-прокси использовать DNS-01, если DNS-провайдер поддерживает автоматизацию. В КЗ оставить только технические метрики узла, без журналов запросов посетителей, HTTP-кеша и данных приложения. Владельцу проекта до включения публичного трафика согласовать расположение данных и применимость правил трансграничной передачи к фактической схеме и договорам. [DNS-01](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge), [Статья 12 закона о персональных данных](https://www.consultant.ru/document/cons_doc_LAW_61801/e4ebbe1780de623c7cf32a59ca82a7bb523a25dd/)

**Контрольная точка.** Через КЗ проходит полный HTTPS-запрос. Проверены сертификат, корректный IP для лимитов входа, авторизация, открытый и закрытый контент. При отказе туннеля прямой вход в РФ продолжает работать. Прокси в Алматы зависит от доступности российского приложения.

## 4. CDN для публичных изображений

1. Взять одинаковый набор публичных превью ленты, обложек и фото товаров. Для пилота создать изолированный источник с разрешёнными публичными копиями. CDN получает доступ к этому источнику. Рабочий бакет с закрытыми объектами и бэкапами в качестве общего источника исключить. Если выбран существующий внешний источник, проверить его HTTPS, `Host` и точный список доступных путей.
2. Создать тестовый CDN-ресурс и подключить отдельный домен через CNAME. Сначала сравнить **Yandex Cloud CDN** и **Timeweb CDN** с прямой загрузкой тех же байтов. Yandex публикует точки в России, Казахстане, Франкфурте и Амстердаме. Timeweb стоит проверить с текущим S3. Cloudflare сообщает о проблемах доступа в РФ, поэтому его проксирование основного домена в этот пилот не входит. [Yandex Cloud CDN](https://yandex.cloud/ru/docs/cdn/concepts/points-of-presence), [Источник и домен Timeweb](https://timeweb.cloud/docs/cdn/settings/origin-and-domains), [Доступ из РФ по данным Cloudflare](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/)
3. Для неизменяемых файлов с версией в имени использовать долгий срок кеширования. Для изменяемого URL использовать TTL источника и очистку конкретного файла при замене. Проверить отдельное кеширование каждого размера, если параметры размера идут в URL. Сохранить качество крупной версии и сравнить её на реальном экране. [Настройки кеша Timeweb](https://timeweb.cloud/docs/cdn/settings/cache), [Кеширование Yandex Cloud](https://yandex.cloud/ru/docs/cdn/concepts/caching)
4. Вход, персональные ответы API, закрытые превью и PDF, аватары и платежи оставить вне пилотного CDN. Сохранить `private, no-store` для закрытой выдачи. Прогреть файл с клубным доступом и отдельно проверить отказ гостю и пользователю без подписки. Убедиться, что путь к закрытому объекту на CDN отсутствует. Обложки VK можно раздавать с CDN. Сам плеер и видеопоток проверяются отдельно. [Закрытая выдача в проекте](../../apps/backend/src/content/private-files.controller.ts#L62)

**Контрольная точка.** CDN стабильно отдаёт публичные изображения с нужным качеством. Повторный запрос с пустым кешем браузера подтверждает попадание в кеш CDN, а возврат в ленту подтверждает работу кеша браузера. Закрытые данные недоступны через публичный источник.

## 5. Приёмка сети и выбор маршрута

Сравнить прямой вход РФ и вход через Алматы на одной версии приложения. Отдельно сравнить прямую выдачу из S3 и два CDN на одинаковых файлах. Провести проверку в два разных периода дня, включая вечер. Для трассировки и измерения публичных тестовых ресурсов можно использовать Globalping. Для входа, Safari на iPhone и Telegram Mini App нужны реальные клиенты. [Globalping](https://github.com/jsdelivr/globalping)

| Откуда | Что проверяем |
| --- | --- |
| Домашний и мобильный интернет в РФ без VPN | Главная, лента с фото, вход, Клуб и открытие закрытого файла после входа |
| VPN, через который раньше зависало, и один рабочий VPN | Те же сценарии с тем же устройством и браузером. Отдельно проверить запуск VK и возврат в ленту |
| Сеть в Европе | Главная, API, фото и время первого ответа. Проверить прямой маршрут и Алматы |
| iPhone и Telegram Mini App, если входит в выпуск | Вход, фото, переход в Клуб, открытие закрытого файла. Сверить адрес кнопки запуска и домен приложения |

Для каждого варианта записать время, сеть, HTTP-код, DNS, установку TLS, время до первого байта и до полного ответа. Для изображений добавить объём, время до первого фото и статус кеша. Проверять ответ целиком, включая изображение заметного размера. `ping` и ответ на маленький health-запрос покрывают только часть сценария.

Алматы выбирать основным входом, если он исправляет зависания на проблемных VPN и проходит проверки без VPN в РФ и из Европы. CDN оставлять, если он ускоряет первый показ фото или снижает ошибки без ухудшения качества. При примерно 100 одновременных посетителях отдельно проверить нагрузку на копии окружения, включая память, соединения MySQL и ошибки. Для двух API использовать [отдельный ресурсный preflight](multi-api-release-preflight-2026-11-03.md).

## 6. Переключение и откат

1. Сохранить текущие DNS-записи, принятые образы, конфигурацию, контрольную сумму бэкапа и результаты приёмки. При необходимости снизить TTL заранее с учётом срока действия старых записей. Уточнить, кто отвечает за переключение и кто подтверждает результат.
2. Перед переключением проверить свежий бэкап принятой БД и возможность восстановления. Основной и резервный маршруты должны работать с одной рабочей БД. Если домен ещё указывает на недоступный Beget, подготовить и проверить прямой адрес нового узла в РФ как запасной маршрут. Для основного имени на обоих путях нужен действующий сертификат.
3. Переключить `A` основного домена на принятый узел. `AAAA` публиковать только после проверки IPv6. Не публиковать одновременно два IPv4 в надежде на аварийное переключение. При запуске проверить DNS, HTTPS, вход, ленту, Клуб, отказ гостю на закрытый файл, настройки оплаты и Mini App, если он включён. Подключение CDN для основных страниц и смену входного маршрута проводить отдельно, чтобы результаты можно было сравнить.
4. При сетевом сбое вернуть основной домен на проверенный прямой HTTPS-вход в РФ. Учитывать, что часть клиентов увидит смену после истечения кеша DNS. При сбое CDN вернуть прямые ссылки на публичные превью. При сбое релиза вернуть предыдущий совместимый образ. Восстановление старой БД поверх новой выполняется только после разбора записей, которые успели появиться после переключения.
5. Настроить внешний мониторинг из нескольких сетей, проверку HTTPS и реальных страниц, контроль срока сертификата, состояния туннеля, 5xx, памяти, диска и свежести бэкапов. Хранить резервные копии отдельно от VPS с независимым доступом. Периодически проверять восстановление на отдельной БД. [Резервное копирование S3 в проекте](s3-backup.md)

**Состояние на 10 ноября 2026 года.** Бэкап найден и проверен на чтение. Новый сервер, восстановление этого архива, связка РФ/КЗ и CDN-пилот пока не проверены. Оценка доступности относится к результатам будущих измерений на выбранных IP и сетях.
