## Гостевой checkout: что реализовано

Две additive tRPC mutations: `club.createGuestNormalCheckout` и
`club.guestNormalCheckoutStatus`. Обе используют POST; секрет восстановления
не передаётся в URL/GET batch. Контракт содержит UUIDv4 и канонический base64url
секрет из32случайных байт. Create дополнительно получает email и прежний plan.
Результаты — pending/succeeded/failed, для status также notRecorded.

Намерение — пара secret+UUID. В существующем normal_checkout_requests хранится
только SHA-256 отдельного guest namespace, не исходный секрет. Authenticated
namespace не менялся. Совпадающий UUID с другим секретом не раскрывает прежний
заказ. Изменение email/plan в той же паре даёт409. Никакой сессии, нового пароля,
роли или доступа по email не выдаётся. Старый канонический аккаунт сохраняется;
новый неоплаченный получатель создаётся по прежней политике, без письма/входа.
Такой предварительный аккаунт может остаться после отказа записи заказа;
атомарность относится к ledger+платежу, не к прежней регистрации получателя.

Новая миграция не нужна. Запись заказа и намерения атомарная; одновременный
повтор, потеря HTTP-ответа и повтор из нового процесса используют тот же заказ.
Блокировка/ожидание удаления получателя запрещают чтение и повтор. Paid без
order-specific receipt не признаётся успехом. Смена merchant/подписи/суммы не
выдаёт другую ссылку и не создаёт замену заказа. Terminal result читается из
существующего доказательства, а не из redirect/query success.

`GUEST_CHECKOUT_RECOVERY_ENABLED=false` добавлен только в .env.example.
При true старый гостевой LIVE createCheckout отказывает412; TEST остаётся
прежним. Явное неверное значение тоже не возвращает гостя к небезопасному
старому LIVE-пути. Новые методы при false/missing/invalid недоступны. При TEST
или TEST-header новый create отклоняется; автоматического fallback нет.
Для новой покупки вошедший пользователь использует прежний createNormalCheckout.
После входа можно восстановить только **существующее своё** guest-намерение с
тем же секретом; другая учётка403, новое guest-намерение с сессией400. Это не
позволяет превратить неизвестный исход в новый normal-заказ. Guest proof не
является login/session credential. Дополнительный RED и финальный140pass
проверили переход после входа и отказ чужому текущему аккаунту.

Проверки:14 начальных RED до регистрации методов. После реализации два
