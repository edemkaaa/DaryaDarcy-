## Образы и среда

Обе сборки выполнены из корня репозитория с frozen lockfile и pinned Node22
base image. В образ входят основной и Prodamus TEST executables. Основной
API запускается штатной командой `node dist/index.mjs`, от пользователя node
(UID1000), с production-окружением. Проверена реальная работа sharp/WebP и
mysql-клиента из образа.

| Локальный тег | Платформа | ID локального образа / OCI revision |
| --- | --- | --- |
| `daryadarcy-audit-api:2c67be67-arm64` | Linux ARM64, нативно в Docker VM Mac | `sha256:d6e7cac24aa0fb5938d6df4a2037bbd87477a459e05e3fa424a9602897102dc5`; revision `2c67be67` |
| `daryadarcy-audit-api:2c67be67-amd64` | Linux AMD64, эмуляция на ARM Mac | `sha256:c15d146ba63e34cbfe484461b88632949981476982a57ca7f90df43bb9bb9251`; revision `2c67be67628837542f9015f816872d8dd3804f36` |

ARM64-сборка имеет короткую локальную revision-метку: это проверочный артефакт,
не полноценная release provenance. AMD64 помечен полным исходным SHA.
Сборки/запуск AMD64 под эмуляцией не заменяют нативную приёмку ресурсов Linux-хоста.
Размер каждого образа около1,3GB. Docker VM: aarch64, 10CPU, около7,75GiB RAM.

На каждый прогон создаётся отдельный MySQL8.4: loopback-порт, tmpfs384MiB,
лимит768MiB, без Docker volumes. Штатный fresh installer применяет51 настоящую
миграцию и проверяет историю. Тест не достраивает схему legacy fixture helpers.
Два API получают отдельную internal Docker network без Интернета, read-only
filesystem, cap-drop/no-new-privileges, временные `/tmp` и `/app/backups`.
Лимит каждой тестовой API-реплики1536MiB. Это параметры локального smoke,
не согласование памяти стенда и не испытание загрузок32/80MiB.

## Что проверено настоящим HTTP и SQL

`tests/backend-image.mysql.test.ts`, по12 сценариев на архитектуру:

1. Non-root executable и реальное Linux sharp/WebP-преобразование.
2. Запуск на полной схеме51 миграции, успешная launch-config и mysql coordination.
3. Сессия между двумя API, отказ обычному пользователю в административной записи.
4. Повтор регистрации не создаёт второй аккаунт/письмо; установка пароля через
   HTTP, вход, HttpOnly/Secure-cookie и отсутствие sessionToken в JSON.
5. Пост: повтор создания без дубля, публикация, конфликт старой ревизии,
   запрет гостевого клубного чтения и удаление с SQL-проверкой.
6. Статья: повтор создания, публикация, конфликт и удаление с SQL-проверкой.
7. Выход на одной реплике отзывает сессию на другой.
8. Единый лимит IP:20 запросов принимаются к валидации, следующие2 получают429
   независимо от выбранной реплики.
9. Синтетическая оплаченная запись даёт клубный доступ; блокировка аккаунта
   отзывает его. Провайдер не вызывается, это не приёмка платежа.
10. Автоматический worker создаёт gzip SQL-бэкап; mysql-клиент из этого же
    образа восстанавливает его в отдельную одноразовую схему. Проверены51
    запись истории и роль тестового администратора.
11. Попытки входа с разных IP разделяют account cooldown между репликами.
12. SQL-запись удерживается контрольной транзакцией, SIGTERM оставляет её
    завершиться; другая реплика отвечает, запись сохраняется, процесс выходит0.
    Подтверждается ожидание именно блокирующей транзакции через data_lock_waits.

Регистрация проверяет durable outbox и установку пароля на искусственных данных.
Письмо не отправляется: SMTP-доступа нет, токен читается только из собственной
зашифрованной тестовой записи. Cookie проверены HTTP-драйвером внутри сети,
это не браузерная приёмка TLS/cookie на опубликованном домене.

## Повторить локально

Нужны Node22, pnpm, локальный Docker с достаточным диском/RAM и уже загруженные
`mysql:8.4` и backend image. Runner не скачивает образы, не читает .env и не
принимает адрес существующей БД. Remote Docker context/DOCKER_HOST отклоняется.

```sh
node tooling/scripts/accept-backend-image.mjs daryadarcy-audit-api:2c67be67-arm64
node tooling/scripts/accept-backend-image.mjs daryadarcy-audit-api:2c67be67-amd64
```

Тег разрешается в точный local image ID до запуска. Команда сама создаёт новую
БД, применяет fresh migrations и запускает только opt-in image suite. Не запускать
этот тест напрямую с адресом общей SQL-фикстуры. Владение, tmpfs, имя и порт
контейнера сверяются до первой записи. Синтетические пароли/сессии не печатаются.

Закрытые логи и result.json сохраняются в `.local-artifacts` рядом с репозиторием,
папка0700, файлы0600. По завершении удаляются только собственные помеченные API,
сеть, DB-контейнер и tmpfs. Образы сохраняются. `productionApproval:false`
не меняется при успешных тестах. Прерывание процесса SIGKILL/остановка самого
Docker может потребовать ручного удаления только ресурсов с owner из result/log.

На Mac из-за нового Xcode license prompt для дочерних git-проверок использован
уже установленный CLT: `DEVELOPER_DIR=/Library/Developer/CommandLineTools`.
Глобальные настройки Xcode и лицензия не менялись.

## Границы результата и следующий шаг

Новых ошибок runtime в выбранных Docker-сценариях не найдено; продукт не
переписывался ради тестов. Добавлены воспроизводимая локальная проверка и отчёт.
Первичные отказы исправлялись в драйвере: UUID запроса статьи, TCP readiness,
контроль ожидания SQL и отдельный startup timeout для эмуляции. Assertions прав
доступа, сохранения и завершения процесса не ослаблялись.

P1 перед несколькими API на сервере остаётся открытым: реальные RAM/disk,
resolved Compose, max_connections с TEST-ingress, история/бэкап, нативный образ,
drain и smoke на целевом хосте. Следовать
[серверному preflight](multi-api-release-preflight-2026-11-03.md).
Этот запуск не включал S3, LIVE-платежи, внешнюю почту, устройства, нагрузку
или пилот и не закрывает общий аудит. Новых задач frontend нет.
