# Несколько API: проверка перед выпуском

## Потеря SQL-связи одной репликой — 10 ноября

На локальном Compose с двумя API, Nginx и одноразовой MySQL TCP-прокси
закрыл только SQL-соединения API A. HTTP и адрес API A в сети Nginx
сохранились. Проверка Docker использовала штатный `/api/launch-config`
с укороченным интервалом для эксперимента.

После перехода A в `unhealthy` её `/api/health` по-прежнему возвращал
200, а `/api/launch-config` возвращал 503. У B оба маршрута отвечали 200.
Через Nginx из 12 запросов настроек шесть ушли на A и получили 503, шесть
ушли на B и получили 200. Каждый запрос имел одну upstream-попытку.
До сбоя и после восстановления SQL все 12 запросов на этапе отвечали
200 через обе реплики. Контейнеры API и MySQL не перезапускались.

В текущем шаблоне Nginx Docker DNS даёт адреса контейнеров без статуса
готовности. Поэтому Docker фиксирует локальную потерю SQL, но состояние
`unhealthy` само по себе не исключает реплику из балансировки. Проверка
остановленного процесса из предыдущих прогонов покрывает другой сценарий.

### Варианты исключения реплики

В отдельном локальном Compose сравнили два варианта. Для проверки записи
подменили успешный ответ `feed.toggleLike` на 503 после коммита. В обоих
вариантах запрос прошёл на одну реплику и оставил одну строку в MySQL.

| Вариант | SQL недоступна только A | SQL недоступна обеим | Возврат после восстановления |
| --- | --- | --- | --- |
| Nginx с `proxy_next_upstream http_503` | 36 ответов 200 через B, включая повтор чтения | 12 ответов 502 `no live upstreams` | обе реплики снова принимают запросы |
| Nginx и внутренний HAProxy с активной проверкой `/api/launch-config` | 36 ответов 200 через B, без повторов | 12 ответов 503, пользовательские запросы не дошли до API | обе реплики снова принимают запросы |

В варианте с HAProxy пользовательские повторы отключены. При отсутствии
готовых реплик 503 отдаёт балансировщик. Когда все 10 соединений в каждом
из двух пулов удерживались тестом, независимое подключение к MySQL работало,
а 12 пользовательских запросов получили 503 без передачи в API. После
освобождения пулов обе реплики снова принимали трафик. Это локальная
проверка с временным внутренним маршрутизатором. Рабочий Compose по
результатам не меняли.

## Повторная локальная приёмка — 10 ноября

- 16 проверок Compose, бюджета ресурсов и маршрутизации прошли. Оба шаблона
  Nginx возвращают реплику в балансировку и подхватывают смену её IP. POST с
  оборванным ответом выполняется один раз.
- 9 проверок на одноразовой MySQL подтвердили очередь 10 по умолчанию и 40
  при включённом профиле двух API. Пул остаётся на 10 соединениях. При
  насыщении API возвращает 503 и восстанавливается после освобождения пула.
- Ещё 4 проверки прошли на отдельной MySQL со всеми 52 миграциями. Лента
  читает глубокую страницу через `posts_feed_listing_idx` без `filesort`,
  сохраняя порядок и смещение.
- Типы, линтер, API-контракт, границы модулей и документация прошли. Новый
  backend-бандл совпал с бандлом ранее проверенного нагрузочного пакета.
- Повторный короткий прогон из распакованного пакета дал 312 ответов HTTP
  200 на 8 клиентах. API B обработал все 15 запросов в окно остановки
  API A (1,72 с). После рестарта обе реплики принимали трафик. Пик MySQL
  составил 18 из 50 соединений. Временные ресурсы удалены.

Для целевого стенда остаются проверка реального бюджета, истории и индекса
`0044`, а также нативный прогон на 100 клиентов. Локальные результаты
относятся к отдельным временным контейнерам на Docker Desktop.

### Проверка индекса Ленты перед запуском

В режиме `pnpm db:preflight --require-feed-index` проверка читает историю
миграций и метаданные индекса `posts_feed_listing_idx` на явно заданном
`MIGRATION_PREFLIGHT_DATABASE_URL`. Если `0044` ещё ожидает применения,
индекс отсутствует или скрыт, команда завершается с кодом 1. Подключение
используется только для чтения. Для обычного `db:push` порядок проверок
остаётся прежним.

На одноразовой MySQL с 52 миграциями проверка прошла с видимым индексом,
отказала при скрытии и переименовании индекса и снова прошла после
восстановления. История во всех случаях оставалась полной.

## Потеря ответа после коммита лайка и сохранения — 9 ноября

Две реплики API и Nginx работали в локальном Compose с одноразовой MySQL
и 52 миграциями. Для каждого сценария использовали отдельную тестовую
пару аккаунт/пост без исходного лайка или сохранения. Каждый POST отправили
через Nginx ровно один раз. Временный перехватчик удерживал успешный ответ
API до отправки первого байта. Отдельное соединение с MySQL подтвердило
коммит, пока клиент ещё ждал ответ. После этого обслуживающий процесс
остановили `SIGKILL`, и Docker автоматически запустил его снова.

| Запрос | Строк до POST / до остановки / после рестарта | Ответ клиенту | Попыток Nginx | До готовности API |
| --- | ---: | ---: | ---: | ---: |
| `feed.toggleLike` | 0 / 1 / 1 | 502 | 1 | 1,78 с |
| `feed.toggleSave` | 0 / 1 / 1 | 502 | 1 | 3,21 с |

Чтение `feed.interactionsForPosts` подтвердило запись на второй реплике
сразу после 502 и на обеих после возвращения трафика. Сверка MySQL
показала ровно по одной новой строке в `likes` и `saved_posts`. Повторных
переключений не отправляли. После неопределённого ответа состояние можно
сверить чтением, поскольку новый вызов `toggle` снова переключит его.

Это два адресных сценария добавления без фоновой нагрузки. Артефакты прогона
находятся в `.local-artifacts/darcy-compose-postcommit-20261109.JNQqsEIq/runtime-607e42`
рядом с репозиторием. Временные контейнеры и БД удалены, инвентарь Docker совпал.

### Снятие лайка и удаление из «Сохранённого»

подтвердили её в БД и на обеих репликах. Затем отправили один POST на
снятие реакции, удержали успешный ответ до отправки первого байта и
проверили отсутствие строки через отдельное соединение с MySQL. Только
после этой сверки отправили `SIGKILL` обслуживающей реплике.

| Снять лайк | 1 / 0 / 0 | 502 | 1 | 3,29 с |
| Убрать из «Сохранённого» | 1 / 0 / 0 | 502 | 1 | 1,79 с |

`feed.interactionsForPosts` подтвердил отсутствие реакции на живой
реплике после 502 и на обеих после восстановления маршрутизации. POST
удаления не повторяли. Docker зафиксировал два аварийных завершения с
кодом 137 и автоматические рестарты. Это адресный прогон без фоновой
нагрузки. Временный стенд удалён, инвентарь Docker совпал.
Журнал и сводка находятся в

## Смешанная нагрузка с записями — 9 ноября

100 виртуальных клиентов использовали 50 тестовых аккаунтов и паузу 800 мс.
Около 79% запросов читали контент, остальные добавляли лайки, сохранения и
комментарии. На каждом API очередь была ограничена 40, пул — 10 соединениями.
Для комментариев использовали штатный ключ операции, включив его зависимый
флаг только в локальном контейнере. Запросы не содержали вложений и ответов
на чужие комментарии.

| Этап | Запросы | HTTP 503 | Записи | p95 HTTP, мс | Пик очереди A / B |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 минута без рестарта | 7 120 | 0 | 1 484 | 191 | 12 / 11 |
| 2 минуты с рестартом | 14 503 | 0 | 3 022 | 97 | 11 / 37 |

В одноразовой БД сверены все 4 506 подтверждённых записей, включая 1 800
лайков, 1 802 сохранения и 904 комментария. Лайки и сохранения выполнялись
на уникальных парах аккаунт/пост, изначально без записи. Дублей и потерь
подтверждённых записей нет. Для каждого комментария совпали ID ответа,
строка в `post_comments` и запись журнала по ключу операции.

Пока API A был остановлен на 2,64 с, API B ответил на все 251 запрос,
включая 51 запись. Два POST перешли на B после отказа TCP-соединения с A
до обработки на A. В MySQL у каждого сохранилась одна запись. Пик MySQL
составил 22 из 50 соединений.

Три отдельные записи направили напрямую на A и удержали блокировками
постов до вставки. MySQL подтвердила ожидание всех трёх транзакций перед
`SIGKILL`. Соединения оборвались. После рестарта в БД не было ни их строк,
ни частичной записи журнала комментария. После сверки каждую операцию
выполнили один раз через Nginx. Отдельно отбросили тело успешного ответа
на комментарий. Два запроса с тем же ключом вернули прежний ID, строка одна.
Переключения лайков и сохранений повторяли только после сверки отсутствия.

## Очередь после оптимизации Ленты — 9 ноября

Все 48 ответов 503 из предыдущего прогона с рестартом совпали с отказом
mysql2 на первом получении соединения, до первого SQL. В момент отказа пул
имел 10 активных соединений и 10 ожидающих. Во время остановки API A был
один из этих ответов. Ещё 28 пришлись на две волны, которые Nginx уже делил

С оптимизированным запросом Ленты повторили по шесть волн из 100 GET в
каждом режиме. Менялся только предел очереди в локальной диагностике.

| Очередь на API | 503 без рестарта из 600 | p95 без рестарта, мс | 503 с рестартом из 600 | p95 с рестартом, мс |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 2 | 272 | 51 | 435 |
| 40 | 0 | 261 | 0 | 361 |
| 90 | 0 | 309 | 0 | 347 |

При пределе 40 очередь достигла 26 запросов во время этапа с рестартом,

p95 составил 346 и 396 мс, худший маршрут на этапе с рестартом — 419 мс.
Очередь достигла 25 запросов. Во время остановки первой реплики вторая

## Возврат реплики в ротацию Nginx — 9 ноября

На одноразовом Compose повторили пять синхронных волн по 100 GET с
`SIGKILL` API A перед второй волной. MySQL работала с лимитом 2 CPU, очередь
mysql2 была штатной на 10 запросов. До и после рестарта Docker DNS отдавал
одни и те же адреса. Из контейнера Nginx прямой `/api/health` реплики A уже
отвечал 200, пока прокси продолжал направлять запросы на B.

В журнале Nginx видны `Connection refused` и `upstream server temporarily
disabled`. После отказа пассивная проверка исключает адрес на `fail_timeout`,
по умолчанию на 10 секунд. После паузы Nginx пробует реплику живым запросом
и возвращает её в обычную ротацию после успеха. Если вся волна уже пришла
до ответа на пробный запрос, её остальные запросы могут уйти на B.
[Параметр fail_timeout](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#fail_timeout),
[логика round-robin Nginx](https://github.com/nginx/nginx/blob/release-1.30.5/src/http/ngx_http_upstream_round_robin.c#L794-L998).

В `edge.conf` и `edge.video.conf` установили `fail_timeout=2s`. В двух
сравнимых прогонах первый наблюдаемый ответ 200 от API A через Nginx пришёл
через 9,85 и 2,75 с после прямого ответа health соответственно. Пока API A
был остановлен, все 100 запросов в каждой волне направлялись на B.
При старом таймере A впервые получил один запрос в пятой волне. При новом
он получил один пробный запрос в четвёртой, а пятую реплики поделили 50/50.
В повторе с дополнительной волной на 10-й секунде она и последняя волна
разошлись 50/50. Дополнительная волна началась примерно через 4,9 с после
прямого health. Замер первого ответа зависит от расписания волн.

Уменьшение паузы ускорило возврат адреса. 503 из-за очереди mysql2 остались.
В сравнимых прогонах их было 93/500 и 128/500, p95 составил 504 и 499 мс.
В повторе с дополнительной волной получено 163/600 ответов 503. Все 503
совпали с отказами заполненного пула. Пределы SQL не менялись.

Два Docker-теста возврата адреса воспроизвели задержку на старых шаблонах
и прошли после изменения. Они также проверили смену IP и одну запись POST
при обрыве ответа. Всего прошли 16 проверок Nginx, Compose и политики выпуска.

## Дополнение 9 ноября: авария worker lock

Локальная правка завершает API с кодом 1 при обнаружении потери блокировки
выполняющейся фоновой задачи. Это намеренный fail-stop без graceful drain.
До выпуска проверить итоговую restart policy всех API, восстановление health,
маршрутизацию на живую реплику и наблюдение за сообщением
`[WorkerLock] Ownership lost; terminating API process`. Базовый Compose
содержит `restart: unless-stopped`; реальные overrides пока не проверены.

Не повторять неопределённые POST автоматически на прокси. При массовой потере
связи с БД могут перезапуститься несколько процессов. Рестарт не отменяет
уже принятые внешние операции. Аварийный перезапуск при настоящем mysqldump
проверен на отдельном Docker-контейнере и одноразовой MySQL. Новый запуск
убрал незавершённый архив и создал полный дамп.
[Проверка бэкапа](../audits/backend-worker-docker-restart-2026-11-09.md#бэкап-при-аварийном-перезапуске).
[Локальная матрица и ограничения](../audits/backend-worker-lock-loss-2026-11-09.md).

## Порядок DevOps

1. Снять read-only факты с целевого хоста: доступный CPU, MemTotal/MemAvailable, диск,
   работающие сервисы и их лимиты. Из MySQL получить фактический
   `@@max_connections`, текущие/пиковые соединения и историю миграций.
   Не подставлять паспортную RAM вместо фактического бюджета общего хоста.
2. Проверить весь private runtime stack, включая SMTP/egress/image-cache и TEST.
   На два API плюс один TEST-ingress приходится три пула по10; с резервом10
   соединений нужно минимум40. Прежних30 не хватает для этого бюджета.
   Кандидат50 — потолок для отдельной проверки, а не замер пикового расхода.
3. В закрытом api.env у всех API/TEST задать API_COORDINATION_MODE=mysql и
   API_REPLICA_COUNT=2. DATABASE_URL/JWT_SECRET/AUTH_LINK_ENCRYPTION_KEY должны
   совпадать между публичными API/TEST. SMS остаётся выключенным. Имеющиеся
   private-file/payment/strict flags не менять вслед за примером.
4. Добавить multi-api profile последним в существующий список overlays.
   Сохранить полный resolved config приватно: он содержит секреты. Файл не
   передавать фронтендеру, не коммитить, не печатать в CI.

```sh
umask 077
RELEASE_CHECK_DIR=$(mktemp -d /tmp/darcy-multi-preflight.XXXXXX)
# В исходной runtime-директории, используя тот же полный список -f overlays:
# docker compose ... -f compose.multi-api.example.yaml config --format json \
#   > "$RELEASE_CHECK_DIR/private-resolved.json"
# Числа ниже — только пример проверки, заменить реальными фактами хоста/БД.
pnpm exec tsx tooling/scripts/multi-api-preflight.ts \
  --config "$RELEASE_CHECK_DIR/private-resolved.json" \
  --host-memory-mib 16384 --mysql-max-connections 50
```

Gate учитывает лимит каждой реплики, всех остальных контейнеров и1GiB резерва
хоста, требует непубличные API-порты и достаточное время остановки. Проверены
топологии api и api+prodamus-test; candidate-api требует отдельного рассмотрения.
Для API и TEST допускается `restart: unless-stopped` или `restart: always`.
Переопределения `deploy.restart_policy` и `network_mode` требуют отдельной
проверки и блокируют этот профиль. Общий JWT-секрет должен содержать минимум
32 байта после нормализации приложения, а ключ ссылок должен быть каноническим
Base64 для 32 байт. У публичного API проверка требует
`API_DB_BURST_QUEUE_ENABLED=true`, чтобы сохранить очередь 40 из прогона.
`ok:true` всегда сопровождается `productionApproval:false`: это не согласование
выкладки и не доказательство производительности, доставки писем или резервирования.
Проверка не пытается автоматически определять роли неизвестных дополнительных
API-сервисов: такие изменения требуют обновления перечня и отдельного ревью.

При старом 8GiB профиле простой scale API до2 превышает выбранный бюджет
сервисов с резервом. Не обходить отказ gate уменьшением RAM одного сервиса без
репетиции и не менять текущие лимиты лишь ради зелёной проверки.

5. Перед применением 0050 — свежий бэкап, проверка восстановления и истории.
   До запуска нового API выполнить `pnpm db:preflight --require-feed-index`
   с отдельной настройкой `MIGRATION_PREFLIGHT_DATABASE_URL` для чтения.
   Сначала одинаковый проверенный backend/TEST bundle и mysql-mode на одной
   реплике, потом проверка схемы/API, затем масштабирование. Не оставлять старый
   TEST-код с локальными квотами рядом с новыми публичными API.
6. Выполнить nginx -t для окончательного edge config. В private-конфиге
   перенести настройки resolver/upstream, включая `fail_timeout=2s`, и ссылки
   API/media с сохранением действующих защитных locations.
   Сохранены запреты payment routes; `non_idempotent` retry не включать.
7. После выпуска проверить health каждой реплики, общий login quota, вход/отзыв
   сессии через разные реплики, отказ одной реплики и смену её адреса. Проверить
   graceful stop с начатым запросом и текущие приватные файлы разрешённым actor.
   Не выполнять реальные списания/письма ради инфраструктурного smoke.

## Откат

Сначала вернуть одну основную реплику и дождаться drain. Вернуть сохранённые

аддитивная; старый код её не использует. Не менять accounts/receipts/leases вручную.
