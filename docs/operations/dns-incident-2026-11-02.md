## Подтверждённые факты

Основной сайт daryadarcy.dev.reeskeen.ru, Mini daryadarcy-mini.dev.reeskeen.ru
и GitLab git.reeskeen.ru не разрешаются с Mac. git fetch завершается
Could not resolve host. SSH по известному155.212.216.16 ранее завершился
таймаутом до входа; работа контейнеров сейчас не подтверждена.

Две независимые службы DNS-over-HTTPS отвечают HTTP200, но DNS Status2/SERVFAIL:

- Google Public DNS для NS/SOA reeskeen.ru сообщает Name servers did not respond
  для NS Beget. В первой серии перечислялись ns1.beget.pro, ns2.beget.pro,
  ns1.beget.com, ns2.beget.com; повторная серия также видит beget.ru.
- Google с cd=true даёт тот же SERVFAIL и EDE22 на делегации reeskeen.ru.
  Отключение валидации в этом одиночном диагностическом запросе не исправляет
  результат; оснований менять защиту DNSSEC нет.
- Cloudflare возвращает EDE22: No Reachable Authority at delegation reeskeen.ru.
- Контрольный Google SOA для beget.com тоже даёт EDE22/недоступные NS Beget.
  Это усиливает гипотезу недоступности авторитетной инфраструктуры/маршрута,
  но не доказывает глобальный сбой всех клиентов Beget.
- Запрос DS reeskeen.ru к Google успешен (Status0), без DS Answer и с ru SOA
  в Authority. Из этого запроса нельзя заключить, что зона удалена или домен
  просрочен. Parent DNS при этом отвечает.

Локальные api.telegram.org и www.apple.com ранее успешно разрешались. Публичные
Google/Cloudflare возвращают одинаковую ошибку независимо от DNS на Mac.
Локальная смена браузерного кеша не восстановит отсутствующий DNS-ответ.

Точно локализовано: DNS-делегация/авторитетный ответ до HTTP приложения.
Корневая причина у провайдера (сеть/доступность NS/обслуживание зоны) требует
проверки владельцем DNS. Состояние самого VPS и причина SSH-таймаута отдельно
не установлены; восстановление DNS не является доказательством исправного VPS.

## Действия владельца DNS / DevOps

1. Открыть текущий кабинет домена и DNS Beget. Сначала экспортировать существующую
   зону и сохранить текущие NS/записи. Проверить обслуживание зоны reeskeen.ru
   и делегацию в кабинете регистратора. По одному SERVFAIL не пересоздавать зону.
2. С независимого Linux-хоста проверить SOA/A у текущих NS: обычный UDP и TCP,
   наличие авторитетного ответа AA. Полученные имена из диагностического Comment
   не являются предложением заменить NS на этот список. Использовать фактическую
   делегацию/настройки владельца.
3. Передать Beget время и публичные результаты EDE22. Уточнить доступность
   авторитетных DNS/зоны; попросить восстановить ответы с сохранением записей.
4. После восстановления DNS сравнить прежние A/AAAA с экспортом. Известный
   адрес Daryadarcy155.212.216.16 — контроль, не разрешение переписать все домены
   на этот IP. Проверить отдельно git, основной сайт и mini.
5. Через панель VPS проверить его питание/сеть/события и SSH-доступ. Затем
   проверить HTTPS /api/health, состояние текущих контейнеров/диска/памяти.
   Проверки делать без выкладки, восстановления БД или смены аккаунтов.
