## 1. Что арендовать

| Ресурс | Стартовая конфигурация |
| --- | --- |
| CPU | 4vCPU, x86_64/amd64, с понятной политикой разделения CPU |
| RAM | 8ГБ; возможность перейти на16ГБ без переустановки |
| Диск | 100ГБNVMe; оригиналы медиа остаются в S3 |
| ОС | Ubuntu24.04LTS с обновлениями безопасности |
| Сеть | Публичный IPv4, HTTPS; желательно порт1Гбит/с. Канал100Мбит/с принять только после проверки пика загрузки фото; проверить тарификацию трафика |
| Бэкапы | Копия БД вне этого VPS, независимый доступ к восстановлению |

На старте web/API/MySQL могут размещаться на одном выделенном под проект VPS.
Это одна точка отказа; доступность при потере VPS зависит от восстановления,
а не от наличия нескольких контейнеров. Сборку образов выполнять отдельно
от обслуживающего посетителей сервера. Существующий staging сохранить отдельно.

Казахстан — кандидат для сетевого теста, а не гарантия работы с любым VPN.
Локацию/IP выбрать после проверки доступа из целевых сетей. На текущем
подключении с заявленным VPN ОАЭ публичный сайт и превью доступны; плохой
VPN-маршрут не измерен. БД не переносить заодно с экспериментом над маршрутом.

## 2. Бюджет памяти сервисов

Начальные ориентиры для отдельного8ГБсервера; настроить и проверить на кандидате,
не переносить эти значения в действующий стенд без согласованного выпуска.

| Сервис | Лимит RAM | Лимит CPU в отдельном профиле |
| --- | ---: | ---: |
| Node API и фоновые задачи | 1536МиБ | 1,5vCPU |
| Next web и обработка публичных превью | 2048МиБ | 2vCPU |
| MySQL8.4 | 2048МиБ | 1vCPU |
| Nginx и служебные egress-прокси суммарно | Бюджет256МиБ | Прежние ограничения; профиль их не меняет |
| ОС, Docker, файловый кеш и свободный резерв | Оставшаяся память, около2ГиБ | Планировать отдельно |

Готов отдельный [compose.resources-8gb.example.yaml](../../infrastructure/deploy/teamassist/compose.resources-8gb.example.yaml).
Подключать его явно последним, после всех необходимых Compose overlays, только
на выделенном сервере минимум4vCPU/8ГиБ с проверенным запасом ресурсов.
Это потолки потребления, а не зарезервированная память/ядра; сумма CPU-потолков
может превышать4. Другие проекты на том же хосте требуют отдельного бюджета.

Профиль меняет только mem_limit/cpus трёх сервисов. Images, networks, mounts,
env/secrets, команды, порты, платёжный режим и флаги сохраняются. Он не является
полным production Compose и не снимает dev-ограничения checkout/webhook.
Node heap, MySQL buffer pool, параллелизм Sharp и лимиты входных файлов не
изменяет. При применении потребуется отдельная процедура обновления сервисов
и проверка фактического docker inspect; простой restart не меняет конфигурацию
созданного контейнера.

Read-only замер26октября: текущий shared host имеет2CPU, MemTotal4 106 096 640байт,
MemAvailable639 098 880байт, swap отсутствует. В момент замера API использовал
около105МиБиз256, web133из384, MySQL310из512; это idle-снимок, не пик.
На этот хост повышенный профиль **не применён**. Перед применением оценивать
и MemTotal, и MemAvailable, все сервисы и резерв ОС, а не только тариф провайдера.

Совместимость проверена настоящим Docker Compose5.5.1 без запуска контейнеров:
base/full/candidate config merge дают точный diff только двух ресурсных полей;
возврат без overlay совпадает с исходным. Дополнительно прошли существующие
S3/candidate merge tests: всего5проверок. Полный test-stack с legacy video,
TEST и synthetic SMTP имеет сумму memory caps6624МиБ; это оставляет1568МиБ
на номинальном8ГиБхосте, но не учитывает чужие проекты/сборки. Контейнеры на
новых лимитах не запускались; приёмка100посетителей и32/80МиБ ещё впереди.

Повторить offline-проверки локально можно командой:

```sh
RESOURCE_COMPOSE_ACCEPTANCE=true PRIVATE_UPLOADS_COMPOSE_ACCEPTANCE=true CANDIDATE_COMPOSE_ACCEPTANCE=true pnpm exec vitest run tests/resource-profile-compose.test.ts tests/private-uploads-compose.test.ts tests/candidate-release-compose.test.ts --maxWorkers=1 --no-file-parallelism
```

Тест создаёт только собственные временные Compose/env fixtures, выполняет
config и удаляет fixtures; up/run/pull, реальные credentials и БД не использует.

В репозиторном dev-шаблоне API256МиБ, web384МиБ, MySQL512МиБ и CPU-квоты
0,4 — это ограниченная тестовая конфигурация, не готовый ресурсный профиль
для нового production VPS. Увеличение тарифа само не изменяет эти лимиты.
Настройки Node heap, native Sharp и параллелизма должны укладываться в лимит
контейнера; не назначать heap равным всей памяти контейнера.

Полные загрузки32/80МиБ ещё не приняты на целевом Linux-стенде. Эти бюджеты
не подтверждают их работоспособность. Проверить пик RSS/лимит контейнера,
время обработки и работу остальных запросов на изолированном кандидате.
100посетителей не означают разрешение100одновременных больших загрузок.

VK-видео воспроизводятся внешним плеером. Если legacy video-service всё ещё
используется действующими материалами, учесть его отдельно: в dev-overlay
он имеет лимит640МиБ и tmpfs. Не удалять его без проверки consumers.

## 3. Состав и сеть

Публичный HTTPS → Nginx/edge → web для страниц и API для /api/ и /media/.
MySQL доступен только API во внутренней сети. Публичные порты:80/443;
SSH по ключу с ограничением источников.3306 и внутренние порты контейнеров
не публиковать в интернет.

Исходящие подключения разделены по назначению: API к MySQL/S3/SMTP/нужному
платёжному провайдеру; web к разрешённым публичным источникам изображений.
Не объединять все сети без проверки. В существующей схеме DNS alias
s3.twcstorage.ru у egress-прокси относится только к API: попадание этого alias
в сеть web заставляет защиту Next отвергать публичные превью как private IP.
Не отключать SSRF-защиту ради восстановления картинок.

| S3 endpoint/bucket/ключи, действующие policy и prefixes | Медиа без потери прав и старых файлов |
| SMTP_HOST/PORT/SECURE/USER/PASS/FROM; optional SMTP_REPLY_TO; отдельно managerEmail | SMTP приложения — регистрация/доступ/reset. Заказ Магазина — mailto из почтового клиента покупателя; SMTP приложения не доказывает его доставку |

Секреты передавать закрытым способом, не в Git, общий документ или логи.
В production использовать отдельные права доступа. Ключи сессий/шифрования
при простом переезде не генерировать заново автоматически. Сохранить
password hashes, роли и sessionVersion существующих администраторов.

Отправитель писем сейчас не требует замены на Gmail Дарьи. Такая замена
потребует её SMTP-доступа и отдельной настройки; действующие реквизиты брать
из закрытого окружения, не из демонстрационных значений .env.example.

1. **Сборка и выпуск.** Docker Engine/Compose; native amd64-сборка из чистого
   Git-контекста. Использовать pnpm9.12.0/frozen lockfile и существующие Dockerfile.
   Зафиксировать source SHA, digest каждого образа и build-time публичные флаги.
   Образы отката сохранять. На 26 октября backend dependency/VK parser fixes
   уже выпущены в ff2c229; web ce56ebe содержит правки поверх frontend1d3e7ab и Next16.4.1.
   26 октября повторный прогон4732passed/332skipped и native26/HTTPS35 прошли;
   [результат повторной проверки](../audits/final-recheck-2026-10-26.md).
   Backend-код между этими source одинаков; проверять code diff и образ отдельно
   от одного лишь общего Git SHA.
2. **Окружение.** Отдельные production env/secrets. NEXT_PUBLIC_* фиксируются
   при сборке: смена только runtime env их не обновляет. Проверить совместимость
   frontend/backend флагов VK, обложек, закрытых загрузок и Библиотеки.
   Обеспечить явную передачу согласованных публичных флагов в Next build:
   чистый Git-контекст не содержит локального .env. Проверить их значения
   в собранном клиенте; секреты в build-time публичные переменные не помещать.
   Обязательно передать `NEXT_PUBLIC_VIDEO_THUMBNAILS_ENABLED=true` в Next build.
   Этот compile-only флаг не входит в пять значений required-server-files.config.env;
   их сверка не доказывает наличие обложек в клиенте. До переключения проверить
   настоящий запрос videos.catalog с includeThumbnails:true, догрузку20→22карточек
   и отсутствие заглушек. Первый кандидат26октября без этого флага был откатан;
   исправленная пересборка проверена и опубликована. Runtime env не заменяет build.
   [Отчёт выпуска](../audits/staging-frontend-rollout-2026-10-26.md).
3. **Платежи.** Согласовать production-конфиг отдельно от dev. В dev Nginx
   намеренно блокирует live checkout/webhook, а TEST использует отдельный runtime.
   Не копировать эти блокировки в production автоматически и не включать реальные
   платежи без отдельной приёмки. Demo/TEST не должны выдавать production-доступ.
4. **Миграции.** До применения снять backup, сверить фактическую историю и схему,
   выполнить штатный preflight. Не заменять БД пустой, не переписывать применённые
   миграции0017–0019 и не запускать DDL вслепую. После — сверить counts и входы.
5. **Фото.** Постоянный volume кеша публичных превью, конечный размер кеша,
   ограниченный параллелизм Sharp. Не очищать кеш при каждой выкладке. Проверить
   actual runtime config/headers: runtime3600 подтверждён;9производных записей
   поста744 адресно исправлены26октября11:55UTC, GET/304 и сохранность остальных
   550файлов проверены. Контроль после часа16:04МСК пройден:9HTTP/disk TTL3600,
   прежние SHA/ETag, web healthy без OOM/перезапуска. Исторический источник
   возврата к30 ещё не доказан; [ремонт и приёмка](../audits/photo-cache-investigation-2026-10-26.md).
   Защищённые bytes не помещать в публичный кеш. Клиентский fallback на тяжёлый
   оригинал описан в передаче фронту, не исправляется одним увеличением RAM.
   Свежий read-only снимок: диск97%/1186МиБ свободно, RAM available659МиБ,
   swap нет. На shared host не запускать stress/cold-cache прогрев массово;
   сначала согласованная очистка/расширение диска или выделенный кандидат.
   [Замеры размеров, сети и план ускорения](../audits/photo-performance-2026-10-26.md).
6. **Резервирование.** Регулярная копия БД вне VPS, проверка успешного завершения,
   контроль возраста и репетиция восстановления в отдельную БД. Согласовать срок
   хранения, допустимую потерю данных и время восстановления. План резервирования
   S3 сверить отдельно: наличие старого скрипта/отчёта не подтверждает его работу.
7. **Наблюдение.** CPU/RAM/RSS, OOM/restarts, свободное место, HTTP5xx/latency,
   MySQL connections/slow queries, Sharp/cache, S3/SMTP errors, свежесть backup.
   Логи ротировать, токены и тела писем/платежей скрывать. Уведомления направить
   назначенному ответственному; тестовые письма и платежи отдельно согласовать.
8. **Откат.** Подготовить возврат прежних образов и конфигурации без удаления
   данных. Additive миграция не требует автоматического восстановления старой БД.
   Восстановление БД — отдельная процедура, поскольку теряет новые записи.

## 6. Проверка перед переключением

- Изолированный кандидат с копией или синтетической БД, без отправки внешних
  писем и реальных платежей. Проверить входы, роли, открытый/клубный контент,
  сохранённое, редакторы, фотографии, загрузки и отказ после отзыва доступа.
- Подтвердить100одновременных посетителей сценариями с паузами, затем отдельно
  всплеск входов после анонса. Старый тест25RPS не равен приёмке100посетителей.
  Использовать ступени/остановку при ошибках и существующие API-критерии плана;
  не запускать нагрузку на обслуживающем посетителей сервере.
- Отдельно проверить холодный/тёплый кеш фотографий, повторные переходы,
  память web/API и исчерпание диска. Сайт, S3 и VK измерять раздельно.
- Проверить доступ с мобильной/домашней сети без VPN и с согласованными
  VPN-выходами. Пропускать только HTML недостаточно: нужны изображения и API.
- После согласованного переключения сверить фактические runtime-образы и
  подключение к нужной БД, историю миграций, контент, админские входы, HTTPS,
  флаги и заголовки кеша. Не считать успешный push подтверждением выкладки.
