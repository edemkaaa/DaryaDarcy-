# Push-регистрация: серверный контракт и передача фронтендеру

## Границы

Изменение21 октября локальное, по поручению закрыть регистрацию при выключенной
функции, проверить вход и ограничить частоту. Фронт/generated contract, рабочая
БД, S3, настройки стенда и доставка уведомлений не менялись. Нового флага
включения нет: `/api/capabilities` по-прежнему возвращает `webPush: false`.

## Контракт `notifications.registerToken`

- Проверка серверной capability выполняется до валидации/лимита/записи.
  При выключенной функции — `FORBIDDEN`/403 для гостя, участника и администратора.
  Нельзя вставить токен или повторно включить прежнюю запись. Прямой вызов
  сервиса тоже проверяет capability. Гостевая регистрация не удалена из будущего
  контракта, но сейчас не разрешена. Контекст с `user.blockedAt` получает403;
  политику optional-auth/перехода недействительной сессии в гостя не меняли.
- Когда capability разрешена: токен — строка до256 символов, без пробелов/
  C0/DEL, `ExpoPushToken[...]`, `ExponentPushToken[...]` с непустой
  непробельной нагрузкой без вложенных скобок, либо прежний UUID-shaped формат.
  Префиксы и legacy-формат сверены с
  [официальным Expo SDK](https://github.com/expo/expo-server-sdk-node/blob/main/src/ExpoClient.ts).
  Токен не обрезается/не перекодируется; это проверка формы, не подтверждение
  принадлежности устройства и не доказательство доставки.
- Необязательный `platform`: только `ios`, `android`, `web`; SQL-предел16
  соблюдён. Значение `web` не добавляет поддержку браузерного Web Push.
  Произвольная строка/URL/пустой токен/неверная платформа дают400 до SQL.
- Владельца сервер получает только из сессии, не из payload. Успех остаётся
  `{success: true}` после SQL upsert; повтор одного токена не создаёт вторую
  запись. Ошибка SQL остаётся500, не ложный успех и не сырая ошибка базы.
- До разбора входа:30 попыток на resolved IP и10 на аккаунт за15 минут.
  Невалидный вход тоже расходует квоту; смена IP не сбрасывает квоту аккаунта.
  Счётчик отдельный для каждого вызова процедуры, включая tRPC batch.
  `TOO_MANY_REQUESTS`/429 и `Retry-After` в секундах; mixed batch может вернуть207
  с отдельными ошибками429. Отказ не продлевает окно. Выключенная функция
  не расходует будущую квоту регистрации.
- IP берётся из существующего Express `req.ip` с прежним trust proxy, не из
  произвольного первого forwarded-заголовка. Proxy trust/CORS не менялись.

## Ограничение выбранного решения

Используется уже существующий process-local limiter: общий bounded store
до10000 ключей, истёкшие окна убираются при обращениях. Переполнение отказывает,
а не вытесняет живую чужую квоту. Новых зависимостей/схемы/постоянного хранения
IP не добавлено. Перезапуск сбрасывает счётчики; несколько API-процессов имеют
отдельные бюджеты. До многопроцессного включения нужен согласованный shared
store — это не выполнено и не выдано за распределённую защиту.

## Фронтендеру

При `webPush: false` не запрашивать разрешение/не регистрировать токен, не
повторять403 в цикле.400 означает ошибку входа;429 — паузу по `Retry-After`,
без автоматического бесконечного повтора. Эти ответы сами по себе не являются
доказанным выходом из аккаунта. Не добавлять обходной маршрут. Типы входа и
ответа не изменились; runtime-валидация стала строгой. Предыдущее расхождение
generated API с `purpose: "publicCover"` относится к отдельному handoff.
