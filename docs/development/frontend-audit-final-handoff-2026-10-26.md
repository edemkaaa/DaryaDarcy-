## 1. Закрытые иллюстрации эстетик — совместный выпуск, высокий приоритет

Сейчас платные блоки гида и результата теста используют публичные
`/assets/results/**`. Прямая ссылка на одну из иллюстраций 26 октября снова
вернула `200` без входа. Защита текста и скрытие блока сами изображения не закрывают.

Сервер поддерживает следующие materialKey и проверенный состав:

| materialKey | Файлов |
| --- | ---: |
| aesthetic-castlecore | 34 |
| aesthetic-cottagecore | 25 |
| aesthetic-darkacademia | 29 |
| aesthetic-fairycore | 30 |
| aesthetic-goblincore | 31 |
| aesthetic-lightacademia | 37 |
| aesthetic-witchcore | 34 |
| Всего | 220 |

Контракт чтения:

- `GET /api/library/materials/{materialKey}/files?cursor=...` →
  `{files:[{fileKey,sortOrder,revision,filename,mimeType,fileSize,url}],nextCursor}`.
- Размер страницы — до 50 файлов. При `nextCursor !== null` читать продолжение;
  курсор передавать как непрозрачную строку, не вычислять самостоятельно.
- Защищённый URL файла: `/api/media/library-files/{materialKey}/{fileKey}`.
  Использовать подтверждённый `url` из списка, проверять принадлежность materialKey.
- `404` означает недоступность, `503` — временный сбой. При отказе не возвращаться
  к публичному URL. `200` с пустым списком не доказывает готовность переноса.

Сопоставление старого пути со слотом:
`/assets/results/{key}/{group}/{name}[.lossless].webp` →
`materialKey="aesthetic-"+key`, `fileKey=group+"-"+name`.
Например, `castlecore/outfits/outfit3.lossless.webp` →
`aesthetic-castlecore / outfits-outfit3`.
Допустимые группы: `moodboards`, `outfits`, `interiors`.
Точный перечень — `docs/audits/library-source-map-2026-10-20.json`, раздел visuals.files.

Подключить **оба** потребителя: `features/library/aesthetics-screen.tsx` и
`features/quiz/aesthetic-result-content.tsx` с их content registry.
В `library-files-api.ts` текущая клиентская allowlist содержит только patterns,
recipes, peterburg — её надо явно расширить семью перечисленными namespace.
Простого включения флага для этого недостаточно.

Использовать текущую сессию и отмену запросов. Ключ кэша должен включать аккаунт
и materialKey. Logout, смена аккаунта и отзыв доступа убирают закрытые картинки
и viewer; созданные Blob URL освобождаются. Не сохранять закрытые bytes в
публичный Service Worker cache и не делать публичный fallback при ошибке.

**Готовность сервера:** локально проверен импорт всех 220 реальных файлов
на одноразовой БД и имитации S3, включая потерю ответа, повтор без дублей,
проверку bytes и отзыв прежних URL. Четыре исходника имели EXIF; подготовлены

Порядок выпуска: backend импортирует проверенные копии и подтверждает все
bindings → frontend подключает оба потребителя → совместная проверка прав →
отдельное адресное закрытие старых публичных originals/responsive/build copies.
До готовности bindings нельзя выпускать экран, который просто потеряет картинки.
Не удалять wildcard-папки. Бесплатный тест, `/assets/quiz/houses/**`, «Лошадка»,

## 6. Аватары и публичные обложки — восстановление потерянного ответа

Текущие `use-profile-avatar.ts` и загрузка обложки в `articles-admin.tsx`
используют старые upload-вызовы. Перейти на следующие tRPC-методы:

| Назначение | Загрузка | Статус |
| --- | --- | --- |
| Аватар | profile.uploadAvatarWithReceipt | profile.avatarUploadStatus |
| Публичная обложка | admin.uploadPublicCover | admin.publicCoverUploadStatus |

Загрузка принимает `{base64,filename,mimeType,idempotencyKey}`; для обложки
обязательно `purpose:"publicCover"`. Статус принимает `{idempotencyKey}`.
Ключ — 16–128 символов `[A-Za-z0-9._:-]`, создаётся один раз на операцию
и передаётся **в input**. Не путать его с отдельным ключом создания поста.
Фото JPEG/PNG/WebP — до 4 МиБ декодированных bytes; Base64 без data:-префикса.

Ответ статуса/загрузки:
`{state:"missing"|"pending"}` либо
`{state:"ready",url,avatarApplied,isCurrent}`.
У обложки avatarApplied=false/isCurrent=null: её надо затем привязать штатным
сохранением статьи/настройки. У аватара сервер сам выполняет безопасную привязку.

До отправки сохранить account-scoped intent и ключ. Потеря ответа → сначала
status. Ready использовать без второго upload; pending/missing — повтор того же
файла с тем же ключом. Новый ключ автоматически не создавать. При 409 остановить
повтор и сообщить о конфликте; 503 сохраняет неопределённый результат операции.
Без локального файла требуется повторный выбор того же файла.

`avatarApplied` — результат исходного завершения, `isCurrent` — совпадение
с текущим профилем. Если старый ответ уже не текущий, прочитать профиль и не
перезаписывать новый аватар поздним `profile.update`. Отмена/уход/logout/смена
аккаунта должны лишать старую задачу права обновлять интерфейс и привязывать URL.
Автоматическое удаление старых изображений и orphan-файлов не включать.

Проверить потерянный PUT ACK/HTTP-ответ, повтор без дублей, новый аватар раньше
старого ответа, другой аккаунт, отзыв admin-роли и сохранение старого профиля
при ошибке. Backend-матрица с настоящими SQL/HTTP и локальным S3-wire прошла.

### VK export без hash — согласованная правка 26 октября

VK выдал пользователю iframe без hash. Ранее оба валидатора требовали его;
backend `parseVkEmbed` исправлен локально, сборщик oEmbed использует тот же
parser. **Текущий frontend ещё требует hash; серверная правка сама по себе
не разблокирует поле редактора или отображение нового источника.**

В `shared/media/vk-video-url.ts`, функция `getVkVideoEmbedUrl`:

- `oid` и `id` по-прежнему обязательны и встречаются ровно один раз.
- При отсутствии hash ссылка допустима. Не добавлять `hash=`, `hash=null`,
  фиктивное значение или hash от другого ролика.
- Если hash присутствует, он должен встречаться ровно один раз и проходить
  прежнюю проверку `[A-Za-z0-9_-]{8,128}`. Пустое значение — ошибка.
- Записывать hash в итоговый URL только при `hash !== null`. Сохранять его
  значение без замены; `autoplay` по-прежнему нормализовать в `0`.
- Не ослаблять проверки HTTPS/точного VK host/пути/credentials/port и остальных
  параметров. Отсутствие hash не означает разрешение на произвольный iframe.

Пример допустимого входа:
`https://vk.ru/video_ext.php?oid=-211171256&id=456239238&autoplay=1`.
Результат нормализации:
`https://vk.ru/video_ext.php?oid=-211171256&id=456239238&autoplay=0`.

В `features/admin/vk-video-field.tsx` заменить подсказку/ошибку: обязательны
oid/id; hash сохраняется, если он есть в экспорте. Пользователь копирует только
src, а не весь HTML. Проверить оба редактора постов, редактирование существующих
постов и VK-каталог: все используют общий helper. В `frontend-vk-video.test.ts`
перенести URL без hash из отказов в успешные случаи для всех трёх VK hosts;
оставить отдельные отказы пустого/повторного/повреждённого hash. Не удалять
проверки существующих ссылок с hash и account/access boundaries.

Backend replay сохраняется: identity — oid/id, не наличие hash. Повтор создания
с изменённым URL даёт409; для замены экспорта нужен явный id существующей записи.
Миграция, правка старых строк и подбор hash не нужны. Клубное разрешение
по-прежнему проверяется приложением; допуск URL не подтверждает доступность
самого видео в VK. Живое воспроизведение проверить после согласованного выпуска.

## 14. Обработчики фото: лишняя работа и качество

Проверка26октября:102существующих unit/loopback checks и6дополнительных
characterization probes. Пробы вызывают действительные функции/извлечённые
effect callbacks с подменёнными browser primitives; это не browser/RSS benchmark.
Frontend source не менялся.

### Исправить в ближайшем срезе

- **Фоновый polling.** В shared/media/image.tsx effect с setInterval100ms
  не проверяет видимость/активность экрана. loadingFallback=null тоже считается
  custom loader. Поэтому невидимые lazy VK-карточки могут проверять complete
  всё время, пока остаются mounted. Проба18таких ресурсов создала18таймеров;
  это180проверок/с, не измеренный процент CPU. Сохранить проверку уже готового
  cached image и обработку пропущенного load, но не держать polling для
  далёких/неактивных изображений. Проверить hidden→visible и повторный вход.
- **Стабильные blob URL комментария.** В use-private-comment-files.ts cleanup
  отзывает все адреса при каждом изменении files, затем создаёт их заново.
  В пробе добавление B поменяло URL неизменённого A. Утечки URL не обнаружено,
  но повторяется локальное чтение/декодирование и сбрасывается Picture lifecycle.
  Сохранять URL неизменённых файлов, отзывать удалённые и весь scope при выходе,
  смене аккаунта/поста. Не сохранять blob URL в durable journal.
- **Не терять качество до сервера.** fileForPhotoUpload всегда кодирует фото
  заново (обычно1920px/q0.82), включая маленький уже готовый JPEG. Аватар сначала
  crop400×400/JPEG0.8, затем uriToBase64 делает JPEG0.82, сервер —WebP85.
  Нужен согласованный путь с одним финальным lossy encode, сохраняя серверную
  проверку bytes/EXIF/orientation/alpha/размеров.400px сам по себе достаточен
  для небольшого аватара с учётом DPR; не увеличивать всё до огромных размеров.
  Нельзя считать новый upload побайтовым оригиналом камеры: он уже преобразован.
  Старые файлы не менять. Для нового высокого разрешения сначала согласовать
  рабочий лимит/качество и обратную совместимость, затем реализовывать.

### Уже учтённое и отдельные проверки

- DomImage.getSize создаёт отдельный Image по исходному URL без AbortSignal
  или deadline. В VideoPreviewCard cleanup запрещает setState, но не прекращает
  сам запрос. По возможности получить пропорции из уже показываемого постера;
  если отдельная загрузка нужна — она должна иметь ограниченный lifecycle.
  Не утверждать, что сейчас каждый VK-ролик делает такой запрос: компонент
  применяется к конкретным media-секциям, не всем карточкам каталога.
- Таймеры/IntersectionObserver Picture очищаются при remount/unmount;
  source/retry меняют key. OperationScope отменяет старые операции;
  AuthProvider меняет корневой scope при смене аккаунта. Это работающие границы.
- Поздний createImageBitmap после timeout закрывается; зависший canvas.toBlob
  обнуляет canvas и освобождает bitmap. Текущие пробы это подтвердили.
  Не переписывать эти участки как якобы отсутствующую защиту.
- Реальное Safari/iPhone duplicate, memory peak больших исходников и full
  browser regression остаются отдельной проверкой; текущие unit-пробы их
  не заменяют. Серверное quality85 пока не менять: private upload payloadHash
  включает нормализованные bytes, смена рецепта требует проверки pending replay.

## 15. Ручной повтор при всё ещё зависшем ответе — подтверждён локально

**Статус: исправлено локально 26 октября после следующего согласования.**
`Picture` перед удалением зависшего img явно освобождает `srcset` и `src`.
Браузер закрывает прежнюю передачу; ручной повтор использует прежний URL,
без cache-buster и изменения подписанных параметров. Дизайн/качество/таймаут
не менялись. Три реальных HTTP browser cases (direct/srcset/preview) прошли:
GET1 закрыт клиентом, GET2 успешен; reload не делает GET3. Дополнительно
на свежей production-сборке Ленты пройден исходный pending→timeout→retry
и просмотрщик без принудительного завершения ответа сервером.
16 unit tests, root/frontend types, lint компонента и сборка прошли.
Три опциональных browser cases добавлены в `tests/picture-retry.browser.test.ts`;
в текущей сессии их fixture проверен через Cua, CLI browser runner не запускался.
Рабочие DB/S3 не затрагивались, push/deploy пока не выполнялись.
Ниже сохранена исходная диагностика до исправления.

Высокий приоритет для восстановления фотографий на нестабильной сети.
26октября в настоящем встроенном браузере воспроизведено дважды, на двух
тестовых URL. Production-сборка текущих исходников, подставной API и собственный
HTTP-сервер на127.0.0.1; рабочие данные/S3 не использовались.

Воспроизведение:

1. Отдать200 и начало тела изображения, затем удерживать ответ открытым.
2. Через30s Picture убирает img и показывает «Повторить загрузку» — это работает.
3. **Не завершать первый ответ.** Нажать повтор. Интерфейс снова показывает
   загрузку, но HTTP-сервер по-прежнему видит только один запрос; старый ответ
   остаётся открытым. Новый img с тем же src присоединяется к ожидающему ресурсу.
4. Принудительно закрыть старый ответ на тестовом сервере. После этого новый
   запрос и восстановление проходят; картинка complete=true/naturalWidth>0.

Текущий E2E «a hung photo stops loading…» сначала делает release() старого
ответа и лишь потом нажимает retry. Поэтому он проверяет другой сценарий
и эту ошибку не обнаруживает. Добавить cache-on HTTP regression без interception,
в котором retry вызывается **до** освобождения первого ответа. SVG был только
локальным транспортным fixture; это не визуальная проверка реальных фото.

Исправление должно завершать предыдущую операцию загрузки до нового повтора
либо давать действительно независимую управляемую попытку. Одной смены React
key недостаточно в проверенном браузере. Сначала проверить явное освобождение
источников и контролируемую отмену; конкретное решение подтвердить тестом.
Не дописывать произвольные cache-buster параметры к подписанным/защищённым
URL и не отключать HTTP-кеш для всех картинок. Сохранить ограничение30s,
рамку фотографии, ручной retry, offline/online и защиту от позднего ответа.

В этой же локальной серии прошли первоначальная загрузка/viewer, настоящий
кеш после reload/возврата, восстановление после503, ошибка сессии503→повтор
и A→logout→B без старого имени/аватара. Это8прошедших сценариев и1новая
неисправленная проблема, не полная приёмка приложения. Дополнительно135unit/
loopback checks прошли; frontend исправления пока не вносились.

  массивы до первых N элементов молча ради зелёного аудита.
- Выкладку, миграции, рабочие bindings, S3-policy и закрытие публичных копий
  выполняет backend отдельным согласованным выпуском. Сама готовность кода
  не доказывает наличия 220 bindings на стенде.
- Реальные платежи/почта, большие 32/80 МиБ, физические устройства и пилот
  остаются отдельной приёмкой; локальные серии их не заменяют.
- В рамках этой передачи исходники frontend, рабочие БД/S3 и стенд не менялись.

Новых разделов, 2FA, Pen Pals, push или платёжного магазина это задание не требует.
