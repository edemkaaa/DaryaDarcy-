# Работа вдвоём: бэкенд и фронтенд

Один репозиторий, два самостоятельных приложения. Бэкендер работает в
`apps/backend`, фронтендер — в `apps/frontend`. Переносить их в отдельные
репозитории или делать копию фронта для каждой ветки сейчас не требуется:
связанный API и клиент можно проверить и объединить одним PR.

## Зоны ответственности

| Область | Кто ведёт | Когда согласовать со вторым разработчиком |
| --- | --- | --- |
| `apps/backend/src/` | Бэкендер | Если меняются запросы, ответы, доступ, ошибки или флаги |
| `packages/database/` и `drizzle.config.ts` | Бэкендер | Если изменение данных влияет на клиентский сценарий |
| `apps/frontend/src/`, `public/`, `e2e/` | Фронтендер | Если нужен новый ответ API или меняется обработка прав/ошибок |
| `apps/frontend/src/shared/api/contract.ts` | Генератор; запускает автор серверного изменения | Фронтендер проверяет использование полей и совместимость |
| `packages/shared/` | Автор затронутого контракта | Всегда проверить обоих потребителей |
| `infrastructure/build/`, `infrastructure/deploy/` | Ответственный за выпуск | Если меняются публичные build flags, API proxy или runtime |
| Корневые `package.json`, `pnpm-lock.yaml`, CI | Автор задачи | Согласовать новые зависимости и обязательные проверки |
| `tests/` | Автор проверяемого поведения | Сквозной сценарий проверяют оба |

Это правила команды, а не настроенная в GitHub блокировка изменений.
Архивные `apps/legacy-*` не являются рабочими копиями текущего фронта.
Бот расположен в соседнем отдельном проекте `daryadarcy-telegram`; перенос
основного приложения туда не требуется.

## Как раскладывать код внутри приложений

Код группируется по функции приложения: профиль, Клуб, видео, Магазин.
Связанные экран, локальные компоненты, обработчики и стили хранятся рядом.
Название каталога отвечает на вопрос «какой сценарий меняю».

### Фронтенд

| Каталог | Что сюда относится | Пример |
| --- | --- | --- |
| `src/app/` | URL, layout и подключение экранов | Страница профиля открывает экран из features |
| `src/features/<раздел>/` | Экран, формы, локальные компоненты, обработчики и стили конкретного раздела | Редактирование имени в `features/profile` |
| `src/domain/<область>/` | Правила и состояние предметной операции, используемые экранами | Сессия, журнал сохранения поста, подписка |
| `src/shared/` | Универсальные элементы и инфраструктура клиента | Кнопка, диалог, HTTP-клиент, браузерное хранилище |

Прежде чем создать файл, найти ближайший существующий модуль того же сценария.
Три–четыре связанных файла могут лежать прямо в каталоге раздела. Подкаталоги
добавляются, когда помогают ориентироваться; одинаковая вложенность для каждой
фичи не требуется.

Практические решения:

- Компонент нужен только профилю: оставить в `features/profile` рядом с его стилями.
- Правило или журнал нужен нескольким экранам одной предметной области:
  использовать соответствующий модуль `domain`.
- Элемент не зависит от конкретного раздела и действительно нужен разным
  сценариям: вынести в подходящий каталог `shared`.
- Общий API-тип уже есть в сгенерированном контракте: использовать его,
  согласовав изменение с бэкендером при несовпадении ответа.

Для новых модулей целевое направление такое: `shared` не зависит от экранов
и предметных операций; `domain` не зависит от `features`.
Переиспользование между разделами оформлять через подходящий
общий модуль. Это правила для новых изменений и ревью, а не требование
массово переименовать существующие файлы.

В существующем коде есть две обратные связи с сессионным `domain`:
[use-cursor-pages.ts](../../apps/frontend/src/shared/api/use-cursor-pages.ts)
использует `checkOperationAccessError`, а
[avatar-cropper.tsx](../../apps/frontend/src/shared/media/avatar-cropper.tsx) —
`useSessionOperation`. Они сохранены как известные исключения. Их наличие не
доказывает ошибку поведения, но текущий граф зависимостей ещё не строго следует
указанному направлению. При отдельном изменении этих связей сохранить отмену
операций, проверку доступа и реакцию на смену аккаунта; не копировать сессионную
логику ради формального устранения импорта.

### Бэкенд

Сценарий размещается в существующем предметном модуле: `identity`, `billing`,
`content`, `profile`, `shop` и других. Контроллер или tRPC-router принимает
вход и проверяет транспортный контракт; сервис ведёт операцию; SQL-репозиторий
отвечает за чтение и запись. Схема и история миграций остаются в
`packages/database`, нейтральные общие контракты — в `packages/shared`.

Новый метод профиля добавляется в модуль `profile`, платёжная операция — в
`billing`. Общие middleware и композиция сервера относятся к `_core`.
Существующие совместимые обёртки `db.ts` сохраняются до отдельной задачи
переноса; новую предметную логику размещать в её модуле.

### Проверка границ

`pnpm check:boundaries` уже проверяет границы приложений и общих пакетов:
фронтенд не получает серверный runtime или SQL-пакет, backend не импортирует
фронтенд, `packages/shared` остаётся независимым от Node built-ins и приложений.
Есть узкое совместимое исключение для type-only `AppRouter`; основной клиент
использует сгенерированный контракт.

Внутреннее направление `app → features → domain → shared` проверяется на ревью:
существующий scanner различает приложения и пакеты, но не эти четыре каталога.
Новых автоматических запретов, перемещений runtime-кода или библиотек этот
регламент не добавляет.

## Как работать одновременно

У каждого разработчика своя локальная копия репозитория. Перед новой задачей
получить актуальный `origin/staging`, затем создать короткую ветку
`fix/backend-...` или `fix/frontend-...`. Для новых возможностей подходит
`feat/backend-...` или `feat/frontend-...`. Ветки содержат одну задачу.

```sh
git fetch origin
git switch staging
git pull --ff-only origin staging
git switch -c fix/backend-example
```

Перед переключением сохранить текущую работу отдельным коммитом в своей ветке.
Если в рабочем дереве уже есть чужие или незавершённые изменения, не выполнять
`reset --hard`, массовый checkout или принудительный pull поверх них.

Открывать PR в `staging`, описывать поведение и фактические проверки.
Второй разработчик проверяет затронутую границу. После объединения оба
обновляют свои копии. `main` и выпуск обновляются отдельным согласованным
шагом; попадание в `staging` само не означает выкладку на сервер.

Общие изменения package/lock/CI не переносить копированием папки целиком.
Разрешать конфликты по смыслу. Для конфликта зависимостей сначала объединить
манифесты, затем штатным pnpm обновить lockfile и проверить его diff.

## Как менять API

1. До реализации записать минимальный вход, выход, права и ошибки в
   [спецификациях](../specifications/README.md) или существующем документе задачи.
2. Бэкендер меняет серверные типы и проверяет настоящий возвращаемый результат.
   Генерирует контракт из корня: `pnpm api:contract`, затем `pnpm check:api`.
3. В тот же PR включить сгенерированный `contract.ts`. Вручную его не редактировать.
   Клиент использует `ApiInputs`/`ApiOutputs`, не импортирует серверный runtime/SQL
   и не добавляет приведения типов для сокрытия несовпадения ответа.
4. Фронтендер подключает сценарий и тестовые ответы. Для несовместимого изменения
   выпускать обе стороны вместе или временно сохранять прежний контракт.
5. Проверить гостя, нужную роль, пустой результат, ошибку и повтор запроса,
   если действие сохраняет данные. Платёжные и почтовые проверки требуют
   отдельного разрешённого окружения.

Локальный контракт создаёт бэкендер, а право на данные всегда проверяет сервер.
Приватные файлы не становятся публичными ради удобства клиентской интеграции.

## Команды из корня

| Задача | Команда |
| --- | --- |
| Только API | `pnpm dev:server` |
| Только Next.js | `pnpm dev:frontend` |
| Оба приложения | `pnpm dev` |
| Собрать API в `dist/` | `pnpm build` |
| Собрать Next в `apps/frontend/.next/` | `pnpm build:frontend` |
| Линтер бэкенда | `pnpm lint:backend` |
| Линтер фронтенда | `pnpm --filter @daryadarcy/frontend lint` |
| Типы обоих приложений | `pnpm check` |
| Контракт и границы импортов | `pnpm check:api` и `pnpm check:boundaries` |
| Локальные unit-тесты | `pnpm exec vitest run --project unit` |
| Общие регрессионные сценарии | `pnpm verify` |
| Браузерные сценарии | `pnpm test:frontend` |

Тесты запускать без рабочих S3/SMTP/платёжных ключей. В частности,
`tests/regression/s3-connection.test.ts` при явных S3-ключах выполняет внешнюю
запись. SQL-suite запускается отдельно на разрешённой одноразовой MySQL по
[инструкции](workflow.md#интеграционные-тесты-бд). Unit-прогон не заменяет SQL
и проверку настоящего браузера.

Перед PR проверить типы, линтер своей стороны, релевантные тесты, API и границы.
Если менялись ссылки или перемещались файлы: `pnpm check:docs`,
`pnpm docs:files`, `pnpm check:files`. Для общей приёмки используются
существующие [GitHub CI](../../.github/workflows/ci.yml) и
[правила репозитория](workflow.md); наличие workflow не является отчётом
об успешном удалённом запуске.

## Назначение ревьюеров в GitHub

GitHub поддерживает `CODEOWNERS`: можно автоматически направлять изменения
бэка бэкендеру, фронта фронтендеру, общих файлов обоим. Для этого нужны
настоящие GitHub-логины с доступом write. Подтверждённого логина фронтендера
в текущей задаче нет, поэтому фиктивные владельцы не добавлены.
Обязательное одобрение включается отдельной защитой ветки; простой файл
`CODEOWNERS` сам по себе не запрещает push или merge.

## На чём основана схема

Использованы встроенные [workspaces pnpm](https://pnpm.io/workspaces),
[выбор пакета через filter](https://pnpm.io/filtering) и
[правила CODEOWNERS GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
Новые сервисы и инструменты управления монорепозиторием для этой схемы не нужны.
