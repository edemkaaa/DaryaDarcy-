# Как читать код Daryadarcy

## С чего начать

[Справочник файлов](file-guide/index.md) перечисляет все пути из Git-инвентаря.
Для исходников он показывает объявления функций, классов, методов и схем,
а для миграций — именованные операции DDL. Номера строк и комментарии берутся
из файлов автоматически: `pnpm docs:files`. После изменений — `pnpm check:files`.
Файл, попавший в справочник, не считается автоматически проверенным на ошибки.

Комментарии написаны по назначению модулей и смысловым этапам. Массовое размещение
пояснений назначения выполнялось по явным картам модулей; сложные сценарии дополнены
адресными комментариями. Это не построчный ручной аудит всех файлов репозитория.
Для типов и простых адаптеров достаточно роли модуля и имени контракта; подробный
разбор нужен там, где есть владение состоянием, побочный эффект или отказ.

## Путь пользовательского действия

```text
Экран frontend
  → domain/shared API-клиент и журнал операции
  → tRPC-роутер или REST-контроллер
  → проверка входа и текущей сессии
  → доменный сервис
  → SQL-репозиторий или транзакция записи
  → результат / квитанция / статус
  → обновление состояния экрана
```

Отдельное изменение может проходить через несколько файлов. Роутер описывает
форму запроса и доступ к процедуре. Сервис определяет сценарий. Репозиторий
читает или меняет данные. Старая обёртка `db.ts` сохранена для совместимых callers
и не должна становиться местом новых несвязанных правил.

## Бэкенд

| Что нужно понять | Где читать | Главное правило |
| --- | --- | --- |
| Запуск и остановка | `_core/index.ts`, `_core/application.ts`, `_core/api-shutdown.ts` | Импорт композиции не запускает HTTP и интервалы; executable владеет жизненным циклом |
| REST и tRPC | `_core/trpc.service.ts`, `routers.ts`, доменные роутеры | Общая политика ошибок и сессии сохраняется на обеих границах |
| Вход и пароль | `identity/`, `_core/sdk.ts` | Проверка текущего пользователя не ограничивается подписью JWT |
| Оплата и доступ | `billing/` | Возврат браузера не подтверждает платёж; право доступа связано с сохранёнными свидетельствами |
| Редакторы | `content/post-*`, `content/article-*` | Ревизия защищает от потери параллельной правки, ключ операции — от повторного создания |
| Фото и вложения | `content/private-*`, `media/` | Загрузить объект и привязать его к материалу — разные этапы |
| Списки | `content/*repository.ts`, `*page.ts` | Проверка доступа и фильтр идут до выдачи; числовые старые cursor остаются offset |
| Фоновые задачи | `workers/`, `database/coordination.ts` | Несколько процессов нуждаются в общей координации и согласованном бюджете БД |
| Админка | `admin/`, доменные сервисы | Состояние сессии и цели проверяется непосредственно перед записью |
| Почтовое отделение | `pen-pals/` | Участие в паре, актуальность анкет и срок заявки проверяются до изменения |

Пути в таблице указаны относительно `apps/backend/src`.
[Назначение каждого backend-файла](file-guide/backend.md).

## Транзакции, повторы и неизвестный результат

Транзакция связывает изменения в MySQL. Она не делает SMTP, VK или платёжного
провайдера частью SQL-коммита. Поэтому результат внешней отправки может остаться
неизвестным: нельзя обещать exactly-once только за счёт lease и записи `sentAt`.

Для создания поста, статьи, комментария и повторяемых административных действий
сохраняются ключ и отпечаток намерения. Если ответ потерян, клиент проверяет статус
либо повторяет исходный ключ в рамках действующего контракта. Новый ключ означает
новое намерение. Лайк и сохранение в форме toggle имеют другую семантику: слепой
повтор способен отменить предыдущее действие.

Сессию, автора и материал повторно проверяют под SQL-блокировкой, когда решение
используется для записи. Порядок блокировок важен для конкурирующих сценариев.
Для чтения поста и его вложений применяется согласованный снимок. Он не обещает
неизменный набор карточек между несколькими offset-страницами.

## Фронтенд

Папка `apps/frontend/src/app` связывает URL с экранами. `features` собирает
пользовательские сценарии. `domain` хранит предметные операции и восстановление,
`shared` — API, навигацию, media и примитивы интерфейса. Конкретные границы
перечислены в [README клиента](../../apps/frontend/README.md).

Особенно важно различать:

- состояние текущего экрана и персональный кэш конкретного аккаунта;
- HTTP-кэш публичной картинки и журнал незавершённой записи;
- отказ авторизации и временную ошибку проверки сессии;
- просмотр карточки и серверное право скачать её закрытый файл;
- draft ввода, зафиксированное намерение и уже сохранённый материал.

При смене аккаунта старый ответ не должен попадать в новый персональный scope.
При потере ответа сохраняются ввод и ключ операции. Медиакомпоненты освобождают
ресурсы при уходе со страницы и восстанавливают разрешённое воспроизведение при
возврате. Клиентская проверка не заменяет серверную.

## База данных

`packages/database/src/schema.ts` описывает актуальную модель и ограничения.
Рядом находятся типы строк и описание навигационных связей Drizzle. SQL-миграции
и их метаданные хранят историю. Изменение комментария в применённой миграции
тоже меняет хеш файла, поэтому пояснения истории находятся в справочнике,
а не дописываются в старый SQL.

`users.contactPhone` — сообщённый номер для связи без подтверждения; это не
равнозначная замена прежнего `users.phone` и не новый способ входа. Роли,
`sessionVersion` и ревизии решают разные задачи: права, отзыв сессий и конфликт
изменений. Их нельзя заменять одним общим флагом.

Список групп таблиц и правила применения — в
[описании БД](../architecture/database.md), полный состав — в
[карте shared/database](file-guide/shared-database.md).

## Проверки и инструменты

Unit-тесты проверяют чистые правила и ограниченные стенды. SQL-тесты используют
только разрешённую одноразовую БД `backend_test`. Внешние S3, Docker, браузерные
и device-сценарии имеют отдельные условия запуска. `skipped` не означает `passed`.
Неполный локальный прогон не даёт допуска к production.

Рабочие команды описаны в [workflow](workflow.md). `tooling/data` и
`tooling/operations` могут менять БД, файлы или отправлять данные, поэтому их
не запускают ради знакомства с проектом. Legacy-папки, исходные требования,
старые дампы и отчёты не удаляются по одному отсутствию import.

## Документация и уборка

Действующие README объясняют запуск и границы. `docs/architecture` объясняет
устройство, ADR сохраняют решения. Датированные аудиты являются снимками своих
проверок. Рабочие задачи остаются в `tasks`, а не размножаются в справочнике.

Убирать можно доказанно воспроизводимые результаты сборки, отчёты и кэши этого
проекта. Исходники, ресурсы, SQL, фикстуры и конфигурации требуют проверки импортов,
CLI, тестов, документации и динамических путей. Результат этого прохода описан
в [отчёте документирования](source-explanation-2026-11-11.md).
