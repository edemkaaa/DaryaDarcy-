30 октября 2026. Локальная реализация BE-01–BE-04 из аудита сетевого обмена.
Фронтенд, рабочая БД, S3, сервер и платёжные режимы не менялись. Пуша и выкладки нет.

**Последующий выпуск 30 октября:** код `54ea67d8` опубликован, 0048/0049
применены после бэкапа и репетиции. Генерируемый frontend contract синхронизирован,
`check:api` проходит. Компоненты фронта прежние, FE-03/FE-04 и совместная приёмка
остаются; strict выключен. [Точные результаты выпуска](../operations/admin-recovery-release-2026-10-30.md).
Остальной текст фиксирует исходный локальный этап и переходный контракт.

## Что подключить фронтендеру

1. Для нового продления или письма до отправки сохранить UUID v4, ID вошедшего
   администратора, действие, целевой userId и параметры. Если сохранение не удалось,
   запрос не отправлять. Перезагрузка и потеря ответа не создают новый ключ.
2. Передавать `idempotencyKey` в `admin.grantClub` или в JSON тела
   `POST /api/admin/access-email/resend`. Ключ не является паролем или правом доступа.
3. Восстанавливать результат через `admin.actionStatus({ idempotencyKey })`.
   На чужом аккаунте намерение не применять; между вкладками использовать одно
   сохранённое намерение, а не создавать независимые ключи при восстановлении.
4. Перед редактированием VK прочитать `admin.vkVideoDetail({ id })`, сохранить
   `editRevision` вместе с черновиком и передать её как `expectedRevision` при update.
   При 409 сохранить ввод, показать актуальную версию и предложить явную сверку.
   Автоматически заменять исходную ревизию и снова сохранять нельзя.

Готов [patch сгенерированного API-контракта](admin-actions-vk-api-2026-10-30.patch).
Он получен штатным генератором, а не ручным редактированием типов. Применить
его либо выполнить `pnpm api:contract` при интеграции. Проверены типы обоих
новых методов и полей без приведений. Текущий frontend contract намеренно
не изменён: обычный `check:api` до синхронизации будет требовать обновление.

## Продление

```ts
admin.grantClub.mutate({ userId: 123, idempotencyKey: savedUuid });
// { ok: true, expiresAt: "2026-12-01T12:00:00.000Z" }
```

Добавляются прежние 31 день от max(сейчас, текущий срок). Для одного ключа
и параметров, включая конкурентные повторы, создаётся одно продление.
Повтор возвращает исходный зафиксированный срок, даже если позднее были
другие продления. Это результат конкретного действия, а не текущая подписка.
Новое намеренное продление требует нового ключа.

## Повторное письмо

```json
{ "userId": 123, "idempotencyKey": "11111111-1111-4111-8111-111111111111" }
```

Успех сохраняет прежние HTTP 202 и `{ "queued": true }`. Повтор того же
намерения не создаёт новую очередь, в том числе после отправки исходного письма.
Новое письмо требует нового ключа и проходит прежний лимит 20 запросов в час
на сотрудника. Повторы также учитываются в лимите; status не расходует лимит
отправки. 202 подтверждает постановку в очередь, не доставку получателю.

## Чтение результата

`admin.actionStatus` — tRPC query, доступен действующему admin/moderator.
Для результата продления нужна роль admin; письмо доступно admin/moderator.
Выбираются только записи вошедшего автора: ключ другого сотрудника возвращает
`notFound`, без сведений об аккаунте, сроках или письме.

Возможные ответы:

```ts
{ state: "notFound" }
{ state: "succeeded", kind: "grantClub", userId: 123, expiresAt: "...ISO..." }
{ state: "succeeded", kind: "resendAccessEmail", userId: 123, queued: true }
{ state: "rejected", kind: "grantClub", userId: 123, code: "NOT_FOUND" }
{ state: "rejected", kind: "resendAccessEmail", userId: 123, code: "CONFLICT" }
```

`notFound` не означает, что первый запрос отменён или уже не завершится.
Безопасно повторять только тот же ключ с теми же параметрами. Состояния pending
нет: эффект и конечный результат фиксируются в одной транзакции. Чтение может
дождаться её завершения; оно не выполняет действие заново.

Бизнес-отказ сохраняется. Изменение состояния получателя не превращает повтор
отклонённого намерения в новое действие. Новое осознанное действие — новый ключ.
Недействительная сессия, утрата прав, ограничение частоты, некорректный ввод и
инфраструктурный сбой не записываются как успешное выполнение.
Ключ с другими параметрами или видом действия у того же автора даёт 409.

## Хранение и транзакции

Миграция `0048_admin_action_operations` добавляет технические квитанции с PK
`(actorUserId, operationKey)`: вид действия, target ID, хеш параметров, минимальный
результат и время. Почта, номер телефона, токены и тело письма туда не копируются.
Срок автоматического истечения не введён, ключи не переиспользуются; автоочистки
нет. Удалять квитанции ради повторного использования ключей нельзя: это снимет
защиту от позднего повтора. При будущей политике очистки нужны сохраняемые
ограничители повторов и отдельное согласование.

В транзакции блокируются автор и получатель в порядке ID, затем проверяются
актуальные identity/sessionVersion/роль/блокировка. Результат записывается вместе
с продлением либо outbox/audit. Сбой записи эффекта или квитанции откатывает всё.
Чтение и повтор снова проверяют права; старый успех их не заменяет.

## VK

Миграция `0049_video_edit_revision` добавляет `videos.editRevision`, начальное
значение 0. `admin.vkVideoDetail` возвращает только поля редактора:
id/title/embedUrl/access/published/thumbnailUrl/editRevision. Нет записи или это
другой provider — 404. Проверяются актуальные права и флаг VK-каталога.

```ts
const detail = await admin.vkVideoDetail.query({ id: 61 });
await admin.upsertVkVideo.mutate({
  id: detail.id,
  expectedRevision: detail.editRevision,
  title,
  embedUrl,
  access,
  published,
  thumbnailUrl,
});
// Как прежде: { id: 61 }. После сохранения перечитать detail для следующего редактирования.
```

Ожидаемая ревизия — целое неотрицательное число. При совпадении update увеличивает
счётчик один раз под блокировкой строки; при несовпадении 409 без изменения данных.
Внутренний updateVideo также увеличивает счётчик. Публичная legacy-проекция не
расширяется внутренней ревизией. Создание по VK-источнику сохраняет прежнюю
уникальность и повторяемость; без id ревизия для создания не нужна.

## Переход и выпуск

До интеграции FE-03 старые вызовы без ключа остаются прежними отдельными действиями:
сервер не может угадать, новый это запрос или повтор. Полная защита требует ключа.
VK с переданной ревизией проверяется всегда. Отсутствие ревизии пока совместимо
с прежним клиентом; при `CONTENT_EDIT_REVISIONS_REQUIRED=true` update без неё
получит 412. Не включать строгий режим до совместной приёмки всех редакторов.

Порядок отдельного выпуска: проверить историю и бэкап, применить добавочные
0048/0049, выпустить API, интегрировать frontend contract/FE-03/FE-04, проверить
потерю ответа/две вкладки/смену аккаунта/конкурентную правку. Лишь после этого
отдельно согласовать обязательные ключи и strict. Эти действия сейчас не выполнены.

## Локальные проверки

Воспроизведение до реализации: 8/8 admin-action сценариев отказали; VK — 4 отказа
из 8. После реализации объединённые шесть SQL/HTTP suites дали 112 passed.
Проверены конкурентные повторы, потерянный ответ с последующим status, другой
автор, смена параметров, сохранённый отказ, потеря прав, rate limit, отправленное
письмо без новой очереди, сбой записи квитанции/эффекта с откатом и чистым повтором.
Для VK проверены два администратора, корректный update, stale/конкурентный конфликт,
legacy/strict переход, неверная ревизия и прежняя уникальность создания.

Реальные письма, платежи, SMS, VK/S3-запросы и рабочие данные не использовались.
Итог: полный SQL-прогон 1547 passed / 299 opt-in skipped; полный unit —
3677 passed / 78 skipped. Дополнительно 15 admin-action проверок прошли,
включая два настоящих обрыва ответа через локальный relay после commit.
Все 50 миграций применились с нуля, повторная проверка истории без pending;
подтверждены составной PK actor/key и default editRevision=0. На свежей схеме
ещё 9 native HTTP checks прошли. Типы, две backend-сборки, границы модулей
и документация приняты. Контракт 107 проверен генератором и TypeScript отдельно.
Одноразовый контейнер и свой symlink dependencies удалены после проверки;
рабочие ресурсы не использовались. Канонический frontend contract до интеграции остаётся прежним.

Финальное ревью отдельно воспроизвело несовпадение миллисекунд расчётного срока
и SQL TIMESTAMP при продлении истёкшей подписки. Квитанция теперь читает срок
из записанного платежа. После этой последней правки шесть профильных suites
повторены: 115 passed; root types и обе сборки повторены. Полный SQL 1547 и unit
3677 выше относятся к предыдущему общему прогону; не выдавать его за повтор
всех тяжёлых проверок после последней правки точности.
