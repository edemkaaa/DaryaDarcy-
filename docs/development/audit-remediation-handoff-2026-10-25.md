## FE01: явный отказ не должен зависеть от существования родителя

Точки: use-private-comment-files.ts `clear/discard`, club-comments.tsx
`readComments/refreshCommentRow`. Сейчас `read(parentId)` выполняется раньше
`journal.clear(current)`; отсутствие родителя прерывает очистку.

Разделить явный discard и post-save cleanup так, чтобы явный отказ очищал именно
захваченную операцию независимо от результата обновления списка. Сохранить
account/post scope, task.assertCurrent и compare-current/revision проверку журнала.
Не очищать чужую/изменённую операцию; не повторять запись при отказе. Обновление
списка может показать отдельную ошибку, но не должно восстанавливать уже
осознанно отменённый локальный intent. Уже созданный на сервере комментарий
такой отказ не удаляет — сохранить соответствующее предупреждение.

Регрессия: lost-ACK reply → родитель исчез → явный discard → форма разблокирована,
старый intent не отправлен повторно; затем новый комментарий. Дополнительно
смена аккаунта и конкурентная замена журнала во время discard. Обычный reload/
повтор при существующем родителе не заменяет эти проверки.

## FE02: неизвестные capabilities не равны подтверждённому false

Точки: shared/api/capabilities.ts `getAppCapabilities` и sendPrivate в
club-comments.tsx. Сейчас null/array/неправильные типы превращаются в false,
после чего новый текст уходит через sendLegacy без idempotencyKey.

На write boundary некорректный/неизвестный ответ должен останавливать отправку
с понятной ошибкой, сохраняя draft. UI может показывать недоступность загрузки,
но это не разрешение на unkeyed write. Отдельно сохранить совместимость с
корректным явным privateContentUploads=false: это другой, подтверждённый режим.
Сохранённый keyed intent никогда не понижать до legacy и не менять его payload/
ключ автоматически. Новая независимая capability для текста пока не вводится.

Регрессии: HTTP200 с null/array/отсутствующим обязательным признаком/строкой
вместо boolean; HTTP-ошибка; отмена/смена аккаунта при чтении. Во всех неизвестных
режимах0addComment writes и draft сохранён. Явный корректный false проверяется
отдельно, true использует устойчивый ключ. Серверный отказ после отправки не
превращать в новый ключ или автоматический повтор.

## B07: canBlockAuthor в жалобах — локально реализовано

moderation.listCommentReports добавляет boolean `canBlockAuthor` для текущего
actor. Не выводить кнопку блокировки при false; отсутствие поля на старом
сервере также трактовать как отсутствие разрешённого действия. Не угадывать
роль по имени/ID, не менять дизайн и не раскрывать authorRole клиенту.

false: self, неактивный/удаляемый actor, отсутствующий автор, уже заблокированный
автор, moderator→moderator/admin. Admin→другой staff сохраняет нынешнюю серверную
политику. Поле — только UI hint: block/unblock вновь проверяют актуальные роли
под row locks. При изменении роли после чтения обработать403 без ложного успеха.

RED13отсутствующих hints → GREEN90unit/native HTTP checks; SQL-роль/конкуренция
на одноразовой MySQL тоже проверены: смена роли после чтения запрещает запись,
self/blocked/missing author возвращают false. Старый API не удаляется, новых прав не выдаётся.

## B02: серверные рубрики и теги Клуба

Новый `club.listByCategory` принимает `{category?, tag?, limit?, cursor?}`.
category: `podborki | community | exclusive | life`; limit 1–50 (20 по умолчанию);
cursor — прежний числовой offset или null. Ответ прежний: `{posts, nextCursor}`.
Фильтрация **до LIMIT** на сервере; неизвестная рубрика/поле даёт 400.

В `features/club/club-subscribed.tsx` заменить загрузку всего архива через
`club.list` на страницы выбранной рубрики/тега. Ключ запроса должен включать
account, category и tag; при смене любого из них сбрасывать курсор. Не догружать
автоматически весь архив, чтобы найти редкий тег. Пустая страница — нормальный
результат. Новую процедуру не подменять старой при 404: старый сервер не умеет
эти фильтры, иначе клиент снова покажет неполный/неправильный результат.

Приоритеты совпадают с shared `primaryClubTab`: явная рубрика важнее
fallback-тегов, при нескольких совпадениях побеждает первая в SECTION_ORDER.
Tag поддерживает существующие slug/русские подписи доски. Новые рубрики,
дизайн и семантика «все материалы» не добавляются. Прежний offset-контракт не
обещает snapshot-стабильность при одновременной перестановке постов.

## B03: ограниченные отметки и статьи

`feed.interactionsForPosts({postIds})` возвращает `{likedIds, savedIds}` только
для переданных опубликованных доступных постов текущего пользователя. До 50
ID в одном запросе; пустой массив допустим, невалидные/лишние ID дают 400.
Дубли входа и исторические дубли отметок не размножают результат. Приватные
посты после отзыва подписки не возвращаются.

В `domain/post/use-post-interactions.ts` запрашивать ID загруженных карточек,
а в detail — текущий ID, не всю историю аккаунта. Account и набор ID входят
в query key. После toggle обновить/инвалидировать соответствующие наборы;
при смене аккаунта отменить старые запросы и не переносить optimistic state.

`admin.articlesPage({limit?, cursor?, direction?:"forward"})`:
`{items,nextCursor}`. Limit 1–50 (20 по умолчанию), cursor opaque string/null.
Карточки содержат id/title/coverUrl/access/published/sortOrder/createdAt/updatedAt,
**без sections**. Порядок: sortOrder ASC, createdAt DESC, id DESC.
`admin.articleDetail({id})` возвращает полную статью, включая черновик, либо null.
Оба метода только admin; null не трактовать как пустой редактируемый объект.

В `features/admin/articles-admin.tsx` перейти на страницы карточек и отдельное
чтение выбранной статьи. После create/edit/delete сбрасывать страницы/курсор,
обновлять detail, публичные статьи, анонсы и `admin.postCounts`. Последний пункт
закрывает ранее найденные устаревшие счётчики после операций со статьями.
Не сохранять статью на основании урезанной карточки и не собирать все полные
тексты при открытии раздела. Перестановка sortOrder требует reload страницы.

### Почему legacy пока оставлены

Инвентаризация 25 октября подтверждает живые потребители:

- `feed.userInteractions`: текущий `domain/post/use-post-interactions.ts` и
  legacy feed/club/post screens.
- `admin.articles`: текущий articles-admin (list, refresh, cache/invalidation),
  legacy articles-admin и browser-test перехватчики старого метода.
- `admin.payments`: текущий admin-screen и legacy admin index.
- `club.list`: текущий club-subscribed и invalidation в post/comment/article flows.

Старые методы не удалены и не обрезаны. Их retirement — отдельный шаг после
перехода всех поддерживаемых consumers и согласования legacy-клиента. Перенос
только одного useQuery без его cache writes, invalidations и тестов недостаточен.

## B06: история оплат старше первых 50

`admin.paymentsPage({limit?,cursor?,direction?:"forward"})` возвращает
`{items,nextCursor}`; limit 1–50 (20 по умолчанию). Порядок createdAt DESC,
id DESC, курсор opaque и привязан к текущему администратору. Не вычислять его
из ID и не переиспользовать после смены аккаунта. null означает конец, не ошибку.
При обновлении списка начинать с первой страницы. Новые оплаты, появившиеся
перед курсором, видны после обновления, а не вставляются задним числом в обход.

В admin-screen заменить legacy last-50 запрос на страницу с догрузкой, сохранять
действующие колонки/дизайн. Проверить 0/20/51/65 записей, одинаковые даты,
удалённую граничную строку и вставку новой записи между страницами. Backend
не меняет Prodamus, статусы расчётов, подписки или выдачу доступа.

## B05: публичные аватары и обложки с восстановлением

Принято пользователем: новый additive контракт, **без автоочистки**. Миграция
0043 должна быть установлена до перехода клиента; новые методы используют S3,
без fallback на другое хранилище. Старые uploadAvatar/uploadPhoto сохранены.

- `profile.uploadAvatarWithReceipt`: прежние base64/filename/mimeType плюс
  `idempotencyKey` (16–128 символов `[A-Za-z0-9._:-]`).
- `profile.avatarUploadStatus({idempotencyKey})` — статус своей операции.
- `admin.uploadPublicCover`: такие же поля и обязательное `purpose:"publicCover"`.
- `admin.publicCoverUploadStatus({idempotencyKey})` — статус своей обложки.

Ответ — `{state:"missing"|"pending"}` или
`{state:"ready",url,avatarApplied,isCurrent}`. Для обложки avatarApplied=false,
isCurrent=null: загрузка не привязывает её к статье/сезону автоматически.
Для аватара `avatarApplied` фиксирует результат первоначального завершения,
`isCurrent` говорит, стоит ли этот URL сейчас. При false нельзя переустанавливать
старый аватар клиентским profile.update. Прочитать актуальный профиль.

До отправки сохранить account-scoped intent и один ключ. Потеря ответа →
сначала status; ready использовать без повторного upload. Pending/missing →
повтор того же файла с тем же ключом, не создавать новый ключ автоматически.
409 означает несовпадение файла/недоступную старую операцию, а не повод для
бесконечного retry. 503 сохраняет неопределённый результат и прежний intent.
При потерянном локальном файле pending требует повторного выбора того же файла,
а не отправки случайного replacement под прежним ключом. Logout/account switch
не должен отправлять или привязывать intent предыдущего аккаунта.

Сервер хранит intent до PUT, использует неизменяемый собственный object key,
проверяет HEAD/метаданные при повторе и повторно проверяет пользователя перед
привязкой. Запоздалая загрузка не перезаписывает изменившийся аватар. Байты снова
проверяются/перекодируются, EXIF не сохраняется. Таймаут/отказ БД не вызывает
удаления файлов. Нет cron/TTL/DELETE или автоматического удаления старых аватаров
и обложек. Ручная сборка orphan-файлов не включена и не объявлена закрытой.

## B01: серверные слоты клубных иллюстраций — подготовлены, не переключены

Существующая закрытая выдача принимает ещё семь materialKey:
`aesthetic-castlecore`, `aesthetic-cottagecore`, `aesthetic-darkacademia`,
`aesthetic-fairycore`, `aesthetic-goblincore`, `aesthetic-lightacademia`,
`aesthetic-witchcore`. Схема привязок 0041 не меняется.

Список: `/api/library/materials/<materialKey>/files`,
файл: `/api/media/library-files/<materialKey>/<fileKey>`.
Флаги и проверка текущей подписки/ролей прежние; ответы private/no-store.
Registry — visuals.files в `docs/audits/library-source-map-2026-10-20.json`:
ровно 220 WebP. Для `/assets/results/<aesthetic>/<group>/<name>[.lossless].webp`
слот: materialKey=`aesthetic-<aesthetic>`, fileKey=`<group>-<name>`;
group только interiors/moodboards/outfits. Проверено: коллизий нет, на эстетику
не больше 50 файлов. Суффикс .lossless не часть логического fileKey.

Нужны **оба** consumers — Библиотека и клубное дополнение результата теста.
До реального импорта привязок не переключать экран вслепую на пустой список.
Не подменять защищённый ответ публичным asset URL при отказе. После logout/отзыва
доступа убирать клубные фото из состояния и освобождать созданные Blob URL.
Сохранить бесплатное описание результата и `/assets/quiz/houses/**`, «Лошадку»,
публичные обложки; рецепты/Петербург остаются как были.

Сейчас проверены synthetic SQL/API/loopback import, replay, доступ admin/member,
гостевой отказ и отзыв прежних URL. Реальные иллюстрации/S3/публичные asset-копии
не менялись. Закрытие точного registry оригиналов, responsive-вариантов и
build-asset копий возможно только совместным выпуском после проверки обоих
consumers. До этого замечание о публичных клубных копиях остаётся открытым.

## Что не делать ради закрытия аудита

Не обрезать legacy arrays до первыхN записей молча; не удалять публичные
иллюстрации до готовности protected bindings и обоих consumers; не закрывать
бесплатный тест/домики/«Лошадку»/публичные обложки. Рецепты/Петербург не переносить
без согласованных исходников. Не объявлять HTTP200 iframe проверкой VK playback.
Действующий план и результаты SQL/S3 acceptance уточняются по каждому срезу.
