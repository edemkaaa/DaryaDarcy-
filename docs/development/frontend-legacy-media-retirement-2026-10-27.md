# Фронтендеру: закрытие старой выдачи клубных изображений

27 октября 2026. Только необходимая связка с подготовленным backend-переносом.
Фронт и дизайн в этом шаге не менялись. Массовые рабочие привязки ещё не изменены.

## Что готово на backend

Операторский перенос одной привязки с сохранением исходных байтов, повтором
после потери ответа и атомарной проверкой прежней ссылки. Новых HTTP/tRPC
процедур и изменений сгенерированного API-контракта нет.

Фото/блоки статей получают существующий URL защищённого content file API;
медиавложения постов — существующий private media URL с прежним media ID.
Нужно использовать текущий загрузчик закрытых файлов с авторизацией, а не
прямой S3 URL или публичный Next image optimizer. JPEG, PNG и анимированный GIF
отдаются inline с правильным MIME; GIF нельзя превращать в неподвижное превью
в месте, где пользователь должен видеть анимацию. Видео поддерживает Range.

Данные для 388 привязок проверены локально; на стенде пока остаются старые
ссылки. Файлы не потеряны и не должны заменяться заглушками на этапе ожидания.

## Обязательная серверная правка перед закрытием старых адресов

Старые клубные изображения могут остаться в кеше `/_next/image` после смены
ссылок в БД и запрета S3. Удаление исходного публичного URL из JSX проблему
не закрывает. Нужен серверный guard, выполняемый **до выдачи кеша optimizer**.

1. Получать список отзываемых ключей только из закрытой серверной конфигурации.
   Он не должен попадать в public/, клиентский bundle, API capabilities, HTML
   или публичный JSON. Путь/версию набора согласовать с оператором выпуска.
2. Безопасно разбирать параметр исходника optimizer и сопоставлять нормализованные
   host/порт/bucket/декодированный ключ S3. Учитывать Unicode, percent-encoding
   и query-варианты одного объекта; не обходить запрет добавлением параметров.
   Некорректные URL и неоднозначное кодирование отклонять; произвольный fetch
   для проверки списка не нужен.
3. Отзывать выбранные старые адреса для всех посетителей, включая админа и
   участника: их новый доступ идёт через защищённый API. Ответ отказа — без
   платных байтов и с no-store. Guard нужен и при уже прогретом кеше.
4. На выпуске адресно инвалидировать производные выбранных старых ключей.
   Не чистить все публичные изображения или закрытые пользовательские blobs.
5. Не включать guard до готовности новых привязок и проверки изображений в
   Ленте/Клубе/детальном посте/статье/«Сохранённом» и админке.

На текущем снимке закрываются 386 исходников. **Две общие публичные обложки**
статей 5/6 сохраняют старые источники: не включать их в запрет. Фото постов
937/942 с теми же исходниками перейдут на отдельные защищённые копии.
49 посторонних объектов старой папки также не включены в отзыв.
Бесплатные «Лошадка»/тест, открытые обложки и VK-плееры не менять.

## Проверка перед приёмкой

- Прогреть старый optimizer URL, затем включить guard в тестовом окружении:
  гость, участник и админ не получают платные байты по старому адресу.
- Повторить с query-параметрами, эквивалентным кодированием, Unicode и портом443;
  изменение width/quality и попадание в уже готовый кеш не обходят guard.
- Новые фото/GIF доступны через защищённую выдачу с корректными размерами,
  прозрачностью и анимацией. Нет повторного сжатия исходников при переносе.
- Гость/обычный аккаунт/отзыв подписки не получают закрытые файлы. При смене
  аккаунта прежние blobs и персональный кеш сбрасываются текущим механизмом.
- Обе публичные обложки, бесплатные материалы и все VK-карточки работают;
  возврат на экраны не создаёт бесконечной загрузки или фонового polling.
