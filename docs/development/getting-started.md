# Локальный запуск и команды Daryadarcy

[Карта документации](../README.md) · [Рабочий процесс](workflow.md) · [README проекта](../../README.md).

Веб-приложение бренда Darya Darcy; прежний нативный Expo-клиент сохранён отдельно. В проект входят публичная лента, видео, закрытый клуб по подписке, библиотека, магазин и интерактивные разделы.

- Домен проекта: [daryadarcy.com](https://daryadarcy.com); доступность и адрес нового развёртывания проверяются отдельно
- Основной веб-клиент: Next.js App Router (`apps/frontend`)
- API: NestJS + tRPC с Express-адаптером (`apps/backend`)
- Репозиторий: модульный монолит на pnpm workspaces

## Быстрый старт

### 1. Требования

- Node.js 22 (версия CI и рекомендуемая версия разработки)
- pnpm 9
- MySQL 8 с кодировкой `utf8mb4`

Для обычной разработки доступ к production, VPS и S3 не нужен.

Для работы API нужна локальная БД с подготовленной схемой. Команда dev её
не создаёт. Подготовка ограниченной dev-базы описана ниже; воспроизводимые
SQL-проверки используют отдельную backend_test по [рабочему процессу](workflow.md).
Fresh-профиль тестовой базы не является способом ремонта существующей рабочей истории.

### 2. Установка

```bash
pnpm install --frozen-lockfile --ignore-scripts
cp .env.example .env
cp apps/frontend/.env.example apps/frontend/.env.local
```

В `.env` для локального запуска достаточно указать:

```dotenv
DATABASE_URL=mysql://user:password@127.0.0.1:3306/daryadarcy?charset=utf8mb4
JWT_SECRET=change-me-local-dev-only
PUBLIC_APP_URL=http://localhost:8081
HOST=127.0.0.1
PORT=3000
```

В apps/frontend/.env.local укажите API_PROXY_TARGET=http://127.0.0.1:3000,
NEXT_PUBLIC_API_BASE_URL оставьте пустым. Это включает same-origin прокси /api
и /media; EXPO_PUBLIC_API_BASE_URL клиент Next.js не читает. Не меняйте CORS для
обычного локального запуска. Для production build/start нужен один согласованный
API_PROXY_TARGET, публичные переменные встраиваются при сборке.

Для отдельной пустой **локальной dev-базы** daryadarcy_dev на 127.0.0.1:3307
можно использовать pnpm db:dev:prepare с соответствующим DATABASE_URL. Скрипт
отказывается работать с другой БД или в production, создаёт схему только на
пустой dev-базе и добавляет тестовые admin/member/reader@daryadarcy.test.
Пароль по умолчанию DarcyDev2026! предназначен только для этой изолированной
базы; DEV_ADMIN_PASSWORD задаёт другой пароль новых тестовых аккаунтов.
Это не маршрут миграции существующей рабочей базы.

Полный список параметров и пояснения находятся в [`.env.example`](../../.env.example). Не копируйте production-секреты в локальный `.env` и никогда не добавляйте `.env` в Git.

Для регистрации и писем доступа также нужен `AUTH_LINK_ENCRYPTION_KEY` — случайные
32 байта в base64 (команда генерации указана в `.env.example`). Без него создание
аккаунта/письма откатывается. Пустые SMTP-параметры не подтверждают доставку.

Регистрация проходит через письмо: `POST /api/auth/register` принимает email, имя
и актуальную версию явно выбранного согласия, возвращает 202 с инструкцией, без
сессии и пароля. Пользователь устанавливает пароль по одноразовой ссылке и затем
входит. Старые веб/API/native-клиенты с мгновенным входом после регистрации нужно
обновлять согласованно. Веб использует HttpOnly cookie, native — SecureStore;
для веба API должен быть same-site или находиться за общим reverse proxy.

### 3. Запуск

```bash
pnpm dev
```

Команда одновременно запускает:

- основной web-клиент — [http://localhost:8081](http://localhost:8081);
- API — [http://localhost:3000](http://localhost:3000);
- проверку API — [http://localhost:3000/api/health](http://localhost:3000/api/health);
- tRPC — `http://localhost:3000/api/trpc`.

Если нужна только одна часть:

```bash
pnpm dev:frontend # основной Next.js-клиент
pnpm dev:server   # только API
pnpm dev:web:vite # старый Vite-клиент, не production-фронтенд
```

## Структура проекта

```text
apps/
  frontend/          Основной веб-клиент Next.js
  backend/           NestJS + tRPC API с Express-адаптером
  legacy-web/        Старый Vite-клиент, сохранён для совместимости
  legacy-expo/       Прежний Expo-клиент, исключён из workspace

packages/
  shared/            Общие контракты и платформо-независимые функции
  database/          Drizzle-схема, связи и SQL-миграции

infrastructure/
  deploy/            Docker/Compose/Nginx; прежние PM2-помощники отмечены отдельно

tooling/
  scripts/           Проверки и сборка
  assets/            Подготовка визуальных ресурсов
  data/              Импорты и преобразование данных
  operations/        Деплой, резервирование и обслуживание
  legacy/            Прежние миграторы и операционные помощники

docs/                Техническая документация и материалы аудита
  decisions/         Архитектурные решения (ADR)

tests/               Дополнительные тестовые сценарии
tests/regression/    Общие регрессионные проверки Vitest
tasks/               План дальнейшего рефакторинга
```

### Границы модулей

- `frontend` использует общие контракты из `packages/shared`; runtime-код API и БД запрещён.
  Основной клиент использует сгенерированный type-only tRPC-контракт
  (pnpm api:contract / pnpm check:api); серверный runtime не попадает в бандл.
- `backend` отвечает за HTTP, tRPC, авторизацию и бизнес-логику; он может использовать `shared` и `database`.
- `database` владеет схемой и миграциями, но не зависит от приложений.
- `infrastructure` и `tooling` не содержат пользовательский интерфейс или бизнес-логику.

Границы проверяются `pnpm check:boundaries` по синтаксическому дереву TypeScript,
включая re-export, require и dynamic import. `pnpm check` дополнительно проверяет типы.

- `legacy-web` не считается основным клиентом и не должен получать новые функции без отдельного решения.

Подробнее: [ADR-0001 — Modular Monorepo](../decisions/0001-modular-monorepo.md).

### Куда вносить изменения

| Задача                                 | Папка                          |
| -------------------------------------- | ------------------------------ |
| Экран или маршрут основного приложения | `apps/frontend/src/app`        |
| Предметный экран или сценарий          | `apps/frontend/src/features`   |
| Общие UI-примитивы                     | `apps/frontend/src/shared/ui`  |
| Клиентская работа с API                | `apps/frontend/src/shared/api` |
| API, авторизация или бизнес-логика     | `apps/backend/src`             |
| Таблица, поле или связь БД             | `packages/database`            |
| Общий тип, контракт или чистая функция | `packages/shared`              |
| Docker/Compose/Nginx и настройка VPS    | `infrastructure/deploy`        |
| Импорт или преобразование данных       | `tooling/data`                 |
| Обработка шрифтов и изображений        | `tooling/assets`               |
| Диагностика, деплой, резервирование    | `tooling/operations`           |
| Проверка или инструмент сборки         | `tooling/scripts`              |

Если задача относится к интерфейсу, начинайте с `apps/frontend`. Папку `apps/legacy-web` меняйте только тогда, когда задача явно касается старого клиента.

Внутри `apps/backend/src`:

| Область                                           | Модуль               |
| ------------------------------------------------- | -------------------- |
| Сборка контрактов tRPC                            | `routers.ts`         |
| HTTP, сессии и общие политики                     | `_core/`             |
| Вход, подтверждение почты, пароль и очередь писем | `identity/`          |
| Профиль, аватар и запрос удаления аккаунта        | `profile/`           |
| Административные операции                         | `admin/`             |
| Приём оплат и подтверждение отмены подписки       | `billing/`           |
| Подписка и обсуждения клуба                       | `club/`              |
| Лента, статьи, репозиторий комментариев           | `content/`           |
| Блокировки и жалобы                               | `moderation/`        |
| Маршруты уведомлений и согласия                   | `notifications/`     |
| Проверка загружаемых фотографий                   | `media/`             |
| Доступность функций и конфигурация запуска        | `launch/`            |
| Старые функции поиска собеседниц и магазина       | `pen-pals/`, `shop/` |

`routers.ts` теперь только собирает доменные маршруты. `db.ts` и административная композиция сохраняют совместимые фасады; внутреннее разделение продолжается
по [плану](../../tasks/todo.md), а не объявлено завершённым. Перенос `shop/` не включает
онлайн-оплату магазина: она остаётся заблокированной до отдельного исправления.

## Основные команды

### Разработка

| Команда             | Что делает                                          |
| ------------------- | --------------------------------------------------- |
| `pnpm dev`          | Запускает API и основной Next.js-клиент             |
| `pnpm dev:server`   | Запускает только API с автоматической перезагрузкой |
| `pnpm dev:frontend` | Запускает основной Next.js-клиент                   |
| `pnpm dev:web:vite` | Запускает старый Vite-клиент                        |

### Проверка качества

| Команда                 | Что делает                                         |
| ----------------------- | -------------------------------------------------- |
| `pnpm test`             | Запускает все Vitest-тесты                         |
| `pnpm verify`           | Запускает выбранные API/UI-регрессии; quiz проверяется `pnpm test:quiz` |
| `pnpm check`            | Проверяет TypeScript без сборки                    |
| `pnpm check:boundaries` | Проверяет разрешённые зависимости между папками    |
| `pnpm check:docs`       | Проверяет локальные ссылки актуальной документации |
| `pnpm check:files`      | Проверяет справочник файлов и блоков               |
| `pnpm lint`             | Проверяет backend и основной Next.js-клиент        |
| `pnpm format`           | Форматирует файлы через Prettier                   |

### Сборка

GitLab и GitHub CI запускают проверки с отдельной MySQL `backend_test`, затем
собирают API и веб. Деплой и рабочие миграции из CI не запускаются. Статус
конкретного запуска проверяется в GitHub Actions/GitLab CI; наличие workflow
не означает, что последняя версия прошла все проверки.

| Команда               | Результат                                 |
| --------------------- | ----------------------------------------- |
| `pnpm build`          | Собирает API в `dist/index.mjs`           |
| `pnpm build:web`      | Собирает Next.js в `apps/frontend/.next`  |
| `pnpm build:web:vite` | Собирает старый Vite-клиент в `web-dist/` |
| `pnpm start`          | Запускает ранее собранный API             |

Перед отправкой изменений рекомендуется выполнить:

```bash
pnpm test
pnpm check
pnpm build
pnpm build:web
```

## База данных

- Схема: [`packages/database/src/schema.ts`](../../packages/database/src/schema.ts)
- Связи: [`packages/database/src/relations.ts`](../../packages/database/src/relations.ts)
- Миграции: [`packages/database/drizzle`](../../packages/database/drizzle)
- Обзор таблиц: [`docs/architecture/database.md`](../architecture/database.md)

Сначала выполните безопасную проверку файлов миграций (без подключения к БД):

```bash
pnpm db:preflight
```

Код 1 означает найденное расхождение, а не применённые изменения. Сейчас три
исторических SQL-файла 0017–0019 отсутствуют в журнале: их нужно сверить с реальной
историей перед выпуском, не добавлять автоматически. Проверка ничего не исправляет.

Для сверки истории конкретной базы задайте отдельно
`MIGRATION_PREFLIGHT_DATABASE_URL` в окружении и используйте ту же команду.
Предпочтительна учётная запись только для чтения: инструмент выполняет лишь
метаданные/SELECT в read-only транзакции, не создаёт даже таблицу журнала.
Без специального флага обычный `DATABASE_URL` и `.env` этой командой не используются. URL, SQL и данные
пользователей в отчёт не попадают; выводятся названия, контрольные суммы,
расхождения и ожидающие миграции. Успех проверки не является разрешением релиза.

`pnpm db:push` **применяет только заранее подготовленные SQL-миграции** после
обязательной `db:preflight --require-database`. Автоматическая генерация удалена:
изменение SQL и журнала нужно подготовить/проверить отдельно в ветке до применения.
Флаг требует явный `DATABASE_URL` из окружения — тот же адрес, который использует
Drizzle. Если задан также `MIGRATION_PREFLIGHT_DATABASE_URL`, строки должны точно
совпадать: проверка другой базы не разрешает применение к этой. `.env` не загружается.
Неверный список миграций останавливает проверку **до** подключения к БД; отсутствующая,
пустая или несогласованная история БД также запрещает применение. Не создавайте
фиктивную историю для тестового baseline. Неизвестные аргументы отклоняются.

Это не команда проверки и не разрешение production-релиза. Не запускать на
рабочей базе до сверки истории/схемы, резервной копии, репетиции на её копии и
согласования выпуска. Проверка и применение не защищены общей блокировкой:
не менять SQL/журнал и не запускать другие миграторы между ними. Прямой вызов
`drizzle-kit migrate` обходит эту защиту и не является штатным маршрутом выпуска.
Старые `migrate-all.mjs` и
`migrate-to-timeweb.mjs` не являются безопасным штатным маршрутом: они обходят
журнал применения и содержат устаревшие пути. Не использовать для этого этапа.

## Конфигурация

Все переменные перечислены в [`.env.example`](../../.env.example) и разделены по назначению:

- БД и авторизация;
- S3 Timeweb;
- Prodamus;
- SMS.ru;
- SMTP;
- Expo Push;
- Admin 2FA;
- параметры деплоя.

S3, платежи, SMS, почта и push-уведомления необязательны для базового локального запуска. Часть интеграционных тестов пропускается без отдельной тестовой MySQL; реальные внешние операции не являются обязательной локальной проверкой.

## Деплой

Актуальные шаблоны контейнеров находятся в `infrastructure/deploy/teamassist`: API,
Next.js, MySQL и Nginx, отдельно профиль нескольких API. Прежние PM2-помощники
сохранены как legacy-инструменты. Новый сервер и его ресурсы требуют отдельной приёмки.

Старый статический deploy:web намеренно останавливается на Next.js. Контейнерные
шаблоны Next.js/Nginx подготовлены отдельно; старые команды ниже не заменяют
проверку нового целевого Compose.

```bash
pnpm deploy:web   # блокируется для нового Next.js-клиента
pnpm deploy:api   # тесты → сборка API → обновление VPS
pnpm smoke        # безопасная HTTP-проверка текущего production
```

> `deploy:web` и `deploy:api` изменяют production. Сценарии требуют отдельной проверки окружения и согласования: сохранены прежние Windows-пути и предположения о сервере. Их перенос не подтверждает готовность выпуска.

Конфигурация деплоя лежит в [`infrastructure/deploy`](../../infrastructure/deploy), сценарии — в [`tooling/operations`](../../tooling/operations). Карта остальных инструментов — [tooling/README.md](../../tooling/README.md).

## Правила безопасной работы

- Не коммитьте `.env`, пароли, токены, приватные ключи и выгрузки пользовательских данных.
- Не меняйте публичные tRPC-процедуры без проверки обратной совместимости.
- Не смешивайте структурный рефакторинг с изменениями оплаты или авторизации в одном коммите.
- После изменения путей проверяйте основной Next.js build и отдельно legacy Vite build.
- Новую общую логику размещайте в `packages/shared`, а работу с БД — в `packages/database` или бэкенде.
