# Daryadarcy: задачи фронтендеру

30 октября 2026. По аудиту запросов и ответов API.

Сохранить текущий дизайн. «Почтовое отделение» в эти работы не входит.
Платёжного провайдера и серверные флаги самостоятельно не переключать.

**Статус бэкенда:** код `54ea67d8` выпущен на стенд с миграциями 0048/0049.
Продления/письма с ключом, статус операции и ревизии VK доступны. Генерируемый
`contract.ts` уже синхронизирован: 107 процедур, `check:api` проходит.
[Результат выпуска и ограничения](../operations/admin-recovery-release-2026-10-30.md).
Фронтендеру ещё нужно подключить поведение из пунктов ниже: наличие типов
не защищает старый вызов без ключа. Строгий режим пока выключен.

## 1. Исправить обработку сетевых ошибок

**Проблема:** если сервер или прокси возвращает HTML вместо JSON, клиент теряет
HTTP-статус. Также теряется `Retry-After`, заданный датой.

**Что сделать:**

- Сохранять HTTP-статус и проверенную задержку повтора до разбора JSON.
- Для не-JSON ответа возвращать типизированную ошибку с исходным статусом.
  Повреждённый ответ 200 считать `invalid-response`, а не успешной записью.
- Для `Retry-After` использовать существующий `parseRetryAfter`: он понимает
  и секунды, и HTTP-дату.
- Сохранить обработку обычных tRPC-ошибок, конфликтов и смешанных пакетов 207.
- Не показывать пользователю HTML, внутренние сообщения или тело ответа прокси.

**Файлы:** `shared/api/request-lifecycle.ts`, `user-facing-errors-link.ts`,
`errors.ts`, `query-client.ts`, `retry-after.ts`.
Пути здесь и ниже указаны относительно `apps/frontend/src`.

**Проверка:** HTML/текст с 401, 403, 413, 429, 502, 503 сохраняет статус;
401 запускает проверку сессии; 503 определяется как временный сбой;
корректный пакет 207 продолжает разбираться. Задержка повтора работает
для секунд и будущей даты, мусор не создаёт бесконечную блокировку.

## 2. Выделить отдельный таймаут для загрузок

**Проблема:** обычный таймаут 15 секунд применяется и к большим файлам.
Документ 32 МиБ после Base64 передаётся примерно 36 секунд уже при скорости
10 Мбит/с, без учёта обработки сервером.

**Что сделать:**

- Выделить файловые tRPC-загрузки в отдельный транспорт, без пакетирования
  с короткими запросами. Начальный таймаут загрузки — 180 секунд; проверить
  его на ограниченной скорости. Обычные запросы оставить с коротким таймаутом.
- Сохранить отмену пользователем и при смене аккаунта.
- При таймауте показывать, что результат загрузки не подтверждён.
  Проверять серверный статус и повторять с прежним ключом операции.
- Сохранить выбранный файл в памяти для безопасного повтора в том же аккаунте.
  Если после перезагрузки файла уже нет, сначала проверить статус операции.
  Большой Base64 не сохранять в localStorage. Новую загрузку с новым ключом
  автоматически не создавать. RAW-загрузку видео не переделывать.

**Файлы:** `shared/api/trpc.ts`, `request-lifecycle.ts`,
`shared/media/private-content-upload.ts`, потребители загрузок.

**Проверка:** разрешённый документ проходит при ограничении отправки до 10 Мбит/с;
зависший запрос завершается по таймауту; потеря ответа не создаёт второй файл.

## 3. Подключить восстановление продлений и повторных писем

**Проблема:** после потери ответа и перезагрузки клиент не знает, выполнено ли
действие. Повтор с новым ключом может создать ещё одно продление или письмо.

### Что сохранять до отправки

UUID v4 (`idempotencyKey`), ID вошедшего администратора, вид действия,
целевой `userId` и исходные параметры. Если надёжно сохранить намерение
не удалось, запрос не отправлять.

Один пользовательский запрос, все его повторы и восстановление после
перезагрузки используют **один и тот же ключ**. Новый ключ нужен только
для явно нового действия. Между вкладками согласовать доступ к сохранённому
намерению. При смене аккаунта его результат не применять к другому пользователю.

### Продление клуба

В существующий вызов добавить ключ:

```ts
await utils.client.admin.grantClub.mutate({
  userId,
  idempotencyKey: savedKey,
});
// Ответ прежний: { ok: true, expiresAt: "...ISO..." }
```

Сервер добавляет 31 день один раз. Повтор возвращает срок исходного продления,
а не текущий общий срок подписки. Для обновления карточки перечитать участницу.

### Повторное письмо

В JSON существующего `POST /api/admin/access-email/resend` добавить ключ:

```json
{
  "userId": 123,
  "idempotencyKey": "11111111-1111-4111-8111-111111111111"
}
```

Ответ HTTP 202 с `{ "queued": true }` означает **«Письмо поставлено в очередь»**.
Не писать «доставлено». Повтор с тем же ключом не создаёт новое письмо.
Лимит отправки сохраняется: 20 запросов в час на сотрудника, включая повторы.

### После потери ответа или перезагрузки

```ts
await utils.client.admin.actionStatus.query({ idempotencyKey: savedKey });
```

| Ответ                                           | Действие клиента                                                                                                                               |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `state: "succeeded", kind: "grantClub"`         | Продление подтверждено; в ответе есть `userId` и `expiresAt`. Завершить намерение и обновить карточку.                                         |
| `state: "succeeded", kind: "resendAccessEmail"` | Постановка письма подтверждена; в ответе есть `userId` и `queued: true`. Завершить намерение.                                                  |
| `state: "rejected"`                             | Показать подтверждённый отказ. В ответе есть `kind`, `userId`, `code: "NOT_FOUND"` или `"CONFLICT"`. Автоматически новое действие не начинать. |
| `state: "notFound"`                             | Результат пока не найден. Это не доказательство отмены первого запроса. Безопасный повтор — с прежним ключом и параметрами.                    |
| Ошибка сети, таймаут или 5xx                    | Сохранить незавершённое намерение и предложить проверку результата.                                                                            |
| 401/403                                         | Обработать сессию/права; результат не применять к другому аккаунту.                                                                            |
| 409 при повторе записи                          | Возможна несовместимость ключа и параметров. Проверить статус и сохранённое намерение, не обходить конфликт новым ключом автоматически.        |
| 429                                             | Выдержать доступную проверенную задержку. Результат можно проверить через status, не повторяя отправку письма.                                 |

Проверять структуру ответа и совпадение `kind`/`userId` с сохранённым
намерением до применения результата.

В status нет состояния `pending`. Чтение не продлевает подписку и не отправляет
письмо. Результат доступен только автору действия с актуальными правами.
После завершения не использовать этот ключ для другого действия.

**Файлы:** `features/admin/admin-screen.tsx`, `use-access-email-resend.ts`,
`shared/api/access-email.ts`, `domain/session/use-confirmed-action.ts`.

**Проверка:** сервер выполнил действие, ответ потерян; после перезагрузки статус
восстановлен, повтор не добавляет второй срок или письмо. Повторить с двумя
вкладками и со сменой аккаунта. Общий список участниц не использовать как
доказательство результата конкретного запроса.

## 4. Подключить ревизии редактора VK

Перед редактированием получать данные через:

```ts
const video = await utils.client.admin.vkVideoDetail.query({ id });
```

Ответ: `id`, `title`, `embedUrl`, `access`, `published`, `thumbnailUrl`,
`editRevision`. Проверить данные перед открытием редактора; `embedUrl` по типу
может быть `null`. Исходную ревизию сохранить вместе с черновиком.

В обновление передавать ревизию, с которой открыли редактор:

```ts
await utils.client.admin.upsertVkVideo.mutate({
  id: video.id,
  expectedRevision: video.editRevision,
  title,
  embedUrl,
  access,
  published,
  thumbnailUrl,
});
// Ответ прежний: { id }. Для следующего редактирования перечитать detail.
```

- При 409 сохранить ввод, загрузить актуальную версию и предложить сверку.
  Не подставлять новую ревизию и не сохранять повторно автоматически.
- При потере ответа сохранить черновик и исходную ревизию. Перечитать detail;
  не считать чужие изменения доказательством успеха своего запроса.
- При 412 запросить актуальную версию перед сохранением.
- Нулевая ревизия корректна: её также нужно передавать, не отбрасывать как falsy.
- Для создания нового ролика `id` и `expectedRevision` не передавать.
- `thumbnailUrl` не передавать, если обложку не меняли; `null` — явное удаление.
- Строгий режим серверной проверки самостоятельно не включать.

**Файлы:** `features/admin/vk-catalog-admin.tsx`, `features/videos/catalog-api.ts`.

**Проверка:** два администратора открыли один ролик. Первый сохранил,
второй получил 409. Запись первого осталась, ввод второго сохранился.
Создание нового ролика и изменение обложки продолжают работать.

## 5. Остальные пункты аудита

Эти задачи не закрыты новыми методами бэкенда:

- **Проверки ответов:** добавить недостающую проверку структуры списков статей,
  старого видеосписка, статистики, счётчиков и календаря до помещения в кеш.
  Некорректный ответ показывать как ошибку, не заменять пустым списком.
  Добавление необязательного поля не должно само по себе ломать совместимость.
- **Накопление страниц:** ограничить удерживаемые страницы админки, сохранённого
  и видеокаталога. Восемь страниц — исходный ориентир; сохранить корректный
  возврат, курсоры и позицию. Reader выкроек ограничить по числу страниц и общему
  времени чтения, сохранив отмену и проверку повторяющихся курсоров.
- **Восстановление покупки:** сначала проверить режим целевой сборки.
  Для NORMAL/GUEST использовать подготовленный протокол восстановления.
  TEST проверять отдельно. Статус подписки не считать доказательством оплаты
  конкретного заказа. Флаги и провайдера автоматически не переключать.

Бинарная передача документов вместо Base64 — отдельное необязательное улучшение.
Она не является условием исправления таймаута из пункта 2.

## 6. Контракт и порядок проверки

1. Получить согласованную версию бэкенда с новыми методами.
2. Получить свежий staging: генерируемый контракт уже обновлён. Проверить
   `pnpm check:api`. [Прежний patch](admin-actions-vk-api-2026-10-30.patch)
   нужен только для старой копии; поверх обновлённого файла его не применять.
3. Выполнить пункты 1–4, затем остальные пункты аудита.
4. Проверить ошибки транспорта, медленную загрузку, потерю ответа,
   перезагрузку, две вкладки, смену аккаунта и конфликт двух редакторов.
   Сначала на локальном тестовом API и временных данных, без настоящих платежей и писем.

**Готово, когда:** повтор одного действия не создаёт второй эффект; неизвестный
результат переживает перезагрузку; устаревшее VK-редактирование не затирает чужие
изменения; ошибки сети не превращаются в ложный успех. До передачи ключей и
ревизий старые вызовы сохраняют прежнее поведение — защиту для них считать
завершённой нельзя.
