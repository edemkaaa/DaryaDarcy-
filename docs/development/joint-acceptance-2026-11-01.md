# Совместная локальная приёмка после синхронизации staging

1 ноября 2026. Исходники основного checkout: `53cd0068`, входящий staging
`b86f48c6`. Проверяется уже полученная интеграция фронта с существующим API;
новые продуктовые функции и ручные правки основного фронтенда не добавлялись.

## Результат

Настоящий Nest API, свежая MySQL 8.4 native ARM64 и production Next/Chromium.
В каждом профиле своя одноразовая БД с 50 миграциями; записи и пользователи
синтетические. SQL-состояние проверяется тестами после запросов. API-ответы
не подменяются; при потере ответа обрывается уже подтверждённый SQL commit.

Проверены: сохранность ввода при 409/412, восстановление после reload,
исходные ключи и один SQL-эффект после повтора, две вкладки, смена аккаунта,
разделение черновиков, ревизии VK и отсутствие ложного подтверждения оплаты
по одному наличию действующей подписки. Для загрузки редактора работает
локальный S3 wire fixture; настоящий S3 не вызывается.

## Изоляция и ограничения

Штатный `accept-content-editors.mjs` читает Linux `/proc/meminfo`. На Mac он
остановился до создания БД. Прогоны выполнены частной копией адаптера вне Git:
исходные тесты/API/UI сохранены, источник памяти заменён на `memory_pressure`
и объём RAM из `sysctl`. Это оценка давления памяти, не Linux MemAvailable
и не замер RSS контейнеров. Максимальная наблюдаемая оценка 9,105 ГБ,
защитный порог 13,2 ГБ. Отдельному MySQL выделено 1536 МиБ, datadir в tmpfs.

В API разрешён TCP только к loopback. В каждом из трёх процессов guard
заблокировал две попытки внешнего соединения; причины этих попыток данным
прогоном не устанавливались. Workers доставки/SMTP не запускались. Merchant,
секрет и подписанные уведомления checkout полностью синтетические; реальные
платежи, Prodamus, письма и внешняя доставка этим не приняты.

Strict включался только в собственной editors fixture. Рабочие флаги,
основной frontend, сервер, БД, S3 и админские входы не менялись. Никаких pull
образов, удаления общих кэшей, образов или volumes. Docker был запущен без
перезапуска. После профилей свои контейнеры/процессы/временные БД убраны;
OOMKilled=false, restarts=0. Хеши четырёх файлов основной `.next` совпали
с исходными, сборки выполнялись в отдельных временных копиях.

## Что теперь передать фронтендеру

В проверенных сценариях b86f48c6 не воспроизводятся прежние замечания о
неподключённых ключах продления/письма и VK revisions. Повторно реализовывать
их по историческому списку не нужно. Локальная приёмка этих сценариев закрыта.

FE-08 целиком не закрывается: production пока использует прежний TEST-профиль,
переключение на NORMAL/GUEST не разрешено этим прогоном. Для старого TEST
журнал неопределённого результата не становится серверной квитанцией.
Нужны отдельные решение о режиме, рабочие настройки и согласованный выпуск.
Удалённый CI ждёт runner/доступа; физические устройства, реальные оплаты/почта
и пилот не заменяются этой проверкой. Нового backend runtime-дефекта в данном
срезе не обнаружено.
