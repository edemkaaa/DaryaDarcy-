## Что остаётся на стороне отображения

Это не отказ PNG и не ошибка backend API. Текущий блок всё ещё кадрирует файл:

- `apps/frontend/src/features/club/club-subscribed.layout.ts`:
  `height: SCREEN_WIDTH * 0.55`.
- `apps/frontend/src/features/club/club-subscribed.tsx`, `data-testid="club-season-banner"`:
  `contentFit="cover"`, `contentPosition="top"`.
- `apps/frontend/src/features/club/club-subscribed.module.scss`:
  `.bannerContainer { overflow:hidden }`, изображение занимает 100% блока.

У копии 2560×1707 при таком блоке показываются примерно первые 1408 строк.
Основная отрезанная область прозрачная: новый макет специально подготовлен
с нижним свободным полем. Однако проверка alpha > 8 обнаружила 60 пикселей
видимого края ниже границы — около 0,00185% непрозрачной области. Нижняя
граница этого края — строка 1414. Поэтому «файл целиком без обрезки» пока
не выполнено буквально, хотя надпись и основные элементы помещаются.

## Минимальная правка, если требуется гарантировать весь файл

Не менять backend, API-контракт, фон, остальные сезоны или сам баннер.
Убрать именно принудительное кадрирование в блоке баннера. Возможны два
варианта с разными последствиями для вёрстки:

1. `contain` при сохранении текущей высоты и верхнего выравнивания — весь
   файл виден, но картинка станет уже и появятся прозрачные поля по бокам.
2. Высота по действительным пропорциям изображения, ширина 100%, `contain`
   и верхнее выравнивание — весь файл виден на полной ширине, но блок станет
   выше. Пропорцию получать из декодированного изображения/сохранённого
   измерения, не фиксировать 3636/2424 для всех сезонов. Учесть смену URL,
   загрузку, ошибку и повтор, не запрашивать оригинал дополнительным probe.

Не применять оба изменения вслепую и не менять глобальный `Picture`:
выбрать вариант для баннера, сохранив согласованное оформление страницы.
Изменение размеров блока выполняет фронтендер, не backend.
