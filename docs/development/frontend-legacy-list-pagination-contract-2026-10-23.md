# Пагинация старых списков: минимальный контракт

23 октября 2026 · проверено по локальной ревизии `4891a30`.
Контракт принят пользователем23октября; три метода реализованы локально в
порядке saved→members→comments. [Фактическая инструкция подключения и типы](frontend-pagination-handoff-2026-10-23.md).
Первоначальная подготовка была только исследованием; дальнейшая реализация
меняет backend, но не фронт, рабочую БД или S3. Без редизайна, push и выкладки.

## 1. Что менять, а что уже есть

| Сейчас                                             | Предлагаемый переход                                           | Текущий потребитель                                                                              |
| -------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `feed.list` — весь массив                          | Использовать существующий `feed.listPaginated`                 | Основная лента уже использует его; остались invalidations и операционные скрипты старого метода. |
| `videos.list` — весь YouTube-массив                | Использовать существующие `videos.catalog` и `videos.playback` | VK-экран уже постраничный; старый экран остаётся в fallback-режиме сборки.                       |
| `feed.savedPosts` — все сохранения                 | Новый `feed.savedPostsPage`                                    | `features/profile/profile-screen.tsx`.                                                           |
| `club.comments` — весь тред                        | Новый `club.commentsPage`, отдельно корни/ответы               | `features/club/club-comments.tsx` и `use-private-comment-files.ts`.                              |
| `admin.members` — все пользователи и paid payments | Новый `admin.membersPage`                                      | `features/admin/admin-screen.tsx`, включая read-after-write действий.                            |

Не добавлять вторую пагинацию для ленты, VK, админских постов или календаря.
У `admin.postsPage` она уже есть; `admin.payments` сейчас ограничен50 записями.
Не возвращать YouTube в каталог и не менять согласованные VK-флаги автоматически.

## 2. Общий формат только для трёх новых списков

```ts
type PageInput = {
  limit?: number; // integer, default20, 1..50; не округлять/не обрезать
  cursor?: string | null; // непрозрачный токен, максимум1024 символа
  direction?: "forward"; // совместимость с tRPC useInfiniteQuery
};
type Page<T> = { items: T[]; nextCursor: string | null };
```

Первый запрос — без cursor или с null. Следующий — ровно с полученным
`nextCursor`. `null` означает конец; отдельные hasMore/номера страниц не нужны.
Пустая здоровая выдача — `{items:[],nextCursor:null}`, не ошибка.

Новые курсоры — keyset по порядку ниже, а не номер страницы/offset. Контекст
включает метод, фильтры, postId/parentId и владельца персональной выдачи.
Невалидный токен/несовместимый контекст —400, права проверяются отдельно при
каждом запросе. Курсор не даёт доступа к объекту и не является секретом сессии.
Новые входы strict; limit0/51/1.5 и неподдерживаемое direction —400.

Существующие числовые cursor у `feed.listPaginated`, `club.list`,
`admin.postsPage` и `videos.catalog` **не менять на строки**. У первых трёх
сейчас offset, у VK — ID. Их пределы и формы `{posts,...}`/`{items,...}` прежние.

Новый серверный SELECT получает не больше limit+1 строк страницы; медиа,
реакции и данные доступа обогащаются только для возвращаемых ID. Нельзя сначала
прочитать все строки в Node и сделать slice. COUNT/агрегация в SQL допустимы,
но не заменяют последующую проверку плана запросов на отдельной БД.

## 3. «Сохранённое»

`feed.savedPostsPage(PageInput & { target: "feed" | "club" }): Page<SavedItem>`

- Требует входа, но не подписки для открытых постов. Владелец берётся из
  текущей сессии; userId от клиента не принимается.
- `SavedItem` сохраняет поля элемента нынешнего `feed.savedPosts`, включая
  медиа и реакции, без нового урезанного контракта карточки.
- `target:"feed"` включает feed/both; `target:"club"` — club/both. Это выбор
  вкладки, не разрешение доступа. Открытые both остаются доступными без подписки.
  Закрытые club, черновики, удалённые и снятые с публикации записи исключаются
  **до LIMIT**, а не фильтруются после получения страницы.
- Порядок: время сохранения DESC, ID строки сохранения DESC. При исторических
  дублях одного postId используется его самая новая строка по этому порядку;
  карточка одна. Миграция/удаление старых дублей для этого не требуются.
- При отзыве подписки открытая часть остаётся; закрытая не выдаётся ни в
  первой, ни в последующих страницах. Клиент также убирает её из своего кеша.

## 4. Комментарии без потери ответов

```ts
// Новый метод club.commentsPage:
type CommentsPageInput = PageInput & {
  postId: number;
  parentId?: number | null;
};
type CommentsPageOutput = Page<CommentItem & { replyCount: number }> & {
  totalCount: number;
};
```

- Нет parentId/null — только корневые комментарии. С parentId — только его
  прямые ответы; ответам на ответы применяется тот же контракт. Порядок в
  каждой группе: createdAt ASC, id ASC — прежняя хронология с явным tie-breaker.
  postId и непустой parentId — положительные безопасные целые, иначе400.
- `CommentItem` — нынешний элемент `club.comments`: authorName/avatar,
  text/photos/parentId, likeCount/likedByMe и остальные текущие поля.
  `replyCount` — число прямых ответов. Дочерние массивы не включать целиком.
  `totalCount` — количество всех комментариев поста, включая ответы, а не
  размер этой страницы/группы; нужен существующему заголовку счётчика.
- Права прежние: вход обязателен; к опубликованному открытому посту достаточно
  входа, к club — действующий клубный доступ. Не заменять всё на
  clubMemberProcedure: это закроет комментарии открытых постов обычным аккаунтам.
- Родитель должен существовать в этом же посте; иначе404 после проверки
  доступа. Не получать чужой тред через подмену parentId/cursor.
- Фронт загружает корни и ответы по отдельным ключам, не скачивает весь тред
  для сборки дерева. Ответ не теряется из-за отсутствия родителя в общем массиве.
  Отсутствие ребёнка в одной странице не доказывает удаление/неуспех отправки.
- Сохранить журнал приватных фото и ключ повторной отправки. После add/update/
  delete обновлять затронутую группу и счётчики, не обходить все страницы ради
  восстановления. Подтверждённый ID берётся из результата add/replay, не из
  поиска в первой странице. При удалении родителя сбрасывать корни и его группу:
  нынешний backend переносит прямых детей в корень, этот смысл не менять.

## 5. Участники админки

`admin.membersPage(PageInput & { userId?: number }): Page<MemberItem>`

- Та же роль admin, что у `admin.members`; модератору список не открывать.
  `MemberItem` — прежний allowlist id/email/name/role/createdAt/blockedAt/
  blockedReason/clubExpiresAt. Хэши, sessionVersion и прочие поля users не выдавать.
- Порядок: createdAt DESC, id DESC. Срок клуба считается по прежнему правилу:
  MAX будущего expiresAt среди paid payments. Выбирать пользователей страницы
  и рассчитывать срок только для её ID, а не читать все платежи в Node.
- Не добавлять поиск, новые фильтры подписок или общий total: текущий экран
  этого не требует. Не подменять срок клуба новой логикой доступа staff.
- Единственный узкий фильтр `userId` нужен для существующей проверки состояния
  после выдачи клуба/блокировки. Без cursor даёт0/1 строку с nextCursor:null;
  userId — положительное безопасное целое. При его изменении cursor сбрасывается.
  Это позволяет не скачивать все страницы ради одного изменённого аккаунта.
- Вкладка оплат показывает email/orderId из самого платежа и не использует
  массив участников. Ей не нужно параллельно выкачивать `admin.members`.
- Проверка текущего состояния не доказывает, какой из параллельных запросов
  его изменил. При потерянном ответе не повторять grantClub вслепую: пагинация
  не делает существующую мутацию идемпотентной.

## 6. Требования к подключению фронта

Ключ кеша персональных данных включает текущий аккаунт, target/postId/parentId/
userId и limit; cursor хранится как pageParam. Новый контекст — новая первая
страница. Данные другого аккаунта и закрытые данные после403 не удерживать.
503/timeout не превращать в «ничего нет» и не подтверждать ими очистку состояния.

Догружать только по действию/достижению конца видимой выдачи, с одним запросом
на конкретный список; дубли ID объединять. Не повторять уже использованный
cursor, не крутить retry-loop при ошибке следующей страницы. Завершение — только
по nextCursor:null, не по числу видимых карточек после локальных фильтров.

Не подключать к новому infinite query минутный refetch всех загруженных страниц.
Фоновое обновление — ограниченный запрос первой страницы; если последовательность
её ID изменилась, она заменяет цепочку и старые cursors сбрасываются. При том же
наборе ID обновить поля первой страницы, а не игнорировать новые данные.
Отзыв доступа очищает закрытый кеш независимо от совпадения ID. Детали
открытого материала и прав проверяются отдельно; точного snapshot всего архива
между запросами не обещаем. Новая запись/перестановка/перенос ответа требуют refresh.

В `use-private-comment-files.ts` и admin read-after-write нельзя оставить
`requireIdList(page)` — валидировать `page.items`, нужную группу/аккаунт и актуальность
операции. Изменить invalidations, отмену запросов и восстановление, не только useQuery.
При переходе с videos.list нельзя отдавать items каталога старому detail без
videos.playback. Серверный batch-предел20 не повышать: клиенту maxItems20.

## 7. Согласованный порядок реализации и приёмки

1. Backend-only на одноразовой БД: savedPostsPage, затем membersPage, затем
   commentsPage. Сначала RED-тесты, затем минимальные SELECT/схемы/DTO. Фронт
   не редактировать; выдать файл сгенерированного контракта фронтендеру отдельно.
2. Проверить0/20/21/50/51 элементов, равные даты, исторические дубли сохранений,
   полный обход без дублей/пропусков на неизменной выборке, удаление граничной
   записи, добавление во время обхода и reset. Родитель с51 ответом не должен
   породить ответ размером всего треда. Реакции/медиа только по странице.
3. Проверить guest/unpaid/member/admin, отзыв доступа между страницами,
   чужой parentId/user-context, отсутствующую БД503. Существующие тесты
   редакторов, приватных фото, отмены/повтора и админских действий сохраняются.
4. Фронтендер переключает потребителей без редизайна, включая fallback видео,
   оба comment recovery paths и read-after-write. Затем совместная локальная
   проверка. Backend-результаты записаны в активном чек-листе; новая frontend-
   интеграция пока не реализована и не принята, её нельзя считать проверенной.
5. Только после миграции всех потребителей отдельно согласовать вывод старых
   feed.list/videos.list/savedPosts/comments/admin.members из публичного API с
   явной ошибкой обновления клиента, а не скрытым LIMIT. Пока они доступны,
   исходный риск полного чтения по прямому запросу **не закрыт**. Учесть smoke,
   импортеры и сборочные fallback-пути, не только активные экраны.

Не включено в этот контракт: рубрики/алиасы Клуба (FE-02/INT-05), индексы BE-06,
пагинация admin articles или всей истории оплат и замена полного
`feed.userInteractions` на чтение реакций по видимым ID. Последний массив также
остаётся отдельным неограниченным чтением; новые страницы его автоматически не
устраняют. Большую нагрузку и рабочие миграции не запускать.
