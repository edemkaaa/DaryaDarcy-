29 октября: последующим поручением разрешены совместное объединение, push и
выпуск. Маска и оформление фронтендера из2fbde316 подключены к contactPhone;
сгенерированный контракт обновлён в составе merge. Инструкции «без frontend/
выкладки» ниже относятся к предыдущему локальному срезу. Текущий статус:

Запрос 29 октября: контакт обязателен при создании новой заявки, без SMS,
проверки владения номером и дополнительных действий. Изменения пока локальные.

## Контракт

- Два существующих блока оплаты используют общее состояние номера.
- `contactPhone`: номер с кодом страны; пробелы/скобки/дефисы допустимы.
  Российское `8 (999) 123-45-67` сохраняется как `+79991234567`.
  Международный номер задаётся с `+`, 8–15 цифр, максимум40 входных символов.
- `club.createCheckout` в действующих TEST/LIVE Prodamus проверяет контакт до
  создания пользователя/платёжной заявки. Ответ остаётся `{url,user:null}`.
- Контакт хранится в `users.contactPhone` рядом с email; в
  `club_payments.contactPhone` сохраняется снимок номера конкретной заявки.
  Обе колонки nullable varchar16, не уникальные: общий семейный номер допустим.
  Миграция0046 добавляет контакт заявки, новая0047 добавляет контакт пользователя.
  Прежние строки/входы не переписываются; у старых пользователей NULL.
- Не обновлять `users.phone`: введённый номер не проверен и не является логином.
- Не добавлять `customer_phone`/телефон в платёжную URL, письма или SMS.
- NORMAL и гостевой LIVE: номер включается в сохранённый intent и hashv2.
  Другой номер с прежним ключом даёт409, повтор прежнего создаёт один заказ.
  У старых заказов NULL/hashv1: их проверка и восстановление не требуют нового номера.
- После входа другим аккаунтом несохранённый черновик номера не показывается.
  Существующие проверки владельца сохранённой покупки остаются.
- Финальная анонимизация аккаунта очищает новый контакт; платёжные записи остаются.
- Старый отдельный YooKassa TEST-клиент этим срезом не расширяется.

## Уточнение владельца: хранить в карточке пользователя

29 октября владелец выбрал карточку пользователя рядом с email, а не только заявку.
Backend дополнен этим поведением; новые правки фронтенда в этом срезе не делались.

- Новый гость: нормализованный контакт записывается при создании аккаунта по email.
  Повторное/параллельное создание не переписывает контакт существующей записи.
- Вошедший пользователь: свежая заявка сохраняет контакт именно его аккаунта.
  Сессия, email, блокировка и запрос удаления повторно проверяются под SQL-lock;
  контакт и заявка меняются атомарно. Ошибка записи откатывает оба изменения.
- Гость с существующим email: контакт сохраняется в заявке, **не в чужой карточке**.
  Для обновления карточки существующего аккаунта нужен вход. Знание email
  не подтверждает владение аккаунтом, даже если старый контакт пока NULL.
- NORMAL: повтор старой заявки не откатывает новый номер из более свежей заявки;
  подмена номера с прежним ключом даёт409 до изменения карточки.
- В `admin.members` и `admin.membersPage.items[]` возвращается
  `contactPhone: string | null` рядом с email. Только роль администратора.
  Публичный профиль/REST me/tRPC me этим полем не расширяются.
- `users.phone` остаётся прежним полем старой авторизации. Новый контакт не
  используется для входа, восстановления пароля или связывания аккаунтов.
- Автоматического переноса старых номеров из заявок в карточки нет: гостевые
  данные не являются основанием для перезаписи чужого контакта.

## Фронтендеру

Передавать поле `contactPhone` в том же запросе, что email и выбранный план:

```json
{ "email": "reader@example.test", "contactPhone": "+7 999 123-45-67", "plan": "monthly" }
```

Это `club.createCheckout`; у `createNormalCheckout` email берётся из сессии,
а `createGuestNormalCheckout` дополнительно требует прежние idempotencyKey/recoveryToken.
Для новой заявки поле обязательно; старые status/recovery вызовы не расширять.
Не добавлять подтверждение телефона, SMS или отдельную регистрацию. Ошибку400
показывать рядом с вводом, конфликт409 не обходить автоматической новой оплатой.

В админской карточке использовать `contactPhone`, а не `phone`; при NULL писать
«Не указан», подпись поля «Контактный телефон (без подтверждения)». Отдельный
endpoint изменения номера не добавлялся. Клиентский автозапрос на сохранение
контакта вне существующего checkout не требуется.

Исходники и сгенерированный контракт фронтенда не изменялись. Для двух добавленных
полей ответа пересоздать контракт командой `pnpm api:contract` вместе с UI-правкой.
[Минимальный diff типов](checkout-contact-phone-api-2026-10-29.patch) подготовлен
из текущего компилятора; содержит только два поля в админских ответах. Поиск/вход
по телефону и публичные ответы остаются прежними.

## Выпуск

Рабочая БД/сервер не менялись. При отдельном решении о выпуске сначала проверить
историю миграций и резервную копию, применить0046 и0047, затем согласованно обновить
API и форму: прежний Prodamus-клиент без поля больше не создаёт новые заявки.
Восстановление уже зарегистрированных заявок сохраняется.
