# Backend контракт каталога обложек и плеера VK

Дата: 20 октября 2026 года. Стенд: <https://daryadarcy.dev.reeskeen.ru/videos>.

Доступная локальная backend-часть перехода на VK подготовлена: каталог выдаёт безопасные обложки по запросу клиента, сохранение VK принимает необязательную обложку, повтор создания не создаёт дубликат. Правила доступа к клубу сохранены. Код не выложен; рабочие БД, S3, каталог и настройки не менялись.

[Пошаговое задание фронтендеру](frontend-video-fixes-2026-10-20.md).

Локальные коммиты: `36fc86d` (catalog opt-in) и `b6dbdf4` (VK cover write/replay). В staging не отправлялись.

## Границы результата

Пользователь подтвердил VK вместо YouTube. Прежний сбой `/video/1` через YouTube-прокси остаётся неустранённым; доработка этого прокси остановлена по смене направления. Не считать текущие тесты его исправлением.

Получен настоящий `video_ext.php` на `vk.ru`, `oid=-211171256`, `id=456239238`. Он проходит локальные parser/input/canonical replay проверки; autoplay нормализуется в 0. Полный URL и hash не хранятся в документации Git. Исходный экспорт — в сообщении пользователя.

Инструмент браузерной проверки отказал в открытии VK по site-safety policy. Обход не выполнялся. Это ограничение инструмента, не ответ сервера VK. Живое воспроизведение, перемотка и полноэкранный режим пока не приняты.

## Каталог

`videos.catalog` принимает прежние `limit`, `cursor`, `direction: "forward"` и новый необязательный `includeThumbnails: boolean`.

- Без параметра или при `false` форма ответа прежняя.
- При `true` каждая карточка дополнительно содержит `thumbnailUrl: string | null`.
- `id/title/duration/access/canWatch`, порядок и пагинация сохраняются.
- В карточках нет embed URL, VK hash, private storage key или источника видео.
- Нет внешних запросов за каждой обложкой и N+1-чтения БД.

Политика адресов едина для чтения и нового сохранения. Принимаются существующие image-адреса `/assets/responsive/` и HTTPS `s3.twcstorage.ru/daryadarcy-s3/feed/` либо `app-assets/`, без query, fragment и credentials. Поддерживаемые расширения: JPEG, PNG, WebP, AVIF. Произвольные VK CDN URL, плееры, подписанные ссылки и закрытые префиксы не допускаются.

Это проверка адреса, не существования файла, MIME его байтов или публичности содержания. Администратор должен выбрать согласованную публичную обложку. Чтение старого неподходящего значения возвращает `null`; новое сохранение неподходящего значения даёт 400.

## Сохранение VK

`admin.upsertVkVideo` сохраняет существующие поля `embedUrl/title/access/published/id?` и необязательное `thumbnailUrl: string | null`.

- Create без ID: дедупликация по VK oid/id через существующий уникальный индекс. Повтор с тем же нормализованным содержимым возвращает прежний ID.
- Изменённое содержимое create для уже существующего источника даёт 409 без перезаписи.
- Update с ID: обновляется только существующая VK-запись. Отсутствующая или YouTube-запись даёт 404; коллизия с другим VK-источником — 409.
- Обложка при create по умолчанию `null`. При update отсутствие поля сохраняет прежнее значение, явный `null` удаляет привязку, строка сохраняет нормализованный адрес.
- Изменение обложки учитывается при replay/conflict, а не молча теряется.
- Права записи остаются только у администратора; проверка актуального аккаунта и сессии не менялась.
- Успех: `{ id: number }`. Нового upload API, миграций или внешнего скачивания нет.

Произвольный iframe/script или ссылка wall не сохраняются вместо embed URL. В API передаётся только экспортированный `src`.

## Получение плеера

Существующий `videos.playback({ id })` возвращает для VK `{ id, provider: "vk", embedUrl }` только после проверки текущего доступа и публикации.

Гость не получает клубный источник, пользователь без доступа получает отказ, участница и администратор сохраняют согласованные права. Блокировка, отзыв сессии и истечение доступа проверяются существующей серверной логикой. Публичный YouTube-worker не становится обходом для VK или клубной записи.

Каталог не является разрешением на воспроизведение. Ранее полученный внешний VK URL сам по себе не обеспечивает DRM; по согласованному объёму защита самого VK-ролика не обещается.

## Проверки

- Исходный RED для catalog opt-in: восемь HTTP/SQL сценариев получали 400.
- Новый RED сохранения обложки: два сценария HTTP/SQL получали 400 на поле `thumbnailUrl`.
- GREEN: 102 проверки в пяти наборах, включая настоящий loopback HTTP/MySQL, старые клиентские parsers, worker/access boundaries.
- Финальная проверка TypeScript, сборка backend, ссылки документации и `git diff --check` прошли. Первоначальная ошибка типа callback закрытия тестового relay исправлена до финальной проверки.
- Потеря ответа проверена локальным HTTP relay: запись совершена настоящим API, ответ оборван, SQL подтвердил строку до повторного запроса, retry вернул тот же ID.
- Проверены конкурентные create без дублей, конфликт изменённой обложки, update без поля, явный null и отказ небезопасных значений без изменения строки.

Свой контейнер `611501a3…` после проверок удалён с guards exact ID/labels/tmpfs/loopback; volumes отсутствовали. Удалены только одноразовые синтетические данные. Образы, рабочие и чужие базы не затронуты.

## Что ещё требуется до выпуска

1. Фронтендеру выполнить `pnpm api:contract`, обновить строгую схему карточки, подключить opt-in и поле обложки. Generated contract намеренно не менялся backend-исполнителем; `pnpm check:api` пока сообщает outdated.
2. Подготовить согласованные VK-экспорты и реальные публичные обложки для нужных записей. Один ролик «Англия» не сопоставляет весь старый YouTube-каталог.
3. Отдельно согласовать публикацию backend/frontend и изменение рабочих данных. Новые колонки и миграции для этой правки не нужны.
4. Выполнить живую проверку VK в обычном браузере: запуск, минимум 60 секунд просмотра, пауза, продолжение, перемотка, fullscreen, смена аккаунта и отзыв доступа.

Нет основания объявлять весь раздел или весь договор закрытым до интеграции и этой приёмки. Рабочие записи, admin credentials, фронт, дизайн, S3 и старые файлы в этой работе не менялись. Пуш и выкладка не выполнялись.
