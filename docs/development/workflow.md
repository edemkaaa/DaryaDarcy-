# Рабочий процесс

## Где работать

Основной репозиторий: https://github.com/edemkaaa/DaryaDarcy-.git (`origin`, HTTPS).
Прежний GitLab сохранён отдельным remote `gitlab` для истории; текущая его
доступность не требуется для локальной работы. Рабочая ветка публикации —
`staging`, исходная точка GitHub также сохраняется в `main`. История переносится
без force-push. Другие ветки и защищённые настройки не меняются без задачи.
Репозиторий оставлен публичным по выбору владельца. Рабочие секреты, дампы,
данные пользователей и сырые операционные выгрузки в Git не добавляются.
Наличие файлов CI не подтверждает успешный запуск pipeline или готовность production.

Изменения делайте небольшими проверяемыми этапами. Сначала изучайте текущий код и задачи, сохраняйте чужие незакоммиченные изменения. После этапа обновляйте [чеклист](../../tasks/todo.md), не закрывая непроверенные пункты.

## Окружение и зависимости

- Node.js 22, pnpm 9.12.0; версии зафиксированы в CI и package.json.
- Только pnpm-lock.yaml: не создавайте npm/yarn lockfile.
- Установка: pnpm install --frozen-lockfile --ignore-scripts.
- Локальный .env создаётся из [.env.example](../../.env.example); секреты и дампы не коммитятся.
- Не используйте production DATABASE_URL для тестов или подготовки миграций.

## Проверка этапа

```sh
pnpm check:boundaries
pnpm check:docs
pnpm check
pnpm test
pnpm build
pnpm build:web
pnpm verify
```

Проверка документации описана в [инструментах](../../tooling/README.md). CI: [GitLab](../../.gitlab-ci.yml) и [GitHub](../../.github/workflows/ci.yml).

Основной клиент — Next.js: `pnpm build:web` пишет его `.next`. Vite остаётся отдельной совместимой сборкой `pnpm build:web:vite` с результатом в `web-dist`. Эти результаты не подменяют друг друга; Expo исключён из активного workspace.

Общие статические веб-ресурсы лежат в [apps/frontend/public](../../apps/frontend/public/). Упаковка обеих сборок требует manifest.webmanifest и privacy.html: пропуск любого файла завершает её с ошибкой, а не выпускает неполный сайт.

## Интеграционные тесты БД

Обычный pnpm test пропускает тесты, которым нужна MySQL. Для полной проверки поднимите отдельную пустую MySQL 8 с БД backend_test и задайте только BACKEND_TEST_DATABASE_URL:

```sh
BACKEND_TEST_DATABASE_URL='mysql://root:local-test-only@127.0.0.1:33317/backend_test' pnpm test:db:wait
BACKEND_TEST_DATABASE_URL='mysql://root:local-test-only@127.0.0.1:33317/backend_test' pnpm test
```

Это пример адреса, не обещание запущенного сервера. Тесты изменяют тестовую БД. Ограничения адресов и имён БД проверяются [политикой тестового подключения](../../tooling/scripts/test-database-policy.ts); не обходите её. CI использует отдельный сервис MySQL, а не рабочую базу.

## Миграции и выпуск

Схема — [schema.ts](../../packages/database/src/schema.ts), история SQL — [drizzle](../../packages/database/drizzle/). pnpm db:preflight проверяет историю и подключение; это не команда применения миграций.

Для пустой одноразовой локальной БД есть проверяемый fresh-профиль из 52 миграций. Он не исправляет журнал существующей БД. В старой истории, особенно 0017–0019, возможны расхождения SQL и записанных хешей: решение принимает preflight по конкретной БД. Нельзя скрывать отказ переименованием, удалением или дописыванием истории вручную.

`pnpm db:push` больше не генерирует SQL автоматически: сначала выполняет
`db:preflight --require-database`, затем применяет подготовленные миграции только
при успехе. Требуется явный `DATABASE_URL` из окружения; `.env` не читается.
Проверяется та же БД, что и при применении. Отдельный
`MIGRATION_PREFLIGHT_DATABASE_URL`, если задан, должен точно совпадать с ней.
Ошибки файлов/конфигурации останавливают команду до подключения; отсутствующая,
пустая или несогласованная история БД не принимается за новую разрешённую базу.
При нынешнем рассогласовании команда должна завершаться ошибкой без изменений.
SQL и журнал готовьте/ревьюйте отдельно; общий lock между проверкой и применением
не реализован. Не запускайте конкурирующие миграторы и не обходите проверку
прямым `drizzle-kit migrate`. Это не разрешение применять изменения к рабочей БД.

Перед выпуском нужны резервная копия и репетиция миграций, приёмка платежей и писем, проверка устройств и доступа к платному контенту. Список не заменяет [актуальный чеклист](../../tasks/todo.md).

## Документы

- README в корне — краткий вход, не журнал всех этапов.
- docs/architecture — описание текущего кода; docs/audits — датированные результаты проверок.
- `pnpm docs:files` обновляет [справочник файлов](file-guide/index.md), `pnpm check:files` проверяет его актуальность. Таблицы строятся автоматически; ручные пояснения находятся в коде.
- docs/archive — история, не активные инструкции. Старые незавершённые пункты сохраняются там, но не считаются выполненными.
- tasks — единственный активный рабочий план.
- Новые ссылки делайте относительными, без путей к компьютеру конкретного разработчика.

Настройки редакторов не являются частью проекта: правила Cursor удалены, локальная .cursor/ игнорируется Git. Общие команды и ограничения хранятся в README, этом документе и tasks/, а не дублируются в правилах отдельных редакторов. Исходные требования, ADR, аудиты и сведения о деплое сохраняются; ненужные шаблоны и разовые пробы можно найти в истории Git, а не среди рабочих файлов.
