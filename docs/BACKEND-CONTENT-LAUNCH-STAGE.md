# Контент и настройки первого запуска — 02.10.2026

Локальная реализация в staging; не разрешение на выпуск. Проверки выполняются
на одноразовой MySQL, а не рабочей базе. Предыдущий этап описан в
[оплатах и доступе](BACKEND-BILLING-IDENTITY-STAGE.md).

## Проверенные серверные модули

- Аватар, фото поста и комментария: проверка настоящего JPEG/PNG/WebP, повторное
  кодирование в WebP, удаление EXIF/XMP, применение ориентации, случайное имя.
  Лимиты: 4 MiB исходного файла, 20 млн пикселей, сторона результата до 2560,
  одновременно до четырёх декодирований на процесс. SVG/HTML/анимация запрещены.
  sharp 0.35.4 уже присутствовал в проекте; теперь явно указан как runtime-зависимость
  backend. Lockfile обновлён без запуска install scripts.
- Публичные, клубные и сохранённые списки, детали и обсуждения требуют обоих
  признаков публикации: published=true и status=published. Проверка клуба и
  блокировок сохранена. Публичная статья не требует подписки; клубное тело скрыто.
- Комментарии хранятся 365 дней вместо 90. Очистка транзакционными пачками до 500:
  удаляются связанные лайки/жалобы, новые ответы на удаляемый комментарий становятся
  корневыми. Рабочая очистка вручную не запускалась.
- Импорт видео с произвольного URL отключён: сервер больше не скачивает адреса,
  заданные пользователем. Существующие ссылки принимаются только с точного
  настроенного S3 origin и внутри своего bucket. Для внешнего видео — загрузка
  файла или отдельный путь embed; прежний интерфейс importVideoUrl сохранён.
- SMS и pen pals по умолчанию выключены серверно. Только точное `true` в
  ENABLE_SMS_LOGIN/ENABLE_PEN_PALS включает их; перед включением нужны отдельные
  проверки безопасности/согласий. Удаление старого pen-pal профиля не блокируется.
  Онлайн-магазин не включается никаким environment-флагом до исправления его
  settlement/outbox. Закрыты checkout, public redirect, fulfillment и mail worker.
- Браузерные запросы с учётными данными разрешены только настроенным origins.
  Чужие Origin и cross-site запросы отклоняются до обработчика; платёжные webhook
  и return остаются отдельными подписанным/навигационным путями, без доверия к Origin.
  Добавлены no-sniff, no-referrer, anti-framing и HSTS для production HTTPS.
  Proxy доверяется только loopback; rate limit использует рассчитанный Express IP,
  не первый произвольный X-Forwarded-For.
- Ошибки tRPC не возвращают SQL, параметры и stack trace пользователю; внутреннее
  сообщение заменено общим. Журналы регистрации/входа/upsert и API не печатают
  исключение с почтой и хешем. Проверено настоящим нарушением ограничения MySQL и
  HTTP-ошибкой с маркерами тестовых персональных данных, не только поиском текста.
- Ограничитель попыток входа/восстановления ограничен 10 000 ключами на процесс;
  истёкшие ключи очищаются раз в минуту. При заполнении новые ключи отклоняются,
  действующие лимиты не вытесняются (иначе можно было бы сбрасывать чужой лимит).
  Четыре теста проверяют квоту, ёмкость, восстановление после истечения и размеры
  ключей. 351 тест / 3 пропуска, типы/границы/сборка API прошли. Ограничитель всё
  ещё локален процессу: для нескольких API-инстансов нужен общий store/edge limit.
- Изменение, лайк, жалоба и удаление комментария проверяют публикацию поста и
  доступ к клубу, а не только факт входа. Чужое удаление не очищает лайки;
  собственное удаление атомарно очищает лайки/жалобы и отвязывает ответы.
  Ответ требует существующего родителя в том же посте. Блокировки строк
  сериализуют ответы/лайки/жалобы с удалением и очисткой; удаление самого поста
  тоже стало транзакционным с очисткой связей. Ошибка очистки откатывает всё.
  13 реальных MySQL + 9 API-сценариев, полный набор 373 / 3 пропуска,
  типы/границы/сборка API прошли. Миграции рабочей базы не запускались.
  Затем комментарии/модерация/retention выделены в `content/comments.ts`, без
  новых фасадов; router и maintenance используют модуль напрямую. Три старых
  неиспользуемых comment-метода удалены из db.ts, чтобы не оставлять обходной путь.
  Повторный полный набор 373 / 3 пропуска и границы на 264 файлах прошли.
- HTTP body parsing выделен в отдельный модуль. Аутентификация и роль проверяются
  до чтения больших видео/JSON upload, включая batched tRPC. Обычный JSON —
  256 KiB, auth JSON/формы — 16 KiB; фото — 6 MiB, admin media — 50 MiB,
  raw video — 80 MiB только после допуска администратора. Подписанный webhook
  остаётся отдельным raw-путём с 2 MiB. Повторная проверка сессии после upload
  сохранена. Ошибки JSON/storage не возвращают или логируют детали payload.
  Десять HTTP-сценариев; полный набор 387 / 3 пропуска, типы/границы/API прошли.
  Это ограничивает расход памяти, **не является полной проверкой формата видео**
  и не заменяет лимиты reverse proxy, stream upload и нагрузочную приёмку.

## Новые API настройки

- GET `/api/capabilities`: серверные переключатели, no-store.
- GET `/api/launch-config`: активный сезон, оформление, контакт менеджера,
  orderMethod=email-client и capabilities, no-store. Не возвращает будущие настройки.
- GET `/api/admin/launch-settings`: полная конфигурация только администратору.
- PUT `/api/admin/launch-settings`: JSON `{expectedRevision, config}`. Четыре сезона,
  ежегодные даты MM-DD, HTTPS-изображения или null, managerEmail. Все даты различны;
  29 февраля и некорректные даты запрещены. Часовой пояс Europe/Moscow.
  Повторное чтение роли/блокировки, сохранение версии и аудит — в одной транзакции.
  Устаревшая версия возвращает 409; неверный JSON — 400; нет прав — 401/403.

По умолчанию выбран фиксированный зимний набор, как требуется к запуску. URL
оформления null: изображения не выдумывались. Для автоматического календаря нужны
четыре подготовленных набора и переключение seasonMode в calendar администратором.
Граница даты вычисляется по Москве, независимо от зоны серверного процесса.

Контакт менеджера — настройка, **не подтверждение отправленного заказа**.
email-client означает открытие почтового приложения; текущий сервер не создаёт
заказ и не сообщает, что письмо доставлено. Подключение клиентской кнопки и
приёмка этого сценария ещё нужны. Автоматическая серверная очередь заказов —
отдельный оставшийся модуль, если нужен заказ без почтового приложения.

Настройки ещё не подключены к существующему сезонному экрану и административному
редактору. Восстановление пароля в интерфейсе уже подключено (ниже);
оставшиеся зависимости, провайдер/SMTP/device E2E, нагрузки и live rollout — в плане.

Границы импорта проверены на 263 файлах. Подготовлены GitLab/GitHub CI с отдельной

использующих их workspace-пакетах. Версии зафиксированы, lockfile обновлён без

Это подтверждённый дефект старой зависимости, **не доказательство доступной
SQL-инъекции в приложении**: опасные динамические идентификаторы в текущих

проверены по источникам разработчиков. TLS рабочей БД требует отдельной проверки;
обновление клиента само по себе не подтверждает защищённость соединения.

Nodemailer обновлён с 6.10.1 до 10.0.13, используются встроенные типы вместо
@types/nodemailer. Проверены major-изменения: Node >=20 (CI использует 22),
SES/API ошибок/удалённые вложения в нашем SMTP-сценарии не используются.

Письма доступа принимают ровно один обычный адрес, URL/file-вложения отключены.

отказ получателя, запрет plaintext-авторизации и списков адресов; до исправления
два последних сценария воспроизводили проблему. 347 тестов / 3 пропуска, типы и
сборка API прошли. Это не проверка доставки через рабочий SMTP или на устройства.
Некорректные адреса старой базы нужно выявить при preflight, а не рассылать по ним.
Решение сверено с [настройками SMTP](https://nodemailer.com/smtp) и
[changelog Nodemailer](https://github.com/nodemailer/nodemailer/blob/master/CHANGELOG.md).

## Вход и восстановление в клиенте

Экран Expo получил отдельный режим установки/восстановления пароля через существующий
серверный запрос инструкции. Этот запрос не сохраняет сессию и не раскрывает наличие
аккаунта. Вход по email выбран по умолчанию; переключатель SMS показывается только при
строгом `smsLogin: true` из серверных capabilities, при ошибке/неизвестном значении
остаётся выключенным. Общий контракт вынесен в packages/shared; React Query повторно
использует результат без отдельного состояния разрешений.

Убрано журналирование cookie, заголовков ответа и полного тела ошибок в HTTP-клиенте.
Три клиентских теста проверяют отсутствие сессии при запросе письма, строгие capabilities
и утечки журнала (последняя воспроизведена до исправления).
На локальном собранном вебе в браузере проверены переключение режима, отсутствие поля
пароля и SMS-кнопки, отправка одного запроса и нейтральное подтверждение. API этой
UI-проверки — локальная заглушка без БД/рассылки, не рабочая доставка письма.
Контрольная точка: 390 тестов / 3 пропуска, типы/границы/API/web проходят.
Остальная клиентская интеграция сезонных настроек и заказов ещё не выполнена.

Веб-клиент переведён на HttpOnly cookie: больше не читает/сохраняет Bearer-токен
и персональные данные в localStorage, удаляет старые записи при обращении к модулю
авторизации. Профиль веба существует только в памяти; после перезагрузки источник
истины — `/api/auth/me`. Native SecureStore сохранён, ошибки хранилища и профиль
больше не печатаются в журнал. Шесть тестов, пять воспроизводили старую проблему;
396 тестов / 3 пропуска, типы/границы/API/web проверены.
Веб и API должны оставаться same-site (либо идти через общий reverse proxy),
а при разных origin нужен явный CORS allowlist. Возврат к localStorage при блокировке
cookies не предусмотрен. Вход в стороннем iframe не является launch-сценарием.
Реальные iOS/Android и рабочая топология cookies требуют приёмки.

Сервер выдаёт новые cookie только хосту API, без автоматического родительского
Domain. Старый расчёт домена применяется лишь для удаления прежней cookie при
выдаче/выходе; выход REST и tRPC очищает оба варианта без устаревшего maxAge.
Production всегда требует Secure; вне production HTTPS определяется только через
Express trust-proxy, а не произвольный сырой заголовок. Ответы авторизации и запросы
с cookie/Bearer получают no-store. Восемь сценариев проверены, включая настоящие
HTTP-заголовки Set-Cookie; старый пропущенный тест logout включён.
Контрольная точка: 405 тестов / 2 пропуска, типы/границы/API проходят.
Прежние потенциально раскрытые сессии этим не отзываются задним числом; политика
их отзыва и HTTPS рабочего окружения остаются preflight-вопросами.
## Регистрация: защита от гонки и частичной записи

На настоящем MySQL через HTTP воспроизведены четыре дефекта: два одновременных
запроса оба получали сессию и перезаписывали пароль; аккаунт, появившийся после
предварительной проверки (например, при checkout), тоже перезаписывался;
принималась произвольная версия согласия; ошибка записи согласия оставляла аккаунт.
Выделен insert-only сервис регистрации: стабильный openId с unique-ограничением
даёт ровно одного победителя, существующие записи не обновляются, аккаунт и согласие
записываются в одной транзакции. Сессия выдаётся только после её успешного завершения.
Проверяется текущая версия существующего текста согласия, а не любая непустая строка.
Четыре воспроизводящих теста теперь проходят; полный checkpoint: 409 / 2 пропуска,
типизация/границы/API проходят.

Это не добавляет уникальный email-индекс в рабочую базу и не решает неоднозначность
старых дубликатов email: их нужно проверить и согласованно объединить до выпуска.
Этот промежуточный checkpoint регистрации затем усилен подтверждением почты,
описанным ниже; старая мгновенная выдача сессии не остаётся launch-поведением.

## Самостоятельная регистрация с доказательством владения почтой

`POST /api/auth/register` теперь отвечает 202 `{ok, message}`, не возвращает
пользователя, Bearer или Set-Cookie. Пароль из старого запроса не сохраняется:
новая запись имеет passwordHash=NULL, а установка выполняется только по ссылке
из письма. Согласие, аккаунт и setup-mail/token записываются атомарно. Недоступное
шифрование outbox откатывает регистрацию. Предварительная регистрация чужого email
больше не даёт сессии, которая могла бы получить доступ после будущей оплаты.
Ранее созданные аккаунты не переименовываются и не меняют пароль.

Expo-форма убрала поле пароля при регистрации, показывает существующий текст
согласия/ссылку на политику и требует явного выбора; checkbox не включён по умолчанию.
Приём ответа регистрации не вызывает applySession. Восстановление доступно отдельно.
В браузере проверены блокировка отправки до согласия, доступность checkbox,
отправка текущей версии текста без пароля и подтверждение без перехода во вход.
UI использовала локальную заглушку, реальная БД проверяется отдельно.
HTTP → MySQL → тестовый получатель → password/complete → login проверен:
до письма login=401, completion не выдаёт сессию, после него login=200.
Полный набор: 412 тестов / 2 пропуска, типы/границы/API/web проходят.

Изменён контракт регистрации: веб/API и будущие native-сборки должны выкатываться
согласованно. Обязательно настроить AUTH_LINK_ENCRYPTION_KEY и проверить рабочую
доставку SMTP, прежде чем открывать регистрацию. Старый отдельный Vite-клиент не
является production-клиентом. Уже действующие пароли старой базы сами по себе не
становятся доказательством прежней проверки почты — это предмет migration preflight.

## Разделение серверных маршрутов

Клуб/подписки/обсуждения вынесены в `club/router.ts`, модерация — в
`moderation/router.ts`. Главный `routers.ts` стал меньше на 224 строки, остаётся
точкой сборки контрактов. Сервис комментариев используется напрямую, новых
compatibility-фасадов не добавлено. Это отдельный структурный шаг без изменения
