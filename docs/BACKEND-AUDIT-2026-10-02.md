# Бэкенд: аудит, решение по архитектуре и начало реализации

Дата: 02.10.2026. Ветка: staging. База аудита: 455a110.
Требования сверены с «Маршрут запуска», v1.5 от 01.10.2026.

## Вывод

**Не переписывать весь проект и не менять стек сейчас. Сохранить Express/tRPC,
TypeScript и Drizzle/MySQL; заменить небезопасные сценарии оплаты и идентификации
поэтапно.** Это не косметический перенос файлов: правила доступа, подтверждения
платежа, повторов и отправки писем требуют переработки.

Текущий стек позволяет выполнить требования. Проблема в доверии входным данным,
состояниях и согласованности операций, а не в Express. Полный rewrite также
потребовал бы заново проверить эти правила, переносить данные и поддерживать
совместимость с существующим Expo-клиентом. Сам по себе новый фреймворк ничего
из перечисленного ниже не исправляет.

На старте 183 теста проходили, 3 были пропущены. Это не доказательство корректной
оплаты: исходные тесты почти не проверяли платёжные и авторизационные границы.
Добавленные регрессионные тесты воспроизвели обходы до исправления.

## Границы проверки

Проверены исходники HTTP/tRPC, checkout, обработчики Prodamus, функции изменения
подписки, регистрация/сессии, блокировки, публикации, загрузки медиа, хранение,
фоновые задачи, локальная проверка и конфигурация CI. Внешние запросы — только
официальная документация и аудит зависимостей. Данные пользователей, реальные
платежи, инфраструктура и продакшен не изменялись.

Это первичный предметный аудит, не полный пентест и не заключение о готовности
к выпуску. MySQL, реальная доставка почты, Prodamus sandbox, конфигурация bucket
и фактически работающий nginx пока не проверены интеграционно.

## Открытые блокеры выпуска

Следующие проблемы подтверждены чтением кода; не заявлены устранёнными и не
выдавались за проверенные атаки на продакшен.

### R01 — повтор платежа меняет срок доступа (критично)

`prodamus.ts:fulfillPaidOrder` сначала вычисляет новую дату через nextClubExpiry,
затем `db.ts:markClubPaymentPaid` повторно обновляет paidAt/expiresAt уже оплаченной
записи. Повторный webhook способен продлить тот же платёж повторно. Проверка
`status === paid` вне транзакции не решает одновременные уведомления.

Решение: отдельный billing repository, изолированное соединение транзакции,
блокировка владельца/платежа в постоянном порядке, уникальный provider payment ID,
атомарное изменение состояния и запись события. Тесты последовательного и
конкурентного повтора на одноразовой MySQL. Сейчас getDb использует одно общее
соединение: просто добавить transaction в обработчик недостаточно.

### R02 — подписанный платёж недостаточно связан с заказом (критично)

Не проверяются ожидаемые сумма/валюта, домен формы и ID подписки. Получатель может
определяться из `_param_userId`, разбора orderId или email, а не из неизменяемой
связи checkout → user. Unknown order может создать paid запись. Для recurrence
при отсутствии provider order ID используется Date.now, то есть нет стабильного
ключа повтора. Даже правильная подпись не доказывает правильность бизнес-связи.

Решение: сохранять snapshot стоимости в момент checkout, использовать integer
minor units, выбирать правильный ключ для конкретной формы/типа уведомления,
проверять provider identity и привязку к заказу. Для подписок хранить устойчивый
provider profile/subscription ID. Новая попытка — новая запись, повтор — no-op.

### R03 — полномочия выводятся из неподтверждённой почты (критично, условно)

`oauth.ts` при регистрации выбирает admin через isOwnerAccount; `db.ts` и другие
проверки признают OWNER_EMAIL без доказательства владения почтой. Если задана
почта владельца и такой записи ещё нет, публичная регистрация может создать
привилегированный аккаунт. Если запись существует, этот конкретный путь занят,
но неверный принцип авторизации остаётся.

Решение: штатные роли только из проверенного административного назначения;
отдельный контролируемый bootstrap владельца. Сначала проверить текущие staff
аккаунты, чтобы миграция не заблокировала законного администратора.

### R04 — отмена может сообщить ложный успех (высокий)

`club.cancel` сначала изменяет БД, затем игнорирует false от
cancelProdamusSubscription. Успешный HTTP-код провайдера тоже недостаточен без
проверки ответа API. Пользователь может увидеть отмену при продолжающихся
списаниях. Блокировка сейчас не отменяет подписку у провайдера.

Решение: состояние cancellationRequested/providerCancelled, проверка ответа,
таймаут, долговечная задача retry и видимый статус менеджеру. Оплаченный срок
при добровольной отмене сохраняется; блокировка закрывает доступ сразу.

### R05 — нет полного жизненного цикла identity/email (высокий)

Нет проверенного потока подтверждения почты, первоначальной установки и
восстановления пароля. Checkout пока создаёт технический аккаунт до оплаты,
хотя презентация описывает создание после. После устранения email-login такой
passwordless аккаунт нельзя запускать для пользователей без setup/reset.
Письма магазина не заменяют transactional outbox письма доступа клуба.

Решение: одноразовые setup/reset ссылки, хранить только хэш токена, срок и факт
использования; outbox с уникальным событием и retry. Не слать постоянный пароль
открытым текстом. Существующий пароль при повторной оплате не менять.

### R06 — блокировка ещё не покрывает всю identity/media поверхность (высокий)

Исправлены tRPC staff/клубные пути, но sdk.authenticateRequest и issueSession не
проверяют blockedAt. Отдельный HTTP upload-video авторизуется собственной
проверкой admin и остаётся кандидатом на обход блокировки; вход может выдавать
сессию заблокированному. Нужна централизованная политика сессии с тестами
HTTP/SMS/OAuth/upload, а не обещание «выход со всех устройств уже готов».

### R07 — произвольный импорт URL / загрузка (высокий)

`admin-video.ts:importVideoFromUrl` скачивает произвольный URL и следует редиректам
без исключения private/loopback адресов. Размер буфера проверяется после
arrayBuffer; без Content-Length ответ может занять память до проверки лимита.
Импорт доступен staff, поэтому это не доказанный публичный SSRF, но граница
доверия неверна. Фото принимают присланный MIME без декодирования/EXIF очистки;
avatar upload не имеет отдельного маленького лимита.

Решение: allowlist источников или убрать скачивание URL в пользу VK embed,
запрет редиректов/внутренних адресов, timeout и потоковый byte cap. Фото
декодировать/перекодировать, ограничить пиксели/размер/форматы, удалить EXIF.

### R08 — закрытые медиа имеют постоянные публичные URL (высокий)

storage.ts использует ACL public-read. Проверка доступа в API не закрывает уже
полученную ссылку на файл. Закрытая доставка потребует отдельного приватного
storage, временных разрешений и проверки подписки. HLS/шифрование/watermark из
презентации — отдельная опция, пока не выбрана; защита от записи экрана не
гарантируется. Нельзя закрыть весь существующий bucket без инвентаризации:
там также публичные картинки и материалы.

### R09 — конфигурация периметра и эксплуатация (высокий / проверка нужна)

index.ts отражает любой Origin с credentials. app не задаёт security headers;
их наличие на фактическом nginx не проверялось. Запрос auth обновляет lastSignedIn
в БД каждый раз, часть списков/статистики выбирает всю таблицу. In-memory
rate limit не общий для нескольких процессов. Публичный YouTube proxy запускает
внешнюю утилиту и проксирует видео без общего quota — источник нагрузки.

Решение: allowlist origin и CSRF модель, headers на приложении/периметре,
shared limiter или явное ограничение одним процессом, пагинация и замеры
нагрузки, публичные ролики через embed. Проверить реальные deployment настройки.

### R10 — зависимости и CI (блокер release review)

`pnpm audit --prod --json` завершился с кодом 1. Сводка native audit:
2 critical, 99 high, 65 moderate, 9 low. Это счётчики отчёта менеджера, **не
число подтверждённых эксплуатируемых дыр в API**. Expo/build tooling попадает в
production dependency tree. Требуется reachability-разбор каждого critical/high.
Есть advisories для tRPC, Drizzle, mysql2, axios, nodemailer и инструментов.
Например, экспериментальный Next caller tRPC здесь не обнаружен; это не причина
объявлять весь пакет безопасным или менять major без тестов.

В корне два lockfile; packageManager и CI указывают pnpm. Нужно зафиксировать
единственный installation contract отдельным изменением. CI запускает только
regression/quiz и web build, не новые backend tests/check/API build; push staging
не входит в ветки запуска текущего GitHub workflow. Работа на GitLab сама по
себе не доказывает выполнение этого workflow. Нельзя считать локальные коммиты
проверенным pipeline или деплоем.

## Что из v1.5 ещё делать

Порядок: безопасность оплаты → транзакции/повторы → identity/setup/reset →
outbox/почта → отмена/блокировки → безопасный контент/фото → настройки запуска.

- Web/PWA — текущий клиент, не новый native backend.
- SMS выключить серверно для первого этапа, не только спрятать кнопку.
- Shop online payment выключить серверно, добавить заказ менеджеру по почте.
- Срок хранения комментариев сейчас 90 дней (`runDataRetentionMaintenance`),
  в v1.5 — год. Менять после проверки состава данных, а не запускать purge сейчас.
- Сезонное оформление — административная конфигурация дат и четырёх наборов.
- Поддержка ссылок/курсива уже частично есть; нужны roundtrip и draft-attachment
  сценарии, не переписывание всего редактора.
- Pen pals позднее, web push — отдельный этап/выбор. Доступные маршруты нужно
  закрывать capability-проверкой, если функция не входит в запуск.
- VK embed и защищённое видео — разные режимы. Последний не внедрять без выбора.

Точный backlog и критерии — `tasks/plan.md`, `tasks/todo.md`. Существующие
незавершённые задачи структурного рефакторинга сохранены, не объявлены выполненными.

Локальные коммиты: 7fe622e, ebd8646, 8fdb8d2, 6eeb92d. Не отправлены на remote,
не выложены. Отдельного backend lint script нет; root lint относится к frontend.
Новые изменения рассмотрены по корректности, читабельности, архитектуре,
безопасности и нагрузке. Новые зависимости и миграции не добавлены. Вердикт:
ремонт улучшает локальный код, **выпуск всего backend пока заблокирован R01–R10**.

Для каждого изменения сначала наблюдался ожидаемый red: 8 ошибок webhook,
6 ошибок checkout, 13 ошибок доступа, 1 ошибка prototype pollution. После
исправления focused tests проходят. Итоговые команды: `pnpm test`, `pnpm check`,
`pnpm build`, `git diff --check`. Снимок итогового результата обновляется ниже.

Поведение старого клиента: возвращается `{ url, user: null }`, автоматического
входа нет; claimPending возвращает false до подтверждения webhook. Клиентский
paid=1 не даёт прав. Это намеренное изменение небезопасных побочных эффектов.
Имена tRPC процедур сохранены; перестройка UI не входила в этот ремонт.

**Не выкатывать текущую итерацию отдельно как готовый запуск:** passwordless
пользователям нужен setup/reset. Кроме того, официальный пример recurrence не
содержит payment_status. Теперь такой payload не выдаст доступ; нужно получить
реальные sandbox fixtures, определить безопасное доказательство успешного
списания и сверить уведомления до включения боевой оплаты. Возвращаемый ignored
не ставит уведомление в retry/outbox — reconciliation пока отдельный блокер.
