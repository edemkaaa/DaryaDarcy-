Сверено с кодом 11 ноября 2026 года. Актуальную модель определяют
[schema.ts](../../packages/database/src/schema.ts),
[relations.ts](../../packages/database/src/relations.ts),

## Контакт, идентичность и публичные адреса

`users.phone` относится к прежней телефонной идентичности. `users.contactPhone`
содержит сообщённый номер для связи без подтверждения: он не является паролем,
способом входа или доказательством владения телефоном. Подтверждённый платёж
может заполнить пустой контакт существующего пользователя; записанный контакт
не должен молча заменяться входящим номером заказа.

`sessionVersion` используется для отзыва сессий. `profileRevision` и ревизии
контента защищают от конкурирующих правок. Роль и блокировка проверяются по
актуальному аккаунту. Публичный DTO выбирается явно и не должен расширяться
при добавлении колонок в `users`.

Числовой первичный ключ остаётся внутренней связью. Публичный UUID поста служит
адресом; его наличие не даёт права читать черновик или клубный материал.
Удалённый/скрытый объект не становится доступным через другой вид ID.

## Где выполняются чтение и запись

Один API-процесс владеет своим ленивым пулом
[connection.ts](../../apps/backend/src/database/connection.ts).
Репозитории получают существующий клиент; совместимые фасады `db.ts` не должны
создавать дополнительное подключение для каждой функции. Бюджет нескольких
процессов суммируется: соединения worker locks тоже занимают ресурсы.

| Данные | Основная точка чтения/записи |
| --- | --- |
| Каталоги Ленты/Клуба | [post-catalog-repository.ts](../../apps/backend/src/content/post-catalog-repository.ts) |
| Административные посты, календарь, счётчики | [post-admin-repository.ts](../../apps/backend/src/content/post-admin-repository.ts), отдельные page/calendar/count helpers в `content/` |
| Карточка и объявление | [post-detail-repository.ts](../../apps/backend/src/content/post-detail-repository.ts) |
| Реакции | [post-reactions.ts](../../apps/backend/src/content/post-reactions.ts) |
| Статьи | [article-repository.ts](../../apps/backend/src/content/article-repository.ts), [article-writes.ts](../../apps/backend/src/content/article-writes.ts) |
| Участники и оплаты | [membership-repository.ts](../../apps/backend/src/admin/membership-repository.ts), отдельные page helpers |
| Доступ и settlement | [billing/](../../apps/backend/src/billing/) |
| Квитанции загрузок и выдача | [content/private-*](../../apps/backend/src/content/), [media/](../../apps/backend/src/media/) |

Пустой успешный результат и отказ БД являются разными состояниями. Сбой чтения
медиа нельзя подменять постом с пустым массивом вложений. Статусные запросы
проверяют сохранённый результат операции, а не повторяют её побочные эффекты.
Часть прежних списков остаётся непагинированной или использует offset;
наличие нового page-метода не меняет автоматически старый вызов.

## Транзакции и журналы

Создание материала, его начальные привязки и квитанция создания фиксируются
согласованно. Хеш ключа привязан к actor и назначению; отдельный отпечаток
проверяет неизменность входного намерения. Повтор ключа не должен создавать
дубликат после потери ответа или после удаления прежнего материала.

Операции редактора сравнивают ожидаемую ревизию под блокировкой строки.
Повторная проверка actor исключает использование роли или сессии, отозванной
пока запрос ожидал соединение/блокировку. Порядок блокировок сохраняется между
конкурирующими сценариями.

Письма после оплаты имеют durable outbox. Принятие SMTP не входит в SQL commit:
после аварии внешний результат может остаться неизвестным. Lease проверяется
перед отправкой и перед записью результата; он не создаёт общей транзакции с SMTP.
Публикационный push имеет отдельно согласованный best-effort режим.

S3-загрузка и привязка в MySQL тоже являются разными операциями. Автоочистка
непривязанных объектов не включается только по ошибке HTTP: commit мог пройти.
Журналы восстановления, индексы и записи миграций не являются удаляемым кешем.

## Миграции

Старые SQL и метаданные Drizzle сохраняются побайтово. Даже комментарий меняет
контрольную сумму применённой миграции; пояснения находятся в справочнике файлов.
Исторические расхождения 0017–0019 проверяются по конкретной целевой БД.
Нельзя исправлять отказ preflight удалением строк журнала или добавлением
фиктивной истории.

Для пустых изолированных баз существует проверяемый fresh-профиль (52 шага
на дату сверки). Он не ремонтирует существующую рабочую историю.
`pnpm db:preflight` проверяет файлы и явно выбранную историю, но ничего не
применяет. `pnpm db:push` требует успешного preflight для того же `DATABASE_URL`
и затем применяет заранее подготовленный SQL. Общей блокировки между проверкой
и применением нет: конкурентные миграторы не запускают.

Новая база, восстановление из снимка и обновление существующей базы — разные
процедуры. Перед рабочими изменениями нужны резервная копия, сверка привязок и
репетиция на отдельной БД. Для тестов разрешена только одноразовая `backend_test`
по [политике подключения](../../tooling/scripts/test-database-policy.ts).
Применение миграции не подтверждается датой её файла или старым отчётом.
