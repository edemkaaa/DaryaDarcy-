# Несколько API-процессов: локальный контракт

Решения владельца 03.11.2026: нужны несколько API-процессов; push о новых
публикациях остаётся best effort. Это не меняет обязательства писем после оплаты.

## Границы

- Один основной MySQL, общая схема для всех API. Новый Redis/брокер не нужен.
- `API_REPLICA_COUNT` по умолчанию 1; `API_COORDINATION_MODE` — `local` или
  `mysql`, по умолчанию `local`. Более одной реплики допускается только с `mysql`.
  Legacy SMS-вход при нескольких репликах запрещён: по договору он выключен,
  его старый локальный счётчик не объявляется распределённым.
  Ошибка конфигурации или отсутствие схемы останавливает запуск до listener.
- В mysql-режиме все существующие HTTP-квоты и задержка входа на аккаунт общие.
  Ключи хешируются; email, IP, пароли и recovery proof не хранятся в таблице.
  Пороги прежние. При отказе общего хранилища запрос завершается ошибкой,
  локальный обход лимита не допускается. Успешный вход не выдаёт cookie, если
  завершение проверки лимита не подтверждено.
- Миграция 0050 добавляет только служебные временные счётчики с индексом срока
  жизни. Максимум 10000 живых записей каждого типа; истёкшие удаляются порциями.
  Существующие таблицы и данные не преобразуются.
- Короткие операции счётчиков сериализованы именованной блокировкой MySQL.
  Время берётся у БД. Отложенный успешный вход не обнуляет более новую попытку.
- Одновременный запуск одинакового фонового задания между репликами исключает
  именованная блокировка на отдельном удерживаемом соединении. Не получившая
  блокировку реплика пропускает этот запуск. При ошибке блокировки работа не
  начинается. Соединение освобождается после работы; сомнительное уничтожается.
- Это координация на одном MySQL, не обещание exactly once при потере соединения
  или аварии во время внешней отправки. Доменные receipts/транзакции сохраняются.
  Автоповтор публикационного push и новая очередь не добавляются.
  Взаимное исключение действует пока жива удерживаемая SQL-сессия; это также не
  глобальное расписание «один запуск на интервал». Реплики могут выполнить job
  последовательно, и domain due-checks/claims должны оставаться идемпотентными.
- На реплику остаётся пул 10 соединений, включая удерживаемые worker locks.
  Ресурсы, общий max_connections, deployment и восстановление после отказа БД
  проверяются отдельно перед включением нескольких процессов на сервере.

## Проверка и выпуск

Сначала disposable MySQL: настоящие миграции, два независимых процесса,
конкурентная квота/вход, отказ хранилища, истечение, устаревший success,
взаимное исключение jobs и освобождение после ошибки/остановки. Затем unit,
типы, backend lint/build и неизменность API-контракта. Фронт не меняется.

Сейчас работа только локальная. На сервере новая миграция и режим не включаются.
Выпуск потребует свежего бэкапа, проверки истории, применения 0050 и одинаковой
настройки всех API (включая ограниченный TEST-ingress), прежде чем их масштабировать.
Откат приложения — сначала к одной реплике; таблицу временных счётчиков можно
оставить. Не удалять её, пока есть процесс, использующий mysql-координацию.

## Обоснование MySQL-блокировок

Используются документированные session-scoped GET_LOCK/RELEASE_LOCK: commit не
освобождает такую блокировку; окончание сессии освобождает. Поэтому соединение
удерживается до завершения работы, имя включает хеш схемы и области, при
сомнительном unlock соединение уничтожается. Не применять эту схему к нескольким
независимым primary MySQL или NDB. Источник:
[MySQL 8.4 locking functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html).
Заимствование/возврат соединений соответствует
[mysql2 Promise API](https://sidorares.github.io/node-mysql2/docs/documentation/promise-wrapper).
