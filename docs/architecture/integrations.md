## Секреты и конфигурация

Параметры перечислены в [.env.example](../../.env.example). Рабочие ключи, SMTP-пароли, S3-ключи и платёжные секреты не коммитятся. Для тестов внешние операции должны быть изолированы; уборка репозитория не запускает платежи, отправку писем или загрузку в S3.

AUTH_LINK_ENCRYPTION_KEY нужен для зашифрованных ссылок в outbox. Если SMTP не настроен, сохранение задания не означает, что адресат получил письмо.

## Prodamus: граница демо-режима

Обычная подпись сама по себе не доказывает реальную оплату: согласно
[документации Prodamus](https://help.prodamus.ru/payform/tekhnicheskaya-dokumentaciya/webhook-ob-oplate),
демо-режим из настроек может сохранять обычный ключ. Боевой обработчик локальной
ветки отклоняет включённый `demo_mode` / `demoMode` или `subscription.demo` до
выдачи доступа и отмены подписки. Отсутствующий маркер не подтверждает режим
провайдера; подпись с суффиксом `demo` по-прежнему не принимается как боевая.

Предоставленный `testpage1.payform.ru` содержит чужие определения подписок и
общие адреса уведомлений. Создание демо-ссылки проверено, но оплата, доставка
callback и доступ не проверены. План отдельного диагностического подключения
с вымышленными данными — в [tasks/plan.md](../../tasks/plan.md); включение
демо-выдачи доступа, смена общих адресов и автопродление этим не разрешены.

В локальной ветке добавлен отдельный диагностический контур, по умолчанию
выключенный: `POST /api/prodamus/sandbox/webhook` и операторская команда
[prodamus-sandbox-link.ts](../../tooling/scripts/prodamus-sandbox-link.ts).
Она строит только подписанную демо-ссылку на фиксированный тестовый магазин,
без пользовательских данных и создания покупки. На сервер не выложено.
Контракт и порядок проверки — в [руководстве стенда](../operations/teamassist-staging.md#демо-prodamus--локальный-диагностический-контур-2026-10-08).
Успешный ответ `{mode: "demo", accessGranted: false, notificationVerified: true}`
означает только проверку конкретного демо-уведомления, не доступ, боевую оплату
или сохранённую квитанцию. Проверка доставки от Prodamus ещё не выполнена.

## Prodamus TEST: подтверждение возврата в локальной ветке

Для отдельно согласованного dev-only клуба добавлен
`POST /api/prodamus/test/result`, см.
[контроллер](../../apps/backend/src/billing/prodamus-test-club.controller.ts) и
[проверку результата](../../apps/backend/src/billing/prodamus-test-result.ts).
Это не изменение боевого webhook или способ входа по email. На сервер новый
маршрут не открыт и новый код не выложен; frontend-диалог пока не подключён.

Новые TEST checkout-ссылки сохраняют `/club?paid=1`, добавляя в **fragment**
`paymentReturn` — HMAC capability для одного заказа, действующую 24 часа от
создания checkout. Она подписана отдельным назначением, не является паролем,
сессией или разрешением открыть контент. `paid=1` без proof не подтверждает
платёж; прежние ссылки не переписываются. Платёжный провайдер получает proof
в подписанном success URL, но HTTP-запрос возврата к нашему сайту не содержит
fragment. Клиент должен убрать proof из адреса до сторонней телеметрии и не
сохранять его в общедоступных логах/ссылках.

Запрос: JSON `{token}`, без query/cookie, `Content-Type: application/json`,
валидный UUID `Idempotency-Key`, повторяемый для одной проверки возврата.
Клиент использует `credentials: "omit"`. Используется прежний общий бюджет
проверки возврата (60/IP и 12/client intent в минуту), без изменения лимитов,
CORS, доверия к прокси или cookie-авторизации. GET/посторонние пути закрыты в
ограниченном TEST runtime. Ответы не кешируются.

Ответ содержит только `state`, `nextAction`, `emailStatus`:

- `unknown` / `pending`: остальные поля `null`; неверный/истёкший proof,
  неизвестный заказ или нарушенная привязка не дают успеха.
- `succeeded`: только оплаченный заказ, его durable receipt и точное
  transactional mail-событие для текущего незаблокированного получателя.
  `nextAction` — `setup` либо `login`, `emailStatus` — `pending`, `sent` либо
  `unavailable`. `sent` означает принятие SMTP, не доказанную доставку в inbox.
- Некорректный транспорт — 400/415, исчерпанный бюджет — 429 с Retry-After,
  выключенная конфигурация/недоступное хранилище — 503 с постоянной ошибкой.

Чтение не вызывает провайдера/SMTP, не создаёт пользователя, токен входа,
сессию, новую квитанцию или срок доступа. Email, ID пользователя, password hash
и зашифрованная ссылка из outbox не возвращаются; hash и ссылка даже не входят
в выбранные поля результата. Существующий аккаунт не получает новый reset.
Оплаченный статус не заменяет обычную проверку подписки текущей сессии.
Удалённая/непривязанная история receipt/mail остаётся `unknown`, не угадывается.
Настоящая оплата пользователя, его письмо, диалог и новый edge rollout требуют
отдельной сквозной приёмки; исходная диагностическая интеграция выше остаётся
историей другого контура.
