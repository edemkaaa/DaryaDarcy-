# API и границы модулей

API запускается через NestJS с Express-адаптером; контракт tRPC сохраняется. Точка запуска — [src/\_core/index.ts](../../apps/backend/src/_core/index.ts), композиция без запуска фоновых задач — [application.ts](../../apps/backend/src/_core/application.ts), модули Nest — [app.module.ts](../../apps/backend/src/app.module.ts), состав tRPC — [routers.ts](../../apps/backend/src/routers.ts). Этот документ описывает исходный код, не подтверждает состояние сервера.

Перенос идёт по модулям: health, capabilities и настройки запуска уже обслуживаются
контроллерами NestJS. Установка/восстановление пароля и повторное письмо доступа
тоже перенесены в нативный IdentityModule, вместе со входом, регистрацией,
сессией и закрытыми по флагу SMS-маршрутами. Чтение ленты (списки, поиск, страницы и теги), видео, закладок, взаимодействий и статей обслуживает [ContentReadService](../../apps/backend/src/content/content-read.service.ts). Создание, правку, ручную публикацию и реакции постов обслуживает [ContentWriteService](../../apps/backend/src/content/content-write.service.ts), обсуждения — [ContentCommentService](../../apps/backend/src/content/content-comment.service.ts), административные tRPC-загрузки — [ContentUploadService](../../apps/backend/src/content/content-upload.service.ts), внедрённые через ContentModule. tRPC-роутеры сохраняют входные схемы и middleware; сервисы — правила видимости и последовательность записи/анонса. Raw-видеозагрузка, импорт по ссылке и остальные административные операции остаются следующими этапами.
Остальные HTTP-адаптеры и tRPC подключены в ту же HTTP-программу и
сохраняют существующие проверки доступа. MySQL / Drizzle не меняются; TypeORM
не вводится. План и проверки — в [ADR-005](../decisions/0005-nestjs-modular-backend.md).
Порядок middleware остаётся обязательным: HTTP-защита → raw webhook и проверка
загрузок → ограниченные парсеры → обработчики. Стандартные body-парсеры Nest
отключены. Фоновые интервалы пока запускаются из index.ts; их lifecycle ещё
не перенесён в Nest, штатное завершение workers не заявляется.

HTTP-композиция tRPC принадлежит [TrpcModule](../../apps/backend/src/_core/trpc.module.ts): [TrpcService](../../apps/backend/src/_core/trpc.service.ts) получает сервисы контента и сессий через Nest и собирает роутер/контекст для текущего приложения. Standalone appRouter остаётся для прямых вызовов и инструментов, но HTTP использует явно внедрённые сервисы; глобального service locator и необязательных fallback-зависимостей нет.

Middleware сессии и ролей tRPC остаются в [\_core/trpc.ts](../../apps/backend/src/_core/trpc.ts), общая доменная проверка подписки — в [identity/club-access.ts](../../apps/backend/src/identity/club-access.ts), с прежним реэкспортом для остальных модулей. Материалы и обсуждения клуба не являются публичными. Блокировка аккаунта и актуальная роль проверяются сервером.

feed.listPaginated принимает целый limit от 1 до 50 (по умолчанию 12) и optional/null cursor — неотрицательное безопасное целое смещение. Дробные/отрицательные значения и небезопасные целые отклоняются как BAD_REQUEST / HTTP 400 до запроса в БД; раньше дробные LIMIT/OFFSET и отрицательный OFFSET приводили к SQL-ошибке и HTTP 500. cursor отсутствует или null — первая страница, ответ сохраняет posts и nextCursor.

Каталог использует прежние SQL-helpers: публичная лента исключает club, draft, scheduled и published=false, фильтрует теги и текст, сохраняет порядок и вложения. Видео остаются публичными только при published=true, заголовки нормализуются в NFC. Внедрение сервисов не переносит SQL/владение пулом из db.ts и не вводит защиту публичных URL файлов. YouTube HTTP-стрим остаётся переходным адаптером: скрытая запись отклоняется до внешней загрузки, Range и проверка публикации при кешированном разрешении сохраняются.

ContentWriteService получает уже проверенные данные из [общих входных схем](../../apps/backend/src/content/post-write-input.ts); adminProcedure проверяет свежую сессию и роль до вызова сервиса. Сам сервис не является публичным HTTP-обработчиком: другие адаптеры обязаны сохранить эту границу авторизации. Хеш payload для защиты от повторного создания строится из валидированного намерения, до добавления серверных дат и нормализации для хранения; ключ запроса отдельно привязан к ID администратора. SQL-транзакции остаются в существующих helpers, доступ к пулу через db.ts пока переходный. Анонс вызывается только после commit и только владельцем создания/перехода; окно потери push между commit и отправкой остаётся задачей N12, не устранено переносом в Nest.

Ручное admin.confirmPost сохраняет ответ {success:true} при повторе и отсутствующем
ID, но анонсирует только свою завершённую публикацию. Транзакция с блокировкой
поста находится в [content/publication.ts](../../apps/backend/src/content/publication.ts).
Подтверждение до scheduledAt разрешено, existing publishedAt сохраняется.
admin.updatePost сохраняет пост и замену видео одной транзакцией в
[content/post-editor.ts](../../apps/backend/src/content/post-editor.ts), с той же
блокировкой поста. Ошибка вложения откатывает весь edit. Поле videos отсутствует —
вложения сохраняются; [] удаляет только видео. Анонс использует сохранённый текст
и аудиторию и возвращается только владельцу перехода в публикацию после commit.
admin.createPost сохраняет новый пост и начальные видео одной транзакцией в
[content/post-creator.ts](../../apps/backend/src/content/post-creator.ts).
Числовой ID возвращается после commit; незавершённый пост невидим читателям и
планировщику. Ошибка видео откатывает весь create, без анонса публикации.
Это не очередь доставки push. Отдельные uploadMedia и legacy-создание тизеров
не объединены с другими операциями. Конфликты версий редактора не выявляются;
повтор createPost без ключа после потери ответа небезопасен: создаётся новый пост.

### Ключ повторного создания публикации

admin.createPost принимает optional idempotencyKey: 16–128 символов из
A–Z, a–z, 0–9, точки, подчёркивания, двоеточия и дефиса; UUID подходит.
Клиент создаёт ключ один раз на намерение сохранить новый пост и сохраняет его
для повторов, а не генерирует на каждую попытку. Ответ остаётся числовым ID.
Тот же ключ и принятые данные возвращают исходный ID без новых вложений и анонса.
Другие данные с тем же ключом дают CONFLICT / HTTP 409, без изменения поста.
Новый ключ означает отдельное создание, даже при одинаковом тексте.

Ключ привязан к текущему аутентифицированному администратору и операции;
сессия, блокировка и роль проверяются при каждом повторе. В БД хранится хеш ключа,
а не сам ключ или тело запроса. Хеш данных учитывает defaults схемы и порядок
массивов, но не порядок свойств объектов и генерируемую сервером дату публикации.
Данные с ключом должны быть JSON-совместимыми. Ошибка транзакции откатывает ключ
вместе с постом/вложениями. Конкурентный повтор ждёт владельца ключа в пределах
таймаута блокировок MySQL; ошибка ожидания не подтверждает успех или откат другого
запроса. При неизвестном результате повторяют **тот же ключ и данные**.

Запись результата не удаляется при редактировании/удалении поста и не имеет TTL:
повтор вернёт старый ID, но не восстановит пост. См. [ADR-004](../decisions/0004-post-creation-idempotency.md).
Фронтенд пока не передаёт ключ: подключение редактора — отдельный этап.

### Кодирование и ключи загружаемых медиа

admin.uploadMedia принимает непустой канонический стандартный base64: без пробелов,
data-URI и URL-safe алфавита, с корректным padding там, где он требуется. Пустые,
повреждённые и неканонические строки возвращают BAD_REQUEST / HTTP 400 до записи
в хранилище или БД. Предел кодированной строки — прежние 50 MiB JSON; HTTP-предел
включает также метаданные, поэтому это не разрешение на файл размером 50 MiB
после декодирования. Парсер и права администратора не изменены.

Ключи имеют вид `feed/videos/<UUID>`, `feed/audio/<UUID>` или `feed/documents/<UUID>`:
имя, путь и расширение клиента в них не входят. URL — непрозрачный идентификатор,
расширение по нему определять нельзя. filename остаётся отдельным отображаемым
именем с прежним подавлением сырых имён камеры. Поля MIME/type, размер в байтах,
optional postId сохраняются. Прежние поля ответа url/mediaId сохранены;
добавлены обязательные mimeType и fileSize с итоговым серверным MIME и числом
декодированных байт, одинаковые для standalone- и связанных загрузок.
Повтор успешной загрузки создаёт
новый объект: UUID не делает запрос идемпотентным. Старые объекты не переименованы.

Заявленный MIME проверяется до декодирования: `audio/*` для аудио, `video/*` для видео;
для документов — application/pdf, application/msword,
application/vnd.openxmlformats-officedocument.wordprocessingml.document и text/plain.
application/octet-stream допускается во всех трёх категориях как fallback редактора.
Пустое/некорректное MIME-имя, управляющие символы, значение длиннее 128 символов
или несовместимая категория дают BAD_REQUEST / HTTP 400 до записи в storage/SQL.
Имя нормализуется в нижний регистр, пробелы вокруг него удаляются; корректные
ASCII-параметры сохраняются, включая charset/codecs с token или quoted-string
значениями. Параметры без значения, незакрытые кавычки, пустые параметры и
синтаксис нескольких MIME-значений отклоняются; HTAB не принимается, а obs-text
внутри параметров не допускается (внешние пробелы нормализуются).
Правила name=value/token/quoted-string основаны на [RFC 9110 §5.6.6](https://httpwg.org/specs/rfc9110.html#parameter).
После декодирования MIME уточняется по байтам. Storage и SQL-связь, создаваемая
этим вызовом при переданном postId, получают одно уточнённое значение.
Имена/типы прежних полей запроса и ответа не изменились; допустимые MIME-значения
ограничены. Редактору необходимо передавать mimeType/fileSize из ответа загрузки
при финальном сохранении вложений. Подключение редактора и обновление его типов
оставлены фронтендеру; см. [передачу изменений](../development/backend-handoff-2026-10-05.md).

Проверка base64 подтверждает только кодирование, не формат и безопасность файла.
Аудио/видео дополнительно проходят распознавание бинарной сигнатуры через file-type
22.1.1 до записи в storage/SQL. Неизвестные форматы, HTML/SVG без сигнатуры медиа,
документы/архивы/изображения и однозначно чужая категория дают BAD_REQUEST / 400.
В обоих местах сохраняется распознанный MIME: например, WAV с заявленным
audio/mpeg, audio/x-wav или application/octet-stream получает audio/wav. Параметры
клиента сохраняются только при точном совпадении MIME-имени; codecs остаётся
метаданными, а не результатом проверки кодека. MP4 и WebM — общие контейнеры:
для категории audio используются audio/mp4 и audio/webm без анализа дорожек.
Распознавание выполняется в worker thread с отдельной копией ограниченных по
размеру байтов и пятисекундным тайм-аутом активной задачи. Задачи последовательны
внутри процесса; worker завершается до запуска следующего. Тайм-аут/ошибка парсера
отклоняют файл, сбой запуска/runtime обработчика даёт безопасный общий 500.
Общий объём ожидающих HTTP-запросов этим не ограничен; это не новая HTTP-квота
и не защита от общего DoS. Размеры HTTP/base64 и права администратора прежние.
[file-type](https://github.com/sindresorhus/file-type) прямо описывает сигнатуру
как best-effort подсказку: проверка дорожек/воспроизведения, целостности файла,
скриптов/макросов/полиглотов и антивирус здесь не реализованы.

Для документов с заявленным application/pdf или
application/vnd.openxmlformats-officedocument.wordprocessingml.document теперь
требуется точное совпадение распознанного MIME после нормализации MIME-имени.
HTML/SVG, неизвестные байты, обычный ZIP, пакет с объявленным макро-типом Word
и перестановка PDF/DOCX дают BAD_REQUEST / 400 до storage/SQL. Корректные параметры
заявленного MIME и исходные байты сохраняются. Это классификация сигнатуры/пакета,
не проверка целого PDF/OPC, отсутствия JavaScript или скрытых макросов. CFB-контейнер
не является доказательством DOCX, а сигнатура DOC не отличает Word от Excel.
TXT (text/plain) отклоняет распознанные бинарные форматы, затем проверяет весь
текст через fatal TextDecoder порциями 16 KiB, не меняя исходные байты.
Проверка текста синхронная и линейная; порции ограничивают временные строки,
не общее время CPU/объём ожидающих запросов и не служат защитой от DoS.
Допустимы UTF-8, UTF-16LE/BE и Windows-1251, включая поддерживаемые aliases.
Без charset используется UTF-8 или Unicode BOM; Windows-1251 требует явного
text/plain; charset=windows-1251. Повторный/пустой/неподдерживаемый charset,
конфликт BOM, неполные/ошибочные последовательности и C0/C1 кроме tab/LF/CR/form
feed дают 400 до storage/SQL. При отсутствии charset он дописывается, итоговый
MIME ограничен теми же 128 символами. Параметры проходят существующую ASCII-грамматику;
полная quoted-string не интерпретируется как вложенный параметр.
Декодирование с fatal/stream опирается на [Node 22 TextDecoder](https://nodejs.org/download/release/v22.23.0/docs/api/util.html#class-utiltextdecoder).

Document/application/octet-stream больше не сохраняет произвольные бинарные
байты: допустимы распознанный PDF/DOCX или прошедший проверку Unicode-текст.
MIME заменяется на application/pdf, DOCX или text/plain с определённым charset;
параметры opaque-типа не переносятся. Чужие распознанные бинарные типы, включая
обычный ZIP, DOCM, аудио/видео и generic CFB, дают 400. Нераспознанные байты
должны пройти полную проверку UTF-8/BOM-текста; legacy-кодировка не угадывается.
Picker без charset может отклонить TXT Windows-1251: используйте UTF-8 или
передайте text/plain с нужным charset. Буквальный HTML/код остаётся допустимым
текстом, а не активным MIME: это не HTML-фильтр и не защита от MIME-sniffing;
проверка Content-Disposition/nosniff/приватности у провайдера остаётся открытой.

Старый DOC (application/msword) всё ещё проверяется только по метаданным.
Смена метки на него обходит проверку содержимого документов; нельзя считать
generic CFB доказательством Word или объявлять все документы безопасными.
Standalone-редактор позднее сохраняет клиентский MIME через create/update,
не уточнённый uploadMedia: целостность метаданных/владения требует отдельной
правки; сервер уже возвращает mimeType/fileSize, редактор их пока не использует.
Нельзя выпускать проект на основании
только этого шага. Новых зависимостей/HTTP-квот/схем нет.
Ранее загруженные объекты повторно не проверялись.
Хранилище и SQL не составляют одну транзакцию. Непривязанный объект после ошибки
не удаляется автоматически: для безопасной уборки нужны проверка сохранённых
ссылок и владения, в том числе при неизвестном результате SQL commit.

### Отдельная загрузка видео

`POST /api/admin/upload-video?filename=...` принимает бинарное тело только от
действующего администратора. Авторизация выполняется до чтения тела и повторно
в обработчике; HTTP-предел остаётся 80 MiB, превышение даёт 413.
Успешный ответ по-прежнему `{ url }`, без метаданных tRPC-загрузки.

Тот же нормализатор MIME и изолированный распознаватель сигнатур теперь проверяют
эту загрузку до записи в хранилище. При отсутствующем Content-Type используется
video/mp4; допустим также application/octet-stream. Несовместимый/повреждённый
MIME, неизвестные байты, HTML/SVG, документы, архивы и отдельные аудиоформаты
дают 400 с общим сообщением. Распознанный MIME заменяет неверную видео-метку;
параметры сохраняются только при совпадении MIME-имени. Исходные байты не меняются.
MP4/WebM/MOV проверены как контейнеры, не на наличие видеодорожки, воспроизведение
или вредоносное содержимое. Сбои инфраструктуры/хранилища дают общий 500 без
внутренних деталей. URL не следует разбирать для определения формата файла.
Новые ключи имеют вид `feed/reels/<UUID>_<очищенное имя>`: время больше не
используется как идентификатор, одинаковые имена не направляют разные загрузки
в один объект. Существующие объекты не переименованы. Это не идемпотентность:
повторный успешный запрос создаёт новый объект. Реестр владения и миграция
raw-обработчика в Nest-сервис — отдельные задачи.

### Сохранение аудио и документов

Новый редактор сначала вызывает admin.uploadMedia **без postId**, затем одним
admin.createPost или admin.updatePost передаёт optional attachments: массив
{type:audio|document,url,filename,mimeType,fileSize}. updatePost также принимает
optional removedMediaIds. Добавления и удаления привязок входят в ту же транзакцию,
что текст и видео; удалять этим полем можно только аудио/документы данного поста.
Старые вызовы без новых полей сохраняют прежнее поведение. При новом запросе с
вложениями к отсутствующему посту возвращается NOT_FOUND, без создания привязок.

Промежуточный draft не создаётся: ошибка загрузки не изменяет опубликованный пост,
а успешная правка уже опубликованного поста не вызывает повторный анонс. После
потери ответа редактор не повторяет неподтверждённую запись автоматически. После
явного 4xx повтор использует подтверждённые загрузки. Уже завершённое сохранение
нельзя повторить тем же редактором. Серверная защита createPost работает только
при передаче idempotencyKey; текущие вызовы редактора остаются без ключа.

Загрузка и транзакция БД не атомарны между собой: после отмены/ошибки в хранилище
могут остаться непривязанные файлы. Автоматическое удаление таких файлов здесь не
введено. URL проверяется как HTTP(S) без credentials, не загружается сервером;
право задавать публичные ссылки остаётся только у администратора, как у photos/videos.
Это исправление не делает публичное хранилище защищённым для платного контента.
Контракт клиента генерируется командой pnpm api:contract и проверяется pnpm check:api.

## HTTP вне tRPC

Общая HTTP-политика сессии и ролей — [SessionService](../../apps/backend/src/identity/session.service.ts), экспортированный IdentityModule. Каждый запрос повторно проверяет JWT и актуальный аккаунт в БД; optional-проверка возвращает null при недоступной сессии. Контроллеры сохраняют собственные форматы ошибок. TrpcService использует эту же optional-проверку для HTTP-контекста; tRPC middleware и самостоятельный createContext сохраняются.

[HTTP-guards](../../apps/backend/src/identity/http-access.ts) проверяют права до входа в обработчик: настройки доступны только admin, повторное письмо — admin/moderator. Проверка записи настроек и аудит письма дополнительно остаются внутри доменных транзакций. Узкий фильтр отказов сохраняет прежние plain-text/JSON ответы и no-store; глобальная защита публичных маршрутов не вводилась.

- POST /api/auth/register — регистрация через письмо, ответ 202 без сессии.
- POST /api/auth/login, /api/auth/logout, /api/auth/session; GET /api/auth/me — вход и сессия, см. [SessionController](../../apps/backend/src/identity/session.controller.ts) и [SessionService](../../apps/backend/src/identity/session.service.ts). Пароль, TOTP, актуальная версия сессии и host-only cookie сохраняют прежние правила; регистрация не авторизует по email.
- Заблокированный аккаунт не входит даже с верным паролем: ответ 401 совпадает с неверными credentials, без cookie и обновления даты входа. Прежний побочный эффект и ответ 500 устранены отдельной правкой N13.
- POST /api/auth/logout возвращает {success:true}; только этот ответ подтверждает выход клиенту. Пустой/невалидный ответ не снимает локальную блокировку доступа.
- POST /api/auth/password/request, /api/auth/password/complete; GET /api/auth/password — установка/восстановление пароля.
- POST /api/admin/access-email/resend — повторное письмо администратором. См. [identity/password.controller.ts](../../apps/backend/src/identity/password.controller.ts) и [PasswordService](../../apps/backend/src/identity/password.service.ts). Пароли и письма используют прежние одноразовые токены и outbox; смена пароля не создаёт сессию автоматически.
- GET /api/launch-config; GET и PUT /api/admin/launch-settings — настройки запуска, см. [launch/launch.controller.ts](../../apps/backend/src/launch/launch.controller.ts) и [launch/launch.service.ts](../../apps/backend/src/launch/launch.service.ts). Проверка revision, актуальной роли и аудит остаются в одной Drizzle-транзакции; устаревшая правка возвращает 409, не меняя данные.
- GET /api/capabilities — фактические серверные флаги, см. [launch/capabilities.ts](../../apps/backend/src/launch/capabilities.ts).
- Обработчики Prodamus и операций с файлами подключены в [композиции приложения](../../apps/backend/src/_core/application.ts); протокол платежей — [prodamus.ts](../../apps/backend/src/prodamus.ts).

SMS-маршруты существуют, но выключены без ENABLE_SMS_LOGIN=true. Онлайн-оплата магазина и Web Push отключены серверной политикой.

## Платежи и безопасность изменений

Checkout не авторизует пользователя по email. claimPending не выдаёт подписку. Продление и выдача доступа идут через проверенную обработку платежа; подтверждение отмены учитывается отдельно. Состояние платежей, писем и повторных попыток хранится в БД.

[База данных](database.md) · [интеграции](integrations.md) · [инструкция бэкенда](../../apps/backend/README.md). При изменении контракта обновляйте тесты и все затронутые клиенты.
