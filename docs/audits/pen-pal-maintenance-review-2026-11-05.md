## Замеры на 3 000 анкетах

На одноразовой MySQL после 51 миграции выполнено по три прогона до и после.
В сценарии подбора каждая синтетическая анкета содержала адрес длиной 900
символов. Для сценария существующих связей у владельца было 200 совпадений.
В сценарии очистки восемь анкет имели оплаченный срок, истёкший более 90 дней назад.

| Сценарий | До | После |
| --- | ---: | ---: |
| Подбор по интересам, данные от MySQL | 3 062 941 байт | 106 830 байт |
| Подбор при 200 связях, SELECT | 203 | 7 |
| Очистка, транзакции | 3 000 | 8 |
| Очистка, медиана трёх локальных прогонов | 4 355 мс | 22 мс |

Подбор читает ID и интересы для ранжирования и завершает проверку
существующих связей, когда набрано достаточно карточек. Очистка выбирает
кандидатов по последнему оплаченному сроку порциями до 100 и повторно
сверяет его под блокировкой пользователя перед деактивацией. Ранжирование
по-прежнему читает весь список активных анкет. Замер времени относится
к указанному локальному набору, где просроченных анкет было мало.

Прошли 151 SQL-тест и 167 HTTP/unit-тестов. Дополнительный SQL-сценарий
проверил вторую страницу очистки и сохранение анкеты после продления.
Миграции, типы API и сроки хранения остались прежними. Замеры сохранены
в `../.local-artifacts/pen-pal-scale-20261105`.

## Подтверждённые проблемы

### P2: устаревший кандидат на удаление

purgeStalePenPalData выбирала неактивные анкеты старше 30 дней. Затем DELETE
проверял только userId. Между этими запросами реальная penPals.upsert могла
сохранить актуальную анкету. Старый DELETE всё равно удалял её. Вариант с новым
upsert и последующим remove также нарушал новый срок хранения неактивной анкеты.
Кроме того, два прохода очистки могли оба учитывать одну уже удалённую строку:
счётчик увеличивался независимо от affectedRows.

В тестах приостанавливается настоящий ответ SELECT кандидатов, затем настоящий
router сохраняет анкету и при необходимости отзывает участие. Значения SQL не
подменяются. Для двух проходов второй заканчивает обработку до продолжения первого.

### P2: деактивация после уже завершённого продления

Активные анкеты обрабатывались по getLatestClubExpiry вне транзакции.
deactivatePenPalProfileV2 блокировала пользователя, но не перечитывала оплату
после ожидания. Продление успевало записать новый срок, а очистка затем
деактивировала анкету и удаляла её связи по старому решению.

На отдельной БД транзакция удерживает users owner-lock. Очистка доходит до
ожидания этой блокировки (проверено через performance_schema), затем настоящий
grantClubAccessInTransaction записывает новый срок и коммитится. Старый код
всё равно считает анкету обработанной; исправленный сохраняет её и связь.
Это синтетическая административная выдача доступа, не обращение в Prodamus,
не реальный платёж и не отправка письма. Settlement использует тот же owner-lock;
реальная платёжная цепочка данным опытом не принимается.

Первый прогон до изменения production-кода: **4 ожидаемых падения и 6 контролей**.

## Исправлено локально

- DELETE неактивной анкеты повторно проверяет её id/userId, active=false и
  updatedAt до прежней 30-дневной границы. Обновлённая или заменённая строка
  не удаляется по старому списку кандидатов.
- Счётчик удаления использует affectedRows, без фиктивного успеха второго прохода.
- Деактивация активной анкеты выполняется одной транзакцией: owner-lock,
  актуальная активность анкеты под блокировкой, последний paid expiry,
  деактивация и удаление связей. После ожидания виден завершившийся grant.
- Повторный проход не считает уже неактивную анкету новой деактивацией.
- Из первоначального active-списка выбираются только userId, без адресов и
  других данных анкеты. Dynamic import агрегатного db-фасада больше не нужен.

Сроки и правила прежние: 30 дней для неактивных анкет, деактивация при последнем
оплаченном сроке старше 90 дней. При отсутствии paid history анкета сохраняется,
как раньше; новые правила допуска к Pen Pals не вводились. Истёкшие
неподтверждённые заявки удаляются, взаимно подтверждённые не удаляются только
из-за старого confirmDeadline. Миграций, флагов и изменений API нет.

## Проверки

- **10 новых SQL-сценариев:** повторное заполнение; заполнение/withdrawal;
  два прохода по одному кандидату; обычное удаление старой анкеты; сохранение
  недавно отозванной; реальный конкурентный grant; обычная деактивация;
  rollback при SQL-отказе удаления связи; отсутствие paid history;
  истёкшая невзаимная и сохранённая взаимная связь.
- **150/150 SQL** в восьми файлах: новый набор и прежние matches, profile
  lifecycle, address access, native retention worker, запрос удаления,
  security regressions и Nest profile. Native worker acceptance включён явно.
- **167/167 HTTP/unit** в девяти файлах: прежние 127 и worker jobs/lifecycle,
  Nest workers, multi-API coordination config.
- Root/frontend types, backend lint, API/TEST сборки, check:api (107 процедур,
  46501 байт), boundaries (907 файлов) и git diff --check проходят.

Каждый SQL-прогон использовал собственную tmpfs MySQL 8.4, loopback и 51 миграцию
с проверкой истории. Базы/контейнеры удалены после проверки ownership. Реальные
SMTP/S3/провайдеры не использовались. Артефакты вне Git:
../.local-artifacts/pen-pal-maintenance-20261105: red.log, green.log,
sql-regressions.log, unit.log, migration.log, build/type/lint/API/boundaries
логи, run-*.py и sql-cleanup.json.

## Остаток аудита и приоритеты

- **P1 выпуска:** новые итоговые runtime images после всех последних исправлений,
  AMD64-приёмка, fresh staging и серверный preflight. Принятый ARM64 2adb313e
  новых почтовых и lifecycle-правок не содержит. 5 ноября диск восстановился
  примерно до 6,3 ГиБ; прежний блокер места нужно оценить заново при подготовке
  сборок. Новые Docker images этим срезом не собирались.
- **P2 архитектура:** подбор и maintenance читают списки анкет и выполняют
  дополнительные запросы на участницу. Перед включением/масштабированием нужны
  отдельные замеры и решение о порционной обработке. Массовый рефакторинг,
  очереди и новые сервисы не добавлялись.
- **P2 эксплуатация:** подтвердить общую координацию jobs и конфигурацию
  нескольких API в целевой среде. Локальные транзакции не заменяют приёмку сервера.
- Границы stale form/exactly-once и best-effort push прежние. Весь аудит
  backend/production и договорная приёмка остаются открытыми; десять новых
  сценариев не означают проверку всех возможных гонок и внешних отказов.

Следующий локальный выпускной шаг — актуальный image-кандидат и его приёмка;
Pen Pals на стенде этим изменением не включать.
