# Безопасность бэкенда Daryadarcy

4 ноября 2026. Исходное исследование выполнено на source f9de55f9.
После согласования владельцем подтверждённые дефекты исправлены локально.
Использованы security-and-hardening, code-review, test-driven-development и
verification-before-completion. Аудит остальных модулей и среды остаётся открытым.

## Исправлено локально

| Приоритет | Исправление | Подтверждение |
| --- | --- | --- |
| P1 | grantClub без ключа передаёт actor; роль, openId, epoch, блокировка и запрос удаления проверяются под SQL-блокировкой actor/цели | Старый и keyed-вызов отказывают после отзыва прав; текущий admin выдаёт доступ |
| P2 | Legacy resend использует ту же транзакционную проверку actor | Отозванная сессия/роль, блокировка и удаление не создают письмо; текущий admin ставит письмо в очередь |
| P2 | Legacy uploadAvatar проверяет epoch и profileRevision до внешней операции и перед записью через saveProfile | После обезличивания avatarUrl остаётся NULL; новый профиль не перезаписывается; обычное сохранение работает |
| P2 | Production API отказывается запускаться без JWT_SECRET длиной минимум 32 UTF-8 байта | Проверен отказ короткого ключа и успешный HTTP health с достаточно длинным синтетическим ключом |
| P2 | follow-redirects обновлён до 1.16.2, qs до 6.16.1 | Свежий pnpm audit --prod: 326 зависимостей, 0 advisory всех уровней |

Первые пять регрессий сначала упали на старом коде по ожидаемым утверждениям,
затем прошли после исправления. Расширенный итог: **147/147 SQL-тестов** в девяти
файлах на отдельной MySQL после 51 миграции, **200/200 HTTP/boundary/unit-тестов**
в девяти файлах. SQL-набор включает grant, keyed recovery, очередь писем,
профиль, retirement и compiled production checkout/guest recovery.
Два production test fixtures получили достаточно длинные синтетические ключи.
Сборки API и TEST, root/frontend types, backend lint, API-контракт и проверка
границ проходят. Миграций и новых обязательных клиентских полей нет.

У старого uploadAvatar по-прежнему ответ {url}; успешная запись теперь увеличивает
profileRevision, поэтому перед последующим profile.update нужна свежая ревизия.
Текущий frontend использует uploadAvatarWithReceipt, его код/контракт не менялись.
Если сессия отозвана во время внешней загрузки, непривязанный объект может
остаться в хранилище: автоматическое удаление не добавлялось. Это ограничение
старого пути; профиль после отказа не изменяется.

Артефакты исправления: `../.local-artifacts/security-fixes-20261104`:
baseline.log (RED), sql-regressions.log, boundaries.log, dependency-audit.json,
build/type/lint/contract логи и sql-cleanup.json. Временная БД удалена.
Frontend, рабочие БД/S3/сервер не менялись; push/deploy не выполнялись.
Новый ARM64 image 2adb313e собран штатным Dockerfile и принят 59/59. Хеши и
версии зависимостей проверены внутри контейнера. AMD64 ещё требуется собрать
и принять; старые 5da01b97 не содержат текущих исправлений.
[Приёмка и точные идентификаторы](../operations/backend-image-local-acceptance-2026-11-03.md).

## Остаётся открытым

- **P1 перед выпуском:** свежая сверка staging, новый AMD64-образ и проверка целевого
  env/сети/ACL/резервной копии, в том числе координации нескольких API и JWT-ключа.
  Недоступность сервера в предыдущей проверке не доказывает его неисправность.
- **P2 аудит кода:** ID-only lifecycle writers Pen Pals и profileExtras,
  прочие admin/content writers, доставка/владение push и legacy shop/integrations.
  Непроверенный путь не объявляется подтверждённой уязвимостью.
- **P2 архитектура:** прежние границы общего пула/совместимых фасадов и
  неопределённый исход аварийной внешней отправки сохраняются; эти исправления
  их не устраняют. Ранее согласованный best-effort push не расширялся до очереди.
- **P3:** необязательная очистка legacy helpers; проверка содержимого всей
  истории Git отдельным secret-scanner не выполнялась.

Далее сохранено описание исходных воспроизведений. Формулировки о найденных
пробелах относятся к source f9de55f9, а не к исправленному рабочему дереву.

## Границы и активы

Основные границы — браузер/API, JWT/актуальная SQL-модель пользователя,
администратор/целевой аккаунт, webhook/платёж, API/S3 и почтовая очередь/SMTP.
Защищаемые активы — роли, подписки, персональные данные, закрытые материалы,
парольные ссылки, журналы и доступ к инфраструктуре. Производственный сервер
по последней проверке недоступен, его env/ACL/сеть и актуальная версия не подтверждены.

## P1 — старая выдача подписки обходит отзыв прав

В apps/backend/src/admin/router.ts:121 ветка grantClub без idempotencyKey
передаёт в grantClubDays только userId цели. billing/grants.ts проверяет цель,
но не актуальную роль/epoch инициатора. Ветка с ключом использует executeAdminAction
и проверяет их под блокировкой.

Два SQL-воспроизведения сохраняют настоящий tRPC-контекст администратора,
затем снимают роль либо увеличивают sessionVersion. Ветка с UUID-ключом
отказывает FORBIDDEN/UNAUTHORIZED, а вызов без ключа возвращает ok=true.
В club_payments появляется paid-запись на 31 день для другого синтетического
аккаунта. Условие — уже начатый, ранее авторизованный запрос. Свежая отозванная
cookie не обходится этим тестом. Рабочий стенд не атаковали.

Минимальный fix — передавать доверенного actor в старый путь и проверять его
актуальную роль/epoch в транзакции выдачи. Сохранить публичный контракт,
различие отдельных старых вызовов и порядок блокировки actor/цели.
Отзыв роли/epoch должен сохранять подписку и журнал без изменений.

## P2 — повторная отправка письма принимает отозванную сессию

identity/password.service.ts:29 передаёт в legacy resend только actor.id.
identity/access.ts:283 читает роль без блокировки actor и без проверки epoch.
После увеличения sessionVersion настоящий PasswordService.resend со старым
контекстом возвращает true и создаёт письмо в access_email_outbox.
SMTP не запускался. Получатель берётся из БД, произвольный адрес не подставляется.

Минимальный fix — доверенный actor и транзакционная проверка epoch/роли для
ветки без ключа, совместимые с новым executeAdminAction. После отказа очередь,
password_tokens и журнал должны остаться неизменными.

## P2 — старый аватар повторно записывает данные после удаления

profile/profile.service.ts:69–71 ожидает uploadPhoto и обновляет users по ID,
без проверки сессии/revision после внешней операции. Настоящий запрос старого
profile.uploadAvatar приостановлен на заменённой внешней uploadPhoto-границе.
Реальный processScheduledAccountDeletions обезличивает аккаунт и увеличивает
sessionVersion. После завершения имитации загрузки запрос успешно сохраняет
avatarUrl в уже очищенный аккаунт. SQL подтвердил version=1 и ненулевой avatarUrl.
S3 и реальные файлы не использовались.

Минимальный fix — передавать actor и сверять его перед итоговой записью после
загрузки. Учесть profileRevision и совместимость receipt-пути. По прежнему
решению пользователя расширение функциональности аватаров отложено; здесь
зафиксирован только дефект существующей безопасности/целостности.

## P2 — production допускает заведомо слабый JWT-ключ

_core/env.ts:9 возвращает JWT_SECRET без проверки, application.ts:21 проверяет
координацию, но не силу ключа. С NODE_ENV=production и синтетическим ключом
длиной один байт реальный Nest/API запустился, health вернул 200, SDK подписал
и проверил сессию. Действительный секрет сервера в исследовании не читался.
Это подтверждённый пробел защиты от ошибочной конфигурации, а не доказательство
слабого рабочего ключа или уже произошедшей компрометации.

Минимальный fix — остановка production до listener при отсутствии/недостаточной
длине JWT-ключа, с безопасной диагностикой без значения секрета. Требование
к конфигурации согласовать с существующим release/preflight, 2FA не включать.

## P2 — уведомления о production-зависимостях

pnpm audit --prod --json проверил граф из 327 production dependencies.
Получены 1 high, 1 moderate, critical=0. Это оценка пакетов, а не найденные
high/critical атаки через данный API.

- follow-redirects 1.16.1 требует обновления до 1.16.2 или новее. Advisory касается
  передачи custom credentials при redirect с sensitiveHeaders из другого JS realm.
  В просмотренном application-коде sensitiveHeaders/cross-realm путь не найден.
  [Advisory](https://github.com/advisories/GHSA-mrwp-f3q8-3g9p).
- qs 6.16.0 требует обновления до 6.16.1 или новее. Advisory относится к stringify
  с comma-форматом и специально сформированными элементами массива. Такой вызов
  в просмотренном application-коде не найден. Наличие parse в Express само по
  себе не подтверждает эту цепочку. [Advisory](https://github.com/advisories/GHSA-6pq8-jhm2-2vcw).

План — узкое обновление resolutions/lockfile, native audit, тесты границ и
новые образы. Зависимости не обновлялись автоматически в ходе исследования.
Dev-зависимости и полная история Git отдельным secret-scanner здесь не проверены.
Среди отслеживаемых backend/packages/infrastructure путей не обнаружены файлы
с именами .env/api.env/secrets.json и расширениями .pem/.key. Это проверка имён,
а не доказательство отсутствия секретов в содержимом/истории.

## Доказательства и следующий шаг

Пять целевых characterization-проверок подтвердили описанное поведение на
одноразовой MySQL после 51 миграции — 5/5 за 1,47 с. Их успех означает
воспроизведение проблем, а не безопасность старых путей. Отдельно 152 выбранных
boundary-теста проходят в девяти файлах за 1,85 с. Проверены HTTP security,
публичные auth-ответы, logout, hash failure, webhook, push и private-content inputs.
Эти тесты пропустили найденные старые ветки и не закрывают аудит целиком.

Артефакты находятся рядом с репозиторием в
`../.local-artifacts/security-review-20261104`: точный probe, SQL/migration/cleanup
логи, dependency-audit.json, boundary-tests.log, review.json. Probe сохранён
отдельно, временный файл удалён из Git-дерева. Одноразовые БД удалены.
Рабочие данные, S3 и доставка писем не использовались.

Исходные рекомендации реализованы в локальном продолжении выше. Перед выпуском
нужны новый source/image-кандидат и серверные проверки; прежние 52/52 новые
случаи не покрывали. Аудит среды и оставшихся модулей остаётся открытым.
