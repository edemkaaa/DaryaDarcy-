## Замечания исходного аудита, исправлены локально

### COMP-1, P2: валидный TXT ломает список файлов Библиотеки

**Производитель:** `apps/backend/src/content/text-content-type.ts:37` добавляет
кодировку, например `text/plain; charset=utf-8`. Подготовка переноса принимает
этот документ, а `apps/backend/src/content/library-files.ts:129` возвращает
сохранённый `mimeType` без удаления параметров.

**Потребитель:** `apps/frontend/src/features/library/library-files-api.ts:31`
разрешает точное значение `text/plain`, без параметров. `parseLibraryFiles`
отклоняет всю страницу через `invalidResponse`, а `getLibraryFiles` не возвращает
даже корректные соседние файлы. Экран показывает ошибку чтения материала.

**Воспроизведение:** настоящий `prepareLibraryMigration` получает синтетический
UTF-8 TXT. Его итоговый MIME передан настоящему клиентскому парсеру в форме
ответа списка. Результат: отказ. Контрольная замена только MIME на `text/plain`
устраняет отказ. SQL/S3 для этой проверки не использовались. Сериализация полей
списка подтверждена исходником и существующими SQL-тестами; эти SQL-тесты в данном
аудите заново не запускались. Наличие такого TXT на рабочем стенде не утверждается.

**Минимальное исправление:** согласовать допустимые MIME с параметрами у REST-ответа
и клиента. Проверять разрешённый базовый тип и допустимые параметры; сохранить
кодировку в выдаче файла. Не расширять разрешения на HTML/SVG/произвольный URL.
Тест должен использовать MIME, полученный серверной функцией, а не вручную
упрощённый `text/plain`. Проверить UTF-8, поддерживаемые другие кодировки,
недопустимый тип, смешанный список TXT/PDF и последующую страницу.

**Исполнитель:** фронтендер для парсера; совместная проверка контракта с бэкендом.

### COMP-2, P2: явный отказ отмены подписки остаётся «неизвестным результатом»

Последняя локальная бэк-правка разделяет ожидаемый отказ и инфраструктурный сбой:
`apps/backend/src/billing/club-subscription.service.ts:85` возвращает 400 только
для `CancellationUnavailableError`, остальные ошибки становятся 500. Пример
ожидаемого отказа: оплаченный старый заказ без проверенного профиля провайдера.
В этом случае запрос отмены не записан; пользователь должен увидеть отказ
и предложение обратиться в поддержку.

Однако `apps/frontend/src/features/profile/use-subscription-cancellation.tsx:128`
сохраняет старое правило: только 401/403/429 выводятся как отказ, 400 остаётся
`unknown`. Повторное чтение `cancellationStatus: none` в строке 81 тоже оставляет
`unknown`; кнопка заблокирована условием в строке 167. Без перезагрузки интерфейс
не выходит из этого состояния и не показывает сообщение сервера о причине.

**Воспроизведение:** настоящий клиент, React-провайдеры и hook в Chromium,
локальный HTTP с контролируемыми ответами. Активная подписка, исходный `none`,
затем tRPC `BAD_REQUEST/400` на отмену, затем снова `none` при проверке.
Подтверждены один запрос записи, отсутствие повторных записей, оставшийся
`unknown/blocked=true` и отсутствие текста серверного отказа. Это браузерная
проверка клиента; реальный платёжный провайдер и SQL здесь не подключались.
Серверный отказ до записи проверен HTTP/MySQL в предыдущем локальном срезе.

**Минимальное исправление:** после выпуска нового серверного контракта отличать
подтверждённый tRPC `BAD_REQUEST` от таймаута, 5xx, невалидного ответа или HTML
ошибки прокси. Показать отказ/поддержку без ложного ожидания подтверждения.
Не приравнивать любой HTTP 400 к доказанному отказу и не снимать защиту `unknown`
после одного чтения `none` при потерянном ответе: предыдущая запись ещё может идти.
Сохранить прежние сценарии `pending`, `confirmed`, 500 после commit и смены аккаунта.

**Исполнитель:** фронтендер, согласованно с выпуском локальной бэк-правки
`2cc62436`. Изменение SQL, провайдера или формата успешного ответа не требуется.

### COMP-3, P3: разные ограничения длины имени файла Библиотеки

`apps/backend/src/content/library-migration-manifest.ts:15` принимает имя до
512 символов. Имя хранится и возвращается без усечения. Клиентский
`library-files-api.ts:30` ограничивает его 255 символами. Один такой элемент
отклоняет всю страницу, как в COMP-1.

**Воспроизведение:** корректное синтетическое WebP с именем в 256 символов
принимается настоящей серверной подготовкой переноса и отклоняется клиентским
парсером. Короткое имя с теми же байтами/MIME проходит. Это дефект допустимого
контракта на границе, а не доказательство наличия длинного имени в рабочей БД.

**Минимальное исправление:** выровнять клиент с существующим пределом 512,
сохранить проверку пустого имени/управляющих символов и добавить граничные случаи
255/256/512/513. Не обрезать существующие метаданные в БД.

**Исполнитель:** фронтендер; совместный тест производителя и потребителя.

## Что остаётся до вывода о рабочем стенде

1. Восстановить DNS/SSH, прочитать фактические версии и изменения staging.
   Последняя успешная сверка показывала разницу обычного web и отдельной Mini;
   свежесть runtime сейчас неизвестна.
2. Выпустить локально исправленные COMP-1/2/3 и E2E fixtures после согласования,
   затем проверить совместную версию на стенде. Повторно реализовывать их не нужно.
3. Определить режим оплаты. Последняя принятая конфигурация оставалась TEST;
   боевых настроек Prodamus нет. TEST/legacy не умеют восстановить потерянный
   первый ID заказа так, как NORMAL/GUEST. Автоматически переключать режим нельзя.
4. Принять механику заказа через почтовое приложение и фактическую доставку
   отправленного покупателем письма либо отдельно согласовать серверную форму.
   Диагностическое письмо SMTP не закрывает этот сценарий.
5. Остальные организационные/инфраструктурные условия остаются в
   [плане выпуска](release-readiness-2026-11-02.md): runner, ресурсы,
   первый пароль, контакты, зима к дате запуска, устройства и пилот.
   Большие загрузки и отложенные проверки не возобновлялись.

Критических новых обходов доступа в проверенных местах не подтверждено.
Это не гарантия отсутствия уязвимостей во всём приложении или внешних сервисах.
