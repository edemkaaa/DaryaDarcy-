# Скорость экранов с постами и видео: исследование 26 октября 2026

Основание: просьба проверить все места загрузки постов/видео и найти ускорения
без потери качества. Продуктовый код, рабочие данные, S3-объекты, дизайн,
платёжные настройки и серверные лимиты не менялись. Push/deploy не выполнялись.

**Основной резерв — размеры миниатюр, повторные запросы и публичные обложки.**
Снижать quality, разрешение viewer или качество видео для этого не требуется.
Кеш превью работает; повторная массовая очистка не нужна.

## Метод и границы

- Живой опубликованный web `ce56ebe`, API `ff2c229`; исходники на `a762b4a`.
  Чтение сервера/SQL, обычные последовательные GET/HEAD, переходы в существующей
  админской сессии. Контент/аккаунты для проверки не создавались.
- Свежая собственная вкладка: desktop1280×720/DPR2, приложение ограничено480px.
  Дополнительный viewport390×844/DPR1; это не физический iPhone/Android и не
  проверка Retina на мобильном устройстве. Override сброшен после проверки.
- Проверены список/сетка/фильтр/возврат Ленты, пост744/viewer, Клуб, профиль,
  Библиотека/статья6, админские посты/видео/статьи/календарь, каталог20→22VK.
  У текущего аккаунта нет сохранённых постов: карточки «Сохранённого» исследованы
  по исходникам, не на заполненном живом списке. Пустой видео-тег в Ленте не
  подменялся искусственным наполнением.
- Отдельная страница видео: исследованы источник и реальные catalog/playback API.
  Внешний VK не активировался: прежний site-safety запрет не обходился.
  Поэтому время запуска самого провайдера, звук и полный экран здесь не измерены.
- Три последовательных измерения публичных API в одном HTTPS-соединении.
  Первый запрос включает установление соединения. Это выборка текущей сети,
  не p95, не100пользователей и не сравнение VPN-стран. LCP/INP/CPU flamegraph
  браузера не снимались; DOM-готовность не объявляется временем загрузки страницы.

В исходной пользовательской вкладке и свежей вкладке `/videos` различаются
общие JS chunk hashes и webpack runtime. Старая вкладка продолжает исполнять
предыдущий клиент; в ней ещё были прежние sizes. Её не перезагружали, чтобы не
затронуть состояние пользователя. После сохранения своих черновиков достаточно
обычного обновления страницы; удалять cookies/IndexedDB/весь кеш не требуется.

  или рендерить весь архив не нужно.
- Разделы подключаются через dynamic import и сохраняют посещённый DOM/прокрутку.
  Неактивные разделы выключают polling, скрытые media приостанавливаются.

### Фото и кеш

Для публичного фото744 с `Accept:image/webp`, quality75:

| Ширина | Байты WebP | Повторный GET, мс | Conditional GET |
| --- | ---: | ---: | --- |
| 320 | 17 518 | 65 | 304/0B |
| 640 | 54 212 | 68 | 304/0B |
| 960 | 103 772 | 137 | 304/0B |
| 1440 | 231 650 | 73 | 304/0B |

Ответы: max-age3600/must-revalidate, Vary:Accept, ETag; встречаются HIT/STALE.
Отдельная начальная серия без Accept:image/webp получила JPEG: MISS для320/960/
1440 занимали1,18–1,57с целиком, повтор —69–94мс. Это другая negotiated-ветка;
нельзя выдавать её за холодный WebP или чистое время Sharp. Первый WebP HIT650мс
также включал новый TLS/network путь: HIT не гарантирует мгновенную сеть.

Серверный image-cache:573файла,55 732 954B;536с TTL3600,37с TTL31536000,
старых TTL30 нет. Лимит128МиБ сейчас не достигнут. Увеличивать кеш вслепую или
снова удалять его целиком оснований нет: очистка вернёт дорогие MISS.

**Новый подтверждённый перерасход:** миниатюра админского поста56px использует
w960, поскольку Picture не получает sizes. На одном и том же публичном legacy
источнике WebP q75: w960 —146 128B; w160 —7 256B, то есть на95,0% меньше.
Это сравнение байтов, не обещание ускорить всю страницу в20раз. Для DPR2
достаточно112физических пикселей; browser должен сам выбирать вариант по DPR.

### Все22обложки VK

22анонимных GET200:5 491 659B суммарно. Это вес полного каталога, а не первого
экрана: lazy loading не скачивает все22одновременно. Явного Cache-Control нет;
Last-Modified/ETag есть. Возможен heuristic cache — отсутствие max-age не означает
доказанное отсутствие любого кеширования.

19PNG:5 443 271B →3 685 524B при WebP lossless, **−32,29%**. Сравнены
RGBA-байты всех19исходников и результатов: точное совпадение, размер кадра
сохранён, ICC/alpha у этих источников отсутствуют. Три JPEG оставлены как есть:
итог22кандидатов —3 733 912B вместо5 491 659B, **−32,01%**.

У19PNG размер примерно533×300; у69 —480×360; у75/78 —лишь130×96.
На карточке440px два последних источника уже растягиваются. Конвертация не
восстановит недостающие детали; для улучшения нужны настоящие крупные обложки,
а не upscale и не более агрессивное сжатие.

## Ограничение приватности, найденное при замерах

Для фото, использованного в сравнении56px, SQL подтвердил **post938, target=club,
published=1**. Исходник в старом `feed/photos/…IMG_8054.jpeg` вернул анонимный
S3 HEAD200/804071B; анонимный optimizer GET также200. Это конкретный старый
публичный клубный файл, не утверждение о всех файлах проекта.

Следовательно, нельзя считать всю папку feed гарантированно бесплатной и
увеличивать для неё public TTL до года. Нужна отдельная инвентаризация старых
клубных фото и согласованный перенос/закрытие исходных публичных адресов;
одна защита API поста не закрывает уже известный адрес файла. В рамках этой
задачи файл/ссылки/БД не менялись. Новый годовой immutable-cache предлагается
только для проверенных открытых VK-обложек. Private API остаётся no-store и
проверяет доступ; отключать его защиту ради скорости нельзя.
