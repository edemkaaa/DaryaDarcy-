## Подтверждённые ошибки

### Исходная версия черновика профиля теряется после перезагрузки

Приоритет P1. Связано с I-01 и сохранностью ввода FE-02.

`apps/frontend/src/features/profile/profile-name-editor.tsx:44` сохраняет черновик имени обычной строкой. При его восстановлении строки 96–99 вызывают `beginEdit()`, который в `domain/profile/use-profile-update.ts:199` берёт текущую `user.profileRevision`. Версия начала редактирования в черновике отсутствует.

Воспроизведение в Chromium с текущей production-сборкой и синтетическим API, который действительно проверяет CAS:

1. Открыть имя при `profileRevision=0`, ввести `Old unsent draft`, не сохранять.
2. Изменить серверный профиль на `Newer server name`, `profileRevision=1`.
3. Перезагрузить страницу и открыть восстановленный черновик.
4. Нажать «Сохранить имя».

Фактически отправлено `expectedRevision=1`, сервер принял старый черновик и заменил более новое имя. Ожидается сохранение исходной версии 0 и конфликт либо явное сравнение перед переходом к версии 1.

Та же структура видна в `features/club/profile-setup.tsx:69`: черновик анкеты содержит имя, пол и аватар, но не исходную ревизию; восстановление вызывает `beginInitialEdit`, берущий текущую версию. Для анкеты это подтверждено чтением кода; отдельное browser-воспроизведение анкеты не выполнялось.

Доработка: хранить исходную версию и исходный снимок вместе с редактируемыми полями, восстанавливать их без присвоения версии свежего GET. Старые черновики без версии должны сохранять ввод и требовать явной сверки. После `check()` при неподтверждённом результате не оставлять единственную актуальную версию только в ref: сейчас pending-запись удаляется, а обычный черновик всё ещё не хранит версию. Добавить проверки reload, смены версии между вкладками и восстановления после проверки конфликта для обеих форм.

### Старая вкладка результата удаляет новое прохождение теста

Приоритет P2. FE-03 требует очищать только соответствующее прохождение.

`features/quiz/quiz-screen.tsx:78` безусловно удаляет `QUIZ_PROGRESS_KEY` при выходе из фазы вопросов, включая `RESTART`. В `domain/quiz/quiz-progress.ts` есть версия формата и набора вопросов, но нет идентификатора прохождения или версии записи. Проверяется владелец аккаунта, но две вкладки одного владельца не различаются.

Воспроизведение в Chromium:

1. Во вкладке A открыть прежний сохранённый результат `/quiz/result`.
2. Во вкладке B начать новый тест, выбрать ответ и перейти ко второму вопросу.
3. Во вкладке A нажать «Пройти ещё раз».

После шага 3 локальная запись прогресса вкладки B становится `null`. Ответы остаются только в памяти B; восстановить их после reload нельзя.

Доработка: идентифицировать прохождение и проверять принадлежность записи перед обновлением/удалением. Старая вкладка не должна стирать или перезаписывать новое прохождение; для согласования вкладок использовать существующие browser-механизмы координации. Добавить проверки двух вкладок для restart и завершения, а также для запоздавшего ответа на вопрос. Текущие unit-тесты проверяют формат прогресса и вопросы, а обычный E2E — восстановление одной вкладки.

## Тесты и автоматизация

### Browser-тест ошибки хранилища профиля не доходит до нужного условия

Приоритет P2. FE-02, FE-07 и INT-08.

`e2e/audit-draft-persistence.spec.ts:216` ожидает «Запрос не отправлен» при отказе localStorage. Общая фикстура `e2e/editor-fixtures.ts:49` не возвращает `profileRevision`; обработчик теста возвращает `{success:true}` без версии результата. Приложение правильно запрещает запись без версии раньше проверки pending storage и показывает «Версия профиля недоступна».

В основном browser-прогоне этот тест упал. Его диагностическая копия с полноценной текущей фикстурой профиля прошла: ошибка хранения показана, ввод сохранён в форме, mutations не отправлены. Исправлять нужно фикстуру и assertions вокруг актуального контракта, сохраняя отдельную проверку отказа при отсутствии версии. Production-защиту ослаблять нельзя.

### CI не проверяет все предусмотренные конфигурации

Приоритет P2. INT-08.

В `.gitlab-ci.yml` и `.github/workflows/ci.yml` нет `pnpm lint`. Есть только обычная `build:web` и основной browser-запуск. Guest/NORMAL E2E пропускаются без `GUEST_CHECKOUT_UI_ENABLED` / `NORMAL_CHECKOUT_UI_ENABLED`; включение только этих тестовых переменных без соответствующей сборки тоже недостаточно.

Добавить отдельные согласованные сборки и browser-конфигурации для guest/NORMAL, действующего VK-каталога и используемого TEST-режима. Явно задавать build-time flags, а не полагаться на окружение runner. Публиковать trace/результаты при ошибках. SQL isolation уже есть; менять frontend API или повторно добавлять native video wrapper не требуется. Удалённый pipeline и причина прежнего GitLab API 403 этой локальной проверкой не подтверждены.

### Репозиторная передача содержит устаревший актуальный остаток

Приоритет P2 для корректности планирования.

Присланный файл имеет 789 строк, `docs/development/frontend-audit-handoff-2026-10-27.md` — 778. Отличается раздел актуального остатка: в репозитории всё ещё написано, что guest mutations в клиенте отсутствуют; фактический код и присланный файл подтверждают реализацию. Из-за этого один документ одновременно содержит сведения разных срезов.

Обновить актуальный раздел, сохранить историю как историю и добавить найденные здесь пробелы. Нельзя просто скопировать утверждение о полном закрытии I-01: восстановление обычного черновика профиля остаётся дефектным.

Продуктовые исходники и существующие тесты не изменялись; добавлен только этот отчёт. Локальные диагностические spec вынесены в /tmp. В конце восстановлена сборка с исходными настройками .env.local без изменения самого файла. Профильная анкета проверена статически в части потери версии; конкретный browser-probe выполнялся для редактора имени. Тесты Chromium не доказывают поведение физического iPhone/Safari. Required mode контента, guest/LIVE и retirement на сервере не включались.

Диагностические probes и traces сохранены в `/tmp/daryadarcy-handoff-probes`; перед повтором spec нужно поместить в `apps/frontend/e2e`, поскольку он использует соседние fixtures. Это временные артефакты, не постоянные regression tests. При исправлении ошибок перенести содержательные сценарии в существующие suites.
