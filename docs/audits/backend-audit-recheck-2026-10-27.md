## Что именно проверялось

Одна собственная одноразовая MySQL8.4 arm64: канонические44миграции,
синтетические аккаунты/посты/статьи/видео, служебный счётчик UPDATE.
Секреты рабочей среды не передавались тестовому приложению. Почтовые и платёжные
провайдеры не настраивались, письма и платежи не запускались. S3 заменён
собственным localhost SDK wire с настоящими HTTP/MD5/IfNoneMatch и явными gates.
Это проверка SQL/HTTP-механики, не новая приёмка настоящего S3.

В отличие от исходного аудита, приведённые выше HTTP/SQL случаи воспроизведены
заново против production-кода, без подмены ORM/SDK авторизации или сервисов записи.
В тесте памяти заменён только конечный бизнес-обработчик после настоящего
registerRequestBodies: он удерживает полученные тела, не сохраняет их в S3.
Видеосервис получает реальный каталог из тестового API; внешняя подготовка
YouTube заменена собственным10-байтным файлом.

Все эксперименты находятся вне Git в закрытом каталоге
`.local-artifacts/backend-audit-recheck-20261027-2ed6fdb6`. В отчёт не включены пользовательские тексты,
пароли, cookie, содержимое рабочей БД и закрытые ссылки.

## Уточнения, которые меняют решения

### Память и доступность

На живом API подтверждены memory=256МиБ, memory+swap limit=512МиБ,
PRIVATE_POST_MEDIA_UPLOAD_ENABLED=true и PRIVATE_POST_VIDEO_UPLOAD_ENABLED=true.
512МиБ здесь не является лимитом оперативной памяти контейнера.
Edge разрешает тело85m и передаёт его без предварительной полной буферизации;
`limit_conn` в загруженной конфигурации отсутствует. По запросам в исходниках
нет общего допуска загрузок перед raw parser.

Изолированный ingress удержал24МиБ клиентских тел: arrayBuffers вырос примерно
с1,10 до25,10МиБ, RSS — с147,55 до187,12МиБ. Клиенты были в другом процессе.
Это не замер3×80МиБ, не нагрузочная приёмка и не доказательство недавнего OOM
стенда. Текущий контейнер healthy, OOMKilled=false/restarts=0.

В тесте пула десять загрузок одного актёра по18байт заняли10соединений,
девять SQL-операций ожидали/выполнялись. Независимое публичное чтение стояло
в очереди дольше350мс и получило200 после снятия S3 gate (514мс суммарно).
Для этого не нужны большие файлы или десять разных администраторов.
Требуемый паттерн — короткий intent, сеть без SQL-lock, повторная проверка
роли/sessionVersion/retirement и фиксация. Наш оператор legacy-переноса уже
использует этот порядок; **обычные редакторские загрузки ещё нет**.

### Индексы: ускорившийся кандидат оказался небезопасным для записи

Измерения на12000синтетических постах, семь повторов на вариант, медиана:

| Вариант | Первая страница | OFFSET8000 | План |
| --- | ---: | ---: | --- |
| Каноническая схема | 8,04мс | 9,25мс | ALL,filesort |
| Обычный composite по фильтрам/дате | 7,00мс | 9,69мс | ALL,filesort сохранились |
| Экспериментальный functional COALESCE index | 1,64мс | 9,47мс | ref,filesort исчез |

Поиск/тег в этой выборке массовые, не редкие: результаты не переносятся на все
запросы или на100одновременных пользователей. Поиск LIKE и JSON-фильтрация
не стали полнотекстовым/инвертированным индексом, глубина OFFSET сохранила цену.

**Этот functional index отклонён.** При следующей записи без явного publishedAt
он вызвал MySQL3751 ER_WARN_DATA_TRUNCATED_FUNCTIONAL_INDEX. Независимый INSERT
воспроизвёл отказ и при SYSTEM, и при +00:00; с явной датой INSERT проходил.
Нельзя выпускать этот DDL по одному успешному EXPLAIN. Оба лабораторных индекса
удалены; после возврата канонической схемы20native-контролей оператора прошли.
На рабочую БД индексы не добавлялись. Будущий вариант должен пройти NULL/default
даты, insert/edit/import, timezone и сохранение точного порядка до миграции.
Корневой механизм плохого плана понятен; конкретный безопасный DDL этим аудитом
ещё не выбран.

### Анонсы и legacy-удаление

Поведение статьи подтверждено цепочкой HTTP createPost → updateArticle →
deleteArticle, а не одним UPDATE вручную. Причина — разрешённый произвольный
source и findTeaser(limit1). Для удаления media есть положительный контроль:
канонический updatePost вернул BAD_REQUEST и сохранил вложение; legacy маршрут
удалил его без проверки тела и без очистки связанного receipt.
Доступ здесь административный; утечку чужих пользовательских данных этот тест
не доказывает. Исправление должно использовать общие правила записи и учитывать
существующие дубли, не удалять их вслепую на стенде.

### Типы, валидация и завершение

Потеряны типы feed.getById.media, feed.listPaginated.posts.commentCount,
club.list.posts.media и club.list.posts.commentCount. Это не потеря байтов
на проводе: они реально получены. Отдельная модель Date/string клиента из
пункта14 — ответственность frontend-типов; серверную сериализацию дат ошибочной
этим не объявляем.

source длиной33символа при VARCHAR32 даёт INTERNAL_SERVER_ERROR через реальный
HTTP; дробный id98940.5 проходит схему и возвращает undefined. Дробный ID сам
по себе не доказательство доступа к чужой записи, но контракт границы неверен.

Основной источник запуска не имеет SIGTERM listeners; при сигнале оборвалось
ожидание конкретной загрузки. Её сохранённый pending intent может быть
восстановлен: shutdown-проблему нельзя обобщать как гарантированную потерю
данных. Для остановки использовать существующий WorkerJobs.stop()/pending,
остановку приёма запросов и закрытие пула с общим сроком. Billing/mail уже
имеют durable механизмы; новую универсальную очередь без отдельной причины
в этот вывод не включаем.

### Legacy YouTube и VK — разные пути

Порог1001 относится к **опубликованным публичным YouTube** в videos.list.
Рост числа VK-карточек сам по себе его не достигает. Range, HEAD и thumbnail
на1000YouTube каждый сделали по два полных HTTP-чтения каталога; контроль
снятия с публикации между чтениями вернул404, его необходимо сохранить.
Проверка в2МиБ срабатывает по распакованному телу ответа.

На стенде используются VK-плееры; восстанавливать/расширять YouTube вопреки
принятому переходу не нужно. Сначала определить необходимость legacy маршрутов.
Если их сохранять — проверять один идентификатор, сохранив отзыв; если выводить
из эксплуатации — согласованный явный отказ после проверки потребителей.

## Порядок Клуба: что описывает фронтендер

[Серверный порядок](../../apps/backend/src/content/post-order.ts): sortOrder ASC,
COALESCE(publishedAt,createdAt) DESC,id ASC до LIMIT/OFFSET.
[Клубный frontend](../../apps/frontend/src/features/club/club-subscribed.tsx)
после объединения полученных страниц заново сортирует только по дате.
Это подтверждённое расхождение, а не вопрос скорости кеша или пропавших постов.

READ ONLY на текущем стенде: **189** опубликованных клубных постов,
27сsortOrder=0 и162сsortOrder>0. Все162положительных значения точно равны
Unix-времени отображаемой даты. В этой группе ASC даёт направление от старых
к новым. Пост754 за16.03.2024 начинает положительную группу; пост887 за26.05.2026
завершает её, на позиции189 общего списка без фильтра. По одной дате887был бы
на позиции11. Самый новый ручной пост954 уже первый: неверно утверждать, что
абсолютно все новые публикации находятся в конце.

Моделирование frontend-сортировки порциями12 на фактических метаданных без
фильтра: при загрузке до48записей десять ранее показанных карточек меняют
позицию. Это проверка алгоритма на текущих данных, не новый браузерный прогон
каждой рубрики. В рубриках действует тот же SQL-порядок; конкретные позиции
после фильтра будут другими.

Предложение фронтендера разумно **для выбранной хронологической ленты**:
сортировать пользовательский Клуб по дате/ID до пагинации и сохранять этот
порядок на клиенте. Но глобальная замена postListOrder затронет также админские
списки и календарь. Порядок пользовательского Клуба нужно задать отдельно;
ручной порядок/его обещания в админке согласовать. Другой возможный контракт —
ручной приоритет: тогда нужна отдельная нормализация legacy timestamp-значений
и согласованный клиент. Ни сортировка, ни162рабочих значения здесь не менялись.

## Приоритет следующих правок

1. Общий бюджет приёма загрузок до чтения тела и разделение SQL/S3 в обычных
   upload-путях; сохранить idempotency/recovery/конкурентный отзыв прав.
2. Анонсы статей и deleteMedia: целостность общих операций записи, затем DTO и
   граничная валидация; подготовка frontend к уточнённому контракту отдельным документом.
3. Отдельно согласовать порядок Клуба до SQL pagination и клиентского объединения.
4. Частота activity, legacy полные выдачи, завершение процесса; безопасный индекс
   только после приёмки чтений **и записей**. YouTube — по принятому scope перехода.

Это результаты исследования, не реализованные исправления. Готовность всего
договора, большие реальные загрузки, боевые оплаты, устройства и пилот здесь
не принимались. Подготовленный перенос388файлов и его свежий backup сохранены,
массовое применение/закрытие старых URL не выполнялось.

## Проверки и очистка

Девять независимых JSON receipts: SQL/HTTP, типы, видеокаталог, процессы,
пул, индексы/read-write, runtime и READ ONLY порядок. Исходные неудачные
попытки тестовой обвязки (tsx config, production-запрет HTTP loopback)
сохранены отдельно и не классифицированы как дефекты приложения.
Первый native-прогон после экспериментального индекса упал именно на его
INSERT; после удаления обоих кандидатов **20из20 native тестов прошли**.
check:api —102процедуры; это положительный контроль генерации, не полноты DTO.

Собственная временная БД удалена по ID/name/owner/tmpfs guard:
OOM=false/restarts=0, volumes не создавались. Временные HTTP/SDK wire и дочерние
процессы завершены; образы, чужие контейнеры и резервные копии не удалялись.
Продуктовые файлы и frontend не менялись. Проверки ссылок документации и diff
выполняются перед сохранением отчёта.
