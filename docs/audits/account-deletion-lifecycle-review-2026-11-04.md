# Запрос удаления аккаунта: отзыв доступа и повторы

4 ноября 2026. Исходный снимок d2d1f005, чистая ветка
feature/stage-one-completion-2026-10-10. Проверен следующий локальный пункт
security-аудита: profileExtras.requestAccountDeletion. Фронт и рабочие данные
не менялись; без push/deploy.

## Граница и воспроизведение

Маршрут проверяет пользователя при входе в запрос, но передавал в
ProfileService и identity/account-retention только числовой ID. UPDATE users
не сверял актуальный openId/sessionVersion/blockedAt. Уже авторизованный запрос,
дождавшись блокировки строки, мог записать accountDeletionRequestedAt после
отзыва сессии, блокировки или смены identity. Реальный локальный HTTP во всех
трёх случаях возвращал 200. Это действие над своим аккаунтом через устаревший
контекст, а не доказанный доступ к чужому аккаунту или обход свежей авторизации.

Отдельный HTTP-запрос приостановлен на границе сервиса после настоящей JWT-
аутентификации. Реальный worker обезличил синтетический аккаунт и увеличил
sessionVersion. Продолженный запрос возвращал 200 и снова отмечал уже очищенный
аккаунт на удаление. Внешний S3 и почта в сценарии не участвовали.

Ещё один тест показал, что повтор изменял дату уже принятой заявки:
2026-10-30 10:00:00 заменялось текущим временем. Для аккаунта без оплаченной
подписки это сдвигало начало существующего 30-дневного периода. Правила для
аккаунтов с историей подписки зависят от срока доступа и здесь не менялись.

Пять новых проверок сначала упали по этим ожидаемым утверждениям; обычный
запрос и отказ гостю проходили. Таким образом дефекты подтверждены до изменения.

## Исправлено локально — P2

- HTTP и сервис передают доверенный actor с id/openId/sessionVersion.
- Канонический writer в транзакции блокирует users-строку и проверяет её
  актуальную identity, epoch и блокировку перед любой записью.
- Пропавший/заменённый аккаунт или отозванная сессия возвращают UNAUTHORIZED;
  блокировка после начала запроса — FORBIDDEN.
- Уже принятая заявка возвращает прежний успешный ответ без новой записи даты.
  Восстановление после потери ответа не требует нового ключа операции.
- Сроки, подписки, фоновое обезличивание и отсутствие немедленного удаления
  при принятии заявки сохранены. Отмену заявки или новый экран не добавляли.

Публичная процедура по-прежнему без входных полей, ответ {ok:true}. При пропаже
аккаунта после аутентификации теперь 401 вместо прежнего общего 500. Действующие
401/403 необходимо обрабатывать как отказ, не как принятую заявку. Новых полей
в контракте frontend нет; check:api подтверждает прежние 107 процедур.

## Проверка

- 7/7 новых HTTP/JWT/SQL-сценариев: три изменения доступа во время ожидания,
  повтор с прежней датой, продолжение после обезличивания, обычный запрос и гость.
- 91/91 SQL-тестов в шести файлах. Проверены profile revisions, legacy security
  guards, реальные profile HTTP-записи, отзыв после retirement и существующий
  retention. Включены пять opt-in worker lifecycle-проверок на одноразовой БД.
- 89/89 unit/HTTP-проверок в четырёх файлах: профиль, availability/revocation,
  legacy upload retirement.
- Root/frontend types, backend lint, API-контракт, границы модулей, API/TEST
  сборки проходят. Схема и миграции не менялись.

Один общий прогон выявил пересечение email фикстуры с соседним тестом.
Новый набор использует отдельные deletion-owner/deletion-neighbor адреса;
повторный общий прогон прошёл полностью. Рабочие данные этим не затрагивались.

БД создана отдельно из 51 проверенной миграции в tmpfs. Для гонок подтверждалось
настоящее ожидание SQL-блокировки, произвольные задержки не применялись.
После прогона БД удалена. Артефакты:
`../.local-artifacts/account-deletion-20261104` (red.log, green.log,
sql-regressions.log, http.log, migration.log, sql-cleanup.json и build/check logs).
