# Потеря блокировки работающей фоновой задачи

9 ноября 2026. Локальная проверка от `982a55e9`. Рабочий сайт, БД, S3,
фронтенд и админские входы не использовались и не менялись. Пуша и выкладки нет.

## Подтверждённая ошибка

`WorkerJobs → runExclusiveWorker → withDatabaseLock` удерживал именованную
блокировку отдельным MySQL-соединением. Callback работал через другие
соединения и не узнавал о потере блокировки. В двух воспроизведениях старая
реплика A продолжала работу после запуска B; тестовая таблица содержала
результаты B и A вместо одного B.

Условия: два отдельных Node/Nest HTTP-процесса, MySQL 8.4 в собственном
контейнере на tmpfs, полная цепочка 52 миграций. Задача синтетическая, без
платежей, писем и внешнего хранилища. Уничтожалось только соединение,
владение которым предварительно проверялось через `IS_USED_LOCK`.

Семантика согласуется с [документацией MySQL](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html):
именованная блокировка освобождается при завершении удерживающей её сессии;
она не останавливает код другого соединения.

## Минимальное исправление

- Только для фоновых задач в `mysql`-режиме добавлен `worker-lock-guard`.
- Перед callback проверяется владение блокировкой; затем проверка повторяется
  раз в секунду, без наложения запросов, с SQL-таймаутом 3 секунды.
- События `error`/`end`, потеря владения или ошибка проверки при активной
  задаче завершают **этот API-процесс с кодом 1**. Сообщение не содержит
  пользовательских данных, SQL или параметров соединения.
- Graceful drain здесь намеренно не используется: отклонение Promise и
  ожидание callback не отменяют его последующих записей и отправок.
- После обычного завершения/исключения callback мониторинг отключается;
  незавершённая проверка дожидается результата до возврата соединения в пул.
  Поздний сбой уже свободной сессии не завершает API.

Локальный режим, блокировки входных запросов, DTO, схема БД и логика
конкретных задач прежние. Новых сервисов, флагов и миграций нет. Пока задача
работает, добавляется максимум одна проверка в секунду на её lock-соединение;
необходимость этого соединения существовала и до исправления.

## Проверки

| Сценарий | Подтверждение |
| --- | --- |
| `KILL CONNECTION` удерживающей сессии | A завершается, не возобновляет callback; B записывает единственный результат и отвечает по HTTP |
| `RELEASE_ALL_LOCKS` при живой сессии | Проверка владения обнаруживает потерю и завершает A |
| Молчаливый разрыв через локальный TCP-транспорт | FIN/error не доставляются A; проверка истекает по таймауту; B продолжает работать |
| Потеря idle-сессии после нормального завершения | A остаётся живым и запускает следующую задачу |
| Callback завершился/выбросил ошибку во время проверки | Ожидание SQL завершается до возврата guard, обработчики и таймер сняты, поздняя ошибка не завершает процесс |

Новые приёмочные тесты: `tests/worker-lock-loss.mysql.test.ts` (4),
`tests/worker-lock-guard.test.ts` (2). До исправления два SQL-теста падали
именно на лишней записи A; обычное завершение уже работало.

Соседние SQL-наборы: `api-coordination`, `api-worker-shutdown`,
`api-graceful-shutdown`, `worker-stale-lease`, `vk-worker-boundary`,
`database-pool-admission`. Всего 26 SQL-тестов прошли. Локальные логи и
подтверждение удаления собственного контейнера:
`.local-artifacts/worker-lock-loss-20261109.zd8qr_zp` рядом с репозиторием.

Дополнительно прошли 50 unit/HTTP/compiled-проверок, TypeScript, backend
lint, неизменный API-контракт (107 процедур), границы зависимостей (910 файлов),
сборка API и проверка документации. Старый `workers-built.test.ts` потребовал
синтетический JWT_SECRET в изолированном production-окружении: без него
нынешняя проверка конфигурации отклоняла запуск ещё до проверки workers.
Рабочие секреты не использовались, production-валидация не ослаблялась.

## Ограничения и остаток

- **P1 перед выпуском:** проверить restart policy/health/routing и бюджет
  соединений у всех реплик. В базовом Compose есть `restart: unless-stopped`,
  но фактический серверный stack этим прогоном не проверен. При потере
  lock-соединения в единственной реплике будет перерыв до её перезапуска.
- **P2:** это остановка после обнаружения потери права на работу, а не
  абсолютная гарантия отсутствия параллельных эффектов. До обнаружения есть
  окно: обычно до следующей проверки плюс её таймаут; блокировка event loop
  может увеличить его. Зависший event loop, failover между MySQL-серверами и
  произвольные сетевые разделения полностью не покрыты.
- **P2:** принятые внешним сервисом письма/запросы и уже исполняемые SQL
  не отменяются завершением Node. Существующие ключи операций и проверки
  lease сохраняются; exactly-once не заявляется. Для строгого исключения
  устаревших эффектов нужен контроль версии владения на стороне каждой
  записи/получателя, а не только heartbeat.
- **P2, эксплуатация:** аварийный выход не выполняет async-finally, включая
  уборку временного `.partial` и файла настроек `mysqldump`. Остановка дочерних
  процессов и уборка собственных аварийных файлов при рестарте не проверялись
  этим срезом. Это также относится к прежним deadline/SIGKILL-сценариям.
- Пагинация Ленты/Клуба по offset остаётся отдельным согласуемым контрактом;
  её ограничение этим исправлением не меняется.

Общий аудит остаётся открытым. Проверена конкретная потеря worker lock,
а не все варианты аварии и не готовность рабочего окружения.
