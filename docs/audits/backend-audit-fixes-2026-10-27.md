## Существенные детали

### Загрузки и восстановление

Ограничен именно приём RAW-видео, а не все HTTP-запросы или все форматы файлов.
Это устраняет воспроизведённое накопление нескольких RAW-тел; приём 80 МиБ
в контейнере 256 МиБ и совокупная нагрузка разных форматов не объявлены принятыми.
Квоты 4/32/80 МиБ, настройки контейнеров и флаги не менялись.

Первый SQL commit фиксирует прежние actor/key/payload/namespace и assetId.
После внешнего эффекта проверяются та же запись/assetId, текущая сессия, роль,
блокировка, удаление аккаунта, recovery fence, срок восстановления, а для фото
комментария — видимость поста, клубный доступ и окно комментариев.
Отзыв во время сети может оставить собственный приватный объект и pending:
готового доступного вложения такая операция не создаёт. Автоочистка не включалась.

Параллельные повторы могут послать несколько условных PUT одного ключа.
Только один создаёт объект; 412 сверяется через HEAD по прежним metadata/типу/
размеру/ETag. Потерянный ACK остаётся pending до согласования повтором.
Ни перезаписи, ни второго assetId, ни подмены файла через другой payload нет.

### Совместимые списки

Ограничение 200 применяется к старым full-feed, saved/liked ID, comments, admin posts,
полным фильтрованным/отложенным постам, admin members и admin articles.
Переданные ID для старого saved списка ограничиваются до гидрации публикаций.
Для членов SQL возвращает MAX будущего оплаченного expiresAt только выбранных
участниц, а не все платежи; сохранён UTC-декодер TIMESTAMP.
`admin.payments` уже имел SQL LIMIT 50. Page API не менялись.

Переполнение — 413/PAYLOAD_TOO_LARGE с предложением постраничного метода.
Основные экраны уже на page API; точечная проверка потребителей перед выпуском
всё равно необходима. Полные выдачи не считаются совместимым способом обходить
пагинацию при росте данных.

### Исторические анонсы и журналы

Редактирование статьи обновляет все её старые анонсы, сохраняя их обсуждения.
Дубли не удаляются молча при обычной правке. Unpublish/delete статьи удаляет
все связанные анонсы и обсуждения общим транзакционным удалением.
Физический UNIQUE по всем значениям posts.source не добавлялся: прочие источники
по договору могут повторяться. Article PK сериализует штатные создатели анонса.
Внешний SQL-импорт обязан соблюдать это правило; автоматическое слияние старых
обсуждений не вводилось.

После удаления медиа исторические postId/mediaId в recovery receipt служат
запретом повторной привязки. Их нельзя обнулить как «мусор», иначе восстановится
возможность воскресить удалённый файл. Live выдача проверяет наличие post_media
и возвращает 404; существующая политика orphan/retention остаётся прежней.

### Индексы и выпуск 0044

Первый вариант COALESCE без CAST, а также IFNULL/IF, воспроизводимо ломает INSERT
с датой по умолчанию. Он **не** включён в миграцию. На этой MySQL 8.4 вариант
с CAST принимает все проверенные implicit/NULL/backdate записи.

MySQL отклонила LOCK=NONE для функционального индекса. Миграция использует
ALGORITHM=INPLACE, LOCK=SHARED и требует согласованного окна запрета записей,
резервной копии и проверки реальной версии/истории/дат перед будущим применением.
Рабочая схема в этой работе не менялась. Изменение кода сортировки совместимо
со старой схемой: до миграции CAST работает, но новых индексов ещё нет.

Клубная первая страница на синтетике использует порядок индекса без filesort.
Для Ленты оптимизатор иногда выбирает filesort даже при пригодном индексе;
FORCE INDEX применяется **только в тесте возможности**, не в продукте.
Поиск LIKE/JSON и глубокий OFFSET не стали индексным поиском: менять семантику
поиска или вводить новый keyset-контракт без отдельной задачи не стали.
Значения страниц старого и нового выражения даты сравниваются независимо.

Кодовый откат не требует удаления индексов. Если требуется откат именно DDL:

```sql
ALTER TABLE posts
  DROP INDEX posts_feed_listing_idx,
  DROP INDEX posts_club_listing_idx,
  ALGORITHM=INPLACE, LOCK=NONE;
```

Это инструкция, не команда на рабочей БД. Журнал применённых миграций вручную
не переписывать; повторное применение согласовать по фактической схеме/истории.

### Завершение и видеосервис

Восемь секунд выбраны внутри стандартных десяти секунд остановки контейнера.
Дедлайн не гарантирует завершение медленного внешнего действия; для uploads и
оплат сохранён существующий durable recovery. Новая очередь маркетинговых push
не вводилась. Запущенная отправка scheduled job теперь входит в его ожидание;
обычные detached уведомления публикации не получили гарантию доставки после crash.

Backend и legacy video-service следует выпускать согласованно: новый сервис
использует `videos.publicYoutubeState`. Ответ — только published boolean,
лимит читателя 4096 байт, redirect запрещён, проверка до и после подготовки.
Недоступная authority даёт отказ, а не публичный обход. Это исправление старого
YouTube-пути; 22 VK iframe, их записи и источники не менялись.
