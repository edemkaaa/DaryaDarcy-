## Исправления и повторная проверка — 6 ноября

Применены `test-driven-development`, `code-review` и
`verification-before-completion`. Новые проверки сначала упали на исходной
версии по обеим заявленным причинам; затем прошли после узких изменений.

- Пул сохраняет 10 соединений и ожидание коротких всплесков, но очередь теперь
  ограничена 10 запросами. В первой серии из 30 при полностью занятом пуле
  лишние 20 получают 503 раньше трёхсекундного таймаута; остальные 10 получают
  503 по таймауту. Следующая серия из 30 отклоняется сразу, очередь не растёт.
  После освобождения пула обычный SELECT и новая операция работают;
  просроченные callbacks не выполняются.
- REST-видео передаёт сигнал закрытия незавершённого ответа до существующего
  S3-helper. HTTP/S3-соединение закрывается после отмены, admission освобождается
  только после завершения работы. Listener снимается, в закрытый ответ JSON не
  отправляется. Воспроизведение использует реальный HTTP/JWT/SQL/AWS SDK и
  локальный транспорт хранилища. После отмены запись остаётся `pending`;
  если хранилище всё же приняло байты, повтор с тем же ключом возвращает тот же
  `assetId` и `ready` без второго PUT.

Прошли 147 SQL-тестов (7 наборов), 23 unit/HTTP-теста, `tsc --noEmit`,
`lint:backend`, `check:api` (107 процедур), `check:boundaries` (908 файлов)
и сборка основного API. SQL-наборы включают два процесса координации,
graceful shutdown, чтение контента, закрытые вложения и обрывы публичных загрузок.
Одноразовая MySQL получила все 52 миграции, затем контейнер с tmpfs удалён.
Логи RED, GREEN и регрессий:
`.local-artifacts/backend-admission-fixes-20261106.ctqt6x_u` рядом с репозиторием.

Ограничения: предел очереди не отменяет уже принятые драйвером ожидания. Их
остаётся не больше 10 до освобождения соединений; отдельный отменяемый пул
не добавлялся. При насыщении обычный SQL также может получить отказ очереди;
ответ 503 проверен именно на границе координации. Отмена HTTP не откатывает
уже принятый S3-файл или завершившийся SQL-коммит: для этого сохранён прежний
контракт восстановления по ключу. Реальный Timeweb и большие загрузки в этом
проходе не проверялись. Миграции и API-контракт не изменены; пуша и выкладки нет.

## P2 — ожидания MySQL после 503: неограниченный рост исправлен локально

Ниже исходное воспроизведение до исправления.

Подтверждено на отдельной MySQL 8.4.11 с настоящими `getDb` и
`withDatabaseLock`, без подмены драйвера.

В [connection.ts](../../apps/backend/src/database/connection.ts) задано
`connectionLimit: 10`, но предел очереди отсутствует. Фактические настройки
драйвера: `queueLimit: 0`, `waitForConnections: true`. Ноль означает отсутствие
предела. В [coordination.ts](../../apps/backend/src/database/coordination.ts)
таймер обрывает ожидание вызывающего кода через 3 секунды, но `Promise.race`
не отменяет поставленный в очередь `pool.getConnection()`.

Воспроизведение:

1. Занять 10 соединений только тестовой базы.
2. Отправить 30 вызовов координации: через 3003 мс все получили 503,
   в очереди драйвера осталось 30 ожиданий.
3. Повторить: через 3002 мс ещё 30 отказов, очередь выросла до 60.
4. Освободить соединения: очередь опустела, просроченные callbacks операций
   не запустились. Защита от запоздалого выполнения работает.

Последствие: при длительной занятости соединений продолжают удерживаться
ожидания уже отклонённых запросов. OOM и нагрузка реальных пользователей
этим небольшим тестом не доказаны. Это проблема устойчивости, не обход доступа.

Минимальный следующий шаг: ограничить ожидания на стороне приложения/пула,
сохранив корректное освобождение поздно полученного соединения и ответ 503.
Проверить обычный запрос, насыщение, повторные серии после таймаута и восстановление.
Не увеличивать количество соединений без расчёта общего бюджета нескольких API.
Изменение `queueLimit` ограничит рост, но само по себе не отменит старые ожидания.

## P2 — отмена REST-видео: исправлено локально

Ниже исходное состояние до исправления.

В [private-video-upload.controller.ts](../../apps/backend/src/content/private-video-upload.controller.ts)
`storePrivateAttachment` вызывается без сигнала отмены. При обрыве клиента
обработка продолжается до завершения или таймаута хранилища, а слот загрузки
занят. Такое поведение прямо закреплено существующим
[тестом admission](../../tests/video-upload-admission.test.ts), который прошёл.

Это ранее выбранное поведение, а не новая утечка файлов: SQL-журнал и проверки
прав сохраняются. Но отменённая загрузка удерживает тело до 80 МиБ и мешает
следующей загрузке в том же API-процессе. tRPC-загрузки уже передают отмену.
Полный REST-разрыв с настоящим SDK и медленным локальным S3 в этом проходе
не воспроизводился; размер фактически удержанной памяти не замерялся.

Минимальный следующий шаг: такой воспроизводящий сценарий, затем передача
сигнала закрытия HTTP до существующего S3-helper. Слот освобождать после
завершения отмены, а принятую хранилищем операцию восстанавливать прежним ключом.

## Что пока не считать подтверждённой ошибкой

- Числовые ID остаются в API намеренно для совместимости. UUID не заменяет
  авторизацию; скрывать все внутренние ID новой переработкой не требуется.
- OFFSET в Ленте/Клубе сохраняет риск смещения страниц при одновременных
  публикациях. Тесты текущей сортировки прошли; динамический сценарий и
  компенсация на клиенте целиком заново не проверены. Это дальнейшее исследование.
- Общий pool и совместимые фасады сами по себе не требуют замены Nest-модулями
  или новыми сервисами. Исправлять следует подтверждённое поведение очереди.
