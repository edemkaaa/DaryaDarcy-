# Поздняя запись после окончательного удаления аккаунта

4 ноября. Ошибка обнаружена в версии `a34699fd` и исправлена локально. Проверены семь операций, сохранность данных после отказа, обычная запись до удаления и удаление чужого комментария после отзыва роли администратора. На одноразовой MySQL прошли 79 тестов, 5 пропущены. Сборка и приёмка нового образа остаются отдельным шагом перед выпуском.

## Первоначальное воспроизведение

## P1: часть writers не проверяет актуальную версию сессии

Запрос может пройти первоначальную авторизацию, задержаться, затем продолжить
выполнение после окончательного удаления аккаунта. Retention действительно
очищает данные и увеличивает users.sessionVersion, но не все writers сверяют
эту версию внутри транзакции перед изменением данных.

На новой одноразовой MySQL8.4 после 51 настоящей миграции выполнен реальный
processScheduledAccountDeletions, затем вызваны маршруты через сохранённый
до удаления tRPC context. Без подмены SQL/политик получены следующие результаты:

| Операция | Фактический эффект после завершённой очистки |
| --- | --- |
| club.addComment без ключа | Успех, новый post_comments с переданным личным текстом |
| club.updateComment | Успех, обезличенный текст снова заменён переданным текстом |
| club.toggleCommentLike | Успех, новая comment_likes от удалённого аккаунта |
| club.reportComment | Успех, новая comment_reports с переданной причиной |
| feed.toggleLike | true, новая likes от удалённого аккаунта |
| feed.toggleSave | true, новая saved_posts от удалённого аккаунта |
| club.deleteComment от прежнего admin | Успех, удалён комментарий соседнего пользователя |

Это один класс пропущенной проверки в 7 путях. Свежий запрос с уже отозванной
cookie этим исследованием не взломан: существующая первоначальная проверка
сессии его отвергает. Условия воспроизведения — ранее авторизованный, ещё
выполняющийся запрос. Произвольный userId через публичный input не подставлялся.
Публичный HTTP-тайминг гонки здесь не измерялся: тRPC context намеренно сохранён
до реальной SQL-анонимизации, затем продолжен. Работающий стенд не проверялся.

## Причина в коде

- `content/comments.ts:121`: actor/epoch проверяются только в recoverable-ветке;
  обычный текст без idempotencyKey проходит дальше без этой проверки.
- `content/content-comment.service.ts:113–132`: update/like/delete/report получают
  текущего на момент ingress пользователя, но передают writers только id/флаг staff.
- `content/comments.ts:189–292`: транзакции блокируют комментарий, проверяют
  владельца, но не проверяют actor.sessionVersion. asStaff вычислен до транзакции.
- `content/feed-router.ts:42–49`, `content/content-write.service.ts:26–31`,
  `db.ts:322–335`: при передаче реакции сохраняется только userId.
- `content/post-reactions.ts:57–70`: пользователь уже блокируется перед реакцией,
  но sessionVersion не выбирается/не сравнивается; после retirement blockedAt=null.
- `identity/account-retention.ts:128–154`: очистка и увеличение версии действительно
  атомарны. Повторный обход retention не заменяет fence в writer.

Keyed комментарии уже используют private-comment-actor внутри транзакции.
Посты/статьи имеют собственный actor fence. Эти защиты не распространяются
автоматически на перечисленные старые пути.

## Минимальное полезное исправление

1. Передавать доверенные id/sessionVersion из ctx.user до транзакций этих writers;
   публичный input/ответ и фронтовый контракт не расширять.
2. Блокировать актуальную users-строку и сверять epoch до блокировок post/comment
   и любых эффектов. Отозванный actor получает UNAUTHORIZED, заблокированный —
   FORBIDDEN. Роль для staff deletion определять по актуальной записи.
3. Сохранить прежнюю политику pending-deletion/подписки; не вводить новые сроки,
   настройки или автоматические удаления. Для доверенных maintenance consumers
   сохранить явно внутренний путь и существующие транзакционные границы.
4. Превратить сохранённые 7 RED-регрессий в GREEN и проверить конкуренцию
   actor → post/comment, rollback, смену роли/блокировку и совместимые helper calls.
   Новая таблица/миграция для этого не требуется.

Исправление добавлено в рабочую ветку. Аналогичные оставшиеся
moderation/profile writers нужно проверить отдельно; здесь им не присвоен
статус «без ошибок» и их поведение не объявлено воспроизведённым.

## Проверки и доказательства

- Новые semantic RED: 7 failed / 1 positive passed, 1,36 с. Каждый failed получил
  успешный результат и подтверждённое изменение SQL вместо UNAUTHORIZED.
- Существующие 5 файлов: 70 passed / 5 skipped, 5,76 с, exit 0. Это account-retention,
  authenticated-retirement, recovery-export, content-recovery-compaction,
  comment-mutations. Пропуски не считаются успехом.
- Оба раза 51 настоящая migration применена штатным fresh installer; журнал
  legacy fixture helpers только отмечает уже применённые migrations. История
  рабочей БД не исправлялась. Новые tmpfs-контейнеры удалены после каждого прогона.
- `../.local-artifacts/recovery-code-review-20261104` рядом с репозиторием содержит
  review.json, SQL/миграционные логи, cleanup JSON и точный исходник RED-теста.
  В репозиторий добавлен регрессионный тест, проверяющий также состояние записей после отказа.
