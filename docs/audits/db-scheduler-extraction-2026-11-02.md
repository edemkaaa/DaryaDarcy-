# CQ-4: планировщик публикаций выделен из db-фасада

2 ноября 2026. База `0e02a1c2`. Работа локальная.

## Изменение

Оставшаяся транзакция публикации отложенных постов перенесена из `db.ts` в
`content/scheduled-publication.ts`. Старый export `publishDueScheduledPosts()`
с прежним возвращаемым типом делегирует ей `await getDb()`. Воркеры и остальные
потребители продолжают использовать фасад; их импорты и поведение не менялись.

При отсутствии БД по-прежнему возвращается пустой массив. Выборка due-строк,
порядок ID, FOR UPDATE SKIP LOCKED, обновление дат и возврат объявляемой партии
после commit сохранены. Новых подключений и пулов нет. AST всей логики после
получения db совпадает с исходным; getDb/closeDb тоже совпадают по AST.
Nullable-контракт, UTC, connectionLimit и обработка ошибок getDb прежние.

## Проверки

- До изменения: 4/4 SQL-сценария планировщика прошли на новой одноразовой MySQL.
- После: 56/56 SQL-сценариев в scheduled-publication и manual-publication проходят,
  без skip и изменения тестов. Проверены два параллельных воркера, следующий тик,
  заблокированная строка и отмена публикации, rollback всей партии с повтором,
  совместная ручная/автоматическая публикация и ревизии постов/вложений.
- 30/30 целевых unit-тестов воркеров и объявления публикаций проходят.
- Backend TypeScript, lint без предупреждений и штатная backend-сборка проходят.
- Границы модулей: 896 файлов; API-контракт: 107 процедур / 46 501 байт, без изменений.
- diff-check и проверка документации проходят.

Одноразовая MySQL 8.4 ARM64 запущена из уже имеющегося образа, отдельным контейнером,
с БД backend_test, случайным портом только на 127.0.0.1 и tmpfs для данных.
Лимит RAM 768 МиБ, CPU 1; существующие контейнеры/volumes не использовались.
После проверок только свой контейнер удалён; tmpfs и временный файл учётных данных
убраны, образ сохранён. Схему готовили существующие SQL fixtures; это не проверка
полной истории миграций рабочей БД.

Доказательства вне Git: `../.local-artifacts/cq4-scheduler-20261102/`:
baseline.log, sql-after.log, equivalence.json, cleanup.json и локальный driver.
Рабочая БД, S3, фронт и админские входы не затрагивались. Пуша/выкладки нет.
