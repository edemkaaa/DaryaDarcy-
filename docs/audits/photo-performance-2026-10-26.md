# Загрузка фотографий: замеры и порядок ускорения

26 октября 2026. Домен: daryadarcy.dev.reeskeen.ru. Исследование после адресного
исправления TTL девяти превью. Продуктовый код, настройки сервера, БД,
админские входы и исходные S3-файлы не менялись. Выполнялись обычные GET,
чтение DOM существующей сессии и read-only SSH. Новая ширина превью при GET
может штатно заполнить производный кеш; целевой оригинал при этом не меняется.

## Подтверждённые наблюдения

Встроенный браузер: viewport319px, DPR2. Это один размер и одна текущая сеть,
не полный набор устройств и не воспроизведение проблемного VPN.

| Участок | Что наблюдалось | Следствие |
| --- | --- | --- |
| Фото первого поста Ленты | Ячейка106px, currentSrc выбирает640px. Общий sizes описывает100vw/480px | В сетке нужно передавать реальную ширину ячейки, учитывая число колонок |
| Библиотека | Карточка138px, выбран статический вариант1200px, sizes100vw | Проверить те же размеры карточек и доступные маленькие варианты |
| Магазин | Изображение85px, выбран900px при наличии320px в srcset | Даже подготовленные варианты используются не по размеру карточки |
| Видео | Первая обложка — прямой PNG из публичного S3, без вариантов | Сначала подготовить отдельные небольшие WebP, не менять оригиналы |
| Возврат Клуб→Лента | Все9фото видимой сетки complete=true, currentSrc прежний | Повторную бесконечную загрузку в этом возврате не наблюдали; cache-hit этим не доказан |
| Карусели/списки | Feed carousel ограничивает источники соседними слайдами; списки имеют windowing, дальние VK-карточки lazy | Эти механизмы уже есть, повторно переписывать их не нужно |

В Клубе фотографии соседнего окна строк загружаются eager: это явно сделано
для clipped scroller, до двух экранов вперёд. Уменьшение этого окна — только
после отдельного замера первого экрана и быстрой прокрутки; не удалять работающий
механизм ради формального уменьшения количества запросов.

## Числа HTTP и размеров

Два последовательных прохода curl, без cookies; каждый запрос устанавливает
своё соединение. Сжатие ответа разрешено. Это не пользовательский LCP,
не браузерный waterfall, не percentiles и не нагрузочный тест.

| Запрос | Передано по сети | Полное время двух запросов |
| --- | ---: | --- |
| HTML /feed | около7,6КБ gzip | 0,293 / 0,177s |
| HTML /videos | около5,8КБ gzip | 0,168 / 0,206s |
| HTML /library | около8,1КБ gzip | 0,390 / 0,177s |
| HTML /shop | около9,1КБ gzip | 0,298 / 0,219s |
| feed.listPaginated limit12 | 16 573байта | 0,800 / 0,897s |
| Первая фотография,320px/WebP | 17 518байт | 1,485s MISS / 0,306s HIT |
| Та же фотография,640px/WebP | 54 212байт | 0,265 / 0,353s, HIT |
| Та же фотография,1440px/WebP | 231 650байт | 0,515 / 0,650s, HIT |
| Первая обложка VK,533×301PNG | 297 943байта | 0,766 / 0,530s |
| Публичная бумажная текстура1440px | 226 992байта | 0,469 / 0,494s |

Разница320/640 для этой фотографии — **минус68% байтов**. Это пример,
не обещание такого же процента для всего сайта. Первый MISS320 включает
получение исходника и обработку; разделить их время этим замером нельзя.
В обоих API-запросах TLS занял около0,68s до HTTP, поэтому приписывать полное
время0,8s SQL нельзя. API и весь экран следует измерять отдельно.

У превью max-age3600. У статической текстуры — год и immutable. У проверенной
S3-обложки нет явного Cache-Control; присутствует ETag. Это не означает,
что браузер вообще не кеширует её: возможна эвристическая свежесть.

Локальное сравнение одной публичной обложки, без записи в S3/БД:

- PNG:297943байта,533×301.
- WebP lossless:198984байта; декодированные RGBA совпадают полностью.
- WebP quality85:37150байт, те же размеры, примерно в8раз меньше PNG.
  Это вариант с потерями; перед выпуском нужна визуальная приёмка текста/лиц.
  По одному примеру качество остальных21обложки не подтверждено.

В локальном каталоге есть и другие простые резервы: обложка карточки
Библиотеки1200px весит172800байт, её существующий320px —22356байт.
У декоративной рамки1200px196004байта,320px75350байт. Это размеры локальных
файлов с теми же hash-именами; отдельный сетевой GET этих примеров не выполнялся.

## Safari и восстановление при ошибке

Наш Picture задаёт src перед srcSet/sizes. В установленном Next
get-img-props.js явно оставляет src последним: Safari может начать запрос
до назначения srcSet/sizes. Риск дополнительных запросов подтверждён
сопоставлением реализации, но реальный двойной запрос на iPhone здесь
не записывался. Фронтендеру нужен отдельный WebKit/iPhone network regression.

Тот же Picture при ошибке /_next/image автоматически переключается на
оригинальный URL. На плохой сети это может добавить многомегабайтный файл
после неудачного превью. Нельзя просто выключить восстановление: сначала
проверить отказ оптимизатора, offline→online, ручной повтор и отсутствие
бесконечного loader, затем выбрать ограниченное восстановление превью.
Закрытые файлы не должны попадать в публичный оптимизатор или общий кеш.

## Минимальная последовательность

1. **Frontend: размеры и Safari.** Передать slot-aware sizes в PhotoTile,
   grid/feed/club/library/shop; полноэкранный viewer сохраняет100vw. Сначала
   использовать существующие320/640варианты, новые создавать только при
   подтверждённом пробеле. Назначать sizes/srcSet до src. Дизайн сохранить.
2. **Публичные обложки VK.** Отдельные WebP с сохранением оригиналов,
   hash в новом имени и длительным immutable только для неизменяемых копий.
   Предпочесть существующую выдачу/конвейер, не открывать оптимизатор для
   произвольного URL и не менять все22thumbnailUrl без согласованного выпуска.
3. **Первый экран и возвраты.** Измерить LCP-элемент; eager/high — ему,
   остальным оставить ограниченную отложенную загрузку. Проверить отказ
   превью и fallback; не увеличивать TTL/React Query cache глобально для
   сессий, подписок, приватной выдачи, платежей и playback.
4. **DevOps и проверка100посетителей.** Сначала резерв диска/RAM либо
   выделенный VPS, затем отдельный кандидат и одноразовая БД без внешних
   писем/оплат. Ступени10→25→50→100посетителей с паузами и отдельный всплеск
   открытия.100посетителей не равны100RPS; новые цели API сверх существующих
   5/10/25RPS требуют отдельного профиля, а не обхода лимитов runner.

Приёмка frontend: viewport319/390/480/desktop, DPR1/2/3, сетки1–4колонки;
currentSrc соответствует slot×DPR с округлением до доступного варианта,
качество viewer не ухудшается. Повторный переход к тем же фото при том же
viewport в пределах свежести не передаёт body повторно либо даёт304;
контролировать фактическую сеть, не только complete/fade. Браузерный HTTP-кеш
в тесте должен быть включён; interception может менять его поведение.

Цель первого экрана для следующего фиксированного lab-сценария: видимые фото
готовы за2,5s при3Мбит/s, RTT150ms и одинаковом устройстве, холодный/тёплый
прогоны раздельно. Это предлагаемая цель, не результат текущего исследования
и не гарантия для любого VPN. Уже имеющийся measure-frontend-loading.mjs
сначала актуализировать по страницам/ролям, не писать новый мониторинг.

Нагрузка: прежние критерии runner — read p95≤500ms/p99≤1500ms,
write p95≤1000ms/p99≤2000ms, без ошибок/пропущенных стартов/OOM/restarts;
плюс отдельная память web и очередь холодных изображений. Не стрессовать
рабочий сервер. Архитектурные изменения и CDN — только если после этих
простых шагов измерения покажут необходимость.
