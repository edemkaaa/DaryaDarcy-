# Оплаты клуба и доступ к аккаунту

Состояние на 02.10.2026: серверная реализация выполнена и проверена локально.
**Выпуск запрещён до внешней приёмки и проверки миграций.** Этот этап относится
к подписке клуба. Старые оплаты магазина и его доставка не переведены на новый
механизм; их нельзя считать проверенными или включать в первый выпуск.

## Что изменилось

- MySQL работает через пул: параллельные транзакции не используют одно соединение.
  Блокировка пользователя сериализует разные оплаты одного участника.
- Оплата клуба, уникальная квитанция и письмо доступа фиксируются одной
  транзакцией. Повтор не продлевает срок и не создаёт второе письмо. Тот же
  provider payment ID с другим заказом/суммой/получателем отклоняется.
- Цена сохраняется при checkout; сумма проверяется целыми копейками. Нужны
  RUB, ожидаемый домен формы, соответствующий ключ подписи и известный заказ.
  ID пользователя и email из уведомления не выбирают произвольного владельца.
- Ежемесячный provider profile связывается с аккаунтом при первоначальном
  подтверждённом платеже. Автосписание использует эту связь и устойчивый payment ID,
  а не email или текущее время. Неизвестный профиль отклоняется.
- Отмена сначала сохраняется как запрос, затем подтверждается провайдером.
  HTTP 200 с текстом ошибки не считается успехом. Ошибки повторяются с задержкой;
  оплаченный срок не сокращается. Платёж в момент ожидающей отмены не превращает
  ожидание в подтверждённую отмену.
- Одноразовый случайный токен: SHA-256 в таблице токенов, AES-256-GCM в ожидающем
  письме. Setup действует 24 часа, reset — час. Повтор, просрочка, блокировка и
  смена email делают ссылку недействительной. Setup не заменяет существующий пароль.
- Завершение смены пароля увеличивает sessionVersion и отзывает прежние сессии.
  Оно не выдаёт новую сессию и не обходит штатную 2FA сотрудников.
- Полномочия сотрудников берутся только из явной роли. OWNER_EMAIL и OWNER_OPEN_ID
  больше не дают прав при регистрации, входе, в tRPC или загрузке видео.
- Блокировка отзывает сессии и ставит известные автосписания в очередь отключения
  от имени менеджера. Заблокированная запись не проходит общую проверку сессии.

Протокол проверен по официальным описаниям [уведомлений подписок](https://help.prodamus.ru/payform/integracii/tekhnicheskaya-dokumentaciya-po-avtoplatezham/uvedomleniya)
и [setActivity](https://help.prodamus.ru/payform/integracii/rest-api-1/setactivity).
Документация не заменяет проверку реальных sandbox-пакетов конкретной формы.

## Проверка checkout 06.10.2026

На тестовом стенде подтверждены 503 для `club.createCheckout`, Prodamus return,
webhook и `/api/pay/:productId`: это явный запрет nginx, не ошибка интерфейса.
В API нет ключа Prodamus и ID подписки; платёжная форма — выключенная заглушка.
Этот этап **не снимает запрет**, не включает магазин и не выполняет списаний.

Исправления в исходниках бэкенда:

- Все ссылки возврата/уведомлений берут origin из `PUBLIC_APP_URL`, без
  подстановки исходного production-сайта и без доверия к Host запроса.
  Неверная конфигурация browser return даёт безопасный 503.
- Ежемесячный тариф передаёт документированное `payment_method=SBP`, а не `sbp`.
  Полугодовой разовый тариф не навязывает российский СБП зарубежным картам:
  покупатель выбирает доступный метод в форме провайдера.
- До создания получателя/заказа обязательны явная HTTPS-форма
  `<merchant>.payform.ru` без credentials, порта, пути, query/hash, ключ подписи,
  корректная положительная цена и безопасный `PUBLIC_APP_URL`.
  Ежемесячный тариф также требует положительный числовой ID подписки: отсутствие
  ID больше не превращает подписку в разовую покупку. Полугодовому тарифу ID
  не нужен. Ссылка строится до сохранения pending-заказа.
- При неверных настройках `club.createCheckout` отвечает tRPC
  `PRECONDITION_FAILED`: «Оплата временно недоступна. Попробуйте позже.»
  Значения настроек и исходная причина не раскрываются. Успешный контракт
  `{url, user: null}` и запрет выдачи сессии через checkout сохранены.

Сверено с [документацией формирования платёжных ссылок Prodamus](https://help.prodamus.ru/payform/integracii/rest-api/instrukcii-dlya-samostoyatelnaya-integracii-servisov).
При `subscription` массив `products` не определяет цену подписки: её цена в
кабинете должна совпадать с `CLUB_PRICE`, включая первый платёж, демо-периоды и
скидки. Интервал нужно согласовать с выдаваемыми сервером 30 днями.
Поддержку СБП именно для этой подписки и доступность зарубежных методов нужно
подтвердить в кабинете и тестовом сценарии, не предполагать по названию тарифа.

Для отдельного тестового включения нужны форма/ключи без production-списаний,
ID подписки и согласованный `SYS`; ключ уведомлений подписки может отличаться
от основного. [URL уведомлений подписок настраивается отдельно](https://help.prodamus.ru/payform/integracii/rest-api/url-dlya-uvedomlenii-i-sekretnyi-klyuch),
а не только параметром checkout. `demo_mode` и обработку demo-уведомлений нельзя
включать вслепую: тестовый режим не является доказательством реальной оплаты и
не должен выдавать production-доступ.

Изменения пока **локальные**, без push/деплоя. Фронтенд, его типы и тесты не
менялись. Проверка с настоящим Prodamus, автосписаниями и отменой остаётся
условием включения; сетевые ограничения стенда не ослаблены.

Проверки этого изменения: 64 теста checkout/configuration/webhook прошли;
полный набор **без `*.mysql.test.ts` — 590 passed / 4 skipped**. TypeScript,
сборка API, проверки границ зависимостей, документации и неизменности API-контракта
прошли. Новые проверки настроек/записи заказа сначала воспроизвели ошибки,
затем стали проходить после исправления. В этих проверках persistence заменён
fixture-реализацией; это не повторный прогон транзакций на настоящем MySQL и
не оплата через провайдера. Исторические MySQL-доказательства приведены ниже
отдельно и не заменяют свежую приёмку перед выпуском.

## Контракт серверных методов

### Ручная выдача дней клуба

Существующий admin.grantClub по-прежнему выдаёт 31 день и возвращает прежний
ответ. Расчёт и запись перенесены в [billing/grants.ts](../../apps/backend/src/billing/grants.ts):
транзакция берёт ту же блокировку пользователя, что settlement и очистка
аккаунта. Разные одновременные выдачи складывают дни, а не перезаписывают срок;
каждая получает отдельный UUID заказа вместо номера на основе текущей миллисекунды.
Заблокированный или анонимизированный аккаунт новую выдачу не получает. Внутренний
параметр дней должен быть положительным целым числом с безопасным диапазоном.

Проверено 12 сценариев на одноразовой MySQL: одновременные выдачи, срок по умолчанию,
истёкшая подписка, недопустимые дни и отсутствующий/заблокированный/удалённый
получатель. Это **не идемпотентность повтора одного HTTP-запроса**: повторное
нажатие администратора остаётся новой выдачей. Для защиты от такого повтора нужны
отдельный request ID и согласованный клиентский контракт. Письма и внешние оплаты
этот модуль не отправляет; новые права сотрудников не добавлены.

### Остальные методы

| Метод | Запрос и ответ |
|---|---|
| `POST /api/auth/password/request` | JSON `{email}`. Одинаковый 202 для известного, неизвестного, заблокированного или ограниченного по почте получателя; 429 для ограничения IP; 503 при сбое приёма |
| `POST /api/auth/password/complete` | JSON `{token,password}`. 200 `{ok:true}` либо 400 при недействительной ссылке/пароле; длина 8–200. Cookies и sessionToken не выдаются |
| `GET /api/auth/password#token=…` | Минимальная серверная форма установки пароля. Fragment не передаётся серверу; страница очищает его и отправляет токен только в POST body. No-store, no-referrer, CSP с nonce |
| `POST /api/admin/access-email/resend` | Только admin/moderator, JSON `{userId}`, проверка Origin и лимит. 202 означает запись в очередь, не доставку. Адрес берётся из аккаунта с действующей оплатой; действие записывается в аудит |
| `club.cancel` | Прежнее имя tRPC. `ok:true` только после подтверждения отключения всех известных профилей. При неудаче сообщает, что запрос сохранён, но списания ещё могут быть активны |
| `/api/prodamus/webhook` | Неверная подпись — 400; нарушенная связь успешного платежа/отмены — 422; ошибка БД — 500. Требует явного успешного статуса оплаты; уведомление без него доступ не выдаёт |

Публичные лимиты запросов пароля: 10/IP за 15 минут, 3/email за час;
завершение — 20/IP за 15 минут. Лимитер пока в памяти процесса: перед несколькими
API-инстансами нужен общий лимитер или согласованный контроль на периметре.

Фронтенд этого этапа не переделывался. До выпуска нужно подключить кнопку
«Установить/восстановить пароль» к request API и проверить форму письма на
реальных Android/iPhone/web браузерах. Серверная форма по ссылке уже существует.

## Письма и повторные попытки

Worker запускается при старте API и каждые 30 секунд, обрабатывает до 20 событий
за проход. Транзакция забирает запись с FOR UPDATE SKIP LOCKED и lease; отправка
идёт вне транзакции. SMTP timeouts меньше пятиминутного lease. После сбоя —
экспоненциальная задержка; после 12 попыток — discardedAt и lastError. Просроченные
или устаревшие ссылки также имеют отдельный discarded-статус, не ложный sentAt.
Повторить доступ можно через защищённый resend API или новый запрос пароля.

Гарантия: **одно событие на оплату и доставка с повторными попытками**, не
exactly-once SMTP. Падение после отправки и до фиксации sentAt может привести к
повторному письму. Стабильный Message-ID уменьшает дубли, но не гарантирует их
исключение. Токены, SMTP payload, адреса получателей и ответы провайдера не
выводятся новыми обработчиками в журнал ошибок. После доставки/отбрасывания
зашифрованный токен удаляется из outbox payload.

Контроль очередей оператором обязателен: количество pending/discarded писем,
возраст старейшего события, cancelRequestedAt без cancelledAt, callbacks 422/500.
Пример безопасного запроса состояния — без email, токенов и payload:

```sql
SELECT id, kind, attempts, createdAt, nextAttemptAt, sentAt, discardedAt, lastError
FROM access_email_outbox
WHERE sentAt IS NULL ORDER BY createdAt;
SELECT userId, attempts, cancelRequestedAt, nextAttemptAt
FROM billing_profiles
WHERE cancelRequestedAt IS NOT NULL AND cancelledAt IS NULL;
```

## Подготовка запуска

1. Сделать backup и проверить версию MySQL: механизм SKIP LOCKED проверен на
   MySQL 8.4; эксплуатационная версия должна поддерживать эти запросы.
2. Сверить фактическую схему и журнал миграций. В репозитории исторически есть
   файлы 0017–0019 без записей в journal; они не добавлены автоматически, чтобы
   не повторить неизвестные изменения рабочей БД. **Не запускать db:push/generate
   вслепую:** старые snapshots также не описывают полностью текущую схему.
3. На копии базы проверить исходную схему, затем применить проверенные аддитивные
   миграции 0020, 0021, 0022 через согласованный процесс учёта миграций. DDL не
   считается общей атомарной транзакцией: при сбое сначала проверить частичное
   состояние, а не повторять ALTER/CREATE вслепую.
4. Настроить отдельный AUTH_LINK_ENCRYPTION_KEY: 32 случайных байта в canonical
   base64. Хранить отдельно от базы и JWT_SECRET. Потеря/неправильная ротация ключа
   делает ожидающие зашифрованные ссылки нечитаемыми — потребуется resend.
5. Настроить SMTP и HTTPS PUBLIC_APP_URL. PUBLIC_AUTH_URL задаётся отдельно,
   если серверная password-страница расположена на другом публичном origin;
   иначе берётся PUBLIC_APP_URL. `/api/auth/password` должен попадать на API,
   `/login` — на frontend. Настроить SPF/DKIM и проверить попадание писем в inbox.
6. Проверить явные роли законных сотрудников и 2FA до удаления старых способов
   bootstrap. Не назначать admin пользователю только из-за совпадения email.
7. Сверить старые pending/paid заказы, сохранённую цену, provider payment ID и
   профили автосписаний. Старые paid без квитанций и monthly без известного
   профиля требуют отдельной сверки; их нельзя автоматически «принять по email».
   Отсутствие профиля не означает, что автосписания отключены. Для legacy ЧС также
   нужна сверка/остановка списаний в кабинете провайдера.
8. Пройти sandbox: первая оплата, разные способы оплаты, повтор/параллельные
   уведомления, failed/error, продление, неизвестный профиль, отмена/timeout,
   поздний платёж после отмены, блокировка и уже списанный платёж без выдачи доступа.
   Сверить actual payment_status, domain, id/profile_id, error_code и подписи.
   Не ослаблять валидацию для решения несовместимости: приостановить checkout,
   сохранить сверку и отдельно обработать реально списанные деньги.
9. Пройти реальный SMTP, мобильные формы, очередь после перезапуска, нагрузку,
   алерты и возвраты. Проверить хранение/удаление персональных данных новых таблиц.
   Закрыть остальные блокеры исходного аудита: CORS/CSRF, медиа, зависимости,
   выключение магазина/SMS и capability gates первого выпуска.

Не откатывать сервер к известным обходам оплаты/входа. При проблеме остановить
checkout и согласовать совместимый rollback с сохранением квитанций, очередей
и всех подтверждённых оплат. DROP новых таблиц после живых платежей недопустим.

## Локальные доказательства

На одноразовой MySQL 8.4 проверены последовательные и конкурентные повторы,
разные оплаты одного пользователя, повтор provider ID на другом заказе,
сумма, неизвестные/известные recurring profiles, транзакционный rollback при
ошибке записи ссылки, токен replay/expiry/email-change, параллельное потребление,
reset без преждевременной замены пароля, SMTP failure/retry и staff resend с аудитом.

Локальный HTTP server проверяет настоящий parser/HMAC/handlers и MySQL;
имитируются только платёжный HTTP endpoint и отправка SMTP. Проверено, что 200
с ошибкой не подтверждает отмену, а завершение пароля не устанавливает cookie.

Финальный набор: **252 passed / 3 skipped**; пять последовательных полных
прогонов с MySQL после исправления ожидания очереди. TypeScript и API build
проходят. Пропуски — прежний logout-тест и S3 integration tests без credentials.
Это не тест реальных SMTP, Prodamus или production инфраструктуры.

Повторить на локальной одноразовой базе с именем `backend_test`:

```sh
BACKEND_TEST_DATABASE_URL='mysql://USER:LOCAL_PASSWORD@127.0.0.1:PORT/backend_test' pnpm test
pnpm check
pnpm build
```

Тесты изменяют только fixture-записи в специально созданной базе. Не использовать
рабочую копию пользователей или финансовые данные под этим именем.
