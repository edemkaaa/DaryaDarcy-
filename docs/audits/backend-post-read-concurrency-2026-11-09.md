# Чтение постов при параллельном редактировании — 9 ноября 2026

## Результат

Найдены два разных случая. Смешивание версий карточки и вложений исправлено
локально без изменения API. Повторы и пропуски между страницами остаются
ограничением числового offset-контракта и требуют совместного перехода фронта
и бэка. Общий аудит не завершён.

## Исправлено: разные версии внутри одного ответа

В `post-catalog-repository` и `post-detail-repository` карточка читалась
одним SELECT, вложения — следующим. Между ними редактор мог атомарно сменить
текст, доступ и вложения. В результате ответ содержал старый открытый пост
и новые данные его клубного вложения.

Шесть проверок через настоящий HTTP/JWT/MySQL воспроизвели этот результат:
`feed.list`, `feed.listPaginated`, `feed.getById`, `feed.savedPosts`,
`club.list`, `club.listByCategory`. Пауза вводилась перед чтением вложений;
изменение поста и медиа выполнялось другой SQL-транзакцией. Использованы
только синтетические URL, реальные файлы не запрашивались. Подтверждена
выдача новых URL/метаданных, а не обход защиты скачивания частных S3-объектов.

Оба чтения теперь выполняются в одной короткой транзакции `REPEATABLE READ`,
`READ ONLY`, по существующему образцу `getAdminPostDetail`. Внутри неё нет
внешних вызовов или блокирующих чтений `FOR UPDATE`. После фиксации правки
новый запрос уже видит новую версию и её правила доступа. Операция чтения,
начавшаяся раньше, может вернуть прежнюю согласованную версию; это не
обещание мгновенно отозвать уже переданные пользователю данные.

Порядок, фильтры, поля и числовой `nextCursor` не менялись. Миграции не нужны.
На время двух чтений удерживается одно соединение пула; добавлены команды
начала/окончания транзакции. Нагрузочное испытание рабочего сервера не проводилось.
Старый `feed.savedPosts` тоже использует защищённое чтение карточек по ID;
пагинированное «Сохранённое» продолжает работать внутри своей транзакции.

## Открыто: смещение между страницами

Настоящий HTTP подтвердил одинаковое поведение в `feed.listPaginated`,
`club.list`, `club.listByCategory` при размере страницы 2:

1. Исходный порядок A, B, C, D; первая страница возвращает A, B и cursor=2.
2. Добавляется новая публикация перед A. Запрос с cursor=2 возвращает B, C:
   B повторяется.
3. Если вместо этого убрать A из исходной выдачи, cursor=2 возвращает D:
   C пропускается.

Сортировка с уникальным ID делает порядок однозначным, но не предотвращает
смещение. Транзакция отдельного HTTP-запроса не закрепляет набор между
страницами. Удаление дублей на фронте не восстанавливает пропущенные карточки.

Минимальный следующий контракт: отдельный непрозрачный курсор по последнему
ключу сортировки, привязанный к фильтрам; старые числовые вызовы сохраняются
на переходный период. Для Клуба ключ состоит из даты публикации (или создания)
и ID, для Ленты включает её существующий `sortOrder`. Редактирование самих
ключей сортировки всё равно требует обновления списка; неизменный снимок
всего каталога здесь не обещается. Фронту понадобятся новая цепочка страниц
и сброс старого кэша. Переход не реализован молча в совместимом API.

## Проверки

- До исправления: все 6 новых сценариев смешивания версий упали по ожидаемым
  новым URL/именам вместо старых.
- После исправления: 109 SQL-тестов в 6 постоянных наборах прошли. Проверены
  чтение контента, фильтры Клуба, порядок, «Сохранённое», насыщение пула,
  отказы доступа и восстановление.
- Дополнительно 3 диагностических HTTP-сценария подтвердили ограничение offset.
  Их исходник и вывод сохранены вне Git; они не закрепляют ошибочное поведение
  в постоянном регрессионном наборе.
- 51 unit/HTTP-тест прошёл; типы, линтер, границы модулей (909 файлов),
  API-контракт (107 процедур) и сборка API прошли.

Доказательства вне Git:
`.local-artifacts/post-read-snapshot-20261109.am0a1y2a` рядом с репозиторием:
`sql-regressions-red.log`, `sql-regressions.log`, `sql-acceptance.log`,
`post-offset-probe.mysql.test.ts`, `sql-cleanup.json`.
Все тестовые контейнеры удалены, данные tmpfs уничтожены.

## Приоритеты остатка

- **P1, выпуск:** серверная конфигурация нескольких API, общий бюджет
  соединений, свежий staging, миграционная история и бэкап.
- **P2, код и интеграция:** новый контракт пагинации Ленты/Клуба.
- **P2, дальнейший аудит:** потеря lock-соединения при живом API и внешней
  операции; авария после внешней отправки до записи результата в БД.
- **Внешняя приёмка:** LIVE Prodamus, доменная почта, устройства и пилот
  остаются отдельными условиями выпуска, не закрыты этими тестами.

Фронт, рабочая БД, S3 и админские входы не менялись. Пуша и выкладки нет.
