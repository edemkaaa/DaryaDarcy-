## Откуда берутся30секунд

Проверено на действующем web Next16.3.8, image digest
`sha256:a2cb8dc8d95eef2ef5a5ab140493ed62631ad9740d916277228f4fccb3bdeadc`:

- next.config.mjs **и** .next/required-server-files.json содержат
  images.minimumCacheTTL=3600. NODE_ENV=production; отдельного standalone
  config override в окружении нет.
- Прямой HTTP к web, HTTP к внутреннему edge и публичный HTTPS для тех же
  двух ключей отдают max-age30. Значение появляется в web, не подменяется Nginx.
- В persistent image-cache найдено9файлов с TTL30,513сTTL3600 и37сTTL31536000.
  Все9старых записей — публичные фото поста744, width1440/q75/WebP,
  суммарно1 964 054байта. Другие размеры/материалы этим finding не охватываются.
- Ключи этих9файлов входят в адресно пересозданные43записи23октября.
  Сохранённый after-cache отчёт тогда показывает3600; сейчас в двух проверенных
  записях имя начинается с30, а SHA bytes совпадает с прежним производным WebP.
- Один активный web монтирует этот volume, созданный7октября. Перезапусков
  web с25октября21:08UTC нет. Причина исторического возврата9записей к30
  отдельно не установлена; восстановление backup или второй writer не доказаны.

Таким образом, это не проблема выбора локации VPS и не неприменённая настройка
3600. Непосредственный источник заголовка — TTL в производной записи кеша.

## Механизм в запущенной версии Next

Прочитан фактический next/dist/server/image-optimizer.js из web-образа:

1. ImageOptimizerCache.get читает maxAge из имени файла и возвращает
   cacheControl.revalidate=maxAge. Минимальный TTL влияет отдельно на серверное
   время revalidateAfter, но не заменяет это возвращаемое значение.
2. Если ETag оригинала не изменился, imageOptimizer переиспользует bytes превью
   вместе с previousCacheEntry.cacheControl.revalidate. Старое30 сохраняется,
   хотя новый вычисленный нижний предел равен3600.
3. Файловый set пишет полученный revalidate в имя файла, а expireAt считает
   через max(revalidate, minimumCacheTTL). Поэтому сервер может иметь HIT
   на час, одновременно отправляя браузеру max-age30.
4. setResponseHeaders передаёт этот maxAge в Cache-Control. Условный запрос
   браузера с прежним ETag получает304 без image body, но требует сетевой обмен.

На Mac в отдельном96МиБпроцессе воспроизведены3ветви двух извлечённых функций
из фактического runtime. Кодек заменён синтетическим, внешнего I/O нет:

| Предыдущее состояние | Config minimum | Возвращённый TTL |
| --- | ---: | ---: |
| Тот же ETag, запись30 | 3600 | 30 |
| Тот же ETag, запись3600 | 3600 | 3600 |
| Новый ETag, запись30 | 3600 | 3600 |

Все3assertions прошли. Это подтверждает ветвь выбора TTL, не заменяет полный
тест Next/Sharp и не доказывает исторический источник возврата старых метаданных.
SHA скопированного runtime source:
`38b92fde5bc72aa23c999d283052da11a6dfb36be75c2d92683d539551065a3c`.

## Узкий следующий шаг

Для отдельного согласованного исправления подготовить план ровно9подтверждённых
public cache keys: архив производных файлов и метаданных, сверка provenance,
согласованное обновление дискового и процессного состояния web. Простое повторение
удаления без проверки повторного использования старого состояния не считать
устойчивым исправлением. Не патчить node_modules на работающем стенде.

Приёмка: все9ответов сразу и после следующего срока обновления имеют TTL>=3600,
после согласованного restart/release значение не возвращается к30, ETag/bytes
превью и исходники сохранены, условные запросы304/0bytes, остальные550файлов
кеша не изменены. Закрытые файлы/БД/админские входы не затрагивать. Публичный
Cache-Control не выставлять глобально для API или произвольного /_next/image.

Для frontend отдельно проверить fallback и загрузку размеров постеров при
искусственном отказе превью. По текущим данным нельзя считать их причиной
конкретного пользовательского VPN-сбоя. Заголовок3600 сокращает перепроверки,
но не гарантирует доступ по недоступному VPN-маршруту.

Никаких удалений/переименований кеша, изменений source/config, перезапусков,
SQL, S3 PUT/DELETE, push/deploy в этом исследовании не выполнялось.

`.local-artifacts/photo-cache-investigation-20261026.np9ik3s0` — SSH inspection,

## Согласованное исправление и первичная проверка

После исследования владелец разрешил адресное исправление. 26 октября
в **11:55:56 UTC (14:55:56 МСК)** изменены только префиксы TTL в именах
9 файлов: `30` → `3600`. Срок expiry, ETag превью и оригинала, WebP bytes,
inode и mtime сохранены. Повторное сжатие или загрузка оригиналов не нужны.

Перед записью остановлен единственный writer — web. Проверка и переименование
выполнены отдельным helper-контейнером на том же уже установленном образе:
192 МиБ, heap64 МиБ, CPU0.25, без сети, root filesystem read-only,
единственный writable mount — image-cache. Helper удалён после выполнения.
Web запущен тем же контейнером, на прежнем образе, с прежними ресурсами,
окружением и IP. API/MySQL и остальные 23 работавших контейнера не изменились.
Хеши настроек до/после совпали. Поднятие лимитов на shared host не выполнялось.

Первая попытка была отклонена до переименования: предварительный HTTP GET
просроченной записи запустил штатную revalidation, изменив expiry в имени.
Web автоматически запущен обратно. Свежая копия повторно проверена: изменился
только expiry, bytes/ETag прежние. Второй запуск успешно исправил все 9 записей.
Этот наблюдаемый случай не доказывает причину исторического возврата TTL
после исправления 23 октября.

Проверки:

- 14 локальных guard/rollback checks: правильный scope, чужие/подписанные
  источники, path traversal, symlink, изменённые bytes, неизвестный ключ,
  другой размер, collision, сохранение inode и откат при искусственном отказе.
  Первые два новых теста выявили различие `/var` и `/private/var` в fixture
  macOS; исправлен canonical root теста, защитное условие не ослаблялось.
- Полная сверка 559 файлов до/после записи: отличаются только 9 префиксов
  имён; остальные **550 файлов неизменны**, суммарное число прежнее.
- Все **9 публичных HTTPS GET**: 200, `max-age=3600`, прежние SHA256,
  размеры и ETag. Все 9 условных GET: **304, 0 bytes**.
- Контрольный прямой web и edge: `HIT`, `max-age=3600`. После операции
  дисковые метаданные: 522 записи с TTL3600, 37 с TTL31536000, с TTL30 — 0.
- HEAD девяти исходных S3 URL: прежние ETag, Content-Length и Last-Modified.
  PUT/DELETE, SQL, изменение аккаунтов, frontend source и выкладка не выполнялись.
- `/api/health`, `/feed`, `/club`, `/videos`, `/library`, `/shop`: 200.
  Web healthy, без OOM. Первая проверка после рестарта пройдена;
  это не повторная проверка всего интерфейса или пользовательских входов.

Резервная копия 9 производных файлов сохранена в закрытых каталогах на сервере
и Mac, независимо сверена по SHA256. Архив актуального снимка:
`ea403ecc705a5b6ddede5cbfe660754b7102eb1f2a22799a5235d30f9026f9c7`.
Приватные operator/plan/backup и отчёты находятся вне Git:
`.local-artifacts/preview-ttl-repair-20261026.mj2d8no_`;
на сервере — `preview-ttl-repair-20261026.j5ex4ott` внутри каталога стенда.
При откате останавливать web и восстанавливать только эти 9 метаданных после
сверки актуальных SHA/ключей; не разворачивать архив поверх неизвестного кеша.

**Ожидается:** контроль после следующего часа. В текущем чате создана
одноразовая автоматизация `ttl`, следующий контроль примерно в **16:02 МСК**.
`verify-http.py hour` запрещает преждевременный запуск, проверяет все 9 GET,
условные 304 и оригиналы; дополнительно прочитать дисковые TTL и здоровье web.
Контроль ничего не ремонтирует и не перезапускает. Результат после часа
пока не получен; устойчивость после будущих выпусков также не объявляется
доказанной этой первой проверкой.
