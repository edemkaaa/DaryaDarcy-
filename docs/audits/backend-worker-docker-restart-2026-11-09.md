# Docker: восстановление Node и перезапуск фоновых задач

9 ноября 2026. Локальная проверка после a26e0bf9. Production-код и фронт не менялись.

## Результат

Два сценария настоящего Docker прошли за 105 секунд. Использованы настоящие
`createBackendApplication`, Nest HTTP, `WorkerJobs`, `IntervalJobs` и MySQL lock
с контролем потери владения. Прикладные эффекты заменены синтетической
транзакцией: письма, платежи, публикации, backup и S3 не вызываются.

| Проверка | Наблюдение |
| --- | --- |
| Потеря MySQL-соединения, владевшего lock | Docker event `die` содержит exitCode=1 |
| Автоматический перезапуск | `restart: unless-stopped`, RestartCount=1, новый boot и поколение 2; ручного restart нет |
| HTTP после рестарта | Настоящий `/api/trpc/auth.me` отвечает 200 |
| Lock свободен | Задача выполняется после старта нового процесса |
| Lock занят при старте | Первый запуск пропускается, HTTP доступен, записи нет |
| Освобождение занятого lock | Задача завершается на следующем настоящем 60-секундном тике |
| Сохранность результата | Первая транзакция откатилась; один commit принадлежит новому процессу, старый callback не завершился |
| Второй API | Отвечает по HTTP, поколение 1, RestartCount=0 |

Каждый контейнер до инъекции сбоя работает не менее 10 секунд. Проверяется
отсутствие OOM. Случайный внешний порт Docker заново читается после рестарта:
он может измениться; внутренний порт 3000 постоянен. Это не проверка edge routing.

## Что было с Docker

Старый локальный `node:22-bookworm-slim` не запускался до Node:
`failed to stat parent ... snapshots/2153/fs: no such file or directory`.
Повторный pull, затем адресное удаление и загрузка того же digest не помогли.
Во время следующей попытки Docker сообщил I/O error; в журнале VM подтверждены
ошибки записи EXT4 и режим read-only. На Mac оставалось около 150 МБ.
Причина исходного исчезновения слоя отдельно не доказана.

Удалены только 281 МиБ пересоздаваемого webpack-кэша этого проекта и 19
точно выбранных записей кэша наших backend-сборок (около 2,94 ГБ). Перед удалением
каждая запись проверена как reclaimable и non-shared; использован `buildx prune`
с точным `id`, без общей очистки. Источник — цепочка Dockerfile.backend с
production-dependencies и `index.mjs/prodamus-test.mjs`; журнал ID сохранён.
Docker пришлось перезапустить после зависания штатного завершения. Все ранее
существовавшие контейнеры уже были остановлены. Reset/data purge не выполнялись.

Повреждённая базовая версия заменена исправным официальным Linux ARM64 Node
**22.23.4**, digest:
`sha256:a09c611805f0d53d16ca876bd550ec9a4ae0bce65036d270659892d068f59a7c`.
Ей присвоен локальный tag `node:22-bookworm-slim`. Временный неудачный Alpine
образ удалён. Версии в Dockerfile/lockfile проекта не менялись.

## Как устроен повторяемый тест

`tests/worker-restart.mysql.test.ts` сохраняет прежний нативный режим по умолчанию.
Docker включается только явно, через `tests/helpers/worker-restart-docker.ts`:

- `BACKEND_TEST_DATABASE_URL`: одноразовая локальная `backend_test`;
- `WORKER_RESTART_DOCKER_IMAGE`: уже скачанный `node@sha256:…`, без pull;
- `WORKER_RESTART_MYSQL_CONTAINER`: полный ID новой MySQL с меткой
  `codex.owner=daryadarcy-fresh-backend-audit-…` и tmpfs `/var/lib/mysql`;
- `WORKER_RESTART_LINUX_MODULES`: отдельный каталог Linux-пакетов `@img`,
  совпадающих с установленным sharp и архитектурой Node.

Команда: `pnpm exec vitest run --project mysql tests/worker-restart.mysql.test.ts`.
Без image-переменной Docker не вызывается. Не указывать рабочую БД.

В этом прогоне: свежая MySQL 8.4, все 52 миграции, данные в tmpfs; Node ARM64
работает нативно в Linux VM Docker Desktop. Два API по 384 МиБ/1 CPU.
Helper собирается esbuild; зависимости проекта и отдельные Linux-модули Sharp
0.35.5/libvips 1.3.4 монтируются только для чтения. Корень проекта и .env
не передаются. Это настоящий API внутри Docker, **не финальный release image**.

Для каждой попытки создаются собственные контейнеры и сеть, затем удаляются
по метке владельца. Порты публикуются только на loopback. Тест не использует
внешние сервисы; общий доступ контейнеров к сети не является отдельным security gate.

Артефакты вне Git: `.local-artifacts/docker-node-repair-20261109.pjk_44ak`
рядом с репозиторием. Там сохранены миграции, SQL-прогон, сведения об очистке,
инвентарь образов/томов и локальный harness. Ошибки первых попыток тестового
адаптера сохранены отдельно; итоговый `sql-regressions.log` содержит 2/2 PASS.

## Итоговая проверка

- Docker SQL/HTTP: 2/2, 105 секунд.
- Повторный нативный прогон: 6/6 (рестарт и потеря lock), 75 секунд.
- Unit/HTTP/compiled: 50/50; TypeScript без ошибок.
- API-контракт: 107 процедур, изменений нет; документация: 189 документов.
- Все 12 имён существующих томов и оба прежних container ID сохранены.
  Все пять исходных не-Node образов сохранили ID. Тестовых сетей/контейнеров
  не осталось; одноразовые tmpfs-БД удалены. Это сверка инвентаря, не проверка
  содержимого существующих баз.
- Повторный запуск `node:22-bookworm-slim node --version`: v22.23.4.
  После адресной очистки на Mac осталось около 2 ГиБ свободного места.

## Оставшиеся условия

- **P1 перед выпуском:** итоговый серверный образ/Compose overrides, restart policy,
  health, edge routing и суммарный бюджет процессов/соединений. Локальный Docker
  restart закрыт; серверная приёмка остаётся открытой.
- **P2:** окно до обнаружения потери lock и уже принятые внешние отправки;
  один SQL commit не доказывает exactly-once для почты или провайдера.
- **P2:** дочерний mysqldump и уборка аварийных backup-файлов отдельно.

Базы, старые файлы, админские входы и образы отката намеренно не изменялись.
Проверка содержимого существующих томов не выполнялась. Пуша и выкладки нет.
