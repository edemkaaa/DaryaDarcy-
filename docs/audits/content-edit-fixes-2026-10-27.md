## Конфликтующие редакции

`admin.postDetail` и `admin.articleDetail` добавляют `editRevision`: непрозрачный
64-символьный отпечаток сохранённого состояния. Результат по отсутствующему ID
по-прежнему null. Публичные ответы и компактные списки не получают это поле.
В `admin.updatePost`/`admin.updateArticle` добавлен `expectedRevision`.

Отпечаток поста включает хранимые поля и вложения, включая posterUrl, порядок
и даты. Реакции и вычисляемые поля не входят. Статья использует исходные хранимые
блоки до нормализации публичного DTO. Сервер вычисляет версию; клиент её не
собирает из полей формы. Это отпечаток состояния, а не монотонный счётчик.

Новая колонка/миграция не нужна: изменение внутренним writer, переносом файлов
или синхронизацией анонса отражается в отпечатке автоматически. Не используется
один updatedAt: у старых строк есть секундная точность и операции, сохраняющие дату.
Одинаковое полностью восстановленное состояние может иметь прежний отпечаток.

Для поста административный detail читается в одной READ ONLY REPEATABLE READ
транзакции. При записи после проверки полномочий блокируется родитель, затем
вложения читаются FOR UPDATE. Это текущий снимок даже после более раннего
consistent read проверки загрузок. Сравнение выполняется до изменения текста,
даты, статуса, связей, вложений или уведомления. У статьи проверка под её row lock
предшествует изменению статьи, анонсов и привязок файлов. При несовпадении —
HTTP409/CONFLICT, без записи. Нельзя автоматически взять свежую версию и повторить
старую форму: это снова разрешило бы перезапись чужого текста.

## Переход старого клиента

Схема расширена совместимо: expectedRevision пока optional на wire.
**Если версия передана, она проверяется всегда**, включая режим совместимости.

| CONTENT_EDIT_REVISIONS_REQUIRED | Поведение client update |
| --- | --- |
| отсутствует / false | Старый вызов без версии сохраняет прежнее поведение; риск старого клиента остаётся |
| true | Нет версии →412/PRECONDITION_FAILED; неверная версия →409; актуальная →обычная запись |
| другое значение | 503, без записи; опечатка настройки не отключает защиту молча |

**BE-01 нельзя считать закрытым на стенде/для старых клиентов до обновления всех
редакторов и включения true.** В этой работе реальная настройка не менялась.
Фронтендер сначала подключает контракт и сохраняет ввод при конфликте; после
отдельной приёмки включается строгий режим. Пример настройки добавлен только
в `.env.example`, не в действующие env.

Текущие серверные команды подтверждения публикации/удаления вложения не передают
устаревшую форму и продолжают работать. Для внутренних current-state команд
precondition не нужен. HTTP update всегда передаёт объект precondition на
транзакционный уровень, даже если клиент не прислал поле; через wire выбрать
внутренний обход нельзя. Успешные ответы mutations сохранены:
`{success:true}` для поста, `{ok:true}` для статьи. После сохранения клиент должен
перечитать detail перед следующей записью. Потерянный ответ сверяется чтением;
409 на повторе сам по себе не доказывает, что предыдущая попытка не записалась.
Новая идемпотентная схема обновлений этим шагом не вводилась.

## Ограничение текста

Существующая `posts.text TEXT` сохраняется. Лимит — **65535 байт UTF-8**,
проверяемый входными схемами создания/обновления и сервисом после санитаризации
до вызова persistence. Превышение возвращает400/BAD_REQUEST с пояснением,
не SQL500 и не молчаливое обрезание.

ASCII65535, кириллица32767+один ASCII и emoji16383+три ASCII проходят точно
по границе; ASCII65536, кириллица40000/80000байт и emoji16384 отклоняются.
Это не лимит65535символов. Поле richText, JSON-блоки статей и существующий общий
лимит тела запроса не подменяются этим правилом. Клиенту нужен TextEncoder для
payload.text, а не String.length. Пустой update text/отсутствующее поле сохраняют
существующую политику обязательного содержимого поста.
