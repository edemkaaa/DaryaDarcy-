## P1. TEST-оплата мешает отменить действующую подписку

### Причина и область действия

В [cancellation-evidence.ts](../../apps/backend/src/billing/cancellation-evidence.ts#L22) месячные платежи выбираются по `LIKE 'club-%'`. Туда же попадают разовые заказы `club-test-*`, созданные [ProdamusTestClubService](../../apps/backend/src/billing/prodamus-test-club.service.ts#L103). Этот TEST-платёж ограничен одной оплатой и создаётся без профиля автосписания. Проверка требует сопоставить каждый такой платёж с профилем и считает его неподтверждённой месячной подпиской.

В [requestClubCancellation](../../apps/backend/src/billing/cancellation.ts#L154) этого достаточно для `CancellationUnavailableError` ещё до постановки отмены в очередь. При переходе существующего тестового аккаунта на LIVE его корректно привязанная подписка становится недоступна для отмены через приложение. Условие воспроизведения включает сохранённый оплаченный TEST-заказ и следующий настоящий месячный заказ с профилем. Это риск повторных списаний после обращения пользователя за отменой.

У `hasUnboundMonthlyPayment` три места вызова в `cancellation.ts`. Они влияют на принятие отмены и отображение подтверждённого статуса. Функция вынесена в новый локальный модуль. В базе `HEAD` аналогичная выборка по префиксу находилась внутри `requestClubCancellation`, поэтому часть логики унаследована.

### Воспроизведение

1. На одноразовой БД создать одного синтетического пользователя.
2. Провести `settleClubOrder` для разового RUB TEST-заказа без профиля. Получено `true`.
3. Провести `settleClubOrder` для следующего месячного заказа с доменом, subscription ID и profile ID. Получено `true`.
4. Запросить отмену. Получен `CancellationUnavailableError`, функция отправки провайдеру вызвана **0 раз**.
5. Только на тестовой БД исключить первую TEST-запись из истории платежей и повторить отмену. Получено `confirmed=true`, функция отправки вызвана **1 раз**.

### Минимальное исправление

Различать подтверждённые разовые TEST-оплаты и месячные подписки при проверке финансовых свидетельств. Сохранить отказ для действительно неподтверждённой месячной подписки. Основанием различения должны быть происхождение заказа и сохранённые свидетельства оплаты. Добавить регрессию для последовательности TEST, LIVE, отмена и повторное чтение статуса. Историю оплат пользователя сохранять.

## P2. Допустимое имя приводит к ложному успешному входу

### Причина и область действия

[SessionService.issueSession](../../apps/backend/src/identity/session.service.ts#L104) помещает полное имя в JWT. [SDKServer.signSession](../../apps/backend/src/_core/sdk.ts#L170) подписывает его без ограничения размера, после чего токен записывается в cookie. Регистрация ограничивает весь JSON размером 16 КиБ, но имя внутри этого размера принимается. [Валидация профиля](../../apps/backend/src/profile/profile-input.ts#L11) также допускает имя до 65 535 байт.

Такое имя помещается в MySQL, однако раздувает сессионную cookie. В проверенном Chromium браузер отказывается сохранить эту cookie. Сервер при этом возвращает входу HTTP 200. Следующий запрос профиля подтверждает гостевое состояние. После изменения профиля с уже действующей сессией проблема может проявиться при следующем входе.

Контроллер использует `issueSession` в двух местах, для пароля и SMS. Сценарий подтверждён через пароль. По `git blame` передача имени присутствует с `35a1b061c`, подписание имени в SDK унаследовано из ранней базы `b06a46a2`. Это существующая ошибка, обнаруженная при проверке соседнего кода авторизации.

### Воспроизведение

1. Зарегистрировать синтетический email с именем из 2048 кириллических букв, всего **4096 байт UTF-8**. Получен HTTP **202**. Схема обновления профиля также принимает это имя.
2. Подготовить пароль только для этого пользователя в одноразовой БД и выполнить настоящий HTTP-вход в Chromium.
3. Вход возвращает **200**, сохранённых сессионных cookie **0**, `/api/auth/me` возвращает гостя.
4. Изменить только имя того же синтетического пользователя на короткое и повторить вход. Получен **200**, сессионная cookie **1**, профиль подтверждает вход.

Для выполнения диагностического запроса со страницы API использован отдельный браузерный контекст с `bypassCSP`. Это касается только локальной проверочной страницы. Серверная политика CSP и правила обработки cookie оставались прежними.

### Минимальное исправление

Сделать выдаваемый JWT компактным и независимым от отображаемого имени. Имя для интерфейса уже возвращается в профиле после чтения пользователя из БД. При изменении выдачи сохранить проверку старых токенов. Добавить браузерную регрессию, проверяющую фактическое сохранение cookie и следующий `/api/auth/me`, включая существующий аккаунт с длинным именем.
