# HTTP при перегрузке БД — 6 ноября 2026

Локальный срез после `79f86461`. Применены systematic-debugging,
test-driven-development, code-review и verification-before-completion.
Фронт, рабочая БД, S3, платежи и почта не менялись; пуша и выкладки нет.

## Что обнаружено

Настоящий пул приложения занят десятью соединениями и десятью ожиданиями.
Следующие HTTP-запросы получают отказ драйвера. Проверка использует реальную
одноразовую MySQL, Nest, tRPC и JWT; SQL-ошибки не подменяются.

| Сценарий | До правки | После правки и восстановления |
| --- | --- | --- |
| REST `/api/auth/me` с действующей сессией | 503, cookie сохраняется | Прежнее корректное поведение; тот же токен снова открывает профиль |
| tRPC `auth.me` | 500 вместо временной недоступности | 503 / `SERVICE_UNAVAILABLE`, без `user:null` и без удаления cookie |
| REST login, локальные лимиты | 500 | 503 без cookie; после освобождения БД вход с прежним паролем работает |
| REST login, общие MySQL-лимиты | Внутренний 503 терялся в catch и становился 500 | 503 без обхода общего ограничения попыток |
| Публичный `feed.listPaginated` | 500 | 503; после восстановления возвращается существующий пост, а не пустой успешный ответ |
| `admin.createPost` после авторизации | 500 при входе в транзакцию | 503, нет частичного поста и записи журнала; повтор прежнего намерения создаёт один черновик |

Ложного гостя, успешного пустого списка или успешной записи до исправления
не обнаружено. Подтверждённый дефект — потеря статуса временной недоступности.
В сценарии записи тест останавливает сервис после настоящей авторизации,
заполняет пул, затем запускает исходный метод сервиса. Проверяются обе таблицы,
повтор с тем же ключом и сохранность существующего поста.

## Минимальное исправление

- Общий обработчик распознаёт только `ServiceUnavailableException` и точную
  ошибку переполнения очереди mysql2, в том числе внутри `cause` Drizzle/tRPC.
  Драйвер не предоставляет отдельный код для этой ошибки; поведение закреплено
  тестом с настоящим пулом. При обновлении mysql2 этот тест обязателен.
- tRPC переводит такой внутренний сбой в безопасный 503 как при создании
  контекста, так и внутри процедуры. Ответ не содержит SQL, stack или исходное
  сообщение исключения. Обход цепочки причин ограничен.
- REST login сохраняет тот же смысл ошибки. Успешные ответы и DTO не менялись.
- Явные 400/401/403/404/409/429 остаются прежними. Неизвестные ошибки и SQL lock
  timeout автоматически не объявляются безопасными для повтора; остаются 500.

## Проверки

Сначала новые ожидания воспроизвели дефект: 5 SQL/HTTP-сценариев получили 500
вместо 503; ещё 11 модульных/HTTP-проверок подтвердили потерю статуса в адаптерах.
После правок прошли:

- 111 SQL-тестов: насыщение, восстановление, сессии, чтение контента и
  координация двух процессов;
- 132 модульных/HTTP-теста: ошибки сессий, вход, logout, права, сохранение
  клиентского состояния и неизменность остальных кодов ошибок;
- типы, линтер backend, API-контракт (107 процедур), сборка API и границы модулей.

Локальные логи: `.local-artifacts/api-pool-pressure-20261106.iy5he_n0`
рядом с репозиторием. Тестовая БД получила все 52 миграции; контейнер с tmpfs
удалён. Docker пришлось перезапустить после зависания. Образы, постоянные
volumes и файлы других проектов не удалялись.

## Границы и следующий шаг

Это проверка отказов API, а не замер допустимого числа пользователей. Браузерное
поведение и реальный сервер в этом проходе не проверялись. 503 сам по себе не
доказывает, что любая операция не была выполнена: для операций записи сохраняется
прежний ключ и восстановление результата, автоматического повтора записей нет.
Обычные запросы, уже попавшие в ограниченную очередь пула, не получили нового
общего таймаута; отдельно отменять SQL этим изменением не начинали.

Аудит открыт. P1 перед выпуском нескольких API: серверный бюджет соединений и
памяти, конфигурация общей координации. P2: дальнейшая проверка завершения одного
процесса во время работы и конкурентной пагинации, ограничения внешней отправки.
P3: необязательная очистка совместимых helpers. Рабочие данные и архитектуру
не менять ради формального закрытия этих пунктов.
