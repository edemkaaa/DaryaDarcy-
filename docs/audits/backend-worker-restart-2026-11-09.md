# Восстановление API и задачи после потери блокировки

9 ноября 2026. Проверка локального кода после `39529641`.
Production-код не менялся: новых ошибок в проверенных сценариях не выявлено.
Добавлены два постоянных SQL/HTTP/OS-теста и изолированный helper.

## Что именно проверено

Настоящие `createBackendApplication`, Nest HTTP, `WorkerJobs`, `IntervalJobs`,
MySQL-координация и контроль потери lock. Два отдельных Node-процесса и
одноразовая MySQL 8.4 с полной цепочкой 52 миграций. Перезапуск выполняет
**тестовый контроллер процессов**, автоматически после `exit(1)`.

Внешние задачи заменены синтетической транзакцией в отдельной таблице.
Первая версия API начинает изменение и удерживается до аварии. Новая версия
процесса автоматически запускает тот же планировщик; задача дописывает
результат после повторного получения права на работу. Реальные публикации,
письма, платежи, backup и S3 не вызываются.

| Сценарий | Результат |
| --- | --- |
| Потеря lock при незавершённой транзакции | Первый API выходит с кодом 1; контроллер запускает новый процесс |
| Повторный старт со свободной блокировкой | Новый процесс отвечает по HTTP и автоматически завершает задачу |
| При старте lock занят другой тестовой MySQL-сессией | Задача пропускает запуск; HTTP работает; параллельной записи нет |
| Lock освобождён после пропущенного запуска | Задача выполняется на настоящем следующем 60-секундном тике, без изменения часов и ручного вызова |
| Сохранность результата | Незавершённая транзакция первого процесса откатывается; один результат принадлежит новой версии процесса |
| Второй API | Отвечает по HTTP и не перезапускается |

Проверяется новый случайный идентификатор запуска и поколение процесса,
один аварийный выход, один автоматический перезапуск и отсутствие результата
старого callback. SQL-таблицы не содержат данных пользователей.

Тесты: `tests/worker-restart.mysql.test.ts`, helper
`tests/helpers/worker-restart-process.ts`. Логи вне Git:
`.local-artifacts/worker-restart-20261109.jfag9xnb` рядом с репозиторием.

Финальный прогон: 6 SQL-тестов (2 новых + 4 проверки потери lock),
50 unit/HTTP/compiled-проверок, TypeScript без ошибок, неизменный API-контракт
(107 процедур), проверка документации (188 документов).
Отрицательный контроль временно отключал `jobs.start()` во втором запуске
тестового процесса: HTTP восстанавливался, но тест падал на отсутствии
результата задачи. Helper восстановлен в `finally`; итоговый прогон прошёл
после восстановления. Production-код при этом не редактировался.

Созданные SQL-таблицы, процессы и контейнер с одноразовой БД удалены.
Сборка production-образа в этом срезе не выполнялась.

## Почему Docker остаётся отдельной проверкой

Сначала подготовлен запуск двух тестовых API под настоящей Docker restart
policy. Уже имеющийся `node:22-bookworm-slim` не запустился: Docker сообщил
`failed to stat parent ... snapshots/2153/fs: no such file or directory`.
Это произошло до запуска Node. Образы не удалялись и не скачивались;
рабочие контейнеры не изменялись. Созданные этим прогоном ресурсы удалены
по точной метке владельца. Неисполненный Docker-вариант не оставлен в CI.

Следовательно, результат подтверждает восстановление приложения после
перезапуска OS-процесса, **но не подтверждает Docker restart policy, готовый
Linux-образ или итоговый серверный stack**. Постоянные тесты запускают
нативный Node и настоящую фабрику приложения, без Linux-сборки и новых образов.

## Оставшиеся условия

- **P1 перед выпуском:** на исправном локальном Docker/runner или серверном
  кандидате проверить restart policy, health, маршрутизацию на живую реплику
  и общий бюджет ресурсов. Рабочий сервер в этом срезе не использовался.
- **P2:** гарантия отсутствия дубля подтверждена для синтетической SQL-задачи.
  Принятое внешним сервисом письмо/запрос не откатывается с процессом;
  окно до обнаружения потери lock остаётся.
- **P2:** дочерний `mysqldump` и уборка аварийных backup-файлов здесь не
  проверены. Их нельзя считать закрытыми на основании восстановления scheduler.
- При занятом lock обработка продолжается на следующем штатном интервале;
  мгновенный повтор и отдельная очередь не добавлялись.

Фронт, рабочая БД, S3, существующий контент и админские входы не менялись.
Пуша и выкладки нет. Общий аудит остаётся открытым.
