# Pen Pals: заявки, отзыв сессии и выдача адреса

4 ноября 2026. Исходный source 9ed803fd, ветка
feature/stage-one-completion-2026-10-10. Следующий локальный срез после
[анкет и согласия](pen-pal-profile-lifecycle-review-2026-11-04.md).
Использованы security-and-hardening, test-driven-development, code-review и
verification-before-completion. Frontend, рабочие данные, S3 и сервер не менялись;
push/deploy и включение Pen Pals не выполнялись.

## Подтверждено до исправления

**P2: устаревший actor.** requestMatch/respondMatch принимали числовой userId.
Проверка участников и активных анкет уже существовала, но identity/sessionVersion
запроса повторно не проверялись. Отказ от заявки вообще не блокировал users-строку.
me/find также использовали ID без проверки актуального actor при чтении.

Реальный router с настоящим ранее прочитанным User продолжал операции после
отзыва epoch, замены openId или блокировки. Для request/accept реальный HTTP/JWT
запрос дожидался SQL-lock, после отзыва сессии возвращал 200. Decline/me/find
не ждали owner-lock. Это гонка ранее авторизованного запроса, а не доказанный
обход свежей отозванной cookie. Первый прогон: 21 ожидаемое падение и 4 контроля.

**P2: скрытый отказ записи.** find перехватывал любую ошибку insert в pen_pal_shown
как duplicate. Настоящий SQL trigger отказывал во вставке, однако HTTP возвращал
200 с карточками. Ошибка инфраструктуры выдавалась за успешный поиск.

**P2: устаревшие данные собеседницы.** Дополнительный опыт остановил реальный SQL
после чтения users-строки собеседницы. После её блокировки чтение из ранее
полученных данных ещё возвращало карточку/адрес. Этот промежуточный вариант
зафиксирован в address-red.log; затем данные участницы и связь объединены в один
актуальный SQL-запрос вместо отдельных проверок и выдачи старого профиля.

## Исправлено локально

- Общий guard id/openId/sessionVersion/blockedAt используется анкетами, заявками
  и собственными чтениями. Он выполняется под users row-lock в той же транзакции.
- Request/accept сохраняют порядок блокировок low/high. Отказ проверяет владельца
  заявки и актуальную сессию, но не требует активной анкеты или доступности
  собеседницы. Внешняя заявка остаётся 404; просроченное подтверждение — 409.
- me и find проверяют actor непосредственно в транзакции. Отзыв сессии/identity —
  401, блокировка самого пользователя — 403. Отсутствие БД не превращается в
  успешный пустой поиск.
- find использует READ COMMITTED: завершившийся withdrawal собеседницы виден
  после первоначального чтения. Перед выдачей адреса один SELECT объединяет
  актуальную связь, активную анкету и неблокированный аккаунт. Адрес выдаётся
  только при взаимном подтверждении. Отдельные устаревающие чтения удалены.
- Очистка истёкших связей внутри find ограничена текущим участником.
- Повторная запись показанной анкеты разрешена через duplicate-key update;
  прочие SQL-ошибки проходят в обычный безопасный 500 и откатывают транзакцию.

Новых таблиц, миграций, процедур, клиентских полей или бизнес-функций нет.
Публичные DTO прежние: me — профиль/null; find — needsProfile/matches;
requestMatch — matchId; respondMatch — ok. check:api подтверждает прежний контракт.

## Проверки

- 27 новых SQL-сценариев: 15 captured-actor отказов; 5 настоящих HTTP/JWT
  запросов с ожиданием блокировки и отзывом epoch; взаимная/невзаимная выдача;
  завершённый withdrawal; 3 управляемые гонки чтения/withdrawal/блокировки;
  реальный отказ записи shown без ложного успеха.
- **140/140 SQL** в семи файлах: новые случаи, прежние анкеты/заявки,
  account retention с включёнными native-worker сценариями, запрос удаления,
  security regressions и Nest profile.
- **127/127 HTTP/unit** в пяти файлах: match access, feature capabilities,
  profile, session revocation/availability. SQL double обновлён под четыре
  поля actor; чужие заявки, сроки и ownership-предикаты не ослаблены.
- Root/frontend types, backend lint, check:api (107 процедур, 46501 bytes),
  boundaries (907 файлов), API/TEST сборки и git diff --check проходят.

Все SQL-операции выполнялись на отдельной tmpfs MySQL 8.4 после 51 миграции.
Проверки ожидания используют performance_schema; в гонках чтения приостанавливается
настоящий SQL-ответ, данные не подменяются. Тестовые БД удалены, чужой контейнер
не изменён. Приватные артефакты вне Git:
../.local-artifacts/pen-pal-access-20261104 (red.log, address-red.log, green.log,
unit.log, migration/build/type/lint/contract/boundaries logs и sql-cleanup.json).

## Оставшееся, по приоритетам

- **P1 выпуска:** итоговые runtime images из нового source, AMD64-приёмка,
  свежий staging и серверный preflight. ARM64 2adb313e этих последующих guards
  не содержит; на Mac около 0,65 ГиБ свободно, полную Docker-сборку не запускали.
- **P2 следующий срез:** maintenance-переходы Pen Pals, особенно удаление старой
  неактивной анкеты одновременно с новым upsert. Прежние retention-тесты проходят,
  но эта конкретная гонка ими не подтверждена и ещё не объявляется уязвимостью.
- **P2 архитектура/масштабирование:** подбор всё ещё читает список активных анкет
  и выполняет запрос на каждую существующую связь. Нужны отдельные замеры перед
  изменением алгоритма; этот срез не добавляет пагинацию/очередь/новый сервис.
- Ограничения действующего контракта форм и best-effort уведомлений прежние.
  Нельзя отозвать адрес, уже полученный клиентом; текущая гарантия действует
  на актуальный SQL-read, авторизующий новый ответ, а не на стирание старого.

Выбранный срез закрыт локально; весь Pen Pals, архитектурный аудит и приёмка
рабочей среды остаются открытыми. Функцию на стенде не включать этим изменением.
