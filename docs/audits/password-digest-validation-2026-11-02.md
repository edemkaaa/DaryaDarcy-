# Проверка длины сохранённого хеша пароля

2 ноября 2026. База `662aa0ba`. Исправление локальное.

## Подтверждённая ошибка

`verifyPassword` выбирал длину вычисляемого scrypt-результата из сохранённого digest.
При пустом digest сравнивались два пустых Buffer: на синтетическом хеше проверка
возвращала true даже для неправильного пароля. При усечённом digest сравнивался
только префикс: регрессии для 1 и 31 байта тоже воспроизвели принятие повреждённого
хеша с правильным паролем, вместо отказа из-за повреждённого формата.

Это дефект проверки сохранённой записи. Для его использования нужна повреждённая
или изменённая запись passwordHash. Не установлено, что обычный пользователь может
создать такую запись через API; рабочая БД на наличие повреждённых хешей не проверялась.
Обход входа для штатных аккаунтов этим исследованием не доказан.

## Исправление

В `apps/backend/src/_core/password.ts` digest должен иметь KEYLEN=32 байта, как
выдаёт существующий `hashPassword`. Остальные длины дают false до вычисления scrypt.
Сам scrypt теперь явно вычисляет KEYLEN. Параметры генерации, соль, формат хранения,
обычный вход, cookie и публичные ответы API не менялись. Перехеширования, миграции
и изменения существующих аккаунтов нет. Повреждённую запись нельзя принимать
через fallback; для такого аккаунта требуется нормальное восстановление пароля.

Это узкое исправление длины digest, не новый алгоритм хеширования и не полная
валидация всех параметров произвольных импортированных scrypt-строк.

## Проверки

- До исправления новая регрессия: 3 fail / 3 pass. Отказы на длинах 0, 1, 31
  показали прежнее принятие; длина 33 уже отвергалась несовпадением.
- После: 62/62 целевых теста в 7 файлах прошли. Включены обычные пароли,
  ограничения входа, сессии, отзыв и доступность проверки сессии.

  проверены повреждённые digest 0/1/31: HTTP401, обычное сообщение неверного
  пароля, без cookie и без updateUser. Только чтение/запись persistence-сервиса
  подменены синтетическими данными; рабочая БД не используется.
- Положительный HTTP-контроль: штатный новый хеш принимает правильный пароль,
  выдаёт cookie, обновляет активность; JSON по-прежнему без sessionToken.
