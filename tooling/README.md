# Инструменты репозитория

Команды запускаются из корня. Перед ручным запуском читайте сценарий: наличие файла не означает, что он безопасен для рабочей базы или сервера.

## Как читать инструменты

Пояснение в начале исходника описывает его назначение и область действия, а не
разрешение на запуск. Важные ограничения оставлены рядом с проверкой назначения,
переносом данных и очисткой собственных ресурсов. Комментарии не меняют режимы
записи и не превращают старый оператор в безопасную автоматизацию.

- `scripts/*policy*` вычисляют правила и отчёты; соседние CLI выбирают входы,
  соединения и режим применения. Проверка плана отделена от записи.
- `scripts/*candidate*`, `*fresh-database*` и SQL-test setup работают с разными
  явно проверяемыми профилями. Их подключения нельзя взаимозаменять только
  потому, что все используют MySQL.
- `lib/media-reference-map.ts` строит карту использования объектов из снимков;
  `scripts/media-reference-map.ts` предоставляет stdin-вход без SQL и S3.
- `data/` и `operations/` содержат как чтение, так и внешние изменения. Например,
  `list-shop-s3.mjs --acl` открывает объекты, а `delete-test-posts.ts` использует
  старую эвристику, которая способна захватить ручные публикации.
- `assets/` различает lossless-перепаковку, уменьшенные варианты и прежние
  перекодировщики с потерями. Название «оптимизация» само не гарантирует
  сохранения пикселей.

JSON-снимки аудитов, списки URL, SQL-история и двоичные материалы не дополнены
встроенными комментариями: это данные с собственным форматом. Старые инструменты
в `legacy/` остаются историческими; их присутствие не подтверждает пригодность
для нового сервера. Описание файлов и ревью поведения — разные проверки.

## Ежедневные проверки

- pnpm check:docs — ссылки текущей документации на файлы и каталоги репозитория.
- pnpm docs:files / pnpm check:files — обновление и проверка [справочника файлов и блоков](../docs/development/file-guide/index.md). Генератор читает исходники как текст и не запускает операторские инструменты.
- pnpm check:boundaries — границы зависимостей приложений и общих модулей.
- pnpm check — TypeScript.
- pnpm test — тесты; для полной проверки нужна отдельная MySQL, см. [рабочий процесс](../docs/development/workflow.md).

[smoke-image-previews.mjs](operations/smoke-image-previews.mjs) проверяет холодный
альбом из девяти публичных фото, WebP, тёплый кеш и отказ приватных источников.
Запускать отдельным клиентом против временного web-контейнера, не внутри его
лимита памяти. `PREVIEW_SMOKE_URL` допускает только localhost или наш временный
Docker preflight; нагрузка на публичный сайт и другие проекты запрещена.
Пик памяти и `oom_kill` дополнительно проверять у web через cgroup/Docker.

## Где что лежит

| Каталог                     | Назначение                                                                   |
| --------------------------- | ---------------------------------------------------------------------------- |
| [scripts/](scripts/)        | Сборка, проверки, загрузчик окружения, QR и проверка истории миграций        |
| [assets/](assets/)          | Подготовка шрифтов/изображений; некоторые сценарии скачивают внешние ресурсы |
| [data/](data/)              | Импорты, сверки и преобразование данных; могут менять БД или S3              |
| [operations/](operations/)  | Деплой, резервирование, диагностика и обслуживание внешних систем            |
| [legacy/](legacy/README.md) | Прежние миграторы и операционные помощники, сохранённые для деплоя и данных |

Имена pnpm-команд сохранены, пути внутри package.json обновлены. Каталоги инструментов оставлены на одинаковой глубине, чтобы не менять определение корня проекта.

Деплойные сценарии пока содержат прежние предположения об окружении и Windows-пути; перенос не делает их универсальными или готовыми к запуску с любого компьютера. Нужны отдельная проверка и согласование. Некоторые операции вызывают сохранённые legacy-помощники.

pnpm qr сохраняет результат в игнорируемый tmp/expo-qr-code.png. pnpm smoke обращается к внешнему сайту; это не локальный тест. Старый генератор PDF-аудита и его команда удалены; сами отчёты сохранены как результаты прежних проверок.

Результаты сборки, временные диагностики и новые отчёты S3 не коммитятся. Исторические отчёты хранятся в [архиве аудита](../docs/audits/archive/deployment-snapshots/), а политика lifecycle остаётся в [infrastructure/deploy](../infrastructure/deploy/). Перед запуском S3-сценариев требуется проверка путей, описанная в [заметках резервирования](../docs/operations/s3-backup.md).

## Проверка документации

check:docs проверяет Markdown-ссылки и изображения, определения ссылок, пути с пробелами и каталогами маршрутов Expo. Внешние URL не открываются, заголовки после # не проверяются; примеры внутри блоков кода игнорируются.

Проверяются актуальные документы docs/, README приложений и пакетов, навигация tooling/ и рабочие tasks/. Исторические документы docs/archive/ исключены, кроме его README. Проверка работает по Git-инвентарю, а не по node_modules и результатам сборки.

Новые локальные ссылки пишите относительно документа, пути с пробелами заключайте в угловые скобки. Переносите файл вместе с обновлением входящих ссылок.

## Первичное наполнение тестового стенда

[import-public-staging.mjs](data/import-public-staging.mjs) переносит только
анонимно доступные посты, категории и каталог YouTube из исходного сайта.
Не выгружает пользователей, оплаты, закрытый клуб, реакции или комментарии.
Фото остаются ссылками на существующий S3; видеофайлы не скачиваются.

```sh
node tooling/data/import-public-staging.mjs --export /protected/path/public.json
node tooling/data/import-public-staging.mjs --validate /protected/path/public.json
```

Экспорт создаёт новый файл с правами 600 и не перезаписывает существующий.
Хранить snapshot вне репозитория. Скрипт не загружает `.env` автоматически.
Проверка источника отклоняет скрытые/закрытые посты, прикреплённые media,
неизвестные категории, дубликаты ID, сторонние URL и неподдерживаемые форматы.

Перед записью сделать защищённую полную копию **тестовой** БД и проверить её
целостность. Запускать скрипт внутри API-контейнера стенда, где уже установлены
зависимости и настроено его окружение. `--dry-run snapshot.json` проверяет
назначение и пустоту таблиц, но ничего не записывает; это режим по умолчанию.
Только `--apply snapshot.json` разрешает запись. Назначение жёстко ограничено
`mysql/daryadarcy_staging` и `https://daryadarcy.dev.reeskeen.ru`.

Все три таблицы должны быть пустыми и InnoDB. Импорт сохраняет исходные ID,
порядок и даты UTC, использует одну транзакцию и блокировку между импортёрами.
Повторный запуск отказывается от записи, а не обновляет существующий контент.
Не обходить проверку пустоты через DELETE/TRUNCATE: для синхронизации нужна
отдельная согласованная процедура. После операции проверить содержимое всех
трёх таблиц, API и неизменность тестовых аккаунтов/оплат; сохранить backup.

Команда не публикует события и не отправляет письма/push. Выполнение импорта
не подтверждает доступность YouTube у каждого пользователя или работоспособность
приватного клуба. Детали стенда — в [операционной заметке](../docs/operations/teamassist-staging.md).


## Локальная очистка почтовых данных обезличенных аккаунтов

[retired-access-email-cleanup.ts](scripts/retired-access-email-cleanup.ts)
использует `FRESH_DATABASE_URL` и `FRESH_DATABASE_CONTAINER_ID` уже
подготовленной одноразовой MySQL. Режим по умолчанию показывает только счётчики
для партии до 100 аккаунтов. Добавьте `--apply-local` для записи на этой БД.

```sh
pnpm exec tsx tooling/scripts/retired-access-email-cleanup.ts --dry-run
```

При `hasMore: true` после успешной записи можно запустить следующую партию.
Сценарий проверяет локальный Docker, принадлежность контейнера и историю миграций.
Он удаляет токены восстановления, очищает адрес и секрет из почтового журнала,
закрывает неотправленные письма и сохраняет связь письма с оплаченным заказом.
