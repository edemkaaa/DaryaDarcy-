# Фронтенд Daryadarcy

Основной веб-клиент использует Next.js 16, React и TypeScript. [Сохранённый Expo-клиент](../legacy-expo/) служит эталоном перенесённых сценариев, текстов и дизайна; [legacy-web](../legacy-web/) — более ранний Vite-клиент. Клиент работает с отдельным Express + tRPC API. Expo находится вне workspace. Команды сборки Next.js не собирают приложения iOS/Android.

## Где менять

- [src/app/](src/app/) — маршруты App Router и layout.
- [src/features/](src/features/) — экраны и сценарии разделов.
- [src/domain/](src/domain/) — сессия, подписка, профиль и обработка контента.
- [src/shared/](src/shared/) — API, навигация, браузерные функции и общие компоненты.
- [public/](public/) — изображения, шрифты, манифест и юридические страницы.
- [e2e/](e2e/) — браузерные приёмочные тесты.
- [next.config.mjs](next.config.mjs) — конфигурация Next.js и прокси API.

Общие контракты находятся в [packages/shared](../../packages/shared/). Типы tRPC в [src/shared/api/contract.ts](src/shared/api/contract.ts) генерируются из API. После изменения серверного контракта используйте `pnpm api:contract`, затем `pnpm check:api`. Клиент не импортирует серверный runtime или код БД. При изменении API согласовывайте контракт и обновляйте тестовые ответы. Текущий объём работ, результаты проверок и незавершённые задачи — в [WORK_PLAN.md](WORK_PLAN.md).

## Локальный запуск

Используйте Node.js 22 и pnpm 9.12.0, указанный в корневом `package.json`. Из корня репозитория:

```sh
pnpm install --frozen-lockfile
test -f apps/frontend/.env || cp apps/frontend/.env.example apps/frontend/.env
pnpm dev:frontend
```

Фронтенд: http://127.0.0.1:8081. В `.env` пустой `NEXT_PUBLIC_API_BASE_URL` оставляет запросы на том же origin; `API_PROXY_TARGET=http://127.0.0.1:3000` направляет `/api` и `/media` на локальный сервер. Запросы остаются на том же браузерном origin; HttpOnly cookie не требуют ослабления CORS. Next.js также читает `.env.local`; существующий `.env` можно сохранить. `EXPO_PUBLIC_API_BASE_URL` новый клиент не читает. `API_PROXY_TARGET` должен быть настроен и при сборке, и при запуске. После изменения переменных перезапустите Next.js. Не помещайте секреты в `NEXT_PUBLIC_*`.

Поддерживается один публичный origin для сайта, `/api` и `/media`. Отдельный публичный `NEXT_PUBLIC_API_BASE_URL` теперь отклоняется клиентом до запроса: иначе относительные защищённые медиассылки и cookie уходят на разные хосты. Для отдельного внутреннего API используйте `API_PROXY_TARGET`, сохраняя единый публичный адрес.

Сам Next.js запускается без бэкенда, но данные и авторизация требуют доступного API. Браузерные регрессии ниже используют тестовые ответы и позволяют проверять фронтенд без сервера и базы. Запуск и переработка бэкенда не входят в текущую работу над фронтендом; общий `pnpm dev` запускает оба процесса; `pnpm dev:server` запускает только API на 3000. Подготовка локального API описана в [инструкции запуска](../../docs/development/getting-started.md).

Для разработки с удалённым API можно задать в локальном, игнорируемом Git файле `.env.local`:

```dotenv
NEXT_PUBLIC_API_BASE_URL=
API_PROXY_TARGET=https://daryadarcy.dev.reeskeen.ru
# Payment/video flags match staging. These flags do not enable server features.
NEXT_PUBLIC_PRODAMUS_TEST_ENABLED=true
NEXT_PUBLIC_CLUB_TEST_CHECKOUT=false
NEXT_PUBLIC_NORMAL_CHECKOUT_RECOVERY_ENABLED=true
NEXT_PUBLIC_VK_CATALOG_ENABLED=true
# Client opt-in for catalog covers; current staging accepts includeThumbnails.
NEXT_PUBLIC_VIDEO_THUMBNAILS_ENABLED=true
# Legacy library switch; recipes/Petersburg always use protected delivery.
NEXT_PUBLIC_PRIVATE_LIBRARY_FILES_ENABLED=true
```

`NEXT_PUBLIC_VIDEO_THUMBNAILS_ENABLED` отдельно включает подготовленную интеграцию
по документу от 20.10.2026: `includeThumbnails: true` на всех страницах каталога
и поле обложки в форме VK. На 22.10.2026 публичный staging API принимает этот
параметр и возвращает 22 карточки; обложек нет у 69/75/78. Флаг не включает
возможности сервера и требует пересборки клиента. Браузерные проверки нового
режима используют тестовые ответы; они не подтверждают воспроизведение всех
реальных роликов или сохранение обложек на опубликованном сервере.

После изменения цели перезапустите `pnpm dev:frontend`. Браузер обращается к локальным `/api/*` и `/media/*`, Next.js пересылает их удалённому серверу. [src/proxy.ts](src/proxy.ts) только в режиме `development` с HTTPS-целью заменяет Origin собственного локального фронтенда на origin цели. Запросы с чужим Origin, `cross-site` или публичным Host отклоняются. Cookies передаются как обычно; вход нужно выполнить отдельно на локальном фронтенде. Production и локальный HTTP-бэкенд сохраняют прежнюю обработку Origin.

Эта конфигурация предназначена для `pnpm dev:frontend` на `http://127.0.0.1:8081`.
Загрузки фото/видео/документов определяет текущий ответ `/api/capabilities`;
локальные флаги загрузок не нужны. `NEXT_PUBLIC_NORMAL_CHECKOUT_RECOVERY_ENABLED`
используется только в обычном режиме оплаты, поэтому при Prodamus TEST не меняет
платёжный сценарий. Рецепты, гид по Петербургу и четыре зимние выкройки используют
защищённый API независимо от `NEXT_PUBLIC_PRIVATE_LIBRARY_FILES_ENABLED`. Адресов платных
материалов Яндекс.Диска в клиентском коде нет; при недоступном API отображается
ошибка с повтором без перехода к публичному источнику. Выдача требует готовых
серверных bindings и включённых серверных возможностей; клиентская настройка
не заменяет перенос файлов и включение серверной выдачи. Бесплатный сборник
стилизаций сохраняет прежнюю открытую ссылку. «Лошадка-качалка» бесплатна:
карточка библиотеки и кнопки на экране выкроек открывают её Яндекс-ссылку без
подписки и без зависимости от приватного API. Старые публичные ссылки платных
материалов нужно отдельно отозвать в аккаунте владельца Яндекс.Диска и удалить
из прежних размещённых сборок и контролируемых кэшей.
Для проверки с удалённым API используйте
dev-сервер: `next start` сохраняет production-политику Origin и ранее собранные
значения переменных. Локальная работа с API использует реальные данные стенда.

## Установка пароля из письма

`/password#token=…` — отдельная страница вне layout основного приложения:
без AuthProvider, tRPC, вкладок, музыки и фоновых запросов. Поле, кнопки,
шрифты и переключатель видимости пароля используют общие компоненты экрана входа.
Токен читается из fragment, сразу удаляется из адреса и остаётся только в памяти
компонента. Ни пароль, ни токен не сохраняются в localStorage/sessionStorage.
После reload нужно снова открыть исходную ссылку из письма.

Единственная запись — явный POST `/api/auth/password/complete` с токеном и паролем
в JSON body, без cookies. Одноразовость, срок токена, длина пароля и ограничения
попыток проверяет прежний backend. Автоматического входа после сохранения нет.
При потере ответа или 5xx показывается неопределённый результат с переходом
ко входу/запросу новой ссылки; повторной отправки автоматически нет. 429
сохраняет ввод в памяти и разрешает только ручной повтор после Retry-After.

Для маршрута действуют `no-store`, `no-referrer`, nonce CSP, `frame-src 'none'`,
`form-action 'none'` и connect-src только своего origin (в dev дополнительно HMR).
Обычная HTML-отправка формы запрещена; сохранение работает через fetch.
На страницу не добавлять аналитику, сторонние скрипты и общий app layout.

Backend формирует новые ссылки от `PUBLIC_APP_URL` на `/password`; старый
`/api/auth/password` возвращает 303 на этот адрес без fragment в Location.
Браузер сохраняет исходный fragment при таком переходе; сервер токен не получает.
`PUBLIC_AUTH_URL` больше не выбирает адрес установки пароля. Сначала выпустить
frontend с `/password`, затем backend с новыми письмами и переходом старых ссылок.
Публичный origin фронтенда должен проксировать `/api` на backend. Изменения схемы
БД, password/session policy и миграции для этого переноса не требуются.

Проверки: `e2e/password-setup.spec.ts`, `tests/password-page.browser.test.ts`
(настоящий backend redirect), `tests/access-urls.test.ts` и
`tests/frontend-document-security.test.ts`. Browser-фикстуры не отправляют письма
и не меняют пароли настоящих пользователей.

## Сборка и проверки

Скорость переходов оценивайте на production-сборке (`pnpm build:frontend`,
затем `pnpm start:frontend`), предварительно остановив dev-сервер. В режиме
`pnpm dev:frontend` страницы компилируются при первом открытии, а автоматическая
предзагрузка маршрутов выключена; это может давать задержки в несколько секунд.

HTML формируется при запросе: CSP использует новый случайный nonce для каждого
ответа, включая встроенные скрипты Next. Это исключает предварительную сборку
HTML и его публичное кеширование; статические JS/CSS и изображения сохраняют
свой кеш. Параметры `paid`/`checkout` читаются на клиенте. Доступ по-прежнему
зависит от подтверждения API. Заголовок
Видео анимируется только при первом открытии в текущем документе браузера;
возврат между разделами и завершение загрузки списка не повторяют анимацию.

Команды из корня:

```sh
pnpm --filter @daryadarcy/frontend typecheck
pnpm lint
pnpm verify
pnpm build:frontend  # pnpm build:web — тот же Next.js build, результат в apps/frontend/.next
pnpm start:frontend
```

`pnpm verify` запускает выбранные проверки обмена с API: запросы, сессию,
доступ, кеш и сохранение публикаций. Проверки внешнего вида и поведения
отдельных UI-компонентов в этот список не добавляем. Типизация проверяется
отдельной командой `pnpm check`. `pnpm test` сохраняет полный модульный набор,
а `pnpm test:frontend` запускает браузерные сценарии.

Для браузерных проверок сначала соберите фронтенд и установите Chromium для Playwright:

```sh
pnpm --filter @daryadarcy/frontend exec playwright install chromium
pnpm build:frontend
pnpm test:frontend
```

Playwright запускает production-сервер на 8081, если порт свободен. При уже запущенном сервере используется он; для проверки именно новой сборки предварительно остановите прежний процесс. Можно выбрать установленный Chromium через `PLAYWRIGHT_EXECUTABLE_PATH`.

Не запускайте `next build` в той же рабочей копии одновременно с `next dev`: оба процесса используют `.next`. Если dev-сервер нужен для просмотра во время production-проверок, собирайте отдельную копию проекта и запускайте её на другом порту. Режим разработки с HMR не подходит для проверки production-заголовков кеша.

### Защитные заголовки HTML

[src/proxy.ts](src/proxy.ts) задаёт CSP с одноразовым nonce, `X-Frame-Options: DENY`,
`X-Content-Type-Options: nosniff` и `Referrer-Policy: strict-origin-when-cross-origin`.
Inline-скрипты без nonce и HTML-обработчики событий запрещены. В production нет
`unsafe-eval`; существующие React style-атрибуты разрешены через `style-src`.
Встраивание разрешено только для существующих VK/YouTube-плееров. HTTPS-фото,
аудио, видео и локальные blob-превью поддерживаются. `connect-src` разрешает
свой origin; `NEXT_PUBLIC_API_BASE_URL` может указывать только на тот же публичный origin.

Политика находится в [document-headers.ts](src/shared/security/document-headers.ts).
API и `/media` сохраняют собственные заголовки бэкенда, включая страницу установки
пароля. Прокси/CDN при выпуске не должны публично кешировать HTML или добавлять
другую CSP, которая блокирует нужные ресурсы. После выпуска нужно проверить
конечные заголовки через публичный ingress. Версии Next.js и зависимостей этим
изменением не обновлялись.

Регрессии: [security-hardening.spec.ts](e2e/security-hardening.spec.ts),
[frontend-document-security.test.ts](../../tests/frontend-document-security.test.ts)
и [library-client-bundle.test.ts](../../tests/library-client-bundle.test.ts).

Проверки настоящего API выключены по умолчанию. `RUN_REAL_API_TESTS=1` включает отдельные интеграционные сценарии, включая запись черновика, и требует специально подготовленного тестового API. Успешные тесты с подставными ответами не подтверждают серверные права доступа, реальные платежи или работу на всех устройствах.

## Черновики профиля и прогресс теста

Черновики имени и начальной анкеты Клуба сохраняют версию формата, владельца,
исходную `profileRevision`, исходные имя/пол и текущий ввод. Закрытие формы,
повторное открытие и reload восстанавливают эту основу. Фоновое чтение профиля
её не повышает. Старые черновики без версии сохраняют ввод и требуют свежей
сверки. Формат и чтение описаны в [profile-draft.ts](src/domain/profile/profile-draft.ts).

После 409 или неподтверждённого ответа пользователь проверяет сохранение.
Если запись не подтверждена, сравнение с актуальным профилем сначала сохраняется
на устройстве, затем удаляется pending-запись. При ошибке хранилища pending
остаётся. Для новой попытки нужно нажать «Использовать мой черновик», после
чего отдельно сохранить форму с показанной версией. Reload между этими действиями
сохраняет состояние сверки. Новые изменения профиля после сверки снова защищены
серверным сравнением версии. Существующий receipt-протокол фото применяется отдельно.

Прогресс теста версии 2 содержит `runId`, ревизию записи, версию набора вопросов,
вопрос и ответы. Версия 1 читается и переводится в новый формат при следующем
явном действии. Чтение, сравнение исходной записи и запись/завершение согласованы
между вкладками через Web Locks, а при их отсутствии — через readwrite-транзакцию
IndexedDB. База `darcy-quiz-coordination` хранит только пустое хранилище блокировок;
имена, ответы и результаты в неё не записываются.

Устаревшая вкладка не удаляет и не заменяет чужое прохождение либо более свежую
ревизию того же прохождения. Она показывает «Продолжить сохранённый тест»;
это действие загружает актуальные ответы без записи. Результат фиксируется
перед удалением соответствующего прогресса. При отказе хранилища показывается
ошибка; ввод, который удалось обработать, остаётся в памяти текущей страницы.

Правила общего устройства сохранены: localStorage профиля/теста разделён по
владельцу и очищается действующим адаптером при выходе или смене аккаунта.
Анонимный результат не переносится вошедшему пользователю. Черновики статей
и постов в IndexedDB имеют отдельные owner guards и явное удаление в редакторах.
Автоматический срок удаления и общая очистка незавершённых операций не добавлены.

Проверки: [profile-consistency.spec.ts](e2e/profile-consistency.spec.ts),
[audit-draft-persistence.spec.ts](e2e/audit-draft-persistence.spec.ts),
[quiz-multitab.spec.ts](e2e/quiz-multitab.spec.ts). Они проверяют клиентское
поведение с подставными ответами API. Совместная приёмка настоящих редакторов,
CI-конфигурации, LIVE-оплата и серверные флаги остаются отдельными этапами.

## Общая навигация

### Восстановление гостевой оплаты

`NEXT_PUBLIC_GUEST_CHECKOUT_RECOVERY_ENABLED=true` включает отдельный гостевой
LIVE-путь. По умолчанию он выключен; Prodamus TEST и YooKassa TEST его игнорируют.
Для выпуска нужны серверный `GUEST_CHECKOUT_RECOVERY_ENABLED`, боевые настройки
и совместная приёмка. Новые покупки вошедшего пользователя при этом используют
NORMAL recovery и требуют серверный `NORMAL_CHECKOUT_RECOVERY_ENABLED`.
Клиентский флаг сам по себе серверную оплату не включает.

До первого запроса в localStorage записываются UUIDv4, секрет из 32 случайных
байт, каноническая почта и срок. Запись проверяется чтением; Web Locks согласует
вкладки. Ошибка хранилища останавливает оплату. Create и status используют
отдельные POST без batch, TEST-заголовка и секрета в URL. Потеря ответа,
перезагрузка и `notRecorded` сохраняют прежнюю пару ключей. После `429` срок
ручного повтора сохраняется на устройстве; таймер не отправляет запросов.

Незавершённая покупка сохраняет получателя. После входа она восстанавливается
с прежней парой, а привязка к аккаунту записывается только после принятого
сервером результата. Другой аккаунт не получает её данные. Ключи переживают
выход; после привязки восстановление требует входа в тот же аккаунт. Потеря
ключей не восстанавливается по почте. Без ключей на странице возврата перед
новой покупкой требуется явное подтверждение предупреждения о повторной оплате.
Новая покупка после terminal-результата требует отдельного действия и свежей
проверки статуса. Для вошедшего пользователя это действие завершает гостевой
журнал; следующая покупка использует обычный путь аккаунта. Гостевой результат
не создаёт сессию и не открывает доступ; вошедшему пользователю доступ
подтверждает отдельное чтение подписки.

Проверка с синтетическим API требует отдельной production-сборки:

```sh
NEXT_PUBLIC_PRODAMUS_TEST_ENABLED=false NEXT_PUBLIC_CLUB_TEST_CHECKOUT=false NEXT_PUBLIC_NORMAL_CHECKOUT_RECOVERY_ENABLED=true NEXT_PUBLIC_GUEST_CHECKOUT_RECOVERY_ENABLED=true pnpm build:frontend
pnpm --filter @daryadarcy/frontend test:e2e:guest-checkout
```

Конфигурация проверяет гостя и прежний NORMAL-сценарий аккаунта. Реальная оплата,
доставка письма и включение LIVE этим прогоном не подтверждаются.

### Режимы оплаты клуба

Оба тестовых режима по умолчанию выключены и фиксируются при сборке Next.js.
Изменение env уже собранного приложения, URL или localStorage режим не меняют.

| Режим            | `NEXT_PUBLIC_PRODAMUS_TEST_ENABLED` | `NEXT_PUBLIC_CLUB_TEST_CHECKOUT` |
| ---------------- | ----------------------------------- | -------------------------------- |
| Обычный Prodamus | `false`                             | `false`                          |
| Prodamus TEST    | `true`                              | `false`                          |
| YooKassa TEST    | `false`                             | `true`                           |

Неверные значения и два включённых флага показывают недоступность оплаты.
Prodamus TEST соответствует отдельному серверному demo runtime: 790 ₽ за
30 дней, однократная оплата. Гость после возврата на `/club` входит с почтой,
указанной при оплате, и проверяет доступ. Клиент не подтверждает оплату по URL
и отвергает ссылки другого merchant/режима/суммы. Проверка серверного callback
и реальной выдачи доступа выполняется отдельно.

Для локальной TEST-сборки из корня:

```sh
NEXT_PUBLIC_PRODAMUS_TEST_ENABLED=true NEXT_PUBLIC_CLUB_TEST_CHECKOUT=false pnpm build:frontend
CHECKOUT_UI_EXPECTED_MODE=prodamus PLAYWRIGHT_EXECUTABLE_PATH=/usr/bin/chromium node --test tests/frontend-club-checkout-mode.native.test.mjs
```

Локальная сборка TEST-интерфейса не включает серверный TEST
runtime и не меняет маршрутизацию checkout. Перед стандартным E2E-прогоном
пересоберите фронтенд с обоими флагами `false`.

[TabShell](src/app/tab-shell.tsx) оборачивает все страницы внутри корневых providers. Хедер с главной, возвратом и профилем и нижнее меню находятся вне прокручиваемого контента; загрузка, ошибка и статус подписки не скрывают их. При подтверждённом доступе на `/club` основное нижнее меню скрыто: внутри клуба остаются четыре пункта «Подборки», «Комьюнити», «Эксклюзив» и «Лайф». Клубное меню учитывает нижнюю safe area; выход через шапку возвращает основное меню приложения. Страницы разделов не добавляют собственные копии хедера. Музыка клуба остаётся в общем хедере.

[TabScreens](src/app/tab-screens.tsx) сохраняет посещённую главную, шесть экранов нижнего меню, профиль, экраны теста и сохранённого результата и три фиксированные страницы библиотеки: выкройки, гид по эстетикам и «Обо мне». Компоненты загружаются по мере открытия; скрытые панели имеют `hidden`/`inert`. Возврат сохраняет DOM, прокрутку, поиск, фильтры и декодированные изображения, включая повторное открытие выкроек после возврата в библиотеку. Эффекты первого появления остаются при первом открытии и не запускаются заново при смене вкладок. Дата для главной передаётся из корневого layout, чтобы сервер и первый клиентский кадр совпадали; при возврате календарь актуализируется. Остальные маршруты рендерятся обычным `children`; файлы страниц разделов сохраняют маршруты и метаданные Next.js. Не следует дополнительно рендерить копии этих экранов внутри оболочки.

Профиль получает имя и аватар из общего `AuthProvider`, сохраняет открытую форму, вкладку закладок и прокрутку. Свежие сохранённые публикации не запрашиваются повторно при каждом входе; устаревшие перепроверяются одним фоновым запросом. Скрытый профиль не опрашивает API. Выход и смена личности сбрасывают его вместе с остальными приватными экранами. Проверки: [profile-cache.spec.ts](e2e/profile-cache.spec.ts). Периодическое обновление каталога видео и Клуба не вставляет строку «Обновление…» над содержимым и не меняет его координаты.

Фоновые ошибки сессии, подписки и обновления контента используют один [общий слот](src/shared/ui/background-notice.tsx) на 12px выше текущего нижнего меню. Плашка появляется поверх содержимого без сдвига карточек, учитывает высоту клубного меню и оставляет доступными плавающие кнопки. Приоритет: сессия → подписка → контент. «Повторить» запускает восстановление всех зарегистрированных ошибок; на время запросов показывается недоступная кнопка «Проверяем…». Скрытые экраны не показывают сообщения, открытые диалоги остаются выше плашки. Временный сбой сохраняет уже загруженные карточки и закладки; подтверждённая потеря доступа закрывает приватные данные. Первая ошибка загрузки остаётся в области контента, ошибка следующей страницы — в конце списка. Регрессии: [background-notices.spec.ts](e2e/background-notices.spec.ts).

Все эти сообщения используют общий `StatusNotice`: одинаковые бумажный градиент, рамка, радиус 16px, круглый значок и оливковая кнопка. Ошибки первой загрузки и подгрузки отличаются от фоновой плашки расположением и символом, а не отдельной палитрой. Несколько действий размещаются под текстом, чтобы не сжимать его на узких экранах.

Полноэкранные ошибки и проверки доступа используют [ScreenStatus](src/shared/ui/screen-status.tsx): отдельная область прокрутки начинается ниже шапки и заканчивается над основным меню. Длинное сообщение можно прокрутить до действия повтора. Для обычных страниц с прокруткой отступ шапки остаётся внутри контента; если ошибка заменяет прокрутку неподвижным блоком, `TabShell` сохраняет верхний безопасный отступ. Ошибки списков админки включают `ScreenContainer.scrollable`, чтобы панель разделов не вытесняла сообщение под меню на коротком экране. Текст и действия `StatusNotice` переносятся по доступной ширине; несколько действий остаются под текстом. Регрессии размещения: [status-notice-layout.spec.ts](e2e/status-notice-layout.spec.ts).

Оконная отрисовка ленты и клуба освобождает дальние строки при прокрутке, но при скрытии всего раздела сохраняет последнее окно карточек. Поэтому возврат не пересоздаёт фотографии и приостановленные медиа. Общий `Picture` хранит в памяти не более 256 идентификаторов успешно показанных изображений и не повторяет их fade при вынужденном перемонтировании; этот список не содержит байтов изображений и не подтверждает доступ. Кеш и DOM проверяются отдельно в [media-return.spec.ts](e2e/media-return.spec.ts): отсутствие RSC-запроса само по себе не означает отсутствие повторного появления картинки.

Метаданные выкроек и закрытый текст гида хранятся только в памяти текущей личности. При возврате и периодической проверке подтверждённое содержимое остаётся на экране до ответа; ошибка скрывает его, уход останавливает незавершённые чтения и опрос. Смена личности и подтверждённая потеря доступа сбрасывают сохранённые панели. Защищённые файлы продолжают отдаваться сервером с `private, no-store`: быстрый возврат использует сохранённые элементы, а не публичный кеш. Изменение `revision` выкройки пересоздаёт только соответствующее изображение, чтобы новый файл по прежнему защищённому URL обновился.

[tab-styles.ts](src/app/tab-styles.ts) подключает из корневого layout стили сохраняемых экранов и их статических зависимостей. Они готовы до первого кадра нового экрана; JavaScript компонентов остаётся ленивым. При добавлении зависимости со своим stylesheet обновляйте этот список, чтобы содержимое не появлялось раньше оформления.

Контентные запросы включены для активной вкладки: при возврате устаревшие данные обновляются с сохранением кеша и поиска. Параметры оплаты Клуба учитываются только в его активном экране; фоновое подтверждение останавливается при уходе. Скрытые медиа ставятся на паузу, циклы оформления магазина и слайдеров главной останавливаются, диалоги закрываются. Смена личности/выход сбрасывают сохранённые экраны через существующий `AuthProvider` scope, чтобы состояние разных пользователей не смешивалось. Проверки возвратов и обмена с API: [tab-return.spec.ts](e2e/tab-return.spec.ts), отдельно от `verify`.

[TabLoading](src/app/tab-loading.tsx) и общий route fallback показывают фон приложения без приблизительной копии страницы; при ожидании дольше 500 мс появляется спокойная подпись «Открываем раздел…». Баннер и геометрия раздела появляются только у настоящего экрана. [ContentPlaceholder](src/shared/ui/content-placeholder.tsx) используется для ожидания данных уже внутри его структуры; рамки Видео учитывают высоты заголовка, метаданных и отступы карточки. Первые полученные элементы Ленты/Видео появляются за 180 мс через opacity без движения; фоновые обновления и возврат не повторяют эффект.

[motion.tsx](src/shared/browser/motion.tsx) задаёт начальное состояние вступления ещё в HTML и запускает Web Animation в layout effect до первого кадра. После запуска начальный атрибут снимается; при размонтировании анимация отменяется. Как в старом приложении, FadeInDown начинается на 25px ниже, FadeInUp — выше, вступительные Fade используют линейный темп. Сохранены 600 мс баннера и 500 мс с задержкой 200 мс у первой карточки Интерактива. `prefers-reduced-motion` показывает содержимое сразу. Регрессии первого кадра, заполненного списка Видео и reduced motion: [first-entry-motion.spec.ts](e2e/first-entry-motion.spec.ts), отдельно от `verify`.

[LoadingIndicator](src/shared/ui/loading-indicator.tsx) остаётся для проверки доступа и локальных операций: 36px в центре своей области, 20px в конце списка. Кнопки используют тот же `Spinner` размером 20px с цветом, подходящим к фону кнопки. Догрузка Клуба показывает индикатор только для следующей страницы, а не для фонового обновления. `QueryRetryState.loadingContent` заменяет индикатор заглушкой там, где ожидается содержимое; ошибки и повтор запроса сохраняются. Сценарии медленного кода/API, доступа и оплаты: [loading-feedback.spec.ts](e2e/loading-feedback.spec.ts), отдельно от общего `verify`.

Видео использует штатную вертикальную прокрутку `ScrollArea`: не переопределяйте overflow списка на `visible`, это делает нижние карточки недоступными внутри фиксированной оболочки приложения. На `/videos` хедер всегда виден, как в старой версии. Длинный список, доступность последней карточки над меню, неподвижный хедер и сохранение позиции при возврате проверяются отдельно в [videos-scroll.spec.ts](e2e/videos-scroll.spec.ts), включая возврат из Ленты со скрытым хедером.

На страницах со скрываемым хедером при прокрутке вниз он плавно уходит вверх за 250 мс, при движении вверх появляется за 200 мс. `TabShell` задаёт исключение для `/videos` через `useScrollHeader(path, hideOnScroll)`: там хедер сбрасывается в видимое состояние и обработчики скрытия не подключаются. В начале страницы и после смены маршрута хедер виден. Нижнее меню и геометрия содержимого не меняются. Обработчик наблюдает основной вертикальный ScrollArea; вложенная прокрутка, карусели и диалоги не влияют на хедер. Отдельные панели вне основного ScrollArea помечаются `data-scroll-header="ignore"`, как фильтры клуба. Порог движения накапливается в CSS-пикселях, отскок за границы прокрутки не переключает направление. Скрытый хедер становится `inert`; Tab возвращает его для клавиатурной навигации, контрол с клавиатурным фокусом не скрывается. `prefers-reduced-motion` отключает анимацию. Регрессии: [header-scroll.spec.ts](e2e/header-scroll.spec.ts) и [frontend-scroll-header.test.ts](../../tests/frontend-scroll-header.test.ts).

Хедер расположен поверх страницы без отдельной фоновой полосы. На главной, в Ленте, Клубе, Библиотеке и Магазине он вписан в исходный баннер и не добавляет высоту. На остальных страницах бумажный фон принадлежит самому хедеру и скрывается вместе с иконками. Если хедер скрывается при прокрутке, место под него резервирует прокручиваемый `::before` основного `ScrollArea`; для закреплённого хедера остаётся `--screen-safe-top` внутри `ScreenContainer`. Поэтому сверху не остаётся неподвижная полоса и не меняется размер области прокрутки. Индикатор прогресса теста находится внутри той же прокрутки, что и ответы. Сохранены исходные значки, цвета и варианты главной/магазина; пустая область хедера пропускает действия к содержимому. Регрессии на ширинах 390 и 1440 px: [header-surface-scroll.spec.ts](e2e/header-surface-scroll.spec.ts).

[Возврат](src/shared/navigation/router.tsx) использует только историю, созданную приложением. При прямом входе кнопка ведёт в родительский раздел (пост → Лента, видео → Видео, статья → Библиотека, товар → Магазин, тест → Интерактив), либо на главную. Маркер истории сохраняет служебные поля Next.js и переживает обновление текущей вкладки. Проверки прокрутки, прямых ссылок и отказов API: [navigation-layout.spec.ts](e2e/navigation-layout.spec.ts).

## Кеш и возврат на страницу

Один [QueryClient](src/shared/api/query-client.ts) обслуживает все маршруты. По умолчанию данные считаются свежими 30 секунд, неактивный кеш удаляется через 5 минут. Это кеш в памяти текущей вкладки; после полной перезагрузки страницы он создаётся заново. [Политика обновления контента](src/shared/api/content-refresh.ts) запрашивает актуальные данные раз в 60 секунд только для активных экранов: лента и её теги, клуб, комментарии рядом с областью просмотра, статьи библиотеки, сохранённые публикации, списки и обычные страницы видео, оформление клуба и настройки заказа менеджеру. Опрос приостанавливается при скрытом документе и без сети; при возврате видимости и сети устаревшие данные перепроверяются. Скрытые сохранённые вкладки отключают наблюдатели запросов; при открытии устаревший кеш обновляется в фоне. Запрашиваются существующие API, без отдельного сервиса версий или событий: публикации, правки и удаления других администраторов видны после ближайшего успешного чтения. Подтверждённый контент остаётся на экране во время запроса и временного сбоя; отсутствие материала, блокировка и ошибки доступа скрывают прежнее содержимое. Полная перезагрузка документа и очистка всего кеша не нужны. Подписка, оплата, закрытые файлы и подписанные ссылки воспроизведения сохраняют отдельные правила проверки доступа; периодический опрос к ним не применяется. Уведомления сохраняют свой опрос раз в 90 секунд. Статические товары и иллюстрации из сборки обновляются при выпуске приложения. Регрессии: [content-refresh.spec.ts](e2e/content-refresh.spec.ts).

Отдельно Next.js хранит уже посещённые страницы в клиентском Router Cache на 5 минут (`experimental.staleTimes.dynamic` в [next.config.mjs](next.config.mjs)). Повторное открытие вкладки или материала в этот период не требует нового RSC-запроса. Это память текущего документа браузера, а не публичный HTTP-кеш: HTML по-прежнему получает новый nonce и `private, no-store`. Страницы содержат клиентские компоненты; данные и права проверяются через API независимо от кеша маршрутов. Проверки повторных переходов, сохранения главной и отсутствия полной перезагрузки: [navigation-cache.spec.ts](e2e/navigation-cache.spec.ts).

[Сессия](src/domain/session/session-context.tsx) проверяется при запуске, возврате видимой страницы, восстановлении сети, изменениях сессии в другой вкладке и ошибках доступа. Парные `focus`/`visibilitychange` объединяются в пределах одной секунды; сетевое восстановление, межвкладочные события и ошибки доступа проходят сразу. [Подписка](src/domain/subscription/subscription-context.tsx) отдельно перепроверяет права при возврате видимости и сети. Фоновая проверка и временный сбой не заменяют подтверждённый экран загрузкой. Выход, смена пользователя/роли и подтверждённая потеря доступа очищают приватный кеш. Ответы API используют HTTP `no-store`, cookie отправляются через `credentials: include`: кеш данных приложения не служит подтверждением авторизации.

| Ресурс                                                  | Политика                                                                                      |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Статические импорты изображений `/_next/static/media/*` | Имя с хешем; production-сервер отдаёт годовой `immutable` кеш                                 |
| Адаптивные варианты `/assets/responsive/*`              | Имя с хешем содержимого; годовой `immutable` кеш из `next.config.mjs`                         |
| Шрифты и прочие файлы `public` без версии в имени       | Проверка актуальности (`max-age=0`); неизменённый файл может вернуть 304 по ETag              |
| Фото/аватары и другие URL из API                        | Заголовки задаёт сервер или внешнее хранилище; годовой кеш автоматически к ним не применяется |

В текущем серверном `s3Put` нет явного `CacheControl` для новых загрузок. Поэтому проверка локальных иллюстраций не подтверждает срок кеширования загруженных пользователями файлов. Настройку таких объектов следует согласовывать отдельно с сервером и правилами доступа.

Регрессии: [контроллер сессии](../../tests/frontend-session-controller.test.ts), [кеш запросов](../../tests/frontend-query-cache.test.ts), [фокус и меню](e2e/focus-and-menu.spec.ts), [кеш браузера и возврат](e2e/cache-and-resume.spec.ts), [изоляция пользователей](e2e/session-safety.spec.ts). Проверка HTTP-кеша изображений запускается без `page.route`, поскольку [маршрутизация Playwright отключает кеш браузера](https://playwright.dev/docs/api/class-page#page-route).

Серверная оговорка из аудита: текущий `/api/auth/me` может вернуть `user: null` при внутреннем сбое проверки пользователя. Клиент обязан трактовать такой ответ как выход. Различение этого случая и настоящего отзыва сессии требует серверного исправления; бэкенд в этой работе не меняется.

## Ограничения выпуска

Прежний статический `web-dist` и старый `deploy:web` не подходят для Next.js: защитная проверка останавливает этот деплой. Запуск процесса Next.js за nginx, маршруты `/api` и `/media`, переменные сборки/запуска и rollback ещё требуют отдельной проверки и согласования. Локальная сборка не является разрешением production-релиза.
