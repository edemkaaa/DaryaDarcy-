# Бэкенд Daryadarcy

NestJS + tRPC с Express-адаптером, TypeScript, Drizzle / MySQL. Основная работа — в src; схема и миграции — в [packages/database](../../packages/database/). Это постепенный перенос существующего сервера, а не параллельная переписанная система. HTTP-сервер уже запускается через NestJS; остальные доменные адаптеры переводятся по [плану](../../tasks/plan.md). Решение и ограничения — в [ADR 0005](../../docs/decisions/0005-nestjs-modular-backend.md).

## Навигация

```text
src/
  app.module.ts   композиция Nest-модулей
  _core/          запуск NestJS, TrpcModule/TrpcService, контекст и общие middleware
  system/         Nest-контроллер состояния сервера
  routers.ts      только сборка tRPC-роутеров
  identity/       Nest-модуль, контроллеры и сервисы сессий, регистрации, пароля и писем
  billing/        checkout, обработка платежей и отмена подписки
  content/        ContentModule, чтение/запись/комментарии/загрузки; лента, статьи и видео
  club/           материалы и обсуждения клуба
  profile/        профиль и дополнительные поля
  moderation/     жалобы и модерация
  notifications/  push-токены и согласия
  admin/          административные процедуры
  launch/         Nest-модуль, контроллер и сервис настроек запуска; capabilities
  pen-pals/       анкеты и совпадения
  shop/           старые процедуры магазина, запуск отключён
```

## Что важно при изменениях

- routers.ts остаётся точкой сборки; проверки доступа и поведение находятся в доменных модулях.
- app.module.ts собирает Nest-модули. Используйте явный @Inject для зависимостей конструкторов: esbuild не генерирует metadata типов. LaunchService использует существующие функции Drizzle с транзакциями; общий lifecycle пула пока не переносился.
- IdentityModule экспортирует SessionService и HTTP-guards для настроек/повторных писем. Guards проверяют свежую сессию и роль, контроллер получает пользователя от guard, не из тела запроса. Это не замена транзакционной проверки прав и не глобальный guard для всех маршрутов.
- TrpcService собирает HTTP-роутер и контекст из сервисов Nest; createAppRouter принимает обязательные ContentReadService, ContentWriteService, ContentCommentService и ContentUploadService. Самостоятельный appRouter нужен прямым вызовам/инструментам и использует те же фабрики. Чтение ленты (включая поиск/страницы/теги), видео, закладок, взаимодействий и статей, создание/правка/ручная публикация постов, реакции, комментарии и административные tRPC-загрузки фото/медиа перенесены; raw-видеозагрузчик, импорт по ссылке и остальные административные операции ещё переводятся. Проверка подписки — в identity/club-access.ts. SQL-helpers и общий пул пока в db.ts: внедрение сервисов не означает завершённый перенос слоя данных.
- ContentCommentService сохраняет проверки публикации, подписки, окна обсуждения и прав автора/модератора; контекст пользователя берётся из свежей сессии. Список комментариев по-прежнему требует членства в клубе, а изменения публичных обсуждений доступны авторизованным пользователям — это существующее различие, не новая политика. SQL-транзакции/блокировки остаются в content/comments.ts; уведомление об ответе запускается после commit, доставка пока не durable.
- Лайки/закладки постов переключаются в content/post-reactions.ts одной транзакцией с блокировкой строки пользователя: следующий запрос читает уже сохранённое состояние. Старые дубли пары удаляются при выключении реакции; массовой очистки БД нет. Это защита текущих API-записей от конкуренции, не уникальное ограничение схемы и не идемпотентность: повтор после неизвестного результата сети может переключить состояние ещё раз. Индексы и проверки существования поста остаются отдельными задачами.
- ContentWriteService получает авторизованные и валидированные данные от adminProcedure, не пользовательскую роль из payload. Существующие helpers сохраняют пост/медиа/ключ запроса одной транзакцией; анонс вызывается после commit. Это не durable-очередь push: окно потери анонса при остановке процесса остаётся отдельной задачей N12.
- ContentUploadService обрабатывает admin.uploadPhoto и admin.uploadMedia; проверка доступа до чтения больших тел остаётся в _core/request-bodies.ts, повторная проверка свежей сессии — в tRPC. Фото проходят прежнюю проверку байтов, поворот и перекодирование через media/photos.ts. Общие медиа требуют непустой канонический base64 и получают серверный UUID-ключ без клиентского имени/расширения; имя остаётся отдельной метаинформацией. Предел кодированной строки не превышает прежние 50 MiB JSON, это не лимит 50 MiB декодированного файла. Сохранена последовательность «хранилище → связь с постом»; ошибка БД не отменяет загрузку файла. Проверка байтов документов и уборка непривязанных объектов остаются отдельными задачами, как и lifecycle storage/SQL.
- Заявленный Content-Type проверяет content/media-content-type.ts: audio/* для аудио, video/* для видео, PDF/DOC/DOCX/text/plain для документов; application/octet-stream остаётся общим fallback. Несовместимые типы, пустое/некорректное MIME-имя, управляющие символы, некорректные параметры и значения длиннее 128 символов дают 400 до загрузки. Затем аудио/видео проверяются через file-type 22.1.1 в media/file-signature.ts: неизвестные/чужие форматы отклоняются, storage и SQL получают одинаковый распознанный MIME. Параметры сохраняются только при совпадении заявленного и распознанного MIME-имени; alias/fallback и ошибочные метки одной категории заменяются. MP4 и WebM — общие контейнеры, допустимые для обеих категорий без проверки дорожек. Распознавание выполняется по одному в worker thread, с пятисекундным тайм-аутом активной задачи и обязательным завершением worker; очередь не ограничивает общий объём ожидающих HTTP-запросов и не является защитой от общего DoS. Новые HTTP-квоты/429 не добавлены. Это подсказка по сигнатуре, не проверка воспроизведения, кодеков, макросов, полиглотов или антивирус. Документы пока сохраняют проверку только метаданных: HTML под text/plain не отклоняется по байтам. Старый raw-video endpoint этим шагом не защищён.
- Клиент получает тип AppRouter; не копируйте серверные функции в фронтенд.
- Регистрация подтверждается письмом: ответ 202 не означает вход или выданную сессию.
- Checkout не авторизует по email, claim не выдаёт доступ. Платежи и письма имеют сохранённое состояние обработки.
- Пароль устанавливается одноразовой ссылкой; смена пароля изменяет версию сессий.
- Проверяйте повторные запросы, конкуренцию, истёкшие ссылки, заблокированные аккаунты и ошибки внешних сервисов.
- Изменение API должно сопровождаться тестами; [снимок контракта](../../__tests__/trpc-contract.test.ts) защищает имена процедур.

Актуальные ограничения выпуска — в [tasks/todo.md](../../tasks/todo.md).
