# Бэкенд Daryadarcy

NestJS + tRPC с Express-адаптером, TypeScript, Drizzle / MySQL. Основная работа — в src; схема и миграции — в [packages/database](../../packages/database/). Это постепенный перенос существующего сервера, а не параллельная переписанная система. HTTP-сервер уже запускается через NestJS; остальные доменные адаптеры переводятся по [плану](../../tasks/plan.md). Решение и ограничения — в [ADR 0005](../../docs/decisions/0005-nestjs-modular-backend.md).

## Навигация

```text
src/
  app.module.ts   композиция Nest-модулей
  _core/          запуск NestJS, TrpcModule/TrpcService, контекст и общие middleware
  system/         Nest-контроллер состояния сервера
  routers.ts      только сборка tRPC-роутеров
  identity/       Nest-модуль, контроллеры и сервисы сессий, регистрации, пароля и писем
  billing/        checkout, обработка платежей и отмена подписки
  content/        ContentModule, чтение/запись/комментарии/загрузки; лента, статьи и видео
  club/           материалы и обсуждения клуба
  profile/        профиль и дополнительные поля
  moderation/     жалобы и модерация
  notifications/  push-токены и согласия
  admin/          административные процедуры
  launch/         Nest-модуль, контроллер и сервис настроек запуска; capabilities
  pen-pals/       анкеты и совпадения
  shop/           старые процедуры магазина, запуск отключён
```

## Что важно при изменениях

- routers.ts остаётся точкой сборки; проверки доступа и поведение находятся в доменных модулях.
- admin.posts/postsFiltered/scheduledPosts/getPostMedia/stats используют внедрённый ContentReadService. Проверку свежей сессии и роли сохраняет adminProcedure: административные списки включают черновики и закрытые материалы и не подходят для публичного API. Порядки каталога, фильтрованного списка, календаря и вложений сохранены. SQL остаётся в db.ts; пагинация админки и оптимизация статистики этим переносом не добавлены. Остальные административные запросы и изменения ещё переводятся.
- admin.articles использует ContentReadService, а createArticle/updateArticle/deleteArticle — ContentWriteService. Схемы, значения по умолчанию, блоки статьи и ответы сохранены; создание возвращает число, изменение/удаление — {ok:true}. content/article-writes.ts сохраняет статью и анонс одной транзакцией; SQL-ошибка откатывает оба изменения. Правка/удаление сначала блокируют строку статьи, затем изменяют анонс: параллельные запросы article API к одной статье не создают новый дубль. Снятие с публикации и удаление используют общий каскад content/post-deletion.ts в той же транзакции; связанные обсуждения/реакции откатываются вместе со статьёй, файлы хранилища не удаляются. target анонса остаётся club даже для public-статьи, непустая правка отсутствующего ID возвращает {ok:true}, пустая правка даёт прежнюю ошибку. Старые дубли source и изменения анонса через общий post API не исправлены; уникальный индекс, владение source, идемпотентность создания и политика доступа остаются отдельными задачами.
- app.module.ts собирает Nest-модули. Используйте явный @Inject для зависимостей конструкторов: esbuild не генерирует metadata типов. LaunchService использует существующие функции Drizzle с транзакциями; общий lifecycle пула пока не переносился.
- IdentityModule экспортирует SessionService и HTTP-guards для настроек/повторных писем. Guards проверяют свежую сессию и роль, контроллер получает пользователя от guard, не из тела запроса. Это не замена транзакционной проверки прав и не глобальный guard для всех маршрутов.
- TrpcService собирает HTTP-роутер и контекст из сервисов Nest; createAppRouter принимает обязательные ContentReadService, ContentWriteService, ContentCommentService и ContentUploadService. Самостоятельный appRouter нужен прямым вызовам/инструментам и использует те же фабрики. Чтение ленты (включая поиск/страницы/теги), видео, закладок, взаимодействий и статей, создание/правка/ручная публикация постов, реакции, комментарии и административные tRPC-загрузки фото/медиа и импорт ссылки перенесены. Отдельную бинарную загрузку видео обслуживает VideoUploadController; остальные административные операции ещё переводятся. Проверка подписки — в identity/club-access.ts. SQL-helpers и общий пул пока в db.ts: внедрение сервисов не означает завершённый перенос слоя данных.
- ContentCommentService сохраняет проверки публикации, подписки, окна обсуждения и прав автора/модератора; контекст пользователя берётся из свежей сессии. Список комментариев по-прежнему требует членства в клубе, а изменения публичных обсуждений доступны авторизованным пользователям — это существующее различие, не новая политика. SQL-транзакции/блокировки остаются в content/comments.ts; уведомление об ответе запускается после commit, доставка пока не durable.
- Лайки/закладки постов переключаются в content/post-reactions.ts одной транзакцией с блокировкой строки пользователя: следующий запрос читает уже сохранённое состояние. Старые дубли пары удаляются при выключении реакции; массовой очистки БД нет. Это защита текущих API-записей от конкуренции, не уникальное ограничение схемы и не идемпотентность: повтор после неизвестного результата сети может переключить состояние ещё раз. Индексы и проверки существования поста остаются отдельными задачами.
- ContentWriteService получает авторизованные и валидированные данные от adminProcedure, не пользовательскую роль из payload. Существующие helpers сохраняют пост/медиа/ключ запроса одной транзакцией; анонс вызывается после commit. Это не durable-очередь push: окно потери анонса при остановке процесса остаётся отдельной задачей N12.
- ContentUploadService обрабатывает admin.uploadPhoto, admin.uploadMedia и admin.importVideoUrl; проверка доступа до чтения больших тел остаётся в _core/request-bodies.ts, повторная проверка свежей сессии — в tRPC. Фото проходят прежнюю проверку байтов, поворот и перекодирование через media/photos.ts. Общие медиа требуют непустой канонический base64 и получают серверный UUID-ключ без клиентского имени/расширения; имя остаётся отдельной метаинформацией. Предел кодированной строки не превышает прежние 50 MiB JSON, это не лимит 50 MiB декодированного файла. Сохранена последовательность «хранилище → связь с постом»; ошибка БД не отменяет загрузку файла. Проверка старого DOC и уборка непривязанных объектов остаются отдельными задачами, как и lifecycle storage/SQL.
- Заявленный Content-Type проверяет content/media-content-type.ts: audio/* для аудио, video/* для видео, PDF/DOC/DOCX/text/plain для документов; application/octet-stream остаётся общим fallback. Несовместимые типы, пустое/некорректное MIME-имя, управляющие символы, некорректные параметры и значения длиннее 128 символов дают 400 до загрузки. Затем аудио/видео проверяются через file-type 22.1.1 в media/file-signature.ts: неизвестные/чужие форматы отклоняются, storage и связь SQL при переданном postId получают одинаковый распознанный MIME. Параметры сохраняются только при совпадении заявленного и распознанного MIME-имени; alias/fallback и ошибочные метки одной категории заменяются. MP4 и WebM — общие контейнеры, допустимые для обеих категорий без проверки дорожек. Распознавание выполняется по одному в worker thread, с пятисекундным тайм-аутом активной задачи и обязательным завершением worker; очередь не ограничивает общий объём ожидающих HTTP-запросов и не является защитой от общего DoS. Новые HTTP-квоты/429 не добавлены. Это подсказка по сигнатуре, не проверка воспроизведения, кодеков, макросов, полиглотов или антивирус. Raw-video endpoint использует эту же MIME-политику и проверку сигнатуры через ContentUploadService.
- Для документов с заявленным PDF/DOCX требуется точное совпадение MIME с результатом распознавания; неизвестные/чужие байты, обычный ZIP, пакет с объявленным макро-типом Word и перестановка PDF/DOCX дают 400 до storage/SQL. Исходные байты и корректные параметры MIME сохраняются. Это не полная проверка PDF/OPC, отсутствие JavaScript или скрытых макросов.
- TXT отклоняет распознанные бинарные форматы и проверяет весь текст через fatal TextDecoder порциями по 16 KiB без перекодирования. Допустимы UTF-8, UTF-16LE/BE (BOM или явный charset), Windows-1251 с явным charset и их поддерживаемые aliases. По умолчанию — UTF-8/BOM; неоднозначный/неподдерживаемый charset, конфликт BOM, повреждённая кодировка и C0/C1 кроме tab/LF/CR/form feed дают 400. Отсутствующий charset дописывается; итоговый MIME тоже ограничен 128 символами. Document/octet-stream принимает распознанный PDF/DOCX либо проверенный Unicode-текст, заменяя MIME и отбрасывая параметры opaque-типа; другие бинарные форматы отклоняются. Legacy-кодировка без text/plain + charset не угадывается: TXT Windows-1251 из picker без charset может потребовать преобразования в UTF-8. Текст может содержать буквальный HTML/код: это не HTML-фильтр, антивирус или проверка заголовков выдачи провайдером.
- Старый DOC по-прежнему metadata-only: сменой метки на application/msword можно обойти проверку документа. Общая CFB-сигнатура не отличает Word от Excel/PowerPoint/MSI; нужен отдельно проверенный detector. Standalone-загрузка теперь возвращает mimeType/fileSize рядом с прежними url/mediaId, но редактор при последующем сохранении поста ещё использует клиентский MIME, не уточнённый сервером: проверка целостности метаданных/владения остаётся отдельной задачей. Защита всех документов ещё не закончена; новые зависимости, схема, frontend и деплой не менялись.
- Клиент получает тип AppRouter; не копируйте серверные функции в фронтенд.
- admin.importVideoUrl вызывает внедрённый ContentUploadService; URL-policy в content/video-import-policy.ts сохраняет точные HTTPS origin/bucket и отказ от внешнего скачивания. Некорректная/внешняя ссылка даёт BAD_REQUEST / 400, успешный ответ остаётся {url}. Это не доказательство существования, типа или владения объектом. POST /api/admin/upload-video обслуживает [VideoUploadController](src/content/video-upload.controller.ts) через тот же сервис: parser middleware проверяет администратора до чтения тела, контроллер повторно проверяет свежую сессию через SessionService после получения файла. Лимит 80 MiB, ответы, проверка сигнатуры и UUID-ключи сохранены; старый admin-video.ts удалён. ContentModule не владеет lifecycle транспорта/SQL.
- Регистрация подтверждается письмом: ответ 202 не означает вход или выданную сессию.
- Checkout не авторизует по email, claim не выдаёт доступ. Платежи и письма имеют сохранённое состояние обработки.
- Пароль устанавливается одноразовой ссылкой; смена пароля изменяет версию сессий.
- Проверяйте повторные запросы, конкуренцию, истёкшие ссылки, заблокированные аккаунты и ошибки внешних сервисов.
- Изменение API должно сопровождаться тестами; [снимок контракта](../../__tests__/trpc-contract.test.ts) защищает имена процедур.

Актуальные ограничения выпуска — в [tasks/todo.md](../../tasks/todo.md).
